# 中断中不能做和不建议做的事

## 题目

中断服务函数（ISR）里有哪些操作是绝对不能做的？有哪些是不建议做的？

## 考察点

中断上下文的特殊性、阻塞与非阻塞操作、RTOS 中断安全机制、嵌入式实时性约束。

## 回答要点

### 1. 绝对不能做的事（会直接导致系统故障）

#### 1.1 不能调用阻塞/等待函数

ISR 不受调度器管理，一旦阻塞，系统死锁。

```c
// ❌ 致命错误
void UART_IRQHandler(void) {
    vTaskDelay(10);                    // 死锁！ISR 无法被调度
    xSemaphoreTake(mutex, portMAX_DELAY); // 死锁！
    HAL_Delay(100);                    // 死循环等待，卡死系统
    while (!flag);                     // 忙等，卡死
}

// ✅ 正确：用 FromISR 版本 + 通知任务
void UART_IRQHandler(void) {
    BaseType_t woken = pdFALSE;
    xSemaphoreGiveFromISR(uart_sem, &woken);
    portYIELD_FROM_ISR(woken);
}
```

#### 1.2 不能调用 malloc/free（动态内存分配）

malloc 内部需要遍历空闲链表、可能合并块，耗时不确定且不可重入。

```c
// ❌ 致命错误
void DMA_IRQHandler(void) {
    uint8_t *buf = malloc(1024);       // 不确定耗时，不可重入
    free(old_buf);                     // 同上
    pvPortMalloc(256);                 // FreeRTOS 的也不行
}

// ✅ 正确：使用预分配的静态缓冲区或内存池
static uint8_t dma_buf[1024];
```

#### 1.3 不能使用互斥锁（mutex）

mutex 获取失败时会阻塞等待，和 1.1 同理。

```c
// ❌ 致命错误
void ISR(void) {
    mutex_lock(&m);     // 获取不到就睡眠 → 死锁
}

// ✅ 正确：用自旋锁（Linux）或关中断（裸机/RTOS）
// 裸机
uint32_t primask = __disable_irq();
// 访问共享数据
__set_PRIMASK(primask);

// Linux 内核
spin_lock_irqsave(&lock, flags);
// 访问共享数据
spin_unlock_irqrestore(&lock, flags);
```

#### 1.4 不能调用 printf/sprintf

printf 内部可能调用 malloc，格式化耗时不定，还可能涉及系统调用。

```c
// ❌ 严重错误
void Fault_Handler(void) {
    printf("fault at 0x%08X\n", PC);  // 可能几十 ms，栈需求大
}

// ✅ 正确：只保存数据，任务中打印
volatile uint32_t fault_pc;
void Fault_Handler(void) {
    fault_pc = __get_PC();
    // 最小化处理
}
```

### 2. 强烈不建议做的事（可能导致隐性 bug）

#### 2.1 不建议做耗时操作

ISR 执行期间，同级和低级中断被屏蔽。耗时过长会导致其他中断响应不及时。

```c
// ❌ 不建议
void ADC_IRQHandler(void) {
    uint16_t data = ADC->DR;
    ProcessData(data);        // 复杂计算
    UpdateStateMachine(data); // 状态机
    CalculateCRC(data);       // 校验
}

// ✅ 正确：ISR 只存数据，任务中处理
void ADC_IRQHandler(void) {
    uint16_t data = ADC->DR;
    xQueueSendFromISR(adc_queue, &data, &woken);
    portYIELD_FROM_ISR(woken);
}
```

**经验法则**：ISR 执行时间控制在 **10μs 以内**。

#### 2.2 不建议使用浮点运算

Cortex-M0/M0+/M3 **没有硬件 FPU**，浮点运算由软件库模拟，极慢。即使 M4F/M7 有 FPU，ISR 中使用浮点需要额外保存/恢复浮点寄存器（FPU lazy stacking），增加中断延迟。

```c
// ❌ 不建议
void ISR(void) {
    float result = voltage * 3.3f / 4096.0f;  // 浮点运算
}

// ✅ 正确：用整数运算替代
void ISR(void) {
    uint32_t result = (uint32_t)voltage * 3300 / 4096;  // 定点运算
}
```

#### 2.3 不建议调用非可重入函数

如果 main 中正在执行 `func()`，中断打断后又调用同一个 `func()`，内部状态可能被破坏。

```c
// strtok 使用内部 static 状态，不可重入
// ❌ 不建议
void ISR(void) {
    char *token = strtok(buf, ",");    // 破坏 main 中正在使用的状态
}

// ✅ 正确：使用可重入版本 strtok_r，或避免在 ISR 中解析
```

#### 2.4 不建议在 ISR 中调用其他 ISR 的处理逻辑

```c
// ❌ 不建议
void TIM1_IRQHandler(void) {
    TIM2_IRQHandler();   // 直接调用另一个 ISR，中断嵌套管理混乱
}

// ✅ 正确：通过软件触发中断或设置标志通知
```

#### 2.5 不建议访问慢速外设

```c
// ❌ 不建议
void ISR(void) {
    HAL_I2C_Mem_Read(&hi2c, 0x50, 0x00, 1, buf, 8, 100);  // I2C 通信可能几百 μs
    Flash_Write(addr, data);   // Flash 擦写可能几 ms
}

// ✅ 正确：在任务中执行慢速操作
```

#### 2.6 争议话题：能不能在中断里喂狗？

这个问题在嵌入式圈子里争议很大，两派各有道理。

**喂狗的本质**：写一个硬件寄存器（WDG->KR = 0xAAAA），操作本身是原子的、非阻塞的，从技术上看完全可以在 ISR 中执行。

**反对派（不建议在中断中喂狗）**：

```c
// ❌ 不建议：定时器中断中喂狗
void TIM_IRQHandler(void) {
    WDG->KR = 0xAAAA;  // 喂狗
    // ...
}

int main(void) {
    while (1) {
        // 如果主循环卡死（死循环、死锁），但定时器中断仍在运行
        // 看门狗永远不会触发复位！
        // 看门狗的"看门"意义就丧失了
    }
}
```

**核心问题**：看门狗的设计意图是检测**软件异常**（死循环、死锁、跑飞）。如果在中断中喂狗，即使主任务已经卡死，中断仍然正常运行并持续喂狗，**看门狗永远不会触发**，完全失去了保护作用喵。

**支持派（某些场景可以）**：

```c
// ✅ 合理场景：条件喂狗
void TIM_IRQHandler(void) {
    if (system_healthy) {      // 检查系统健康标志
        WDG->KR = 0xAAAA;     // 只有健康时才喂
    }
    // 如果主循环卡死，system_healthy 不会被更新
    // 下一次中断发现标志过期，不再喂狗 → 看门狗复位
}
```

**正确做法**：

| 方案 | 做法 | 适用场景 |
|------|------|---------|
| 主循环喂狗 | 在主 while(1) 中喂 | 简单裸机程序 |
| 任务喂狗 | RTOS 中由独立监控任务喂 | 多任务系统 |
| 条件喂狗 | ISR 中检查健康标志后才喂 | 需要精确定时喂狗的硬件 |
| 窗口看门狗 | 硬件要求在特定窗口内喂 | 必须按时喂的场景 |

```c
// 推荐方案：独立监控任务（RTOS）
void WatchdogTask(void *param) {
    while (1) {
        // 检查所有关键任务是否存活
        if (task_a_alive && task_b_alive && task_c_alive) {
            WDG->KR = 0xAAAA;    // 所有任务正常才喂狗
        }
        // 如果任何任务卡死，不喂狗 → 看门狗复位
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

**总结**：不是"技术上能不能"的问题，而是"设计上该不该"的问题。ISR 中喂狗会**掩盖主任务的异常**，破坏看门狗的保护机制。除非有额外的健康检查逻辑，否则不要在 ISR 中喂狗喵。

### 3. 安全操作清单

| 操作 | ISR 中 | 说明 |
|------|--------|------|
| 读写寄存器 | ✅ | `GPIO->ODR |= (1 << 5)` |
| 读写 volatile 全局变量 | ✅ | `flag = 1` |
| 入队/出队（FromISR 版本） | ✅ | `xQueueSendFromISR` |
| 释放信号量（FromISR） | ✅ | `xSemaphoreGiveFromISR` |
| 任务通知（FromISR） | ✅ | `xTaskNotifyFromISR` |
| 关中断/开中断 | ✅ | `__disable_irq()` |
| 自旋锁 | ✅ | `spin_lock_irqsave` |
| DMA 启动/停止 | ✅ | 配置寄存器即可 |
| 关中断保护共享数据 | ✅ | `taskENTER_CRITICAL_FROM_ISR` |

### 4. ISR 设计原则

```
ISR 只做三件事：
  1. 读硬件状态
  2. 清中断标志
  3. 通知任务（信号量/队列/标志）
```

```c
// 标准模板
void XXX_IRQHandler(void) {
    // 1. 读取硬件状态
    uint32_t status = XXX->SR;

    // 2. 清除中断标志
    XXX->SR = status;

    // 3. 保存数据 + 通知任务
    BaseType_t woken = pdFALSE;
    xQueueSendFromISR(xQueue, &data, &woken);

    // 4. 必要时触发调度
    portYIELD_FROM_ISR(woken);
}
```

### 5. 面试速记

- **不能阻塞**：vTaskDelay、HAL_Delay、mutex_lock、等待队列 → 死锁
- **不能分配内存**：malloc/free → 不确定耗时、不可重入
- **不能 printf**：耗时长、可能阻塞、栈需求大
- **不能做耗时操作**：ISR 控制在 10μs 以内
- **不建议浮点运算**：无 FPU 的 MCU 上极慢，有 FPU 也要额外保存寄存器
- **ISR 三步走**：读状态 → 清标志 → 通知任务
