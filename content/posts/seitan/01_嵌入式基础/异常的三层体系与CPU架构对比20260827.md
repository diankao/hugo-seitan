# 异常的三层体系与 CPU 架构对比

## 题目

ARM 架构的异常、编程语言的异常（C++ try/catch）、操作系统的异常（信号/SEH）是什么关系？不同 CPU 架构的异常机制有何差异？

## 考察点

异常概念的分层理解：硬件异常、操作系统异常、语言异常各自的实现层面与桥接方式；主流 CPU 架构异常向量机制的对比

## 回答要点

### 1. 核心结论：三层是自下而上的分层关系，且语言异常默认不经过底下两层

```
C++ throw/catch     ── 纯运行时库实现，默认不经过下面两层
        │
        │  (但有桥接点，见第 5 节)
        ▼
OS 信号/SEH          ── 翻译、补救硬件异常；进程级通知
        │
        ▼
CPU 异常/向量表      ── 硬件同步事件，只有"跳表"
```

最反直觉的一点：**C++ 的 `throw` 不产生任何硬件异常**。分清"这条 throw 到底走没走 CPU fault"是理解很多崩溃问题的关键。

中断和异常本身的区分（异步 vs 同步）见《中断和异常区别》，本文展开"异常"这个词在三个层面的不同含义。

### 2. 第一层：CPU 架构的异常（硬件同步事件）

异常是精确的硬件概念：**执行某条指令时由 CPU 自己产生的同步事件**，CPU 自动保存现场、查异常向量表跳转。这一层只有"跳表 + 保存现场"，没有"处理"语义。

#### ARM Cortex-M 的异常（嵌入式最常见）

| 异常类型 | 触发场景 |
|---|---|
| Reset | 复位 |
| Undefined Instruction | 遇到未定义编码（NULL 函数指针调用后从 0 取指常走到这） |
| HardFault / MemManage / BusFault / UsageFault | 取指/访存错误、非法操作（野指针写常触发） |
| SVCall | `SVC` 指令（FreeRTOS 系统调用的入口） |
| PendSV | 任务切换 |
| SysTick | 系统节拍 |

Cortex-M 的向量表是一块函数指针数组（含栈顶指针在首位），`VTOR` 寄存器可重定位。

#### x86 的异常（IDT + 异常号）

x86 把中断和异常统一编号进**中断描述符表 IDT**（256 项），0~31 号固定为异常：

| 号 | 异常 | 触发场景 |
|---|---|---|
| 0 | #DE 除零 | DIV/DIVX 除数为 0 |
| 3 | #BP 断点 | `INT3` 指令（调试器插桩的基础） |
| 6 | #UD 非法指令 | 未定义编码 |
| 13 | #GP 通用保护 | 段/特权违规（野指针访问的经典来源） |
| 14 | #PF 缺页 | 访问页表项无效的地址（**Linux 虚拟内存的基石**） |

x86 的关键特色：异常带**错误码**（error code，如 #PF 的错误码告诉你读/写、用户/内核、缺页原因），且硬件判定 privilege 切换。系统调用走 `int 0x80` / `syscall`，本质是"借异常号造的同步陷入"。

#### RISC-V 的异常（不叫异常，叫 trap）

RISC-V 把中断和异常统称 **trap**，用一张向量表 + `mcause` 寄存器（高 位区分中断/异常，低位是编号）：

| mcause | 事件 |
|---|---|
| 0/1/2... | 指令地址未对齐 / 访问 fault / 非法指令等同步异常 |
| 8/11 | ECALL from U/M 模式（系统调用/内核入口） |
| 高位=1 的编号 | 各类外部/定时器/软件中断 |

特色：`mtvec` 可配成直接模式（全进一个入口，软件查 mcause 分发）或向量模式；异常处理完写 `mepc` 返回，`mstatus` 控制全局中断使能。设计上比 ARM/x86 更精简，没有 #GP 这种大杂烩。

#### MIPS / LoongArch

- MIPS：异常统称 exception，`Cause` 寄存器编号，特色是**延迟槽**导致异常地址处理复杂（`EPC` 指向分支指令的情况）；系统调用用 `syscall` 指令
- LoongArch：类似 RISC-V 的 CSRR 系列寄存器（`CSR.ESTAT`/`ERA`），概念上是 mcause/mepc 的对应物

#### 四架构对比表

| 维度 | ARM Cortex-M | x86 | RISC-V | MIPS |
|---|---|---|---|---|
| 统称 | exception | 中断和异常统一进 IDT | trap | exception |
| 向量表 | 函数指针数组（VTOR 可重定位） | IDT 门描述符（中断/异常同表） | mtvec，直接/向量两种模式 | 单一入口 + Cause 分发 |
| 缺页异常 | MemManage fault | #PF (14)，带错误码 | load/store/取指 access fault | TLB refill 例外（软件走 TLB 重填！） |
| 系统调用陷入 | SVC | syscall/int 0x80 | ECALL | syscall 指令 |
| 特色 | 向量表即函数指针，切换最省事 | 错误码最详细，硬件特权判定 | 设计最精简，mcause 一目了然 | TLB 异常交给软件，延迟槽陷阱 |

一个值得记住的差异：**x86 的缺页由硬件给出错误码、Linux 直接用它实现写时复制；MIPS 的 TLB miss 由软件重填，所以 MIPS 内核里 TLB refill handler 是手写汇编且放在向量表最快的位置**。

### 3. 第二层：操作系统的异常（对硬件异常的翻译和治理）

OS 把硬件异常接住后做**分类翻译**，变成自己的抽象：

- **Linux**：内核 fault handler 先判断是否可补救——缺页但地址在进程 VMA 内 → 分配物理页后重新执行那条指令（写时复制、按需分配都靠这实现），进程毫无感知；不可补救 → 发信号 `SIGSEGV`/`SIGBUS`/`SIGFPE`/`SIGILL`。用户态看到的"异常"就是信号
- **Windows**：结构化异常处理（SEH），`EXCEPTION_ACCESS_VIOLATION` 等，内核与用户态注册表链（`__try/__except`）协作

关键点：OS 这层做了硬件做不到的事——**判断异常能否补救**；不能补救才上升为"通知进程你死了"。

### 4. 第三层：语言的异常（C++ try/catch）——纯软件实现

C++ 的 `throw` 是运行时库（libstdc++/libc++）实现的纯软件流程：

```
throw x;
  → __cxa_throw
  → _Unwind_RaiseException（展开器）
  → 读 .eh_frame（x86）/ ARM.exidx（ARM）异常表逐帧回退
  → 找到能接住该类型的 catch，跳进去
```

CPU 全程正常执行指令，没有任何 fault 触发。所以叫 **zero-cost exception**：不 throw 时零开销（无判空无检查），throw 时很贵（查表展开）。

嵌入式注意：MCU 上 C++ 常用 `-fno-exceptions` 直接禁掉这一层；裸机 MCU 上也没有第二三层——HardFault 就是尽头，通常在死循环里等调试器或记录现场后复位（死机定位的故障现场来源）。另外 FreeRTOS 把 `SVC`/`PendSV` 当**施工材料**用（系统调用入口、任务切换）——异常机制不只会"出事"，也是内核的骨架。

### 5. 桥接点：硬件异常被"翻译"成语言异常

三层默认不互通，但有几个著名的桥：

1. **Windows `/EHa` + SEH**：硬件异常（除零、访存违例）沿 SEH 链传播时可被翻译成 C++ 的 `catch(...)`；`__try/__except` 直接用 SEH 语法
2. **JVM/.NET 的空指针优化**：JVM 不显式判空，直接解引用，靠 SIGSEGV handler 捕获后翻译成 `NullPointerException` 抛给 Java 层——**故意利用第二层实现第三层的语义**，热路径零判空开销
3. **Linux C++ 默认行为**：野指针解引用 → 硬件 fault → 内核发 SIGSEGV → 无 handler → 进程崩溃。C++ 的 catch **接不住**它，因为这条路径根本没走到 unwind 机制上

### 6. 一句话总结

- **CPU 异常是硬件事实**：各架构实现不同（ARM 向量表即函数指针、x86 IDT+错误码、RISC-V 统称 trap、MIPS 软件 TLB 重填），但共性是"同步事件 + 查表跳转"
- **OS 异常是对它的翻译治理**：能补救的补救（缺页），不能补救的变成信号/SEH 通知进程
- **语言异常是独立的纯软件机制**：默认不经过下两层，通过 SEH/信号 handler 这类桥接点才连起来
