# DMA串口接收数据解析与吞吐优化

## 题目

用 DMA 做串口通信时，怎么解析数据才能提高吞吐量？接收侧的架构怎么设计，中断里该做什么、不该做什么？

## 考察点

接收侧架构选型（逐字节中断 / IDLE+DMA / 半满全满 / 双缓冲）、中断上下文的最小化、零拷贝与缓冲区设计、解析状态机与游标推进、吞吐量的定量估算与瓶颈定位。

## 回答要点

### 1. 先算账：DMA 之后瓶颈根本不在搬运

DMA 接管搬运后，字节进 RAM 完全不占 CPU，UART 又是外设到内存的单字节传输，DMA 带宽绰绰有余。**吞吐量上不去的瓶颈几乎全在软件侧**，典型有三个：

| 瓶颈 | 典型症状 | 定量账（F103@72MHz 量级） |
|------|---------|------------------------|
| 中断太频 | 逐字节 RXNE 中断 | 115200bps ≈ 11.5k 次中断/秒，尚可；921600bps ≈ 92k 次/秒，光进出中断就吃掉 10% 以上 CPU，算上打断流水线和被中断任务的现场损失，实际 20%+ |
| 中断里干重活 | 回调里 memcpy/解析/printf | 回调执行时间超过下一帧到达间隔，中断越压越多，最终 overrun 丢字节 |
| 数据被反复搬 | DR→ISR 临时变量→队列→解析缓冲→帧缓冲 | 一次接收被拷贝三四次，DMA 省下的 CPU 又被软件还回去了 |

所以答案的组织原则就三个词：**批量、解耦、零拷贝**——让 CPU 每次醒来处理一大段数据，而不是一个字节。

### 2. 中断粒度的选择：从每字节一次到每帧一次

| 接收方案 | 触发粒度 | 典型中断频率 | 数据延迟 | 适用场景 |
|---------|---------|------------|---------|---------|
| RXNE 逐字节中断 | 每字节 | = 字节率 | 最低（逐字节） | 低波特率、简单场合 |
| IDLE+DMA（正常模式） | 每帧 1 次 | = 帧率 | 一帧结束时刻 | 帧式协议、低帧率 |
| IDLE+DMA（循环模式+通知） | 每帧 1 次 | = 帧率 | 一帧结束时刻 | **通用推荐**，帧流混合也行 |
| DMA 循环+HT/TC 分半区 | 每半区 1 次 | = 数据率÷半区 | 半区填满时间 | 连续大流量（采样流、GPS NEMA） |
| 硬件双缓冲 M0AR/M1AR | 每区 1 次 | = 数据率÷区 | 一区填满时间 | 等尺寸块流（ADC/DAC 类） |
| 主循环轮询 NDTR | 无中断 | 0 | 主循环周期 | 裸机、主循环确定且短 |

核心是**空闲中断（IDLE）**：线路连续空闲一个字节时间就触发一次，配合 DMA 计数器能一次拿到"刚到的这一帧"的起止位置——中断次数从字节率降到帧率。100Hz 的帧流就是每秒 100 次中断，CPU 占用可以忽略。STM32 HAL 对应 `HAL_UARTEx_ReceiveToIdle_DMA()`，回调里 `Size` 参数直接给出本次写入长度。

帧式协议选 IDLE；连续数据流没有"帧间隙"，IDLE 可能很久不触发，改用半传输完成（HT）/传输完成（TC）中断把大缓冲切成两半轮流处理——这等效于 DMA 硬件自动管理的双缓冲，延迟和中断频率由缓冲大小调节。

### 3. 解耦：中断里只做"记录+通知"

中断回调的职责上限是三件事：**算写位置、发通知、立刻退出**。解析、组帧、业务处理一律放到主循环或专门的解析任务里：

- RTOS：回调里 `xSemaphoreGiveFromISR()`（或写消息队列传"区间描述"），解析任务阻塞在信号量上，有数据才醒来
- 裸机：置一个 volatile 标志，主循环轮询标志后批量处理
- 更激进的裸机做法：连中断都不要，主循环直接轮询 DMA 的 NDTR 寄存器——前提是主循环周期远短于缓冲区填满时间

这样高波特率下 CPU 的占用从"被中断淹没"变成"按批消费"，且解析耗时长一点也不会反压中断。

### 4. 缓冲区设计：循环模式 + 游标 + 零拷贝

**环形缓冲区**是默认选择：DMA 配循环模式（Circular）往一块 2 的幂大小的缓冲里写，永不重挂；写位置随时可由 `写位置 = 缓冲大小 - NDTR` 得到。解析侧维护自己的读游标，追着写位置消费。16 位的 NDTR 单次读取天然原子，读侧不需要关中断。

**零拷贝**是解析提速的关键一步：解析函数直接在 DMA 缓冲区上用游标推进，帧头位置、载荷区间都用"偏移"记录，**不要把每帧 memcpy 到另一个缓冲再解析**。只有两种情况例外：帧跨了环形缓冲回卷点（此时不得不拼一次），或下层消费者要求连续内存。为此可以把环形缓冲做成"逻辑环形、物理双倍"——申请 2N 的内存让前 N 与后 N 映射同一片数据，回卷帧也天然连续，免拼贴。

**缓冲大小**用"削峰"公式定：容量 ≥ 最坏解析延迟 × 字节率。解析任务可能被高优先级任务阻塞 10ms，921600bps 下就要 ≥ 921B，取 2048；再留一倍余量防突发。缓冲不够时写指针追上读指针会覆盖未解析数据——检测两者距离超过阈值要告警，这是"解析跟不上"的最早信号。

### 5. 解析算法本身：状态机 + 游标，忌重复扫描

- **逐字节状态机**（帧头→长度→载荷→校验）是标准做法：每字节一次 switch，总代价 O(n)，便宜且天然支持跨批次的帧
- **游标持久化**：解析进度（状态机状态+游标位置）跨批次保留，每批只处理新增区间——反模式是"每收到一批就从缓冲区头部重新扫描找帧头"，数据量一大就是 O(n²)
- 帧头查找批量做时用 `memchr()`，库函数是优化过的，比手写逐字节循环快
- 校验用**查表法 CRC**（256 项表，每字节一次查表异或），比逐位多项式除法快 8 倍以上
- 帧长字段可信时，剩余载荷整段交给处理函数，不要在解析层再逐字节过一遍

### 6. 完整示例：STM32 HAL 循环模式 IDLE+DMA + 解析任务

```c
#define RX_BUF_SIZE 2048                  // 2 的幂

static uint8_t  rx_buf[RX_BUF_SIZE];
static uint16_t rx_read = 0;              // 解析侧游标
static SemaphoreHandle_t rx_sem;

void uart_dma_start(void)
{
    rx_sem = xSemaphoreCreateBinary();
    // 循环模式：收满自动回卷，永不重挂
    HAL_UARTEx_ReceiveToIdle_DMA(&huart1, rx_buf, RX_BUF_SIZE);
    // 帧式协议不需要半满通知，关掉少一半无谓回调
    __HAL_DMA_DISABLE_IT(huart1.hdmarx, DMA_IT_HT);
}

// IDLE/传输完成都会进这里：只通知，不解析
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
{
    BaseType_t wakeup = pdFALSE;
    xSemaphoreGiveFromISR(rx_sem, &wakeup);
    portYIELD_FROM_ISR(wakeup);
}

void parse_task(void *arg)
{
    for (;;) {
        xSemaphoreTake(rx_sem, portMAX_DELAY);

        // 写位置不需要关中断：NDTR 单次读取原子
        uint16_t rx_write = RX_BUF_SIZE - __HAL_DMA_GET_COUNTER(huart1.hdmarx);

        while (rx_read != rx_write) {
            frame_feed(rx_buf[rx_read]);          // 直接在 DMA 缓冲上消费，零拷贝
            rx_read = (rx_read + 1) & (RX_BUF_SIZE - 1);
        }
    }
}
```

帧状态机，游标进帧时记下偏移，出帧时把 `(缓冲+偏移, 长度)` 直接交给上层：

```c
typedef enum { S_HEAD0, S_HEAD1, S_LEN, S_PAYLOAD, S_CRC } fstate_t;

static fstate_t state = S_HEAD0;
static uint16_t frame_pos, need, got;
static uint8_t  crc8;

void frame_feed(uint8_t b)
{
    switch (state) {
    case S_HEAD0:
        if (b == 0xAA) state = S_HEAD1;
        break;
    case S_HEAD1:
        state = (b == 0x55) ? S_LEN : S_HEAD0;
        break;
    case S_LEN:
        need = b; got = 0; crc8 = 0;
        state = (need > 0 && need <= 250) ? S_PAYLOAD : S_HEAD0;
        if (state == S_PAYLOAD) frame_pos = rx_read;   // 记录载荷起点，零拷贝
        break;
    case S_PAYLOAD:
        crc8 ^= b;                                     // 演示用，实际用查表 CRC
        if (++got == need) state = S_CRC;
        break;
    case S_CRC:
        if (b == crc8)
            frame_dispatch(frame_pos, need);           // 传偏移和长度，不搬数据
        state = S_HEAD0;
        break;
    }
}
```

裸机把 `parse_task` 的循环体放进主循环、信号量换 volatile 标志即可，结构不变。

### 7. 吞吐量再往上顶的配套手段

- **解析任务优先级**要和数据价值匹配：通信解析通常应高于普通业务任务，否则缓冲削峰能力形同虚设
- **帧大就直切**：如果协议帧定长，干脆把 DMA 循环缓冲按帧长对齐，每中断一次正好一帧，连游标都省了
- **Cache 一致性**：H7/F7 这类带 D-Cache 的芯片，DMA 缓冲要么用 MPU 设成非缓存区，要么解析前 `SCB_InvalidateDCache_by_Addr()`，否则解析到旧数据（详见《DMA数据传输中的cache问题与解决》）
- **收发两侧配合**：发送同样用 DMA+TC 中断，别让发送侧的中断把接收侧的预算吃掉
- **量级判断**：STM32 USART 极限 3Mbps ≈ 300KB/s——这个量级用上述架构绰绰有余；再往上（数 MB/s）该换 SPI/USB/以太网，不是继续压 UART

### 8. 高频坑清单

1. **正常模式收满后忘记重挂**：`HAL_UARTEx_ReceiveToIdle_DMA` 在 Normal 模式下收满一次就停，回调里必须重挂——循环模式没这个问题
2. **缓冲不是 2 的幂还用 `&` 取模**：游标运算必须配合 `RX_BUF_SIZE - 1` 的掩码，否则位置错乱
3. **回调里解析甚至 printf**：高波特率下回调比数据流还慢，越丢越多
4. **每帧 memcpy 出来再解析**：双倍搬运，把 DMA 省的 CPU 又还回去
5. **每批数据从头重扫缓冲找帧头**：O(n²) 反模式，游标必须持久化
6. **HT 中断没关**：帧式协议下平白多一倍回调
7. **写追读无检测**：覆盖丢帧没有告警，问题拖到业务层才暴露成"偶发数据错乱"

### 9. 一句话总结

**DMA 负责批量进 RAM，中断只负责通知，解析用持久游标零拷贝地按批消费**——三个环节都守住"批量"，吞吐量就上来了；逐字节思维才是吞吐量的天敌。
