# 看门狗机制与多任务喂狗设计

## 标签
#嵌入式 #面试题 #看门狗 #IWDG #WWDG #STM32 #系统可靠性

## 题目

什么是看门狗？独立看门狗和窗口看门狗有什么区别？多任务系统中如何设计喂狗机制？喂狗任务挂了怎么办？

## 考察点

MCU外设理解、系统可靠性设计、RTOS多任务环境下的看门狗策略

## 参考答案

### 1. 看门狗的基本原理

看门狗（Watchdog Timer，WDT）本质上是一个硬件定时器，系统启动后开始计时。软件必须在超时之前执行"喂狗"操作（即重置计数器），如果软件因故障未能及时喂狗，计数器溢出后看门狗将产生系统复位，使MCU重新启动。

看门狗的核心价值在于：**检测软件是否按照预期正常运行**。当程序跑飞、死循环、死锁等异常发生时，软件无法按时喂狗，看门狗就会触发复位，将系统从异常状态中拉回。

典型工作流程：

```
系统上电 → 初始化看门狗 → 启动计数器
    ↓
主循环/任务中定期喂狗（重置计数器）
    ↓
如果软件正常运行 → 计数器被周期性清零 → 系统正常工作
如果软件异常（死机/跑飞）→ 未及时喂狗 → 计数器溢出 → 系统复位
```

### 2. 独立看门狗（IWDG）

#### 核心特性

独立看门狗（Independent Watchdog，IWDG）是STM32中最常用的看门狗，其核心特点是**独立于主系统时钟运行**。

- **时钟源**：内部低速时钟 LSI，频率约 32kHz~40kHz（典型值 40kHz），不受主时钟（HSE/HSI/PLL）影响
- **计数方式**：12位递减计数器（0x000~0xFFF），计数到 0x000 时产生复位
- **超时范围**：通过预分频器（Prescaler）和重装载值（Reload）配置，超时时间可从几十微秒到数十秒
- **适用场景**：检测系统级死机，作为系统最后的安全防线

#### 超时时间计算

```
T_timeout = (Prescaler × Reload) / f_LSI

例如：Prescaler = 256, Reload = 0xFFF (4095), f_LSI = 40kHz
T_timeout = (256 × 4095) / 40000 ≈ 26.2秒
```

#### STM32 HAL库配置示例

```c
#include "stm32f4xx_hal.h"

IWDG_HandleTypeDef hiwdg;

void IWDG_Init(void)
{
    hiwdg.Instance = IWDG;
    hiwdg.Init.Prescaler = IWDG_PRESCALER_64;
    hiwdg.Init.Reload = 1000;
    hiwdg.Init.Window = 0xFFF;

    if (HAL_IWDG_Init(&hiwdg) != HAL_OK)
    {
        Error_Handler();
    }
}

void IWDG_Feed(void)
{
    HAL_IWDG_Refresh(&hiwdg);
}

void main(void)
{
    HAL_Init();
    SystemClock_Config();

    IWDG_Init();

    while (1)
    {
        /* 主循环业务逻辑 */
        App_Task_Run();

        /* 每次循环末尾喂狗 */
        IWDG_Feed();

        HAL_Delay(100);
    }
}
```

#### 关键注意事项

- IWDG一旦启动，**无法通过软件关闭**（除非系统复位），这是其作为安全机制的设计初衷
- LSI时钟精度较低（误差可达 ±10%），不适合对时序精度要求高的场景
- 在调试模式下，可以通过 DBGMCU 寄存器暂停 IWDG 计数，避免调试时误触发复位

### 3. 窗口看门狗（WWDG）

#### 核心特性

窗口看门狗（Window Watchdog，WWDG）相比 IWDG 最大的区别在于引入了**"窗口"概念**——喂狗操作必须在规定的时间窗口内完成，**太早喂狗或太晚喂狗都会触发复位**。

- **时钟源**：APB1 总线时钟（PCLK1），精度远高于 LSI
- **计数方式**：7位递减计数器（0x40~0x7F），T6位（bit6）为 0 时产生复位
- **窗口机制**：计数器值必须大于窗口值（Window Value）时才能喂狗；如果计数器值已经小于窗口值再喂狗，同样触发复位
- **提前唤醒中断（EWI）**：当计数器递减到 0x40 时触发 EWI 中断，可用于在复位前执行紧急操作（如保存关键数据）

#### 窗口机制图解

```
计数器值
  0x7F ───────────────────────────────────
         ↑ 看门狗启动，计数器从0x7F开始递减
         │
         │  ← 有效喂狗窗口（计数器值 > Window Value）
         │
  W[6:0] ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
         │  ← 太晚喂狗：计数器 < Window Value，喂狗触发复位！
         │
  0x40 ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
         │  ← EWI中断触发点
         │
  0x3F ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
         ↓ 计数到0x3F（T6=0），系统复位！
```

#### 超时时间计算

```
T_timeout = (1 / f_PCLK1) × 4096 × (Counter - Window)

例如：f_PCLK1 = 42MHz, Counter = 0x7F (127), Window = 0x5F (95)
T_timeout = (1 / 42000000) × 4096 × (127 - 95) ≈ 3.12ms
```

#### STM32 HAL库配置示例

```c
#include "stm32f4xx_hal.h"

WWDG_HandleTypeDef hwwdg;

void WWDG_Init(void)
{
    hwwdg.Instance = WWDG;
    hwwdg.Init.Prescaler = WWDG_PRESCALER_8;
    hwwdg.Init.Window = 0x5F;
    hwwdg.Init.Counter = 0x7F;
    hwwdg.Init.EWIMode = WWDG_EWI_ENABLE;

    if (HAL_WWDG_Init(&hwwdg) != HAL_OK)
    {
        Error_Handler();
    }
}

void WWDG_Feed(void)
{
    HAL_WWDG_Refresh(&hwwdg);
}

void HAL_WWDG_EarlyWakeupCallback(WWDG_HandleTypeDef *hwwdg)
{
    /* 提前唤醒中断回调 */
    /* 在系统复位前执行紧急操作 */
    Save_Critical_Data_To_Backup();
    Log_System_State();
}
```

#### 关键注意事项

- WWDG的超时时间通常很短（毫秒级），适合检测程序时序偏差
- 与 IWDG 不同，WWDG 在系统复位后可以被软件重新配置
- EWI 中断中**不能执行耗时操作**，因为计数器仍在递减，很快就会触发复位

### 4. IWDG vs WWDG 对比

| 对比项 | 独立看门狗（IWDG） | 窗口看门狗（WWDG） |
|--------|---------------------|---------------------|
| 时钟源 | LSI（内部低速时钟，约40kHz） | APB1总线时钟（PCLK1） |
| 时钟精度 | 较低（±10%左右） | 高（与系统时钟同精度） |
| 计数器位数 | 12位（0x000~0xFFF） | 7位（0x40~0x7F） |
| 计数方向 | 递减 | 递减 |
| 喂狗条件 | 任意时刻（只要未超时） | 必须在窗口范围内 |
| 超时范围 | 较大（微秒~数十秒） | 较小（通常毫秒级） |
| 提前唤醒中断 | 无 | 有（EWI） |
| 调试时可暂停 | 是（通过DBGMCU） | 是（通过DBGMCU） |
| 软件可关闭 | 否（启动后无法关闭） | 是（复位后可重新配置） |
| 典型适用场景 | 系统级死机检测 | 程序时序偏差检测 |
| 防护级别 | 系统最后防线 | 精确时序监控 |

**面试回答建议**：IWDG 适合作为系统级的安全兜底，超时时间长，容忍度高；WWDG 适合对时序要求严格的场景，能检测程序是否"跑得太快或太慢"。在实际工程中，两者可以组合使用，形成多层次的可靠性保障。

### 5. 多任务系统中的喂狗机制设计

在裸机系统中，喂狗逻辑简单——在主循环中定期调用即可。但在 RTOS 多任务环境中，情况复杂得多：如果只有一个任务负责喂狗，其他任务死锁了喂狗任务仍正常运行，看门狗就无法检测到异常。因此需要设计合理的多任务喂狗策略。

#### 方案一：独立监控任务方案

创建一个专门的低优先级监控任务，所有关键任务在各自周期内设置"心跳标志"，监控任务检查所有标志位是否都被及时更新。

```
任务A（高优先级）──设置 flag_a──→ 监控任务（最低优先级）
任务B（中优先级）──设置 flag_b──→     检查所有标志
任务C（低优先级）──设置 flag_c──→     全部正常 → 喂狗
                                     任一异常 → 不喂狗 → 系统复位
```

**优点**：逻辑清晰，监控集中化。
**缺点**：监控任务本身如果挂了，看门狗失效。

#### 方案二：分布式喂狗方案（推荐）

每个关键任务设置自己的心跳标志位和一个递减计数器，监控任务只负责检查和喂狗。这是工程中最常用的方案。

```c
#include "stm32f4xx_hal.h"
#include "cmsis_os.h"

#define TASK_HEARTBEAT_TIMEOUT_MS  500

typedef struct {
    uint8_t  flag;
    uint32_t timeout_ms;
    uint32_t last_tick;
} TaskHeartbeat_t;

static TaskHeartbeat_t g_heartbeat[TASK_ID_MAX];

void TaskHeartbeat_Init(void)
{
    for (int i = 0; i < TASK_ID_MAX; i++)
    {
        g_heartbeat[i].flag = 0;
        g_heartbeat[i].timeout_ms = TASK_HEARTBEAT_TIMEOUT_MS;
        g_heartbeat[i].last_tick = osKernelSysTick();
    }
}

void TaskHeartbeat_Feed(TaskID_t task_id)
{
    if (task_id < TASK_ID_MAX)
    {
        g_heartbeat[task_id].flag = 1;
        g_heartbeat[task_id].last_tick = osKernelSysTick();
    }
}

uint8_t TaskHeartbeat_CheckAll(void)
{
    uint32_t now = osKernelSysTick();

    for (int i = 0; i < TASK_ID_MAX; i++)
    {
        if (g_heartbeat[i].flag == 0)
        {
            return 0;
        }

        if ((now - g_heartbeat[i].last_tick) > g_heartbeat[i].timeout_ms)
        {
            return 0;
        }

        g_heartbeat[i].flag = 0;
    }

    return 1;
}

void MonitorTask(void const *argument)
{
    TaskHeartbeat_Init();

    for (;;)
    {
        osDelay(100);

        if (TaskHeartbeat_CheckAll() == 1)
        {
            HAL_IWDG_Refresh(&hiwdg);
        }
    }
}

void ControlTask(void const *argument)
{
    for (;;)
    {
        /* 控制逻辑 */
        Control_Process();

        /* 喂心跳 */
        TaskHeartbeat_Feed(TASK_ID_CONTROL);

        osDelay(50);
    }
}

void CommTask(void const *argument)
{
    for (;;)
    {
        /* 通信处理 */
        Comm_Process();

        /* 喂心跳 */
        TaskHeartbeat_Feed(TASK_ID_COMM);

        osDelay(100);
    }
}

void SensorTask(void const *argument)
{
    for (;;)
    {
        /* 传感器采集 */
        Sensor_Acquire();

        /* 喂心跳 */
        TaskHeartbeat_Feed(TASK_ID_SENSOR);

        osDelay(200);
    }
}
```

**优点**：每个任务独立维护心跳，监控任务只做检查，职责分离；任一任务异常都会导致看门狗复位。
**缺点**：需要合理设置各任务的心跳超时时间，避免误触发。

#### 方案三：分级看门狗方案

采用硬件看门狗 + 软件看门狗组合的分级策略：

- **硬件看门狗（IWDG）**：作为最终防线，超时时间设为较长（如 5~10 秒），监控整个系统
- **软件看门狗**：在 RTOS 中通过软件定时器或高优先级任务实现，超时时间较短（如 1~2 秒），用于快速检测任务级异常
- **任务级看门狗**：每个关键任务有自己的软件看门狗，超时后触发错误处理（如记录日志、尝试恢复），而不是直接复位

```
任务异常 → 任务级看门狗超时 → 尝试恢复/记录日志
    ↓ 恢复失败
软件看门狗超时 → 记录故障信息到非易失存储
    ↓ 仍未恢复
硬件看门狗超时 → 系统复位
```

### 6. 喂狗任务本身挂了怎么办

这是面试中经常追问的深层次问题。监控任务本身也可能因为 bug、栈溢出、死锁等原因挂掉，此时看门狗形同虚设。应对策略如下：

#### 6.1 硬件看门狗作为最后防线

这是最基本也是最有效的策略。监控任务挂了 → 无法喂狗 → IWDG 超时 → 系统硬件复位。只要 IWDG 配置正确且无法被软件关闭，系统最终一定能被复位。

```c
/* IWDG超时时间应大于所有任务周期之和 + 安全裕量 */
/* 例如：任务A周期50ms + 任务B周期100ms + 任务C周期200ms + 监控周期100ms + 裕量 */
/* IWDG超时设为 2~5秒是合理的 */
hiwdg.Init.Prescaler = IWDG_PRESCALER_64;
hiwdg.Init.Reload    = 2500;
```

#### 6.2 软件看门狗互相监控

在 RTOS 中创建两个互相监控的任务，形成"互锁"机制：

```c
void WatchdogTask_A(void const *argument)
{
    for (;;)
    {
        /* 检查任务B是否存活 */
        if (Check_Task_Alive(TASK_B) == 0)
        {
            /* 任务B异常，触发系统复位 */
            NVIC_SystemReset();
        }

        /* 通知任务B：我还活着 */
        Set_Task_Alive(TASK_A);

        osDelay(200);
    }
}

void WatchdogTask_B(void const *argument)
{
    for (;;)
    {
        /* 检查任务A是否存活 */
        if (Check_Task_Alive(TASK_A) == 0)
        {
            /* 任务A异常，触发系统复位 */
            NVIC_SystemReset();
        }

        /* 通知任务A：我还活着 */
        Set_Task_Alive(TASK_B);

        osDelay(200);
    }
}
```

#### 6.3 利用 EWI 中断记录死机信息

WWDG 的提前唤醒中断（EWI）可以在系统复位前争取到宝贵的时间窗口，用于保存故障诊断信息：

```c
void HAL_WWDG_EarlyWakeupCallback(WWDG_HandleTypeDef *hwwdg)
{
    uint32_t fault_info = 0;

    /* 记录当前程序计数器 */
    fault_info = SCB->PC;

    /* 记录到备份寄存器（复位后可读取） */
    HAL_PWR_EnableBkUpAccess();
    __HAL_RCC_BKPSRAM_CLK_ENABLE();

    /* 存储故障信息 */
    *(volatile uint32_t *)BKPSRAM_BASE       = fault_info;
    *(volatile uint32_t *)(BKPSRAM_BASE + 4)  = SCB->HFSR;
    *(volatile uint32_t *)(BKPSRAM_BASE + 8)  = SCB->CFSR;
    *(volatile uint32_t *)(BKPSRAM_BASE + 12) = SCB->BFAR;
    *(volatile uint32_t *)(BKPSRAM_BASE + 16) = SCB->MMFAR;

    /* 设置复位标志 */
    RTC->BKP0R = 0xDEADBEEF;
}

/* 系统启动时检查是否为看门狗复位 */
void Check_Reset_Cause(void)
{
    if (HAL_PWR_GetBkUpAccess() == HAL_OK)
    {
        if (RTC->BKP0R == 0xDEADBEEF)
        {
            uint32_t pc     = *(volatile uint32_t *)BKPSRAM_BASE;
            uint32_t hfsr   = *(volatile uint32_t *)(BKPSRAM_BASE + 4);
            uint32_t cfsr   = *(volatile uint32_t *)(BKPSRAM_BASE + 8);

            /* 读取完毕后清除标志 */
            RTC->BKP0R = 0;

            /* 上报故障信息 */
            Log_Fault_Info(pc, hfsr, cfsr);
        }
    }

    if (__HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST))
    {
        __HAL_RCC_CLEAR_RESET_FLAGS();
        Log_Error("系统由独立看门狗复位");
    }

    if (__HAL_RCC_GET_FLAG(RCC_FLAG_WWDGRST))
    {
        __HAL_RCC_CLEAR_RESET_FLAGS();
        Log_Error("系统由窗口看门狗复位");
    }
}
```

#### 6.4 双看门狗架构

在可靠性要求极高的系统中（如汽车电子、医疗器械），可以同时使用 IWDG 和 WWDG：

- **WWDG**：短超时（毫秒级），监控关键任务的时序正确性
- **IWDG**：长超时（秒级），作为系统级兜底

```c
void System_Init(void)
{
    /* 先初始化WWDG，短超时监控时序 */
    WWDG_Init();

    /* 再初始化IWDG，长超时作为兜底 */
    IWDG_Init();
}
```

### 7. 工程实践建议

#### 最佳实践总结

1. **裸机系统**：使用 IWDG 即可，在主循环中定期喂狗，超时时间设为主循环周期的 3~5 倍
2. **RTOS系统**：采用分布式心跳 + 监控任务方案，每个关键任务维护独立的心跳标志
3. **超时时间设置**：IWDG 超时应为所有任务周期之和加上足够的安全裕量（建议 2~3 倍）
4. **喂狗位置**：在任务的关键路径上喂心跳，不要在任务入口处就喂——应在核心逻辑执行完毕后
5. **调试阶段**：通过 DBGMCU 寄存器暂停看门狗，避免单步调试时误触发复位
6. **故障诊断**：利用 EWI 中断或备份寄存器记录死机现场信息，复位后读取分析
7. **复位原因判断**：系统启动时检查 RCC 复位标志寄存器（RCC_CSR），区分上电复位、看门狗复位、软件复位等
8. **不要在 ISR 中喂狗**：中断服务函数中喂狗会掩盖主程序死机的真相
9. **关键任务才纳入监控**：不需要监控所有任务，只监控影响系统安全的任务即可
10. **测试验证**：在测试阶段故意停止某个任务的喂狗操作，验证看门狗能否正确触发复位

#### 面试回答模板

> 看门狗是嵌入式系统中保障可靠性的重要机制。独立看门狗使用 LSI 时钟，超时范围大，适合系统级死机检测；窗口看门狗使用 APB1 时钟，精度高，且引入了窗口概念，太早或太晚喂狗都会复位，适合时序监控。
>
> 在多任务系统中，我推荐使用分布式心跳方案——每个关键任务维护自己的心跳标志，由一个独立的监控任务统一检查，全部正常才喂狗。对于监控任务本身挂掉的问题，硬件看门狗作为最后防线，超时后直接复位系统。同时可以利用 WWDG 的 EWI 中断在复位前保存故障信息到备份寄存器，便于复位后分析死机原因。在可靠性要求高的场景中，IWDG 和 WWDG 可以组合使用，形成双看门狗架构。
