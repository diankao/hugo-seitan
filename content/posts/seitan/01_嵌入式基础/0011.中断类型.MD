### NVIC 核心寄存器对照表

| 缩写 | 全称 | 中文含义 | 功能口诀/理解 |
| :--- | :--- | :--- | :--- |
| **ISER** | **I**nterrupt **S**et-**E**nable **R**egister | 中断**设置使能**寄存器 | **使能中断**：写 1 使能，写 0 无效（因为是 Set，只能置 1） |
| **ICER** | **I**nterrupt **C**lear-**E**nable **R**egister | 中断**清除使能**寄存器 | **除能中断**：写 1 禁止，写 0 无效（因为是 Clear，只能清 0） |
| **ISPR** | **I**nterrupt **S**et-**P**ending **R**egister | 中断**设置悬起**寄存器 | **手动触发**：写 1 把中断状态设为“等待响应”（即使硬件没请求） |
| **ICPR** | **I**nterrupt **C**lear-**P**ending **R**egister | 中断**清除悬起**寄存器 | **取消请求**：写 1 把“等待响应”的状态取消掉 |
| **IABR** | **I**nterrupt **A**ctive **B**it **R**egister | 中断**活跃位**寄存器 | **正在处理**：只读，查看当前 CPU 正在处理哪个中断 |
| **IP** | **I**nterrupt **P**riority Register | 中断**优先级**寄存器 | **优先级配置**：配置每个中断的抢占优先级和子优先级 |
| **STIR** | **S**oftware **T**riggered **I**nterrupt Register | 软件**触发中断**寄存器 | **软触发**：写一下，软件触发一个中断（用于多核通信或测试） |

---

### 为什么这样设计？（助记小贴士）

1.  **S 和 C 的对立**：
    -   **S = Set**：设置为 1（生效）。
    -   **C = Clear**：清除为 0（失效）。
    -   *例子*：**ISER** 是使能，**ICER** 就是除能；**ISPR** 是设置悬起，**ICPR** 就是清除悬起。

2.  **ER 和 R 的区别**：
    -   **ER** 结尾（如 ISER/ICER）：通常用来输出**控制信号**（使能/除能）。
    -   **R** 结尾（如 IABR）：通常用来**反映状态**（只读）。

3.  **单词解析**：
    -   **Pending**：悬起/挂起。可以理解为中断请求已经发出，但 CPU 正忙，这个请求被“悬在空中”排队等待。
    -   **Active**：活跃。可以理解为 CPU 正在执行这个中断的服务函数，处于“活跃”状态。


在常规的嵌入式开发（如STM32）中，配置中断时确实只用到了 ISER（使能）、ICER（除能）和 IP（优先级）。

之所以用不到其他的寄存器（如 ISPR、ICPR、IABR），是因为那些寄存器解决的是更底层、更特殊的硬件问题，或者是由操作系统（RTOS）内核来管理的，而普通的应用层驱动开发通常不需要手动干预。

我们可以把这些寄存器分为三类来理解：

1. 用于控制（由驱动开发者使用）：ISER、ICER、IP
这三者完成了一个中断最基本的生命周期管理：

ISER：决定外设的中断请求能否被送到CPU（“开门”）。

ICER：决定是否禁止某个中断（“关门”）。

IP：决定多个中断同时发生时，谁先被CPU响应（“插队优先级”）。

这是每个中断使用前必须做的配置，所以你会频繁用到它们。

2. 用于调试/容错（由内核/调试器使用）：ISPR、ICPR
这两个寄存器用来处理“悬起”状态。

悬起（Pending）：当中断条件满足，但CPU暂时无法响应（比如正在处理更高优先级的中断），该中断请求会被硬件锁存起来，等待处理。这个“锁存的请求”就是悬起状态。

为什么一般用不到？

硬件自动管理：当中断来了，硬件自动置位悬起位；当中断处理程序（ISR）开始执行，硬件自动清除悬起位。正常情况下不需要软件介入。

特殊用途：

ISPR：在调试时，如果想模拟一个中断发生（即使硬件没发出信号），可以手动写1来置起悬起位，触发中断。

ICPR：如果在处理异常时，想放弃之前收到的某个中断请求（即“清掉悬起标志”），可以手动清除。

3. 用于状态查询（由操作系统/调试器使用）：IABR
这个寄存器用来查看当前正在服务的中断。

活跃（Active）：CPU正在执行该中断的中断服务程序（ISR）。

为什么一般用不到？

普通程序知道自己正在处理哪个中断（因为就在ISR函数里）。

它的主要作用是支持中断嵌套和优先级抢占。硬件需要知道当前活跃的是谁，以便在更高优先级中断来时决定是否抢占。

查询场景：调试时，查看IABR可以知道CPU是不是卡在某个ISR里了；或者在RTOS中，内核需要了解当前的中断上下文状态。

4. 用于软件触发（由操作系统使用）：STIR
这是一个只写的寄存器，写它就能触发一个中断。

为什么用不到？

这个功能主要用于操作系统进程间通信（IPI，处理器间中断），在多核CPU中，一个核可以通过写STIR去唤醒另一个核。

在单核单片机上，如果一个任务想触发另一个中断，通常直接调用函数比模拟一个硬件中断更高效、更简单。只有在需要完全模拟硬件行为（比如测试）时才会用到。

为什么保留这么多寄存器？（从架构设计角度看）
虽然你暂时用不到，但CM3/CM4内核在设计 NVIC_Type 结构体时保留它们，是为了满足不同场景下的完整需求：

硬件原子操作：

ISER 和 ICER 分开，是为了实现原子的置1和清0。如果只有一个使能寄存器，软件修改时需要“读-改-写”，在多任务或中断环境下可能出错。分成两个，写ISER就是只让对应位=1，写ICER就是只让对应位=0，不需要读，非常安全。

操作系统（RTOS）的支撑：

像FreeRTOS这样的操作系统，在任务切换时可能需要屏蔽特定中断，或者在处理完异常后清除某些悬起位。这时就会用到 ISPR 和 ICPR。

调试与诊断：

当你用J-Link调试，查看NVIC的寄存器组时，IABR 可以告诉你CPU现在到底是不是卡在某个中断里出不来。

总结：
你现在只用 ISER/ICER/IP 是因为你正处于“配置阶段”。就像买车你只用到方向盘、油门和刹车，但车里还配有安全气囊传感器（IABR）、引擎故障诊断接口（ISPR/ICPR）和远程启动钥匙（STIR）——这些不是日常驾驶必须的，但在特定场景下缺一不可。
