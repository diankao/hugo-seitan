# 互斥锁与自旋锁区别

## 题目

互斥锁和自旋锁的区别是什么？各自适合什么场景？

## 考察点

Linux内核同步机制、锁的实现原理、阻塞与忙等的权衡、中断上下文中的锁选择。

## 回答要点

### 1. 核心区别

**互斥锁（Mutex）**：获取不到锁时，线程**睡眠让出 CPU**，等待被唤醒后重新调度。

**自旋锁（Spinlock）**：获取不到锁时，线程**忙等（死循环不断尝试）**，不释放 CPU。

```c
// 互斥锁：获取失败 → 睡眠 → 被唤醒 → 重新调度
mutex_lock(&m);
// 如果锁被占用：当前线程进入 TASK_UNINTERRUPTIBLE 状态，让出 CPU
// 锁释放时：唤醒等待队列中的线程
mutex_unlock(&m);

// 自旋锁：获取失败 → 死循环重试
spin_lock(&s);
// 如果锁被占用：while (lock == 1) { cpu_relax(); }
// 锁释放时：立刻获取（因为一直在运行）
spin_unlock(&s);
```

### 2. 对比表

| 特性 | 互斥锁（Mutex） | 自旋锁（Spinlock） |
|------|----------------|-------------------|
| 等待方式 | **睡眠阻塞** | **忙等（自旋）** |
| CPU 占用 | 不占用（睡眠期间） | 100% 占用（自旋期间） |
| 上下文切换 | 有（睡眠/唤醒） | 无 |
| 适用上下文 | **进程上下文**（可以睡眠） | 任何上下文（不能睡眠的场景） |
| 临界区长度 | 可以较长 | **必须极短** |
| 能否在中断中使用 | 不能 | 可以（需用 `spin_lock_irqsave`） |
| 能否睡眠 | 临界区内可以 | **临界区内绝对不能睡眠** |
| 开销 | 高（两次上下文切换） | 低（无上下文切换） |
| 优先级 | 支持优先级继承 | 无优先级概念 |
| Linux API | `mutex_lock` / `mutex_unlock` | `spin_lock` / `spin_unlock` |

### 3. 自旋锁的实现原理

```c
// 简化的自旋锁实现
typedef struct {
    volatile int locked;
} spinlock_t;

void spin_lock(spinlock_t *lock) {
    while (atomic_cmpxchg(&lock->locked, 0, 1) != 0) {
        // 锁被占用，自旋等待
        // cpu_relax() 提示 CPU 可以降低功耗（x86 上是 pause 指令）
        cpu_relax();
    }
    // atomic_cmpxchg 成功将 0 改为 1，获取到锁
}

void spin_unlock(spinlock_t *lock) {
    // 释放锁：将 locked 写回 0
    atomic_set(&lock->locked, 0);
}
```

**关键点**：`cmpxchg` 是原子操作，硬件保证同一时刻只有一个 CPU 能成功。

### 4. 互斥锁的实现原理

```c
// 简化的互斥锁实现
typedef struct {
    atomic_t count;           // 1=未锁定, 0=锁定, 负数=有等待者
    spinlock_t wait_lock;     // 保护等待队列
    struct list_head wait_list; // 等待队列
} mutex_t;

void mutex_lock(mutex_t *m) {
    // 快速路径：尝试原子地将 count 从 1 改为 0
    if (atomic_dec_and_test(&m->count))
        return;  // 成功获取锁

    // 慢速路径：锁被占用，加入等待队列并睡眠
    spin_lock(&m->wait_lock);
    list_add_tail(&current->list, &m->wait_list);
    set_task_state(current, TASK_UNINTERRUPTIBLE);
    spin_unlock(&m->wait_lock);

    schedule();  // 让出 CPU，等被唤醒

    // 被唤醒后，已经持有锁
}

void mutex_unlock(mutex_t *m) {
    // 快速路径：count 从 0 改为 1
    if (atomic_inc_and_test(&m->count))
        return;  // 没有等待者，直接释放

    // 慢速路径：有等待者，唤醒第一个
    spin_lock(&m->wait_lock);
    struct task_struct *waiter = list_first_entry(&m->wait_list, ...);
    list_del(&waiter->list);
    wake_up_process(waiter);
    spin_unlock(&m->wait_lock);
}
```

**注意**：互斥锁内部用自旋锁保护等待队列，但等待队列的操作极短。

### 5. 自旋锁在中断中的正确用法

```c
// 错误：自旋锁不保护中断
spin_lock(&lock);
// 如果此时中断触发，ISR 中也获取同一把锁 → 死锁！
// ISR 永远等不到锁，因为当前 CPU 被 ISR 抢占

// 正确：同时禁用本地中断
unsigned long flags;
spin_lock_irqsave(&lock, flags);
// 临界区：中断被禁用，不会被 ISR 抢占
spin_unlock_irqrestore(&lock, flags);
```

### 6. 选择原则

```
需要锁保护共享资源？
       │
       ▼
临界区内能睡眠吗？──Yes──▶ 互斥锁
       │
       No
       ▼
在中断上下文中？──Yes──▶ 自旋锁（spin_lock_irqsave）
       │
       No
       ▼
临界区极短（< 几微秒）？──Yes──▶ 自旋锁
       │
       No
       ▼
互斥锁
```

**嵌入式/Linux 内核中的典型场景**：

| 场景 | 选择 | 原因 |
|------|------|------|
| ISR 与进程共享数据 | `spin_lock_irqsave` | ISR 中不能睡眠 |
| 进程上下文短临界区 | `spin_lock` | 无上下文切换开销 |
| 进程上下文长临界区 | `mutex` | 不浪费 CPU |
| 驱动 read/write | `mutex` | 涉及 copy_to_user，可能睡眠 |
| 定时器回调 | `spin_lock` | 软中断上下文，不能睡眠 |
| 工作队列处理函数 | `mutex` | 进程上下文，可以睡眠 |

### 7. 面试速记

- **互斥锁**：获取不到就睡眠，有上下文切换开销，适合长临界区
- **自旋锁**：获取不到就忙等，无上下文切换，适合极短临界区和中断上下文
- **核心规则**：持有自旋锁期间**绝对不能睡眠**
- **中断中使用**：必须用 `spin_lock_irqsave` 禁用本地中断
- **驱动 read/write**：通常用 mutex（因为 copy_to_user 可能睡眠）
