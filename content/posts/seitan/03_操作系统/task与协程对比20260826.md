# task与协程对比

## 题目

task 和协程有什么区别？它们分别用在什么环境？

## 考察点

并发模型的理解：抢占式调度与协作式调度的区别、上下文切换成本、不同语言和平台对并发单元的命名差异

## 回答要点

### 1. 先说结论

"task 和协程"这个说法其实混了三类东西，先把它们拆开：

1. **RTOS 的 task**（FreeRTOS、RT-Thread、Zephyr）：内核里的调度基本单位，抢占式调度，约等于一个轻量线程
2. **语言异步库的 task**（`std::async`、C# `Task`、Python asyncio `Task`）：库/运行时层的"任务"概念，是提交给运行时的一段异步工作，或对协程的调度包装句柄
3. **协程**（C++20、Go、Python、Lua）：用户态协作式调度的函数，只在主动 `yield`/`await` 的点让出执行权

三类不是竞争关系，而是不同层面：RTOS task 是内核级并发单元；语言层 task 是库级并发单元（多数最终跑在 OS 线程上）；协程是语言级协作并发原语，常常被语言层 task 包装和调度。

### 2. RTOS 的 task

FreeRTOS、RT-Thread、Zephyr 等 RTOS 中，整个固件就是一组 task，由调度器按优先级轮转：

```c
// FreeRTOS：创建两个任务
xTaskCreate(vLedTask,     "led",     128, NULL, 1, NULL);
xTaskCreate(vSensorTask,  "sensor",  256, NULL, 2, NULL);  // 优先级更高

void vLedTask(void *arg) {
    for (;;) {
        toggle_led();
        vTaskDelay(pdMS_TO_TICKS(500));  // 主动阻塞让出 CPU
    }
}
```

RTOS task 的特征：

- **抢占式调度**：调度器随时可以打断当前 task 去跑更高优先级的任务，任何两条指令之间都可能发生切换
- **独立栈**：每个 task 有自己的栈（FreeRTOS 最小可到几十~几百字节），切换时保存全套寄存器上下文
- **实时性保证**：高优先级事件（中断释放信号量）能在确定的延迟内抢占执行，这是硬实时场景选它的根本原因
- **内核对象配套**：队列、信号量、事件组等 IPC 由 RTOS 内核提供，跨 task 通信要走这些机制

### 3. 语言异步库的 task

这类 task 是**库/运行时**提供的抽象，不是 OS 概念。它们的共性是：把"一段要异步执行的工作"包装成对象，由库的执行器/线程池调度。分两种情况：

#### 直接包装一段工作

```cpp
// C++：提交给运行时的任务，future 是结果句柄
std::future<int> f = std::async(std::launch::async, [] { return heavy_work(); });
int result = f.get();

// Qt 生态的等价物
auto *watcher = new QFutureWatcher<int>(this);
connect(watcher, &QFutureWatcher<int>::finished, this, [watcher] {
    int result = watcher->result();
});
watcher->setFuture(QtConcurrent::run([] { return heavy_work(); }));
```

`std::async` 底层是 OS 线程（或线程池），`QtConcurrent::run` 底层是 Qt 的全局线程池——**这类 task 本质是"OS 线程上的一个待办事项"**，调度是抢占式的（由 OS 决定），只是生命周期和结果获取被库管理起来了。

#### 包装协程的调度句柄

C# 的 `Task`、Python asyncio 的 `Task` 属于这一种：协程本身不会自己跑起来，`Task` 把协程注册到事件循环上，负责驱动它、跟踪状态（pending/running/done）：

```python
# Python：Task 是协程的调度包装
task = asyncio.create_task(fetch_data())   # 协程被包装成 Task，开始被事件循环调度
result = await task                        # await 等待 Task 完成
```

所以看到 C# `async Task<int> Foo()` 里的 Task，不要和 FreeRTOS 的 task 混淆——它是一个**运行在某个线程事件循环上的协程句柄**，没有独立栈、没有优先级、不参与内核调度。

### 4. 协程

协程是**可以挂起和恢复的函数**：执行到某个点主动暂停，把控制权交还调用者/调度器，之后从暂停点继续。切换发生在用户态，只保存极少量状态，成本纳秒级。

按实现分两类：

| 类型 | 代表 | 特点 |
|------|------|------|
| 有栈协程 | Go goroutine、Lua coroutine、boost.context | 每个协程有独立栈，可以在任意嵌套深度挂起 |
| 无栈协程 | C++20 协程、Rust async/await、JS async/await | 编译器把函数改写成状态机，栈帧不存在了，挂起点只能是标注处 |

常见宿主环境：

- **C++20**：`co_await` / `co_yield` / `co_return` 关键字
- **Boost.Asio**：网络异步编程中最成熟的协程实践（详见第 7 节）
- **Python** asyncio、**Go** goroutine、**Lua** coroutine、**JavaScript** async/await

注意协程和第 3 节的关系：协程是原语，语言层 task 常常是它的调度外壳。也有不经过 task 概念直接用协程的（C++20 `co_await` 一个 `awaitable` 就不需要 Task 这个中间层）。

### 5. 核心对比

| 维度 | RTOS 的 task | 语言异步库的 task | 协程 |
|------|--------------|------------------|------|
| 所在层面 | RTOS 内核 | 库/运行时（通常在 OS 线程上） | 语言特性，用户态 |
| 调度方式 | 抢占式：按优先级/时间片随时打断 | 包装工作的：OS 线程抢占式；包装协程的：事件循环协作式 | 协作式：只在 yield/await 点切换 |
| 切换成本 | 保存全套寄存器上下文（几十~上百周期） | 前者同线程；后者同协程 | 用户态保存少量状态，纳秒级 |
| 栈 | 每个 task 独立栈（几百字节起） | 复用线程池线程的栈 | 无栈（状态机）或有极小栈 |
| 并发规模 | 几十~几百个 task 是常态 | 线程池大小决定（几十~几百） | 轻松百万级（如 Go 单机十万+ goroutine） |
| 阻塞的影响 | 一个 task 阻塞（延时/等信号量）不影响其他 task | 阻塞占用线程池线程，过多会饿死其他任务 | 一个协程不让出，整条线程上的所有协程都卡死 |
| 能否利用多核 | 多核 RTOS 可并行 | 线程池天然多核 | 协程本身单线程，多核需多线程 + 每线程一组协程 |
| 实时性 | 确定性最好 | 无保证 | 无保证 |

#### "协作式"最关键的推论

协程的切换点在源代码里**看得见**（`await` 处），所以两个 `await` 之间的代码不会被同线程的其他协程打断——这段代码天然是临界区。RTOS task 则可能在任何两条指令之间被打断。这是协程能大量减少锁使用的原因，也是"一个协程死循环整条线程卡死"这一缺陷的另一面。

### 6. 为什么写 Qt/Windows 没见过这两个词

Qt 生态有自己的并发封装，概念能对上号：

| Qt/Windows 世界的概念 | 对应概念 |
|----------------------|---------|
| QThread / std::thread | RTOS task 的 OS 线程版本（抢占式） |
| QtConcurrent::run | 语言异步库的 task（提交工作给线程池） |
| 信号槽（QueuedConnection）+ 事件循环 | 协程要解决的异步回调问题，Qt 用事件循环 + 回调实现 |

也就是说在 Qt 里你不是没接触过并发和异步，而是这些概念穿了别的名字。区别在写法：回调风格（信号槽、lambda）会把逻辑打散在多个函数里，协程用 `co_await` 把异步代码写回同步的样子。Qt 6.7+ 已支持在槽函数中 `co_await`，两套风格正在合流。

### 7. Boost 的协程：boost::asio 实战

Boost 是 C++ 协程的先行者，比 C++20 标准早了十年。涉及三个层次：

#### boost.context / boost.coroutine2

最底层：`boost::context` 提供汇编实现的上下文切换（`fibonacci`/`callcc`），是有栈协程的基石；`boost.coroutine2` 在其上封装出对称/非对称协程。一般不直接用，asio 依赖它实现有栈路径。

#### boost.asio 的协程（重点）

asio 原来典型的回调风格：

```cpp
// 回调风格：逻辑被切碎，层层嵌套
void do_read(socket_ptr sock) {
    auto buf = std::make_shared<std::vector<char>>(1024);
    sock->async_read_some(boost::asio::buffer(*buf),
        [sock, buf](boost::system::error_code ec, std::size_t len) {
            if (!ec) {
                boost::asio::async_write(*sock, boost::asio::buffer(*buf, len),
                    [sock, buf](boost::system::error_code ec, std::size_t) {
                        if (!ec) do_read(sock);  // 递归继续
                    });
            }
        });
}
```

用协程改写（asio + C++20 无栈协程）：

```cpp
boost::asio::awaitable<void> session(tcp::socket sock) {
    try {
        char buf[1024];
        for (;;) {
            std::size_t len = co_await sock.async_read_some(
                boost::asio::buffer(buf), boost::asio::use_awaitable);
            co_await boost::asio::async_write(sock,
                boost::asio::buffer(buf, len), boost::asio::use_awaitable);
        }
    } catch (std::exception&) {
        // 连接断开，协程结束
    }
}

// 在 io_context 上启动协程
boost::asio::co_spawn(io_context, session(std::move(sock)),
                      boost::asio::detached);
```

`co_await` 挂起点就是原来回调开始的地方：发起异步读 → 协程挂起 → io_context 事件循环去跑别的协程 → 读完成 → 协程从挂起点恢复。**逻辑线性了，但线程没有阻塞**——这正是协程的价值：回调的写法成本 + 阻塞式代码的可读性。

#### 回调风格 → 协程风格的三件事：错误、返回值、out 参数

把回调代码改写成 `co_await` 时，接口形态会发生三个固定变化，理解它们就掌握了两种风格的翻译规则。

**1. 错误码变成 try/catch**

回调风格的错误通过 `error_code` 参数传给回调：

```cpp
sock->async_read_some(boost::asio::buffer(buf),
    [](boost::system::error_code ec, std::size_t len) {
        if (ec) return;  // 每层回调都要手动检查、手动传播
    });
```

协程风格中，`use_awaitable` 完成令牌会把非零 `error_code` 转换为 `boost::system::system_error` 异常抛出，于是一个 try/catch 就能覆盖整段逻辑的所有错误路径，不用层层手动检查：

```cpp
try {
    for (;;) {
        std::size_t len = co_await sock.async_read_some(
            boost::asio::buffer(buf), boost::asio::use_awaitable);
        co_await boost::asio::async_write(sock,
            boost::asio::buffer(buf, len), boost::asio::use_awaitable);
    }
} catch (const boost::system::system_error& e) {
    // 读失败、写失败、连接断开都汇集到这里
    std::printf("session end: %s\n", e.what());
}
```

不想用异常也可以：把完成令牌换成 `boost::asio::as_tuple(boost::asio::use_awaitable)` 或 `use_awaitable` 配 `boost::system::error_code` 重载，`co_await` 就返回 `std::tuple<error_code, ...>`，回到错误码风格：

```cpp
auto [ec, len] = co_await sock.async_read_some(
    boost::asio::buffer(buf), boost::asio::as_tuple(boost::asio::use_awaitable));
if (ec) { /* 处理错误 */ }
```

**2. 结果成为 co_await 表达式的返回值**

协程函数自己的返回类型也由此确定：asio 统一用 `boost::asio::awaitable<T>`，其中 `T` 就是协程结束时 `co_return` 的类型：

```cpp
// 协程"返回"一个 int：注意函数签名是 awaitable<int>，函数体里 co_return 1
boost::asio::awaitable<int> read_command(tcp::socket& sock) {
    char cmd[16];
    co_await boost::asio::async_read(sock, boost::asio::buffer(cmd, 16),
                                     boost::asio::use_awaitable);
    co_return parse(cmd);
}

// 调用方：co_await 一个 awaitable<int>，表达式类型就是 int
boost::asio::awaitable<void> session(tcp::socket sock) {
    int cmd = co_await read_command(sock);
}
```

这是协程和普通函数最大的形态差异之一：协程的返回类型不是 `T`，而是包装了 `T` 的"任务句柄"（asio 的 `awaitable<T>`、C++20 概念上就是含 `promise_type` 的类型）；真正的业务值通过 `co_return` 交出，调用方用 `co_await` 解包。

**3. out 参数变成返回值**

回调接口里"输出"有两处：错误码 `ec` 和传输长度 `len`，它们作为回调参数（典型的 out 参数）交回给你。协程化之后，错误走了异常，剩余输出直接变成 `co_await` 表达式的值——out 参数消失了。对照：

```cpp
// 回调风格：len 是回调的 out 参数
sock->async_read_some(boost::asio::buffer(buf),
    [](error_code ec, std::size_t len) {   // ec、len 都是输出
        use(buf, len);
    });

// 协程风格：len 是表达式的值
std::size_t len = co_await sock.async_read_some(
    boost::asio::buffer(buf), boost::asio::use_awaitable);
```

一个直接的好处是 `buf` 不再需要 `std::shared_ptr` 续命：回调风格中发起调用后函数就返回了，`buf` 必须靠捕获共享指针活到回调触发；协程风格中 `buf` 就是局部变量，协程挂起期间它随协程帧一起存活，恢复后原样可用——这也是协程版代码更短的主要原因。


asio 同时也保留有栈协程接口（`boost::asio::spawn` + `boost::asio::yield_context`，基于 boost.context），老代码常见：

```cpp
// 有栈风格：用起来像同步代码，底层是 boost.context 切换
boost::asio::spawn(io_context, [](boost::asio::yield_context yield) {
    std::size_t len = sock.async_read_some(boost::asio::buffer(buf), yield);
    boost::asio::async_write(sock, boost::asio::buffer(buf, len), yield);
});
```

#### asio 协程和 RTOS task 的分工对照

以一个网络设备为例，两者经常**分层共存**：

- RTOS task：跑协议栈、控制外设、响应中断后的实时处理（需要抢占保证实时性）
- asio 协程（跑在某个 task/线程的 io_context 里）：管理几十条 TCP 连接的业务逻辑（连接多、大部分时间在等网络，协程最省）

一个 task 里挂几百个连接协程，比一个连接一个 task 省一到两个数量级的内存。

### 8. 嵌入式视角：什么时候选什么

| 场景 | 选择 | 理由 |
|------|------|------|
| 硬实时响应（电机控制、采样控制环） | RTOS task + 中断 | 必须抢占，延迟确定性 |
| 大量"等待型"并发（几十条 TCP/BLE 连接） | 协程（或 RTOS 上的事件循环） | 等待为主，协程内存和切换成本最低 |
| 单核小 RAM MCU、无 RTOS | 事件循环 / 状态机（裸机前后台） | 协程的思想（协作式让出）本来就是前后台系统的抽象化 |
| 应用处理器上的中间件、网关 | Linux + asio 协程 / Go | 并发量大，用户态调度便宜 |

一句话总结：**task 是"内核替你管切换"，协程是"你自己标出切换点"**。前者换来了通用性和实时性，后者换来了数量级更低的并发成本——按延迟要求和并发规模选型即可。
