# RTOS任务切换上下文保存与恢复

## 题目

RTOS中一次任务切换具体保存和恢复了哪些上下文？为什么有些寄存器可以不保存？

## 考察点

Cortex-M异常机制、PendSV上下文切换、AAPCS调用约定、硬件自动压栈与软件压栈的区别。

## 回答要点

### 1. 上下文切换的触发时机

| 触发方式 | 说明 | FreeRTOS 实现 |
|---------|------|--------------|
| 任务主动让出 | 调用 `vTaskDelay`、`xQueueReceive` 等阻塞 API | 内部调用 `portYIELD()` |
| 时间片到期 | SysTick 中断触发，同优先级任务轮转 | `xPortSysTickHandler()` |
| 高优先级就绪 | 中断中唤醒了更高优先级任务 | `portYIELD_FROM_ISR()` |

以上所有方式最终都通过 **PendSV 中断** 来执行实际的上下文切换喵~

### 2. Cortex-M 硬件自动压栈

进入异常（包括 PendSV）时，Cortex-M 硬件**自动**将以下 8 个寄存器压入当前栈（PSP）喵~

```
PSP + 0x1C    xPSR
PSP + 0x18    PC      (返回地址)
PSP + 0x14    LR      (R14)
PSP + 0x10    R12
PSP + 0x0C    R3
PSP + 0x08    R2
PSP + 0x04    R1
PSP + 0x00    R0
```

这 8 个寄存器是 **AAPCS（ARM架构过程调用标准）** 规定的**调用者保存寄存器**（caller-saved），编译器在调用函数前会自动处理喵~

### 3. 软件手动压栈

FreeRTOS 的 PendSV handler 在硬件压栈之后，再**手动**保存剩余的**被调用者保存寄存器**（callee-saved）喵~

```arm
PendSV_Handler:
    MRS     R0, PSP               ; 获取任务栈指针
    STMDB   R0!, {R4-R11, R14}    ; 保存 R4-R11 和 LR（EXC_RETURN）

    LDR     R1, =pxCurrentTCB     ; 获取当前任务控制块
    LDR     R2, [R1]
    STR     R0, [R2]              ; 保存更新后的 SP 到 TCB
```

如果有浮点单元（FPU），还需要保存浮点寄存器：

```arm
    TST     R14, #0x10            ; 检查是否使用了浮点上下文
    IT      EQ
    VSTMDBEQ R0!, {S16-S31}      ; 保存浮点寄存器 S16-S31
```

### 4. 完整的保存列表

| 寄存器 | 保存者 | 原因 |
|--------|--------|------|
| R0-R3 | 硬件自动 | 函数参数/返回值，AAPCS 规定调用者保存 |
| R12 (IP) | 硬件自动 | 临时寄存器，编译器可能在函数调用间使用 |
| LR (R14) | 硬件自动 | 返回地址，必须保存 |
| PC (R15) | 硬件自动 | 下一条指令地址，异常返回时恢复 |
| xPSR | 硬件自动 | 条件标志、中断状态等，必须保存 |
| **R4-R11** | **软件手动** | **AAPCS 规定被调用者保存，编译器假定跨函数调用不变** |
| S16-S31 | 软件手动（有 FPU 时） | 浮点 callee-saved 寄存器 |
| SP (PSP) | 软件手动 | 存入 TCB 的 `pxTopOfStack` |

### 5. 为什么 R0-R3 不需要软件保存

AAPCS 将寄存器分为两类喵~

| 类别 | 寄存器 | 规则 |
|------|--------|------|
| 调用者保存（caller-saved） | R0-R3, R12 | 调用函数前，**调用者**负责保存（如果需要） |
| 被调用者保存（callee-saved） | R4-R11 | 函数返回时，**被调用者**必须恢复原值 |

编译器在生成代码时，如果一个函数要调用另一个函数，它会自动将需要保留的 R0-R3 值保存到栈上喵~ 所以当异常打断任务时，R0-R3 要么已经不被需要，要么已经被编译器保存了喵~

**而 R4-R11 不同**：编译器假定这些寄存器在函数调用前后不变，直接使用它们来存放跨函数调用的局部变量喵~ 如果 RTOS 不保存它们，任务恢复后这些变量的值就丢了喵~

### 6. 恢复过程

```arm
    LDR     R1, =pxCurrentTCB     ; 获取新任务的 TCB
    LDR     R2, [R1]
    LDR     R0, [R2]              ; 从 TCB 恢复 SP

    TST     R14, #0x10
    IT      EQ
    VLDMIAEQ R0!, {S16-S31}      ; 恢复浮点寄存器

    LDMIA   R0!, {R4-R11, R14}   ; 恢复 R4-R11 和 EXC_RETURN

    MSR     PSP, R0               ; 恢复任务栈指针
    BX      R14                   ; 异常返回，硬件自动出栈 R0-R3, R12, LR, PC, xPSR
```

`BX R14`（其中 R14 = EXC_RETURN）触发硬件异常返回，自动从栈中弹出那 8 个寄存器喵~

### 7. 一次完整切换的开销

| 项目 | Cortex-M3/4（无 FPU） | Cortex-M4（有 FPU） |
|------|----------------------|-------------------|
| 硬件压栈 | 8 个寄存器（32字节） | 8 个寄存器（32字节） |
| 软件压栈 | 8 个寄存器（32字节） | 8 + 16 = 24 个寄存器（96字节） |
| 调度器选择 | 查找最高优先级任务 | 同左 |
| 软件出栈 | 8 个寄存器（32字节） | 24 个寄存器（96字节） |
| 硬件出栈 | 8 个寄存器（32字节） | 8 个寄存器（32字节） |
| **总栈使用** | **64 字节** | **128 字节** |
| **典型耗时** | **~30 个时钟周期** | **~60 个时钟周期** |

### 8. 总结

```
任务切换上下文保存：

硬件自动保存（进入异常时）：
  R0, R1, R2, R3, R12, LR, PC, xPSR
  → 这些是 caller-saved，编译器已处理

软件手动保存（PendSV 中）：
  R4, R5, R6, R7, R8, R9, R10, R11
  → 这些是 callee-saved，编译器假定跨调用不变
  → 如果不保存，任务的局部变量就丢了

不需要保存的：
  R13 (SP) → 通过 PSP 保存到 TCB
  R0-R3    → caller-saved，编译器负责
  MSP      → 任务不使用主栈
```
