# 文件链接、删除语义与权限模型对比

## 题目

围绕文件系统的系列问题：硬链接和软链接的本质区别是什么？为什么 Windows 上经常删不掉"被占用"的文件而 Unix 可以随时删？rwx 权限位、umask、SUID 这些东西在 Windows 上有对应物吗？

## 考察点

链接与引用计数、unlink 的真实语义与 Windows 共享冲突的对照、Unix 权限位世界观与 NTFS ACL 模型的差异、SUID 与 UAC 提权的不同解法

## 回答要点

### 1. 地基回顾：名字不是文件

Unix 的文件本体是 inode（编号、属主、权限、时间戳、数据块指针），**文件名只是目录里"名字 → inode 号"的一条记录**（inode/FAT/NTFS 三种"文件本体"的对照见《教材Unix视角与各系统实现差异》第 3 节）。链接的一切差异都从这个地基推出来：

| | 硬链接 `ln a b` | 软链接 `ln -s a b` |
|---|---|---|
| 本质 | 目录里新增一条指向**同一 inode** 的记录 | 一个**独立的小文件**，内容是目标的路径字符串 |
| 引用计数 | inode 的 nlink +1 | 不影响目标 |
| 目标被删后 | 只要还有名字在，数据就活着 | 悬空（dangling），访问报错 |
| 限制 | 不能跨文件系统、不能指向目录 | 都可以 |
| ls -l 里 | 与原文件无法区分 | `l` 开头，名字带 `->` |

### 2. Windows 的链接：支持，但活在平行世界里

NTFS 其实**三种链接都有**，只是日常不可见、工具链别扭：

| 类型 | 命令 | 说明 |
|---|---|---|
| 硬链接 | `mklink /H b a`（或 `fsutil hardlink create`） | 同一 MFT 记录多个名字，语义与 Unix 一致；但资源管理器不显示链接计数 |
| 符号链接 | `mklink b a` | 需管理员权限（或开发者模式）；可指向目录、可跨卷 |
| 目录联接 junction | `mklink /J` | 目录专用、免特权，老版本兼容的"软链接前身" |

两个环境差异决定了体验：FAT/exFAT（U 盘、SD 卡）完全没有链接；而 Unix 世界 ln 是日常操作（软件安装、版本切换 `current -> v1.2.3` 全靠它）。Windows 工程师"没见过硬链接"不是文件系统不支持，是生态不用。另外 Unix 有一整套配套现象：`df -i` 看 inode 用量、inode 耗尽（磁盘有空间但建不了文件）、`ls -i` 看编号——这些运维概念在 NTFS 上没有对应物（NTFS 的 MFT 记录号不暴露）。

### 3. 删除语义：unlink 不是 delete

这是两边日常都在碰、但很少被对照讲透的差异。

**Unix 的"删除"是 unlink**：删掉一条目录项、nlink 减一。**数据真正释放要等两个条件同时满足**：nlink 归零 **且** 没有任何进程还开着它。推论：

- 可以"删掉"一个正在被写的日志文件——写进程（拿着 fd）照写不误，磁盘空间在它关闭 fd 后才回收
- 经典坑随之而来：`df` 看到的空间没降，因为某个进程还捏着被删文件的 fd（`lsof +L1` 专查这种"已 unlink 仍被打开"的文件）；清空大日志的正确姿势是 `> file`（截断）而不是 rm

**Windows 的删除要先过"共享模式"关**：打开文件时（`CreateFile`）就声明了共享位——`FILE_SHARE_READ`/`FILE_SHARE_WRITE`/`FILE_SHARE_DELETE`。别的句柄没声明 `FILE_SHARE_DELETE`，`DeleteFile` 就失败，报 `ERROR_SHARING_VIOLATION`，界面话术就是人尽皆知的**"操作无法完成，因为文件已在另一个程序中打开"**。C 运行库的 `fopen` 默认不带共享删除，所以"删不掉"是常态。

```c
/* Windows 上"允许别人删我正开着的文件"要显式声明 */
HANDLE h = CreateFile(path, GENERIC_READ,
                      FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE,
                      NULL, OPEN_EXISTING, 0, NULL);
```

工程后果最典型的是**替换正在运行的 DLL/EXE**：EXE 装载时句柄不带共享删除，直接覆盖报错。标准解法是**"改名 → 落新文件 → 延迟删除"**——同卷重命名对未共享删除的句柄通常是放行的（这也是热更新安装器、ClickOnce、WiX 的基础操作），删不掉的旧文件用 `MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)` 登记到重启再删。

| | Unix unlink | Windows DeleteFile |
|---|---|---|
| 检查时机 | 只看目录项与引用 | 先查所有现存句柄的共享位 |
| 对"正被打开的文件" | 允许删，空间延迟回收 | 默认拒绝，报共享冲突 |
| 常见坑 | df 不变小（fd 未关） | 文件被占用，删不掉 |
| 替换占用中的文件 | 直接 rename/替换即可 | 改名+落新+重启删除的组合拳 |

### 4. 权限模型：九个位 vs 一张表

**Unix 的 rwx** 是一个 3×3 位矩阵：属主/属组/其他 × 读/写/执行，`ls -l` 的 `-rwxr-xr--` 就是 9 个位。配套两件事常考：

- **umask**：新文件权限 = 申请权限 **与上 umask 的反码**。`open(..., 0666)` 遇 umask 022 得到 `0666 & ~022 = 0644`——umask 是"出厂默认要抠掉哪些位"
- **权限检查按序短路**：进程身份先匹配属主 → 只看属主那 3 位；不匹配再看属组、再看其他。所以"属主没权限但其他人有权限"时属主照样被拒

**Windows 的 DACL** 是另一套世界观：每个文件挂一张**访问控制项（ACE）列表**，每条 ACE 是"某账户 → 允许/拒绝 → 一组细粒度权限（读数据/写数据/遍历文件夹/改 ACL/……十几种）"，按序评估、显式拒绝优先。粒度任意（可以精确到"张三只许读这个文件"），但没有"执行位"——**能不能运行由 PE 头 + 扩展名 + 策略决定，不是权限位**。管理工具是 `icacls`，GUI 是安全选项卡。

两套模型互译时最值得注意的是**默认值哲学**：Unix 传统上"其他用户可读"（/etc 下大量 644），NTFS 默认继承父目录 ACL 且用户 profile 下别人不可见。把 `chmod 777` 当"解决权限问题的万能钥匙"的习惯搬到 Windows 会发现根本没有对应的开关——要么改 ACL，要么换令牌（下面就说令牌）。

### 5. SUID/SGID/粘滞位 vs UAC

rwx 之外还有三个特殊位，八股最爱问 **SUID**："为什么普通用户能改自己的密码？"——因为 `/usr/bin/passwd` 带 SUID 位（`-rwsr-xr-x`），**执行时有效身份切换为文件属主（root）**，于是有权限写 `/etc/shadow`。这是个**文件属性驱动的提权**：任何用户、任何时候、无交互。

- **SGID**（目录上）：目录下新文件自动继承目录属组（团队共享目录的标准配置）
- **粘滞位 t**（`/tmp` 的 `drwxrwxrwt`）：目录人人可写，但**删除别人文件被禁止**（只能删自己的）

Windows 没有 SUID 对应物——**能以什么身份运行不属于文件，属于用户和策略**。提权的机制是 UAC 令牌过滤：管理员账户登录时拿到的是**过滤令牌**（admin 组被禁用），要 `runas`/清单声明 `requireAdministrator` 时经 UAC 确认换**完整令牌**。对照：

| | Unix SUID | Windows UAC |
|---|---|---|
| 提权由谁决定 | 文件属性（属主身份） | 用户账户 + 交互确认/策略 |
| 触发方式 | 执行即生效，无感知 | 弹窗确认（或静默策略） |
| 粒度 | 整个进程生命周期切换有效 UID | 换一份完整令牌起进程 |
| 对应能力 | — | Scheduled Task 以最高权限运行是免弹窗的常用旁路 |

粘滞位的功能在 Windows 上由 ACL 表达（"Everyone 可创建，CREATOR OWNER 才可删"），没有专门开关。

## 扩展问题

可以进一步追问：

- 硬链接为什么不能跨文件系统？（inode 号只在单个文件系统内唯一）
- 目录的"链接数"为什么从 2 起步？（`.` 和父目录里的自身条目）
- `FILE_SHARE_DELETE` 已声明的句柄下，"删掉后还能继续读写"的 POSIX 语义在 Windows 上还原到什么程度？（改名/重开路径会失败，已映射内容可读）
- icacls 的继承与 Unix 默认 ACL（setfacl -d）在"新文件权限来源"上的异同？
