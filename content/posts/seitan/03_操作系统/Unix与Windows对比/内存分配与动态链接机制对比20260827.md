# 内存分配与动态链接机制对比

## 题目

围绕内存与链接的系列问题："malloc 小于 128K 用 brk、大于用 mmap"这个结论的适用范围？overcommit 和 OOM killer 是什么，Windows 有吗？32 位进程用户空间是 3G 还是 2G？dlopen 和 LoadLibrary 差在哪，缺符号时两边行为一样吗？

## 考察点

堆实现的两条路线（brk/mmap vs NT 堆）、内存超卖与记账制两种哲学、32 位地址空间划分的平台差异、ELF 惰性绑定与 PE 加载时解析的行为差别

## 回答要点

### 1. 堆的实现：brk/mmap vs NT 堆

常见结论："glibc 的 malloc，小块（默认 128K 阈值以下）从 brk 扩展的堆里拿，大块用 mmap 独立映射。"——**这是 glibc ptmalloc 的实现细节**，每个要素在 Windows 上都不存在或形态不同。

Unix 路线：

- `brk`/`sbrk` 是**伸缩堆顶**的系统调用：进程末尾的 [heap] 区一段连续内存，malloc 在上面切分回收
- ptmalloc 在此之上做了 arena（主 arena 走 brk，多线程竞争激烈时另起 mmap 的 arena）、bin 分级空闲链、top chunk 收缩；超过阈值（`M_MMAP_THRESHOLD`，默认 128K 且动态调整）的大请求直接 mmap，free 时整段 munmap 归还
- 推论：brk 堆中区释放后"内存不还系统"是正常的（只有堆顶连续空闲才 trim），这就是 Unix 上进程 RSS 只涨不降的常见解释之一

Windows 路线（**没有 brk 这个概念**）：

- 地基是 `VirtualAlloc`（按 64K 粒度保留/提交地址空间，见第 2 节）
- 堆是建在 VirtualAlloc 上的**可枚举对象**：`HeapCreate` 建堆（一个进程可以有多个堆）、`HeapAlloc`/`HeapFree` 分配释放，CRT 的 malloc 默认转发到进程堆
- 现役分配器是 **NT Heap + LFH（低碎片堆）**：按 size class 分级空闲链，一定阈值后自动启用——思想与 ptmalloc 的 bin 分级同源，但碎片治理策略不同（LFH 是按尺寸类聚拢，天然抗碎片）

| | glibc ptmalloc | Windows NT Heap |
|---|---|---|
| 堆的来源 | 主 arena 靠 brk 伸缩 | HeapCreate 在 VirtualAlloc 上建堆 |
| 大块策略 | 超 128K 阈值走 mmap，free 即 munmap | 同样走 VirtualAlloc 大页 |
| 多堆 | 多 arena（按线程竞争） | 显式 HeapCreate 多堆（隔离泄漏/碎片是正当理由） |
| 碎片治理 | bin 空闲链 + trim | LFH 尺寸类 |
| 释放后还系统 | 堆顶连续空闲才 trim | 堆销毁/段释放时归还 |

### 2. overcommit 与 OOM killer vs 记账制

一个让 Windows 工程师三观震动的结论："**malloc 返回非 NULL 不代表内存真的存在**，写到那页才分配物理页，不够了内核挑进程杀掉（OOM killer）。"

Linux 默认允许**超卖（overcommit）**：`/proc/sys/vm/overcommit_memory`：

- `0`（默认）：启发式允许"看起来合理"的超额申请
- `1`：来者不拒，地址空间随便许诺
- `2`：严格模式，commit 总量超限当场拒绝

于是申请成功 ≠ 用的时候有：物理页是真用到才分配的（ Demand Paging + fork COW 都依赖这一点），全局内存耗尽时 **OOM killer** 按 `oom_score`（占用大、运行久、非 root 等加权）挑牺牲者，用 SIGKILL 处决。所以 Linux 服务端才流行"malloc 之后 memset 一遍防欺骗"的玄学操作（以及 cgroup 限制内存防殃及）。

**Windows 是记账制（commit charge）**：`VirtualAlloc(MEM_COMMIT)` 的那一刻就计入"RAM + 页面文件"总账，**超了当场失败**（`ERROR_COMMITMENT_LIMIT`），根本活不到去写那页。推论：

- Windows 上"分配成功但用时被系统杀"基本不存在——要么现在给你记账，要么现在拒绝
- 对应的崩溃形态相反：程序申请被拒（malloc 返回 NULL / std::bad_alloc），老代码不检查返回值就死在空指针上
- OOM killer 在 Windows 上没有对应物；最接近的是"系统低内存时"的乔斯策略（扩大页面文件的提示、Job Object 内存限额的立即终结）

一句话：**Linux 把"内存不够"推迟到最难受的时刻由内核裁决，Windows 把它提前到申请时刻由程序面对**。

### 3. 32 位用户空间：3G 还是 2G

常见背稿："32 位进程 4G 空间，用户 3G、内核 1G。"——这是 **Linux x86 默认（3:1 划分，用户到 0xC0000000）**。Windows x86 默认是 **2G:2G**（用户 0x00000000~0x7FFFFFFF）：

- Windows 想突破 2G：boot 配置 `/3GB`（或 bcdedit）+ PE 头 `IMAGE_FILE_LARGE_ADDRESS_AWARE` → 用户 3G；在 64 位 Windows 上跑的 32 位进程（WOW64），带 LAA 标志即可用**整整 4G**
- Linux 想变 2:2 或 4:4 也是内核编译选项，但默认就是 3:1

实用判断：看到一个 0x8xxxxxxx 的用户态指针，Linux 上在用户空间内（3G 以下都算），Windows 上已落入内核一半——两家"用户空间上限"数值不同，做题和读崩溃转储时都要先问"这是哪家的 32 位"。64 位的划分两边则趋同（128T 级用户空间，细节见《64位系统虚拟地址空间布局》）。

### 4. 动态链接：惰性解析 vs 加载时解析

**ELF 世界（.so）**：

- 编译期 `-fPIC` 位置无关；加载期动态链接器 `ld.so` 按依赖树 mmap 各 .so，重定位
- **函数调用默认惰性绑定**：经 PLT 跳板第一次调用时才解析符号地址写进 GOT，之后直跳——省启动时间，代价是"缺符号可能到调用那一刻才爆"
- 运行时显式加载：`dlopen` / `dlsym` / `dlclose`
- 环境变量是一等公民：`LD_LIBRARY_PATH` 补搜索路径、**`LD_PRELOAD` 预加载劫持全局符号**（打桩/性能插桩的标准手法）

```c
void *h = dlopen("./libplugin.so", RTLD_NOW);   /* RTLD_NOW=立即解析，默认惰性 */
double (*fn)(double) = dlsym(h, "transform");
fn(1.5);
dlclose(h);
```

**PE 世界（DLL）**：

- 导入方向反过来：EXE 的**导入表（IDT/IAT）**列着要用的 DLL 和符号，**加载器在 LoadLibrary 那一刻把所有地址解析好填进 IAT**——没有 PLT/GOT 惰性绑定这一层（`/DELAYLOAD` 是显式 opt-in 的编译器机制，不是默认）
- 行为差异由此而来：**缺一个符号，Unix 可能直到调用时才崩，Windows 当场 LoadLibrary 失败**，错误定位时机完全不同
- `LoadLibrary` / `GetProcAddress` / `FreeLibrary` 对应 dlopen/dlsym/dlclose；**每进程引用计数**，成对 FreeLibrary 归零才卸载（DllMain 收到 DETACH）；忘了配对就是"DLL 卸不掉/句柄泄漏"
- **搜索顺序是安全重灾区**：exe 所在目录 → 系统 目录 → PATH（SafeDllSearchMode 之后的顺序），"放错目录被同名 DLL 劫持"是 Windows 特有攻击面；Unix 的 rpath/runpath 机制对应地管这个

```c
HMODULE h = LoadLibrary(TEXT("plugin.dll"));     /* 解析全部导入，缺符号即失败 */
auto fn = (double(*)(double))GetProcAddress(h, "transform");
fn(1.5);
FreeLibrary(h);
```

LD_PRELOAD 的钩子玩法在 Windows 上没有环境变量级开关，对应物是 DLL 注入、Detours 这类显式技术——同一个需求（拦截别人的库调用），一边是加载器内建机制，一边要动手术。

| | ELF (.so) | PE (DLL) |
|---|---|---|
| 符号解析时机 | 惰性（PLT/GOT 首调用） | 加载时全量填 IAT |
| 缺符号的表现 | 调用到才崩（或 ld.so 报 undefined symbol） | LoadLibrary 当场失败 |
| 运行时加载 | dlopen/dlsym/dlclose | LoadLibrary/GetProcAddress/FreeLibrary |
| 卸载 | dlclose 按引用计数 | FreeLibrary 按引用计数 + DllMain 通知 |
| 路径控制 | LD_LIBRARY_PATH / rpath | 固定搜索顺序，无等价环境变量 |
| 预加载钩子 | LD_PRELOAD | DLL 注入 / Detours |
| 符号导出声明 | 默认导出（-fvisibility 可收紧） | 必须 dllexport/dllimport 显式声明 |

**Qt 的双语字典**：`QLibrary` 内部一边 dlopen 一边 LoadLibrary，`resolve()` 统一 dlsym/GetProcAddress。写插件系统时还有 `Q_PLUGIN_METADATA` 这层元信息封装——同样是"双世界分叉、上表面统一"的样本。

### 5. 收束：三组对照一个模式

本篇三块内容其实是同一个模式的三次重现：

- 堆：同一需求（用户态内存分配），ptmalloc 长在 brk 上，NT Heap 长在 VirtualAlloc 上
- 内存承诺：Linux 超卖+事后裁决，Windows 记账+事前拒绝——**把失败点放在哪个性命周期阶段**是设计哲学差异
- 动态链接：同一需求（运行时符号解析），ELF 选惰性，PE 选加载时——失败时机因此不同

背跨平台结论时先问一句"这是机制还是实现"，基本能滤掉一半的"违背常识"。

## 扩展问题

可以进一步追问：

- glibc 的 mmap 阈值为什么设计成动态调整？（提示：free 一个大块 munlock/munmap 的代价与 trim 失效）
- Windows 页面文件禁用时 commit limit 等于多少？什么工作负载反而因此受益？
- RELRO（Full/Partial）是怎么把 GOT 从可写变只读堵住劫持的？与 Windows 的 IAT 只读化时机比呢？
- DllMain 里为什么不能调用 LoadLibrary？（加载器锁 loader lock 死锁）
- WOW64 下 32 位进程"4G 用户空间"是怎么做到的？（地址空间截断只发生在切到 32 位线程上下文时）
