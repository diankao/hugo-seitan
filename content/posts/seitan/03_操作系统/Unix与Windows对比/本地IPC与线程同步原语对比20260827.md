# 本地IPC与线程同步原语对比

## 题目

围绕进程间通信与线程同步的系列问题：Unix 域套接字是什么，Windows 上对应什么？pthread_mutex 和 Critical Section 是一个东西吗？持有互斥锁的线程崩了，等待者会怎样？

## 考察点

本机字节流 IPC 的平台选型（QLocalSocket 的两副面孔）、互斥锁从用户态快路径到内核对象的分层、被遗弃互斥体与 robust mutex 这对镜像概念、条件变量的 API 形态差异

## 回答要点

### 1. 本机字节流 IPC：Unix 城套接字 vs 命名管道

**Unix 域套接字（AF_UNIX）**是 Unix 上"本机两个进程间的 TCP"：API 与网络 socket 完全一致（bind/listen/accept/connect），但不走网络栈，数据在内核里从一端缓冲区拷到另一端；路径名只当"会合点"用，不算网络地址。它还有一个独门能力——**传递文件描述符本身**（`sendmsg` + SCM_RIGHTS 辅助数据）：把一个打开的文件/管道/socket 的 fd 直接塞给另一个进程，接收方拿到的是"活的句柄"而不是路径。这是 Unix 上权限传递的经典手法（如特权进程打开文件后把 fd 交给无特权进程）。

**Windows 的传统答案**是**命名管道（Named Pipe）**，而且形态更强：

- 全双工、可多实例、可设**消息模式**（PIPE_TYPE_MESSAGE，天然保留消息边界，Unix 管道是纯字节流）
- 命名空间 `\\.\pipe\名字`，服务端 `CreateNamedPipe` + `ConnectNamedPipe`，客户端 `CreateFile` 打开——**同一个服务端名字还能跨网络访问**（`\\服务器\pipe\名字`），这是 Unix 域套接字没有的能力
- SQL Server 等重量级服务至今默认走命名管道本地通信

两边的互有胜负决定了选型差异。而 **AF_UNIX 直到 Windows 10 1803（2018 年）才进入 Windows**，且不支持传句柄——所以"本机 socket"这个 Unix 上的默认答案，在 Windows 上的历史答案是命名管道或 localhost 回环 TCP。

**Qt 的双语字典**：`QLocalServer`/`QLocalSocket` 一个 API 两副面孔——Unix 上是 AF_UNIX，Windows 上是命名管道（QLocalServer 源码里就是这两个 `#ifdef` 分支）。日常用 Qt 的工程师天天在用这套映射而不自知，比如单实例程序检测就是 `QLocalServer::listen` 失败即已有实例。命名管道的 API 细节、NPFS 实现与真实出场场景，详见《Windows命名管道与Unix管道对比》。

### 2. 共享内存：思想一致，入口不同

原理两边完全一致（两进程页表指向同一物理页，详见《共享内存原理与IPC机制》），差异只在入口 API：

| | Unix | Windows |
|---|---|---|
| 创建/打开 | `shm_open` + `ftruncate` + `mmap` | `CreateFileMapping(INVALID_HANDLE_VALUE, ...)`（页文件支持）|
| 映射 | `mmap(NULL, len, RW, MAP_SHARED, fd, 0)` | `MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, ...)` |
| 名字空间 | `/dev/shm` 下的路径 | 内核对象名 `Local\`/`Global\` 前缀 |

注意 Windows 的会话隔离会咬人：服务（Session 0）里 `CreateFileMapping` 默认建在 `Local\`（会话局部），用户进程看不见——跨会话共享必须显式 `Global\` 前缀，这是 Windows 服务与桌面程序共享内存时的经典坑。Qt 的 `QSharedMemory` 封装了这两套入口（并额外处理了崩溃后的残留段清理）。

### 3. 互斥锁的三层世界：从 Critical Section 到内核 MUTEX

常见说法"Windows 的 Critical Section 等价于 pthread_mutex"——**大体对，但要分层看**。两边各自有一个"用户态快路径 + 内核慢路径"的轻量锁和一个纯内核重锁：

**第一层：轻量互斥（CS ≈ pthread_mutex）。** futex 的设计（无竞争时一次 CAS 拿锁放锁、零系统调用；有竞争才 `futex_wait` 进内核睡眠）常被当作 Linux 的精妙发明，而 **Windows 的 CRITICAL_SECTION 从 NT 3.5（1995）起就是这个思路**，比 futex（2002）早了近十年：

```c
CRITICAL_SECTION cs;
InitializeCriticalSection(&cs);        /* 或 InitializeCriticalSectionAndSpinCount(&cs, 4000) */

EnterCriticalSection(&cs);             /* 无竞争：纯用户态 interlock；竞争：进内核等事件 */
/* ... 临界区 ... */
LeaveCriticalSection(&cs);
DeleteCriticalSection(&cs);
```

pthread_mutex 与 CS 的共同点：同进程内使用、支持递归、无竞争成本几十纳秒级。CS 还能配自旋次数（先自旋再睡眠，对短临界区有效）。

**第二层：读写锁。** `pthread_rwlock` 对应 `SRWLOCK`（Vista+）：`AcquireSRWLockExclusive/Shared`，更轻（就是一个指针大小的状态字），但**不能递归、不能跨进程**。

**第三层：内核互斥体（Windows 特有的形态分层）。** `CreateMutex` 创建的是内核对象：

- **可以跨进程**：A、B 进程各自 `OpenMutex` 同名互斥体，实现"只允许一个实例运行"——pthread_mutex 办不到（跨进程要换 POSIX 信号量或文件锁）
- **可以被等**：能进 `WaitForMultipleObjects` 的句柄数组（等待任意内核对象的能力是 Windows dispatcher 体系的独家特性，见《教材Unix视角与各系统实现差异》第 4 节）

```c
HANDLE g_single = CreateMutex(NULL, TRUE, TEXT("MyApp.SingleInstance"));
if (GetLastError() == ERROR_ALREADY_EXISTS) {
    /* 已有实例，退出 */
}
```

### 4. 持锁者暴毙：WAIT_ABANDONED 与 robust mutex 的镜像

一个只有 Windows 工程师天天见、Unix 八股里几乎没有的概念：**内核互斥体有"属主"**。持有互斥体的线程**崩溃退出**而没有释放时，内核不会让互斥体变成孤儿死锁——下一个等待者被唤醒，`WaitForSingleObject` 返回 **`WAIT_ABANDONED`**：所有权转移给你了，但**受保护的数据可能处于不一致状态**，正确做法是校验数据结构甚至直接退出：

```c
DWORD r = WaitForSingleObject(hMutex, INFINITE);
if (r == WAIT_OBJECT_0) {
    /* 正常拿到 */
} else if (r == WAIT_ABANDONED) {
    /* 上一任持有者死亡：拿到了所有权，但数据可信度存疑 */
}
```

CRITICAL_SECTION/pthread_mutex 没有这层语义（属主崩了就死锁或未定义）。Unix 世界的对应物是 **robust mutex**（`pthread_mutexattr_setrobust`）：持锁者死亡后，其他进程锁它时返回 `EOWNERDEAD`，需要 `pthread_mutex_consistent` 修复——概念与 WAIT_ABANDONED 一一镜像，但存在感低得多，很多 Unix 工程师不知道它存在。

### 5. 条件变量：API 形态差异与共同坑

条件变量两边语义一致（等待某条件成立、配合互斥锁使用），API 形态不同：

```c
/* Unix */
pthread_mutex_lock(&m);
while (!ready)                              /* 必须用 while：虚假唤醒 */
    pthread_cond_wait(&cv, &m);             /* 原子地：解锁 m -> 睡 -> 醒来重锁 m */
pthread_mutex_unlock(&m);
pthread_cond_signal(&cv);

/* Windows（Vista 起才有原生 CONDITION_VARIABLE） */
EnterCriticalSection(&cs);
while (!ready)
    SleepConditionVariableCS(&cv, &cs, INFINITE);   /* 同样的原子三步 */
LeaveCriticalSection(&cs);
WakeConditionVariable(&cv);
```

三点值得记住：

1. Windows 的条件变量**来得晚**（Vista，2006），此前要拿 Event + 互斥锁手工模拟（复杂且易错），所以老代码里有一堆自造轮子；SRWLOCK 配套的版本是 `SleepConditionVariableSRW`
2. **虚假唤醒两边都有**，`while` 重查条件是跨平台铁律，不是某一家的坑
3. Windows 条件变量与 CS/SRWLOCK 绑定，不能拿去等内核对象——要等多内核对象还是 `WaitForMultipleObjects` 那套

### 6. 对照总表

| 能力 | Unix | Windows |
|---|---|---|
| 本机字节流 IPC | AF_UNIX 域套接字（可传 fd） | 命名管道（消息模式、可跨网）；AF_UNIX 2018 才加入且弱化 |
| 单实例互斥 | 文件锁 flock / pid 文件 | 命名内核 MUTEX 的 ERROR_ALREADY_EXISTS |
| 跨进程共享内存 | shm_open + mmap | CreateFileMapping + MapViewOfFile（注意 Global\ 前缀） |
| 轻量互斥 | pthread_mutex（futex 底座） | CRITICAL_SECTION（比 futex 更早的同一思路） |
| 读写锁 | pthread_rwlock | SRWLOCK（不递归、不跨进程） |
| 持锁者死亡 | robust mutex，EOWNERDEAD | 内核 MUTEX，WAIT_ABANDONED |
| 条件变量 | pthread_cond_wait | SleepConditionVariableCS/SRW（Vista+） |
| 等待多对象 | poll/epoll 等 fd | WaitForMultipleObjects 等任意句柄（64 上限） |

## 扩展问题

可以进一步追问：

- SCM_RIGHTS 传 fd 时，内核做了什么？（dup 到接收进程 fd 表，引用计数转移）
- futex 的"用户态值 + 内核等待队列哈希"怎么做到不用每次系统调用也能正确睡眠/唤醒？
- 命名管道的 `PIPE_READMODE_MESSAGE` 与字节流模式互操作时，`ReadFile` 的返回行为有什么区别？
- 为什么 SRWLOCK 做不到递归？（提示：递归需要记录属主，状态字就装不下了）
