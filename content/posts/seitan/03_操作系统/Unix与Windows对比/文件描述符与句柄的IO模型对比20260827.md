# 文件描述符与句柄的IO模型对比

## 题目

围绕 IO 抽象与多路复用的系列问题：为什么 read() 能直接读 socket？"select 上限 1024"是通用结论吗？epoll 的 Windows 对应物是什么，两者只是名字不同吗？零拷贝的 sendfile 在 Windows 上有吗？

## 考察点

"一切皆文件"与分类型句柄两种抽象、fd_set 实现差异导致的平台结论分歧、reactor 与 proactor 两种 IO 范式的本质区别、Qt 事件循环在 Windows 上的真实底座

## 回答要点

### 1. 抽象之争：一切皆文件 vs 分类型句柄

Unix 的招牌是 **VFS 统一接口**：每个"文件"挂一组 `file_operations`，于是同一个 `read()`/`write()` 通吃普通文件、管道、socket、tty、设备节点。**fd 是进程 fd 表的下标**，小整数、可复制、可传递；0/1/2 是 stdio 的约定占位。更进一步，/proc、/sys 把进程信息和内核参数也做成"文件"，`cat` 一下就能读。

Windows 的世界是**分类型句柄（HANDLE）**：

- 文件、管道、设备可以用 `ReadFile`/`WriteFile`，但 **socket 属于 WinSock 独立体系**，必须 `send`/`recv`——把 SOCKET 塞给 ReadFile 是未定义行为
- 句柄不是小整数索引（虽然内核里也有表，但值不透明、不是 0/1/2 这种约定），标准流要用 `GetStdHandle(STD_OUTPUT_HANDLE)` 获取
- "空设备"是保留设备名 `NUL`（`> NUL`），不是文件系统里的一个文件；对应 `/dev/null`
- 进程信息、系统参数住在注册表、WMI、性能计数器里，**不以文件形态暴露**——Unix 工程师"一切配置皆可 cat"的体验在 Windows 上没有

```c
/* Unix：同一个 read 通吃 */
n = read(sock_or_pipe_or_file, buf, len);

/* Windows：按对象类型选 API */
n = ReadFile(file_or_pipe, buf, len, &n, NULL);   /* 文件/管道 */
n = recv(sock, buf, len, 0);                       /* socket 另一套 */
```

这决定了上层库的形态：glibc 的 stdio 可以直接建立在 fd 上；Windows CRT 的 `_fileno`/`_write` 是在句柄世界上的又一层模拟，一个 SOCKET 没法"当文件"交给 stdio 缓冲。

### 2. "select 上限 1024"的真相：一个被当成通用结论的实现细节

常见结论："select 最多监听 1024 个 fd，所以高并发要用 epoll。"——**前半句只是 Linux 的实现事实**：

- Linux：`fd_set` 是 **1024 位的位图**（`FD_SETSIZE` 默认 1024，编译期定死），内核 `select` 系统调用同样按这个规模拷贝和扫描位图
- Windows：WinSock 的 `fd_set` 是**句柄数组**，不是位图——`fd_count` 计数 + `fd_array[]`，默认数组大小 64 但可自定义更大，**不存在 1024 这个内核硬上限**，实际限制来自可用句柄数

所以同一段"select 只能管 1024 个连接"的背稿，在 Windows 上根本测不出来。真正跨平台成立的部分是 select 的**另外两个缺陷**：每次调用要线性扫描全部监听集（O(n)），且调用间要重建/拷贝 fd_set。这两个才是 poll→epoll 演进的动机（epoll 内部机制详见《epoll工作原理与selectpoll区别》）。

### 3. epoll 的 Windows 对应物：IOCP——不是同一种东西

Windows 没有 epoll，也不需要：它的答案是 **IOCP（I/O Completion Port）**。两者的差异不是 API 名字，而是**范式**：

- **epoll 是就绪通知（reactor）**：`epoll_wait` 告诉你"这些 fd 现在可以读了"，**读动作由你自己做**——数据还在内核缓冲区，`read` 拷贝到你的 buf，可能阻塞、可能返回 EAGAIN
- **IOCP 是完成通知（proactor）**：你**先**把缓冲区投递给内核（`WSARecv` 带 OVERLAPPED，"帮我读，读完通知我"），内核 DMA+拷贝全做完，把**结果**（字节数、错误码）作为完成包排队，工作线程 `GetQueuedCompletionStatus` 取走的已经是完成的事件

```c
/* IOCP 骨架：先投递，后收结果 */

/* 1. 把 socket 关联到完成端口（并发度给 0 = CPU 核数） */
HANDLE iocp = CreateIoCompletionPort(INVALID_HANDLE_VALUE, NULL, 0, 0);
CreateIoCompletionPort((HANDLE)sock, iocp, clientKey, 0);

/* 2. 投递一个异步读：注意 buf 是现在就交出去的 */
PER_IO_DATA *io = alloc_io();
io->wsabuf.buf = io->buffer;
io->wsabuf.len = sizeof(io->buffer);
DWORD flags = 0;
WSARecv(sock, &io->wsabuf, 1, NULL, &flags, &io->overlapped, NULL);

/* 3. 工作线程：取回的是"已完成"的事件，含字节数与错误码 */
DWORD bytes; ULONG_PTR key; OVERLAPPED *ovl;
BOOL ok = GetQueuedCompletionStatus(iocp, &bytes, &key, &ovl, INFINITE);
/* ok==FALSE 时 WSAGetLastError() 就是这次 IO 的失败原因 */
/* 处理完立刻再投递下一个 WSARecv，形成流水线 */
```

对照表：

| 维度 | epoll（reactor） | IOCP（proactor） |
|---|---|---|
| 通知时机 | **就绪**（可以开始读了） | **完成**（已经读完了） |
| 拷贝谁做 | 用户线程自己 `read` | 内核在投递的缓冲区上做好 |
| 缓冲区归属 | 事件处理时才给 | 投递时就交出（生命周期要小心） |
| 线程模型 | 自己管线程池，epoll_wait 惊群/水平触发自己兜 | 完成端口内建并发度控制（可等待线程数上限） |
| 编程心智 | "事件来了我去干活" | "委托出去等结果回调" |

Unix 后来补的 POSIX AIO 与 io_uring（真正的异步完成模型）才和 IOCP 同范式；io_uring 的"提交队列+完成队列"设计与完成端口的哲学已经非常接近——**Windows 在 1993 年（NT 3.5 的完成端口雏形）就走了这条路**。

### 4. Qt 的底座：QSocketNotifier 在 Windows 上是 select

`QSocketNotifier` 是 Qt 暴露 fd/socket 事件的原语，文档注明其在 Windows 上的实现是 **select 模拟**（且对普通文件不可用——Unix 上"普通文件永远就绪"的语义在 Windows 上没有对应物）。事件循环分发器 `QEventDispatcherWin32` 的等待核心是 `MsgWaitForMultipleObjectsEx`（消息 + 内核句柄一起等）加 select 轮询 socket。这意味着：

- 用 Qt 写的跨平台网络程序，在 Windows 上天然是 select 规模（千级连接没问题，十万级会碰壁）
- 需要 IOCP 级别吞吐时，通常上原生 IOCP 或基于 IOCP 的框架（asio 等），Qt 层只做界面与调度

另一个 Windows 特有件顺带一提：`WSAAsyncSelect` 把 socket 事件翻译成 **Windows 消息**投给窗口过程——"网络事件进消息循环"这个设计在 Unix 世界没有对应物，是两套抽象（fd 世界 vs 消息世界）的强行搭桥。

### 5. 零拷贝：sendfile vs TransmitFile

常见结论："sendfile 让数据不经过用户态实现零拷贝。"原理通用，但 **sendfile(2) 是 Linux 系统调用**；Windows 的对应物是 WinSock 扩展 **`TransmitFile`**（mswsock）：`Trans transmitFile(sock, hFile, ..., &overlapped)` 把文件内容直接发往 socket，同样支持内核态直传（scatter/gather DMA）。时间上 TransmitFile 出现在 WinSock 2 时代，比 Linux 的 sendfile 进主线**更早**。细节上各有扩展：Linux 后来有 splice 泛化"任意两个 fd 之间搬数据"，Windows 有 `TransmitPackets`。背"零拷贝=sendfile"时记住这是个**系统调用名**，不是机制名。

### 6. 总表

| 能力 | Unix/Linux | Windows |
|---|---|---|
| 统一读写接口 | `read`/`write` 通吃 fd | `ReadFile` 管文件管道，socket 用 `send/recv` |
| 标准流 | fd 0/1/2 约定 | `GetStdHandle` |
| 内核信息暴露 | /proc、/sys（皆文件） | 注册表、WMI、性能计数器 |
| 多路复用 | select(1024 位图)/poll/epoll | select(句柄数组无 1024 限)/WSAPoll |
| 异步范式 | reactor（epoll）；io_uring 补 proactor | proactor（IOCP）原生 |
| socket 进消息循环 | 无对应 | `WSAAsyncSelect`/`WSAEventSelect` |
| 零拷贝发送 | sendfile/splice | TransmitFile/TransmitPackets |

## 扩展问题

可以进一步追问：

- epoll 的 LT/ET 之分在 proactor 世界里对应什么？（提示：完成通知天然"边缘"，投递即消耗）
- IOCP 上为什么"每个连接持续保有多个未决读"能显著提高吞吐？投递数量和内存怎么权衡？
- `MsgWaitForMultipleObjectsEx` 让 Qt 事件循环能同时等消息和句柄，它是怎么绕开"64 个句柄"限制的？
- 普通文件在 Unix 上"永远就绪"、在 Windows 上没有 socket 式的未决状态——这如何影响 async fs IO 的设计（libuv 的线程池方案）？
