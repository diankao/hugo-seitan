# 守护进程与Windows服务模型对比

## 题目

围绕后台长驻进程的系列问题：守护进程为什么要 fork 两次？setsid 到底在做什么？Windows 服务是怎么被启动和管理的，和普通 EXE 有什么区别？

## 考察点

会话/进程组/控制终端三层概念、daemon 化每一步的动机、SCM 服务架构与状态机、"脱离终端"这件事两边各自的解法

## 回答要点

### 1. 前置概念：会话、进程组、控制终端

理解 daemon 的每一步之前要先有这三个概念（Unix 特有，Windows 没有对应层）：

- **进程组**：一组相关进程的集合（如一条管道 `ls | grep | wc` 三个进程同组），有组长（组长 PID == 组 ID）
- **会话**：若干进程组的容器，由 `setsid()` 创建，登录 shell 是会话首进程
- **控制终端**：会话绑定的那个 tty/pty。**只有会话首进程才可能占有控制终端**；Ctrl+C 发给前台进程组、终端断开时 SIGHUP 发给会话首进程（shell 再转发给作业）

这三层存在的意义是支持**作业控制**（jobs/fg/bg/nohup 那套交互），而 `nohup` 做的事就是让进程忽略 SIGHUP——这只是"屏蔽症状"。daemon 化要的是根治：彻底离开会话，让 SIGHUP 根本找不到你。

### 2. daemon 化五步与每步的动机

```c
int daemonize(void)
{
    pid_t pid = fork();
    if (pid < 0) return -1;
    if (pid > 0) _exit(0);          /* ① 父进程退出：子进程成孤儿，过继给 init，
                                       脱离登录 shell 的作业管理 */

    if (setsid() < 0) return -1;    /* ② 创建新会话：子进程成为新会话首进程，
                                       且新会话没有控制终端 */

    pid = fork();                   /* ③ 第二次 fork：孙子进程不再是会话首进程，
                                       从此永远无法获得控制终端 */
    if (pid < 0) return -1;
    if (pid > 0) _exit(0);

    chdir("/");                     /* ④ 不占用任何挂载点，防止卸载文件系统失败 */
    umask(0);                       /* ⑤ 权限完全由自己的 open/chmod 参数决定 */

    int nullfd = open("/dev/null", O_RDWR);
    dup2(nullfd, STDIN_FILENO);     /* ⑥ 0/1/2 指向 /dev/null：
    dup2(nullfd, STDOUT_FILENO);       以后 open 到的 fd 不会误当标准流用，
    dup2(nullfd, STDERR_FILENO);       也不会因写终端失败收到信号 */
    if (nullfd > 2) close(nullfd);
    return 0;
}
```

**为什么必须 fork 两次**是最常被追问的点：`setsid` 之后进程成了会话首进程，此刻没有控制终端；但规则是"**没有控制终端的会话首进程 open 一个终端设备时会自动占有它**"（不加 `O_NOCTTY` 的话）。第二次 fork 产生的孙子进程不是会话首进程，就堵死了将来无意中重新挂上终端的可能。现代 Linux 也可以只 fork 一次 + `setsid` 后保证不 open tty，但双 fork 是保证不出错的写法。

### 3. Windows 的答案：服务（Service）与 SCM

Windows 从 NT 起就把"长驻后台程序"做成了**系统级托管体系**，而不是让进程自己"逃离"谁：

- **SCM（服务控制管理器，services.exe）**：持有服务数据库，负责按启动类型（自动/手动/禁用/按需触发）拉起服务、监督状态、执行失败恢复策略（崩溃自动重启就在这配置）
- **服务进程的本质**：一个实现了 ServiceMain 协议的普通 PE。SCM 充当"托管父进程"的角色，服务崩溃不需要自己 fork 子进程来守护——恢复策略就是 SCM 的功能
- **服务账户**：LocalSystem / NetworkService / LocalService 或指定账户，与用户登录会话隔离（Session 0 隔离，服务看不见用户桌面，UI 需走第二进程）
- **共享宿主**：很多服务不是独立 EXE，而是 dll 寄宿在 `svchost.exe` 里按组共享进程

最小服务骨架：

```c
SERVICE_STATUS        g_status;
SERVICE_STATUS_HANDLE g_hStatus;

DWORD WINAPI ServiceCtrlHandler(DWORD ctrl, DWORD evt, void *data, void *ctx)
{
    switch (ctrl) {
    case SERVICE_CONTROL_STOP:
        g_status.dwCurrentState = SERVICE_STOP_PENDING;
        SetServiceStatus(g_hStatus, &g_status);
        /* 通知工作线程收尾，完成后置 SERVICE_STOPPED */
        return NO_ERROR;
    }
    return NO_ERROR;
}

VOID WINAPI ServiceMain(DWORD argc, LPTSTR *argv)
{
    g_hStatus = RegisterServiceCtrlHandlerEx(TEXT("MySvc"), ServiceCtrlHandler, NULL);

    g_status.dwServiceType      = SERVICE_WIN32_OWN_PROCESS;
    g_status.dwCurrentState     = SERVICE_START_PENDING;
    SetServiceStatus(g_hStatus, &g_status);        /* 状态机必须逐步上报 */

    /* ... 初始化资源 ... */

    g_status.dwCurrentState     = SERVICE_RUNNING;
    g_status.dwControlsAccepted = SERVICE_ACCEPT_STOP;
    SetServiceStatus(g_hStatus, &g_status);

    /* ... 工作循环 ... */
}

int main(void)
{
    SERVICE_TABLE_ENTRY table[] = {
        { (LPTSTR)TEXT("MySvc"), ServiceMain }, { NULL, NULL }
    };
    /* 阻塞式派发器：主线程在这里等 SCM 的控制请求 */
    StartServiceCtrlDispatcher(table);
    return 0;
}
```

几个与直觉不同的点：

1. `main` 里调 `StartServiceCtrlDispatcher` 后主线程被阻塞，控制请求由 SCM 在进程内**开新线程**调你的 handler——这点和"终端事件也是内核开新线程执行"同源（见《信号机制与Windows异常处理对比》）
2. 服务必须主动 `SetServiceStatus` 上报状态机（START_PENDING → RUNNING → STOPPED），SCM 看"心跳"判死：超时未上报会记日志
3. 安装/启动是管理员命令：`sc create MySvc binPath= "C:\path\my.exe"`、`sc start MySvc`，对应 Unix 的把脚本放进 systemd unit——但 systemd 是 2015 年才普及的"服务管理器"，Windows SCM 1993 年就有

### 4. 对照：两种"永生"策略

| 维度 | Unix daemon | Windows 服务 |
|---|---|---|
| 脱离终端 | 自己双 fork + setsid | 天生没有控制台（Session 0） |
| 谁负责拉起 | 传统：init 收养即完事；现代：systemd 托管 | SCM 统一托管，启动类型内置 |
| 崩溃自愈 | 传统无（自己再 fork 个看门狗）；systemd Restart= | SCM 失败恢复策略，原生功能 |
| 身份 | 自己 `setuid` 降权 | 服务账户体系（LocalSystem 等） |
| 标准流 | 重定向 /dev/null | 无控制台，日志走事件日志/命名管道 |
| 用户交互 | 无（约定俗成） | 无（Session 0 隔离是机制强制） |
| 协议要求 | 无，普通程序即可 daemon 化 | 必须实现 ServiceMain 协议，否则 SCM 拉不起来 |

值得注意的演化方向：两边在**互相靠拢**——systemd 给 Linux 补上了 SCM 级别的服务管理（unit 文件、自动重启、cgroup 托管），Windows Server 2016+ 也把后台任务往"无 UI、按需启动"推。但 API 形态完全是两套，Qt 也没有官方的服务封装类（第三方 QtService 早已停更），跨平台服务通常拆成"跨平台核心逻辑 + 平台壳"两层。

### 5. 反向概念：Job Object

Windows 有一个 Unix 没有的镜像概念——**作业对象（Job Object）**：把一组进程装进一个内核作业里，统一限额（内存/CPU/进程数）、统一记账、统一结束（`TerminateJobObject` 一键收割整棵进程树）。Unix 上做同样的事要用进程组 + cgroup 拼出来。"管理一堆进程"这个需求，两边把切口放在了不同的抽象层级上。
