# Linux三种执行上下文

## 题目

什么是进程上下文、内核线程上下文、中断上下文？三者有什么区别？

## 考察点

Linux内核执行模型、上下文切换、中断处理限制、内核编程约束。

## 回答要点

### 1. 三种上下文总览

Linux 内核代码在不同场景下以不同的"身份"执行，这就是**上下文**。

| 上下文 | 触发方式 | 能否睡眠 | 能否访问用户空间 | 使用栈 |
|--------|---------|---------|----------------|--------|
| 进程上下文 | 系统调用、异常 | 可以 | 可以（copy_to/from_user） | 进程内核栈（8KB） |
| 内核线程上下文 | kthread_create | 可以 | 不可以（无用户空间映射） | 内核栈（8KB） |
| 中断上下文 | 硬件中断、软中断 | **绝对不能** | 不可以 | 中断栈（独立） |

### 2. 进程上下文（Process Context）

**触发方式**：用户程序通过系统调用（syscall）或触发异常（如缺页）主动/被动进入内核态。

```
用户程序调用 open()
       │
       ▼ syscall 指令
保存用户态寄存器到内核栈
       │
       ▼
进入内核态执行 sys_open()
       │
       ▼
返回用户态（sysret/iret）
```

**特点**：

- **有对应的用户进程**：`current` 宏可以获取当前进程的 task_struct
- **可以睡眠**：因为知道"我是谁"，调度器可以切换到其他进程
- **可以访问用户空间**：通过 `copy_to_user()` / `copy_from_user()`
- **可以被抢占**（CONFIG_PREEMPT）

```c
// 进程上下文的典型代码
static ssize_t my_read(struct file *filp, char __user *buf,
                       size_t count, loff_t *f_pos) {
    // current 指向发起系统调用的用户进程
    struct task_struct *task = current;
    pr_info("进程 %s (pid=%d) 正在读取\n", task->comm, task->pid);

    // 可以睡眠（copy_to_user 可能因缺页而睡眠）
    if (copy_to_user(buf, kernel_buf, count))
        return -EFAULT;

    // 可以使用 mutex
    mutex_lock(&dev_mutex);
    // ...
    mutex_unlock(&dev_mutex);

    return count;
}
```

### 3. 内核线程上下文（Kernel Thread Context）

**触发方式**：由内核通过 `kthread_create()` 创建的线程，始终运行在内核态。

```c
// 创建内核线程
struct task_struct *kthread = kthread_create(my_thread_func, NULL, "my_thread");
wake_up_process(kthread);

int my_thread_func(void *data) {
    while (!kthread_should_stop()) {
        // 执行后台任务
        do_work();

        // 可以睡眠
        msleep(100);

        // 可以使用 mutex
        mutex_lock(&lock);
        // ...
        mutex_unlock(&lock);
    }
    return 0;
}
```

**特点**：

- **有 task_struct**：和用户进程一样有进程描述符
- **可以睡眠**：调度器可以切换到其他线程
- **不能访问用户空间**：没有用户地址空间映射（mm 为 NULL 或空）
- **始终在内核态运行**：从不通过 syscall 进入

**常见内核线程**：

| 内核线程 | 功能 |
|---------|------|
| `kworker` | 工作队列处理 |
| `ksoftirqd` | 软中断处理 |
| `kjournald` | ext3/4 日志提交 |
| `pdflush` | 脏页回写 |
| `kswapd` | 内存回收 |

### 4. 中断上下文（Interrupt Context）

**触发方式**：硬件中断触发后，CPU 自动跳转到 ISR（中断服务程序）执行。

```
硬件产生中断信号
       │
       ▼ CPU 自动保存部分寄存器
进入 ISR（中断服务程序）
       │
       ▼ 不经过调度器！
处理中断
       │
       ▼
返回被中断的代码
```

**特点**：

- **没有 task_struct**：`current` 指向被中断的进程，但不是中断自己的
- **绝对不能睡眠**：因为调度器无法管理中断上下文
- **不能访问用户空间**：不确定被中断的是用户态还是内核态
- **执行时间必须极短**：关中断期间，其他中断被延迟

```c
// 中断上下文的典型代码
static irqreturn_t my_isr(int irq, void *dev_id) {
    // 快速读取硬件状态
    u32 status = readl(regs + STATUS_REG);

    // 清除中断标志
    writel(status, regs + CLEAR_REG);

    // 不能睡眠！以下操作全部禁止：
    // mutex_lock()    ← 可能睡眠
    // kmalloc(GFP_KERNEL) ← 可能睡眠
    // msleep()        ← 必然睡眠
    // copy_to_user()  ← 可能睡眠
    // schedule()      ← 必然睡眠

    // 可以使用自旋锁
    spin_lock(&dev->lock);
    dev->pending_data = status;
    spin_unlock(&dev->lock);

    // 耗时操作推迟到下半部
    tasklet_schedule(&dev->tasklet);

    return IRQ_HANDLED;
}
```

### 5. 三者对比

| 对比项 | 进程上下文 | 内核线程上下文 | 中断上下文 |
|--------|-----------|--------------|-----------|
| 触发 | 系统调用 | kthread_create | 硬件中断 |
| 有 task_struct | 有（自己的） | 有（自己的） | 无 |
| current 有效 | 是 | 是 | 指向被中断进程 |
| 能睡眠 | 能 | 能 | **不能** |
| 能访问用户空间 | 能 | 不能 | 不能 |
| 可用 mutex | 可以 | 可以 | **不能** |
| 可用 spinlock | 可以 | 可以 | 可以 |
| 调度器管理 | 是 | 是 | 否 |
| 抢占 | 可以 | 可以 | 不可（除非开启中断抢占） |

### 6. 如何判断当前上下文

```c
// 判断是否在中断上下文
if (in_interrupt()) {
    // 在中断上下文（包括硬中断和软中断）
}

if (in_irq()) {
    // 在硬中断上下文
}

if (in_softirq()) {
    // 在软中断上下文（包括 tasklet）
}

// 判断是否在进程上下文
if (!in_interrupt() && current->mm) {
    // 在进程上下文（有用户地址空间）
}

// 内核线程：!in_interrupt() && !current->mm
```

### 7. 面试速记

- **进程上下文**：系统调用触发，有进程身份，能睡眠能访问用户空间
- **内核线程上下文**：内核创建的后台线程，能睡眠，不能访问用户空间
- **中断上下文**：硬件触发，无进程身份，**绝对不能睡眠**
- **选择锁**：中断上下文用 spinlock，进程/内核线程上下文用 mutex
- **判断方法**：`in_interrupt()` 区分中断上下文和进程上下文
