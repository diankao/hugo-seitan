# 进程线程与IPC的实际使用场景

背了七件套（管道、命名管道、消息队列、共享内存、信号量、信号、Socket）却觉得开发中从没用过——这是一个普遍的错觉。真相有两个反转：**一是你天天在用，只是这些机制被库、框架和内核包在下面；二是线程和进程根本不竞争同一个岗位**——线程是并发单元，进程是隔离单元。本文用真实软件的例子把这两件事讲透。

## 一、你不是没用过IPC，只是看不见

| 日常动作 | 底下跑的其实是 |
|------|------|
| 终端里 `grep xxx \| wc -l`、`make \| tee log` | **管道**（shell 的竖线就是它） |
| Ctrl+C 停程序、`kill -9`、程序 segfault 崩掉 | **信号**（SIGINT / SIGKILL / SIGSEGV） |
| `nginx -s reload` 热加载配置 | **信号**（master 进程收 SIGHUP） |
| `docker ps`、`systemctl status` | **Unix domain socket**（CLI 和 daemon 在 `/var/run/docker.sock` 上对话） |
| Linux 桌面复制粘贴、拖窗口 | **socket**（X11 / Wayland compositor，剪贴板数据也要过它） |
| 播放音乐不卡顿 | **共享内存**环形缓冲 + 事件同步（PulseAudio / PipeWire / JACK 全是这套） |
| Chrome 一个标签页崩了别的还活着 | 管道 + 共享内存（多进程架构的 Mojo IPC） |
| 手机 App 拿定位、弹通知 | **Binder**（Android 专用的内核级 IPC） |
| `adb logcat` 看设备日志 | socket + 内核环形缓冲 |

IPC 的主场不是应用层业务代码，而是**系统胶水层——进程边界上的所有协作**。写边界以内的代码，自然感觉不到它。

嵌入式侧的对应关系：FreeRTOS 的队列、二值信号量、事件组，就是消息队列、信号量、信号的"任务版"——概念一一对应，只是没有进程概念时共享的是整个地址空间。

## 二、七件套的形象例子

| 机制 | 比喻 | 真实软件 | 为什么非它不可 |
|------|------|------|------|
| 管道 | 亲兄弟间的传声筒 | shell 的 `\|`、`popen`、`QProcess` 读子进程 stdout | 单向字节流，fork 之后接着用，最便宜的进程间流 |
| 命名管道 | 挂了门牌的传声筒 | 常驻采集进程往 FIFO 写，任何时刻 `cat` 搭线看流；Windows 命名管道撑着 SQL Server 本地连接 | 无亲缘关系的进程也能按名字找到 |
| 消息队列 | 快递柜 | QNX 车载任务间命令传递（仪表/中控/网关） | 有边界、可带优先级、深度可控——队列满即背压，实时系统的刚需 |
| 共享内存 | 合租客厅的白板 | PulseAudio/JACK 音频环形缓冲、`v4l2` 摄像头 `mmap` 收帧、PostgreSQL 共享 buffer pool | 唯一"大数据量不心疼"的方式——零拷贝 |
| 信号量 | 白板门口的钥匙计数器 | 与共享内存成对出现：环形缓冲的读写指针、剩余格子计数 | 共享内存没有锁，必须配同步 |
| 信号 | 有人拍了下肩膀 | Ctrl+C、崩溃、`nginx -s reload`、gdb 断点（SIGTRAP 截胡） | 最古老的异步事件通知，不带数据 |
| Socket | 既能对讲也能打长途 | `docker.sock`、X11、MQTT broker 连接 | **前六个出了这台机器就失效，socket 能跨机器、跨语言** |

两个工程现实：进程间互斥现在更多用 `PTHREAD_PROCESS_SHARED` 的 mutex（挂在共享内存里），信号量更多做资源计数；消息队列思想搬到网络上的放大版就是 RabbitMQ/ZeroMQ。

## 三、线程是并发单元，进程是隔离单元

所有线程住在同一个地址空间里，这是它便宜的原因（共享一切，通信免费），也是它的账单：

**连坐账**：任何一个线程的野指针写飞，砸到的是整个进程的堆、栈、全局变量——不管受害者是谁，惩罚都是全进程 segfault。更阴的是症状漂移：分析线程越界写，砸坏采集线程的环形缓冲，崩在无辜者家里。MMU 的页表按进程设界，硬件不区分"哪个线程干的"。

**权限账**：线程共享进程的一切凭证。想"采集服务有 USB 权限、界面没有、解码器禁网沙箱"，线程做不到，进程一句话的事。

所以现实里"故意拆进程"的软件全是隔离动机：

| 软件 | 拆分理由 |
|------|------|
| Chrome | 标签页崩溃不连坐；渲染不可信网页的进程可加沙箱（禁文件系统/网络） |
| VS Code | 扩展跑在独立 extension-host 进程，扩展死循环编辑器不冻结 |
| Android | 每个 App 一个进程，一个 App 崩不带走手机 |
| nginx / gunicorn | worker 崩了 master 秒级拉起——监督重启以进程为单位 |
| PostgreSQL | 每连接一进程，一个连接的 bug/泄漏只污染自己 |

## 四、什么时候被迫拆进程：四个信号

1. **第三方/异构运行时进栈**：分析侧开始用 Python/PyTorch/OpenCV 这类带 GC、自带信号处理和分配器的运行时——它们和 C 采集循环挤一个进程，毛刺和崩溃风险全传染
2. **局部崩溃不可接受**：刺激控制这类安全相关功能，UI 崩了它必须活着
3. **独立重启/升级**：GUI 改版不用停采集
4. **跨机器分布**：采集、分析、记录分给不同机器——这就出 socket 了

脑机接口软件栈是天然教材：采集（硬实时）、分析（重计算）、记录（大 IO）拆三进程的理由正好是上面四条的合集。开源的 LabStreamingLayer（LSL）就是把这套架构做成了标准件：采集端、分析端、记录端各跑各的进程。机器人方向的 ROS 更是整门课建立在 IPC 上：节点 = 进程，topic = 发布订阅消息流，ROS2 底层 DDS 还配了共享内存传输。

## 五、平台与产品：为什么工具软件拆得最狠

单 exe 产品（所有代码自己写、整包发布）用线程就是正确架构，拆进程反而是过度设计。但插件宿主类软件（AI 编程工具、浏览器、IDE）是**平台**——要加载一堆别人写的、不同语言、不同版本、可单独装卸的组件，几乎踩中全部拆分信号：

| 组件 | 拆分理由 |
|------|------|
| 每个外部工具服务器（MCP） | 第三方代码 + 异构运行时（Python/Node 各家发布），崩了主会话不陪葬 |
| 自动化浏览器 | 不可信内容 + 崩溃隔离，Chromium 内部又是一层多进程 |
| 子代理 | 独立上下文 + 并行，进程边界就是上下文边界 |
| 各语言运行时内核 | 语言异构，主程序不是该语言就得给独立进程 |

而且这类工具会话本身就是 IPC 的活现场：主程序与工具服务器之间走 stdio 上的 JSON-RPC（管道），浏览器自动化走 DevTools 协议（socket），子代理结论回传是消息传递——每一次交互都穿过好几道进程边界。

## 六、嵌入式反转：线程世界重建进程边界

FreeRTOS 全是任务（线程）共居一个地址空间——"拆线程就完了"。但后来发生了什么：**FreeRTOS-MPU 版、Zephyr 的 memory domain、AUTOSAR 的分区**，全是往线程世界里塞进程式隔离——因为 ISO 26262 的"免于干扰"要求高低关键级任务之间必须有硬件边界。线程用到最后，安全标准会逼你把进程边界造出来。

## 速记口诀

- IPC 主场在系统胶水层，不在业务代码——shell 竖线、Ctrl+C、docker.sock 都是它
- 线程是并发单元，进程是隔离单元，不竞争同一岗位
- 地址空间共享 = 通信免费 + 故障/权限连坐
- 拆进程四信号：第三方/异构运行时、崩溃不可连坐、独立重启、跨机器
- 平台必须给别人的代码留进程边界，产品自己写的代码线程就够
- 前六种 IPC 出不了本机，socket 独一份跨机器跨语言
- RTOS 全线程，但功能安全标准逼出 MPU 分区——在线程世界里重建进程边界
