# 系统调用原理与跨操作系统对比

## 题目

Linux 中用户态执行系统调用后切换到内核态的过程是怎样的？不同操作系统的实现有什么差异？

## 考察点

系统调用的硬件机制、用户态/内核态切换、跨 OS 对比。

## 回答要点

### 1. 各系统的具体流程

虽然最终原理相同，但实现路径差异很大。

#### 1.1 Windows（以 CreateFile 为例）

封装层次最深，路径最长。

```
你的程序
  │
  ▼
① kernel32.dll（用户态）
  │ CreateFileW → NtCreateFile
  ▼
② ntdll.dll（用户态，NT 层）
  │ NtCreateFile 函数体只有两条指令：
  │   mov eax, 0x55          ; 系统调用号
  │   syscall                 ; 触发特权级切换
  ▼
③ CPU 切换到内核态
  │ 从 LSTAR MSR 读取 KiSystemCall64 地址并跳转
  │ 从 EAX 取服务号 → 查 SSDT（系统服务描述符表）
  │ → 找到内核态 NtCreateFile
  ▼
④ 内核处理
  │ I/O 管理器 → 文件系统驱动 → 磁盘驱动
  ▼
⑤ 原路返回
  sysret 回到用户态
```

#### 1.2 Linux（以 open 为例）

直接了当，调用就是系统调用。

```
你的程序
  │ open("/tmp/test.txt", ...)
  ▼
① glibc 封装函数（用户态）
  │ 将 __NR_open (= 2) 放入 rax
  │ 参数放入 rdi, rsi, rdx
  │ 执行 syscall 指令
  ▼
② CPU 切换到内核态
  │ 执行 entry_SYSCALL_64
  │ 保存用户态寄存器
  │ 从 rax 取调用号 → 查 sys_call_table
  │ → 找到 sys_open
  ▼
③ 内核处理
  │ VFS 层 → 具体文件系统 → 块设备层
  ▼
④ 返回
  ret_from_sys_call → sysret 回到用户态
```

#### 1.3 macOS / iOS（XNU 内核）

在用户态和内核态之间，多了一道"门"。

```
你的程序
  │ open(...)
  ▼
① libSystem.dylib（用户态）
  ▼
② Mach 陷阱 / BSD 系统调用
  │ 正调用号 → BSD 层（类似传统 Unix）
  │ 负调用号 → Mach 层（通过 Mach trap 表）
  ▼
③ 内核处理
  │ BSD 层：直接类似 Unix 系统调用
  │ Mach 层：构造 IPC 消息 → 发给 VFS 服务端进程
  ▼
④ 返回结果
```

### 2. 三系统对比

| 方面 | Linux | Windows | macOS |
|------|-------|---------|-------|
| 用户态封装 | glibc | kernel32.dll → ntdll.dll | libSystem.dylib |
| 系统调用号存放 | `rax` | `eax` | `rax`（正=BSD，负=Mach） |
| 触发指令 | `syscall` | `syscall` | `syscall` |
| 内核入口 | `entry_SYSCALL_64` | `KiSystemCall64`（LSTAR MSR） | `unix_syscall64` |
| 分发表 | `sys_call_table` | SSDT | BSD: `sysent[]` / Mach: `mach_trap_table` |
| 内核函数命名 | `sys_xxx` | `NtXxx` | `sys_xxx` / `mach_xxx_trap` |
| 封装层数 | 1 层（glibc） | 2 层（kernel32 + ntdll） | 1-2 层（libSystem + 可能的 Mach IPC） |

### 3. 最简抽象流程

剥去所有系统差异，只剩下一条不可缩减的核心路径，共四步：

```
[1. 准备] → [2. 触发] → [3. 切换与分发] → [4. 处理与返回]
```

#### 3.1 准备（用户态）

将**系统调用号**和**参数**按约定放进特定寄存器。

```asm
; Linux x86-64 的 open 调用
mov rax, 2          ; __NR_open
mov rdi, pathname   ; 第1个参数：文件路径
mov rsi, flags      ; 第2个参数：打开标志
mov rdx, mode       ; 第3个参数：权限模式
syscall
```

#### 3.2 触发（硬件指令）

执行一条特权指令，这是从用户态进入内核态的**唯一合法入口**：

| 架构 | 指令 | 说明 |
|------|------|------|
| x86-64 | `syscall` | 现代首选，专为此设计 |
| x86（32位） | `sysenter` | 较老的快速系统调用 |
| x86（古老） | `int 0x80` | 中断方式，兼容但慢 |
| ARM | `SVC #0` | 软件中断触发 |
| RISC-V | `ecall` | 环境调用 |

#### 3.3 切换与分发（内核态）

CPU 硬件自动完成：
1. **切换特权级**：Ring 3 → Ring 0（x86）/ EL0 → EL1（ARM）
2. **切换栈**：从用户栈切到内核栈
3. **保存返回地址**：将用户态 PC 存入特殊寄存器（x86 存入 RCX，ARM 存入 ELR_EL1）
4. **跳转到固定入口**：从 MSR（x86）或向量表（ARM）读取内核入口地址

内核入口函数软件完成：
1. 保存用户态寄存器到内核栈（pt_regs 结构）
2. 从约定寄存器读取系统调用号
3. **查表**：在系统调用表中索引到对应的内核函数
4. 调用该内核函数

```c
// Linux 系统调用表（简化）
sys_call_table[__NR_open]  = sys_open;
sys_call_table[__NR_read]  = sys_read;
sys_call_table[__NR_write] = sys_write;
sys_call_table[__NR_close] = sys_close;
// ... 通常 300-400 个条目
```

#### 3.4 处理与返回

```
内核函数执行完毕
  │
  ▼
将返回值放入约定寄存器（x86-64: rax, ARM: r0）
  │
  ▼
恢复用户态寄存器（从 pt_regs）
  │
  ▼
执行返回指令（sysret / eret）
  │
  ▼
CPU 硬件自动：
  - 切换特权级 Ring 0 → Ring 3
  - 切换回用户栈
  - 跳转回用户态下一条指令
```

### 4. ARM Cortex-A 的系统调用（嵌入式视角）

```asm
; ARM64 的 open 系统调用
mov x8, #56         ; __NR_openat（ARM64 用 openat 而非 open）
mov x0, #-100       ; AT_FDCWD（当前目录）
ldr x1, =pathname   ; 文件路径
mov x2, #0          ; O_RDONLY
svc #0              ; 触发系统调用

; 内核入口：el0_svc → el0_svc_handler
; 从 x8 读调用号 → 查 sys_call_table
; 调用 sys_openat
; 返回值在 x0
```

### 5. 系统调用的开销

| 开销来源 | 典型耗时（x86-64） | 说明 |
|---------|-------------------|------|
| `syscall` 指令本身 | ~100-200 ns | 硬件特权级切换 |
| 内核入口保存寄存器 | ~50-100 ns | 保存用户态上下文 |
| 查表 + 调用内核函数 | ~50 ns | 数组索引，很快 |
| 内核函数执行 | 取决于功能 | open ~1-5μs，read ~1-10μs |
| `sysret` 返回 | ~100-200 ns | 恢复特权级和用户栈 |
| **总计（不含业务逻辑）** | **~0.5-1 μs** | 纯切换开销 |

**这就是为什么高频场景要减少系统调用次数**：每次调用至少 0.5-1μs 的固定开销，1 秒调 100 万次就是 0.5-1 秒全花在切换上了。

### 6. 面试速记

- **本质**：一次由硬件强制的、通过号码和跳转表进行的受控特权级跳转
- **四步**：准备（放调用号）→ 触发（syscall/svc）→ 切换与分发（查表）→ 处理与返回（sysret）
- **Linux**：glibc → `syscall` → `entry_SYSCALL_64` → `sys_call_table[调用号]`
- **Windows**：kernel32 → ntdll → `syscall` → SSDT 查表
- **开销**：纯切换 ~0.5-1μs，高频场景必须减少调用次数（mmap、批量 IO、共享内存）
