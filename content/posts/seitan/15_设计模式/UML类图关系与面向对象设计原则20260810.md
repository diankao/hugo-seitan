# UML类图关系与面向对象设计原则

## 题目

1. 类之间的关系有哪些？举例说明。
2. UML 类图了解吗？类之间关系的图例是什么？
3. 面向对象的设计原则有哪些？

## 考察点

面向对象分析与设计、UML 建模、SOLID 原则。

## 回答要点

### 1. 类之间的六种关系（由弱到强）

UML 类图中类与类的关系按耦合度从弱到强排列：

| 关系 | 含义 | UML 符号 | 代码体现 |
|------|------|---------|---------|
| 依赖 (Dependency) | A 用到 B，但 B 不是 A 的成员 | 虚线箭头 `---->` | 参数、局部变量、返回值 |
| 关联 (Association) | A 持有 B 作为成员（长期） | 实线箭头 `────>` | 成员变量 |
| 聚合 (Aggregation) | 弱拥有，部分可独立于整体存在 | 空心菱形 `◇────` | 成员变量（生命周期独立） |
| 组合 (Composition) | 强拥有，部分随整体生灭 | 实心菱形 `◆────` | 成员变量（整体负责创建销毁） |
| 实现 (Realization) | 类实现接口 | 虚线空心三角 `----▷` | `implements` |
| 泛化/继承 (Generalization) | 子类继承父类 | 实线空心三角 `────▷` | `extends` |

### 2. 用现实事物举例

```cpp
// 继承（泛化）：动物 → 狗
class Animal { /* ... */ };
class Dog : public Animal { /* ... */ };          // Dog 是一种 Animal

// 实现：鸟类实现了"会飞"接口
class IFlyable { public: virtual void fly() = 0; };
class Bird : public IFlyable {
public:
    void fly() override { /* ... */ }
};

// 组合（强拥有）：汽车和发动机，发动机随汽车一起报废
class Engine { /* ... */ };
class Car {
    Engine engine;      // 组合：Car 不存在了，engine 也跟着销毁
};

// 聚合（弱拥有）：球队和球员，球员可独立转会
class Player { /* ... */ };
class Team {
    std::vector<Player*> players;   // 聚合：Team 销毁后球员还在
public:
    void addPlayer(Player* p) { players.push_back(p); }
};

// 关联：订单持有顾客引用
class Customer;
class Order {
    Customer* customer;   // 关联：长期持有，但生命周期独立
};

// 依赖：打印服务临时使用文档
class Document;
class Printer {
public:
    void print(Document& doc);   // 依赖：临时使用，不长期持有
};
```

### 3. 聚合 vs 组合（最易混淆）

| 维度 | 聚合（Aggregation） | 组合（Composition） |
|------|--------------------|--------------------|
| 部分能否脱离整体 | 能 | 不能 |
| 整体销毁时部分是否销毁 | 否 | 是 |
| 部分由谁创建 | 外部创建后传入 | 整体内部创建 |
| 现实例子 | 球队 ↔ 球员、图书馆 ↔ 书 | 汽车 ↔ 发动机、人 ↔ 心脏 |

```cpp
// 组合：整体负责创建和销毁部分
class Heart { /* ... */ };
class Person {
    Heart heart;   // Person 创建时 heart 创建，Person 销毁时 heart 销毁
};

// 聚合：部分在外部创建，整体只是引用
class Book { /* ... */ };
class Library {
    std::vector<Book*> books;
public:
    void add(Book* b) { books.push_back(b); }   // 书外部创建，图书馆销毁后书仍在
};
```

### 4. 依赖倒置："针对接口编程"的基础

```cpp
// 不好的设计：高层直接依赖低层具体类
class MySQLDB { public: void save(); };
class OrderService {
    MySQLDB db;    // 强依赖具体数据库，换 DB 要改代码
public:
    void save() { db.save(); }
};

// 好的设计：依赖抽象（接口）
class IDatabase { public: virtual void save() = 0; };
class OrderService {
    IDatabase* db;     // 依赖接口，可注入 MySQL/Redis/...
public:
    OrderService(IDatabase* d) : db(d) {}
    void save() { db->save(); }
};
```

### 5. 面向对象设计原则：SOLID + 其他

| 缩写 | 原则 | 含义 |
|------|------|------|
| **S**RP | 单一职责 (Single Responsibility) | 一个类只有一个引起变化的原因 |
| **O**CP | 开闭原则 (Open-Closed) | 对扩展开放，对修改关闭 |
| **L**SP | 里氏替换 (Liskov Substitution) | 子类必须能替换父类而不破坏行为 |
| **I**SP | 接口隔离 (Interface Segregation) | 不应强迫客户依赖不需要的接口方法 |
| **D**IP | 依赖倒置 (Dependency Inversion) | 高层不依赖低层，二者都依赖抽象 |

#### 单一职责 (SRP)

```cpp
// 反例：一个类管太多
class Employee {
    void calculatePay();      // 财务职责
    void save();              // 持久化职责
    void reportHours();       // 报表职责
};
// 改工资、改存储、改报表都会改这个类 → 职责过多

// 正解：拆分
class Employee {};                    // 数据模型
class PayCalculator {};               // 计算工资
class EmployeeRepository {};          // 持久化
class HoursReporter {};               // 报表
```

#### 开闭原则 (OCP)

```cpp
// 不好的设计：加新形状要改 AreaCalculator
class AreaCalculator {
    double area(Shape& s) {
        if (s.type == CIRCLE)   return circle_area(s);
        if (s.type == RECT)     return rect_area(s);
        // 加 Triangle 还要改这里 → 违反 OCP
    }
};

// 好的设计：通过多态扩展，不改旧代码
class Shape { public: virtual double area() = 0; };
class Circle : public Shape { public: double area() override { /*...*/ } };
class Triangle : public Shape { public: double area() override { /*...*/ } };
// 加 Triangle 只需新增类，AreaCalculator 不用改
```

#### 里氏替换 (LSP)

```cpp
// 经典反例：正方形继承长方形
class Rectangle { public: virtual void setW(int w){w_=w;} virtual void setH(int h){h_=h;} int area(){return w_*h_;} };
class Square : public Rectangle {
public:
    void setW(int w) override { w_ = h_ = w; }   // 强制相等
    void setH(int h) override { w_ = h_ = h; }
};
void func(Rectangle& r) {
    r.setW(5); r.setH(4);
    assert(r.area() == 20);   // Square 传入会失败！违反 LSP
}
```

#### 接口隔离 (ISP)

```cpp
// 反例：胖接口
class IMachine {
public:
    virtual void print() = 0;
    virtual void scan() = 0;
    virtual void fax() = 0;
};
class SimplePrinter : public IMachine {
    void print() override {}
    void scan() override {}   // 简单打印机被迫实现不需要的扫描
    void fax() override {}
};

// 正解：拆成小接口
class IPrinter { public: virtual void print() = 0; };
class IScanner { public: virtual void scan() = 0; };
class SimplePrinter : public IPrinter { /* 只实现 print */ };
```

### 6. 其他常用原则（SOLID 之外）

| 原则 | 含义 |
|------|------|
| **DRY** (Don't Repeat Yourself) | 不要重复，抽取共性 |
| **KISS** (Keep It Simple, Stupid) | 保持简单，避免过度设计 |
| **YAGNI** (You Aren't Gonna Need It) | 不要预先实现用不上的功能 |
| **合成复用原则** (CRP) | 优先用组合/聚合而非继承实现复用 |
| **最少知识原则** (迪米特法则) | 一个对象应尽可能少了解其他对象 |

### 7. 设计原则与设计模式的关系

设计原则是**指导思想**，设计模式是**具体套路**。常见模式的对应：

| 模式 | 主要体现的原则 |
|------|--------------|
| 策略模式 | OCP、DIP（用接口注入不同算法） |
| 工厂模式 | DIP、OCP（客户端依赖抽象产品） |
| 装饰器模式 | OCP、SRP（动态扩展功能不改原类） |
| 适配器模式 | ISP（转换接口让不兼容类协作） |
| 观察者模式 | DIP、OCP（主题依赖抽象观察者） |

> 具体设计模式见 `15_设计模式/` 下已有文章：`设计模式分类与应用场景20260923.md`、`0001.C++设计模式与应用20260227.md` 等。

## 扩展问题

面试官可能会追问：
- 继承和组合各自的优缺点？（继承强耦合、编译期确定；组合灵活、运行期可变 → 优先组合）
- 开闭原则如何在实际项目中落地？（抽象 + 多态 + 依赖注入）
- 迪米特法则的具体含义？（只跟"直接朋友"说话，减少 long chain 调用 `a.b.c().d()`）
- 设计原则和设计模式的关系？（原则是道，模式是术）
