# uCOS任务控制块与消息队列

## 题目

围绕 uC/OS-II 任务管理与任务间通信的系列问题：

1. 任务控制块（TCB）中存储了哪些内容？任务调度队列（就绪表）和 TCB 是什么关系？
2. 消息队列的常用 API 各自的阻塞性如何？中断服务程序中为什么不能调用 `OSQPend()`？

## 考察点

uC/OS-II 任务控制块（TCB）的组成、任务调度数据结构与 TCB 的边界、消息队列常用 API 的阻塞特性以及中断服务程序中对内核 API 的调用限制。

## 回答要点

### 1. 任务控制块（TCB）是什么

TCB（Task Control Block）是内核用来描述一个任务全部属性的核心数据结构，每创建一个任务就分配一个 TCB。uC/OS-II 中对应的类型是 `OS_TCB`，其主要字段如下：

| 字段 | 含义 |
|------|------|
| `OSTCBStkPtr` | 当前任务栈顶指针，上下文切换时保存/恢复现场用 |
| `OSTCBPrio` | 任务优先级（uC/OS-II 中优先级即任务 ID，唯一） |
| `OSTCBStat` | 任务状态（就绪、挂起、等待事件、等待挂起等） |
| `OSTCBDly` | 延时计数（按 tick 递减） |
| `OSTCBEventPtr` | 正在等待的事件控制块指针 |
| `OSTCBMsg` | 等待消息时收到的消息指针 |
| `OSTCBNext / OSTCBPrev` | 双向链表指针，用于把 TCB 挂入空闲链表或等待链表 |

其中**任务优先级、堆栈指针、状态标志**是最核心的三个字段——它们回答了"这个任务是谁、现场在哪、现在什么状态"。

### 2. 任务调度队列不属于 TCB

就绪任务的排队管理是**内核全局的调度数据结构**，不是单个任务的属性：

- uC/OS-II 用**就绪表**（`OSRdyGrp` + `OSRdyTbl`，位图结构）记录所有就绪任务，配合优先级查找表 `OSUnMapTbl` 一次查表就能找到最高优先级任务；
- 这个位图属于内核全局变量，任何任务就绪/阻塞时由内核统一置位/清位；
- TCB 里虽然挂着 `OSTCBNext/OSTCBPrev` 这类链表指针（把 TCB 串到空闲链表或事件等待链表上），但那是"把自己挂上去的钩子"，"调度队列本身"是全局机制，不是存储在某个任务 TCB 里的内容。

一句话区分：**TCB 描述"这个任务是谁、在什么状态"，调度结构描述"所有任务谁该上 CPU"**。

### 3. 消息队列常用 API 及其阻塞特性

| API | 作用 | 阻塞性 | ISR 中能否调用 |
|-----|------|--------|---------------|
| `OSQCreate()` | 创建消息队列，得到事件控制块 | 非阻塞 | 一般在任务初始化时调用 |
| `OSQPend()` | 取消息，队列为空时**挂起当前任务等待** | **阻塞** | **禁止** |
| `OSQAccept()` | 无等待取消息，队列为空直接返回 `NULL` | 非阻塞 | 可以 |
| `OSQPost()` / `OSQPostFront()` | 发消息入队（队尾/队头） | 非阻塞 | 可以 |

逐条展开：

- `OSQPend()` 会把调用者挂起等待，而 ISR 不是任务、没有自己的 TCB 和可挂起的上下文，一旦在 ISR 里阻塞整个系统就死锁了。uC/OS-II 规定 **ISR 中禁止调用任何可能阻塞的 API**；
- `OSQAccept()` 就是为"不等待"设计的非阻塞接口，队列空了直接返回空指针，任务和 ISR 里都能用；
- uC/OS-II 所有事件（队列、信号量、互斥锁、事件组）都要先 `OSQCreate()` 之类显式创建后才能使用；
- `OSQPost()` 可能让一个比当前任务优先级更高的等待任务就绪，此时会触发调度（任务里调用时立即切换，ISR 里调用时推迟到 `OSIntExit()` 时切换）——发消息不只是传数据，还参与调度。

### 4. ISR 中调用内核 API 的通用规则

这条规则不限于消息队列，是 RTOS 的通用约束：

| 调用位置 | 可调用的 API | 禁止调用的 API |
|---------|-------------|---------------|
| 任务上下文 | 全部 | 无 |
| 中断上下文 | 非阻塞版本（`OSQAccept`、`OSQPost` 等） | 一切会阻塞或隐含切换任务的 API（`OSQPend`、`OSTimeDly`、`OSMutexPend` 等） |

对比 FreeRTOS 的做法：FreeRTOS 把 API 做成了两套名字（`xQueueReceive()` / `xQueueReceiveFromISR()`），从函数名上就强制区分了两个上下文；uC/OS-II 则靠开发者自己记住哪些能在 ISR 里用。

```c
void TaskMain(void *p_arg)
{
    (void)p_arg;
    while (1) {
        void *msg = OSQPend((OS_EVENT *)msg_queue, 0, &err);
    }
}

void UartISR(void)
{
    OSIntEnter();
    OSQPost((OS_EVENT *)msg_queue, (void *)rx_buf);
    OSIntExit();
}
```

### 5. 小结

- TCB = 任务的"身份证"：优先级、栈指针、状态、延时、等待的事件都在里面；调度队列是全局机制，不属于 TCB；
- `OSQPend()` 阻塞取消息，只能在任务里调用；`OSQAccept()` 非阻塞，任务和 ISR 都能用；
- `OSQPost()` 发消息可能唤醒更高优先级任务从而引发调度，这正说明"队列不只是传数据，还参与调度"。
