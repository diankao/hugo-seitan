# 温度传感器驱动开发流程

## 题目

介绍一个温度传感器的驱动过程：拿到一颗温度传感器，从器件手册到读出可用温度值，驱动是怎么一步步做的？

## 考察点

驱动开发的整体流程感、数据手册阅读能力、接口类型选型（I2C/单总线/模拟 ADC）、时序与寄存器操作、数据换算与滤波、平台差异意识。

## 回答要点

### 1. 总体流程

驱动过程可以概括为"先看手册、再选接口、后做数据"：

```mermaid
flowchart LR
    A[读数据手册] --> B[确定接口类型]
    B --> C[硬件连接与引脚配置]
    C --> D[实现总线读写时序]
    D --> E[配置测量参数]
    E --> F[读取原始数据并换算]
    F --> G[滤波与校准]
    G --> H[封装接口与测试]
```

关键点：**驱动开发的大部分时间花在读手册上**——接口类型、寄存器表、转换时间、分辨率、换算公式这五样东西直接决定了软件怎么写。

### 2. 第一步：确定接口类型

温度传感器按输出形式分三大类，驱动工作量差异很大：

| 接口类型 | 代表器件 | 占用引脚 | 分辨率/精度 | 驱动特点 |
|---------|---------|---------|------------|---------|
| I2C 数字 | LM75、TMP102、SHT30 | 2 线 | 9~16 位，±0.5℃ | 寄存器化读写，可多器件共总线 |
| 单总线 1-Wire | DS18B20 | 1 线 | 9~12 位，±0.5℃ | 时序严格（µs 级），支持多点组网 |
| SPI 数字 | TMP123、MAX31875 | 4 线 | 12~16 位 | 全双工高速，引脚多 |
| 模拟输出 | NTC 热敏电阻、PT100 | 1 路 ADC | 取决于电路与查表 | 便宜，需分压电路 + 查表/公式换算 |

选型逻辑：板上有 I2C 总线优先数字 I2C（寄存器化、好调试）；成本敏感或只看温度趋势用 NTC + ADC；一根线要挂十几个点（仓储、多区测温）用 DS18B20。

### 3. 第二步：按接口实现驱动（以 I2C 型 TMP102 为例）

以常见的 I2C 温度传感器为例，驱动步骤固定：

1. **上电延时**：手册规定上电到首次通信的等待时间（通常几 ms~几十 ms），不可省略；
2. **配置寄存器**：设置转换模式（连续/关断）、转换速率、故障队列、报警阈值 T_LOW/T_HIGH；
3. **读温度寄存器**：I2C 先写寄存器地址（0x00），再重复起始读 2 字节；
4. **数据换算**：TMP102 温度是 12 位二进制补码、左对齐存放，分辨率 0.0625℃/LSB，负温要按补码符号扩展处理。

```c
#include <stdint.h>

#define TMP102_ADDR     0x48    // A0 引脚接 GND 时的 7 位地址

static float tlast;             // 上次滤波结果
static uint8_t tinited;

int tmp102_read(float *temp)    // 返回 0 成功
{
    uint8_t buf[2];

    if (i2c_mem_read(TMP102_ADDR, 0x00, buf, 2) != 0)
        return -1;

    int16_t raw = (int16_t)((buf[0] << 8) | buf[1]);
    raw >>= 4;                          // 取高 12 位，算术右移自动保留符号
    *temp = raw * 0.0625f;              // 0.0625℃/LSB
    return 0;
}

float tmp102_read_filtered(void)        // 一阶低通滤波，抑制单次毛刺
{
    float t;
    if (tmp102_read(&t) != 0)
        return tinited ? tlast : 0.0f;

    if (!tinited) {                     // 首次读数直接作为滤波初值
        tlast = t;
        tinited = 1;
        return tlast;
    }
    tlast += 0.25f * (t - tlast);
    return tlast;
}
```

不同型号只有两处不同：**寄存器表**（LM75 是 9 位、0.5℃/LSB，换算公式不同）和**换算方式**，驱动框架完全一样。

### 4. DS18B20 单总线的特殊之处

DS18B20 是另一套写法：单总线没有现成外设，靠 GPIO 精确时序模拟，且命令分三层：

1. **复位 + 应答脉冲**：主机拉低 ≥480µs，从机 60~240µs 后回拉低表示在线；
2. **ROM 命令**：单器件用 Skip ROM（0xCC）跳过寻址，多器件必须先 Search ROM（0xF0）枚举 64 位序列号；
3. **功能命令**：Convert T（0x44）启动转换，**最长等 750ms**（12 位分辨率），再 Read Scratchpad（0xBE）读 9 字节，最后 CRC8 校验。

750ms 等待是经典考点：**绝不能在主循环或任务里死等**。标准做法是状态机拆分——发转换命令后记下时间戳就返回，下次轮询发现超时再读结果；RTOS 下也可以用软件定时器或延时任务回调触发读取。

NTC 模拟型的驱动则是另一路：ADC 采样 → 分压电阻反算阻值 → R-T 查表插值或 B 值公式 `T = 1/(1/T0 + ln(R/R0)/B) - 273.15`，工作重点在电路与标定而不是时序。

### 5. 第三步：数据处理与封装

原始值到可用值之间还有三件事：

- **换算**：按手册的位数与 LSB 权重换算，负温器件注意补码与符号扩展；
- **滤波**：滑动平均或一阶低通（IIR）抑制毛刺；温度是慢变量，滤波窗口可以很长，代价几乎为零；
- **校准**：与标准温度计对比做单点偏移校准，消除系统误差。

最后封装成与器件解耦的统一接口（`temp_sensor_read(float *t)`），上层不关心底下是 TMP102 还是 NTC，方便换料。

### 6. 平台差异

| 平台 | 驱动形态 |
|------|---------|
| MCU 裸机 | 直接调 HAL/寄存器或 GPIO 位拆模拟时序；轮询或定时器触发采样 |
| MCU + RTOS | 采样任务周期读取，结果经队列/消息发给使用方；转换等待用状态机或定时器，不阻塞任务 |
| Linux | 写成内核驱动挂在 I2C 子系统上，走 `probe` 流程；温度类器件可直接对接 hwmon/IIO 子系统，用户态读 sysfs；设备树描述挂载信息，细节见《LinuxI2C驱动体系结构》 |

### 7. 高频坑清单

1. **忽略上电/转换延时**：上电就读、转换没完成就读，读到旧值或 0xFFFF；
2. **阻塞等转换**：DS18B20 里死等 750ms，把整个主循环/低优先级任务拖死；
3. **负温处理错**：把补码当无符号数换算，0℃ 以下数值全错；
4. **单总线时序超差**：中断关不干净导致时序漂移，读数全 0xFF——关键段要关中断或用定时器捕获；
5. **I2C 上拉缺失/时钟拉伸**：表现为 NACK 或总线卡死，排查思路见《I2C底层通信机制与异常排查》；
6. **多点 DS18B20 不做 ROM 搜索**：Skip ROM 群发转换可以，读数据必须逐器件寻址，否则总线冲突；
7. **自热与安装误差**：芯片自身功耗升温、传感器贴装位置不代表被测对象温度，属于系统问题而非驱动问题。

### 8. 一句话总结

**温度传感器驱动 = 读手册定接口 + 实现总线时序读原始值 + 按位数补码换算 + 滤波校准封装统一接口**；数字型难在时序与非阻塞，模拟型难在电路与标定。
