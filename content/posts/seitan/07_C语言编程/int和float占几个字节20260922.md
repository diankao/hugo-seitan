# int和float占几个字节

## 题目

1. 嵌入式里面 int、float 之类的各占几个字节？
2. 这件事在什么架构上不一样？
3. C 标准对 int 到底严格规定了什么？

## 考察点

类型宽度是死记硬背还是知道来源：C 标准只规定最小宽度与相对关系而不规定精确字节数、各架构的数据模型（ILP32/LP64/LLP64）、8/16 位 MCU 与 DSP 上的例外、用 stdint.h 写可移植代码的习惯。

## 回答要点

### 1. C 标准对 int 的"严格规定"：只有下限和相对关系

标准（C99 §5.2.4.2.1，即 `<limits.h>` 的最小值）对整数类型只约束三件事：

| 类型 | 标准保证的最小宽度 | 标准保证的关系 |
|------|------------------|---------------|
| char | 8 位（CHAR_BIT ≥ 8） | sizeof(char) == 1 恒成立 |
| short | ≥ 16 位 | sizeof(short) ≤ sizeof(int) |
| int | ≥ 16 位，范围至少 [-32767, +32767] | sizeof(int) ≤ sizeof(long) |
| long | ≥ 32 位 | sizeof(long) ≤ sizeof(long long) |
| long long | ≥ 64 位 | — |

另外 C11 §6.2.5 对 int 有一个方向性描述：普通 int 具有"执行环境架构所建议的自然大小"（natural size），也就是通常取 CPU 通用寄存器/数据总线的宽度，运算效率最高。

**所以标准从未规定 int 必须是 4 字节**——它只保证 int 不小于 16 位、不大于 long。float/double 同理：标准只规定最低表示能力（数值范围至少覆盖 1e-37 ~ 1e37、十进制有效数字下限，见 `<float.h>` 的 `FLT_MAX`、`DBL_DIG` 等），位宽和编码格式交给实现。

### 2. 为什么架构不一样：int 跟着 CPU 字长走

| CPU 字长 | int 实际宽度 | 典型平台 |
|---------|-------------|---------|
| 8 位 | 2 字节 | 8051、AVR |
| 16 位 | 2 字节 | MSP430 |
| 32 位 | 4 字节 | STM32/Cortex-M、x86 |
| 64 位 | 4 字节（没有跟着变 8） | x86-64、ARM64 |

两个方向的"意外"都值得说清楚：

- **8 位机 int 为什么是 16 位**：8 位只有 ±127，连计数器都不够用，编译器厂商把 int 定为 16 位。
- **64 位机 int 为什么停在 32 位**：16 → 32 位时代 int 一直跟着字长走，但到 64 位时，把 int 变 8 字节会让大量既有代码的结构体膨胀、溢出假设失效，于是 Unix 阵营保持 int=32、把 long 升到 64（LP64）；Windows 阵营连 long 都保持 32、用 long long 承载 64 位（LLP64）。x86-64 的 32 位操作数（EAX 一族）本来就是默认路径，性能上没有损失。

### 3. 数据模型：ILP32 / LP64 / LLP64

数据模型描述 int/long/指针三者的宽度组合（I=int，L=long，P=pointer，数字是位数）：

| 数据模型 | short | int | long | long long | 指针 | 典型平台 |
|---------|-------|-----|------|-----------|------|---------|
| LP32 | 2 | 2 | 4 | 8 | 4 | Win16、68K 时代 |
| ILP32 | 2 | 4 | 4 | 8 | 4 | **STM32 等 32 位 MCU**、32 位 x86 |
| LP64 | 2 | 4 | **8** | 8 | 8 | 64 位 Linux/macOS（x86-64、ARM64） |
| LLP64 | 2 | 4 | 4 | 8 | 8 | 64 位 Windows（MSVC、MinGW） |
| ILP64 | 2 | 8 | 8 | 8 | 8 | 早期 64 位 Unix（Alpha），基本绝迹 |

嵌入式最常打交道的组合：Cortex-M 是 ILP32，桌面 Linux 是 LP64，Windows 是 LLP64。**long 是分歧最大的类型**——同一段代码里 `sizeof(long)` 在 64 位 Linux 上是 8、在 64 位 Windows 上是 4，凡是假设"long 能装下指针"的写法只在 32 位和 LP64 平台成立。

### 4. 嵌入式各平台实际大小对照

以各家官方编译器默认配置为准（单位：字节）：

| 平台 | char | short | int | long | 指针 | float | double |
|------|------|-------|-----|------|------|-------|--------|
| 8051（Keil C51） | 1 | 2 | 2 | 4 | 1~3 | 4 | 4（同 float） |
| AVR（avr-gcc，8 位） | 1 | 2 | **2** | 4 | 2 | 4 | **4** |
| MSP430（16 位） | 1 | 2 | **2** | 4 | 2 | 4 | 8 |
| STM32 / Cortex-M | 1 | 2 | 4 | 4 | 4 | 4 | 8 |
| x86-64 Linux | 1 | 2 | 4 | **8** | 8 | 4 | 8 |
| x64 Windows | 1 | 2 | 4 | 4 | 8 | 4 | 8 |
| TI C2000 DSP | 1* | 1* | 1* | 2* | 1~2* | 2* | 2* |

\* C2000 的最小可寻址单元是 16 位，它的"1 字节"= 16 位（CHAR_BIT == 16），表中标 \* 的数字按 16 位字计算。

值得记住的例外：

1. **AVR 上 int 是 2 字节、double 默认是 4 字节**：`sizeof(int)==4` 的假设直接崩溃；想要真 64 位 double 要显式开 `-mdouble=64`。
2. **TI C2000 上 char 是 16 位**：`sizeof(char) == sizeof(int) == 1` 但都是 16 位。这说明"字节"不等于"8 位"——标准里字节就是 `sizeof(char)` 的宽度。
3. **Keil C51 的 double 与 float 同为 4 字节**，且指针分通用指针（3 字节）和存储区专属指针（1~2 字节），大小取决于指向的存储空间。
4. **MSP430 的 int 是 2 字节**：16 位机的自然字长。

### 5. float=4、double=8 从哪来的：IEEE 754 事实标准

C 标准只规定浮点类型的最低能力，不规定二进制位宽。但 1985 年 IEEE 754 发布后，单精度 32 位 / 双精度 64 位成了几乎所有平台的事实标准：

| 类型 | 位宽 | 符号位 | 阶码 | 尾数 | 十进制有效数字 |
|------|------|--------|------|------|---------------|
| float | 32 | 1 | 8 | 23 | 约 7 位 |
| double | 64 | 1 | 11 | 52 | 约 15~16 位 |

例外仍然是嵌入式，而且要分两档看：

- **AVR、C51、C2000：double 退化为 32 位单精度，但格式本身仍是 IEEE 754**。Keil 官方文档明确 float 采用 IEEE-754 格式、double 与 float 完全相同（不支持 64 位浮点运算）；avr-gcc 默认 `-mdouble=32`；TI C2000 同理（默认 double 32 位，开选项可到 64 位）。写 `double x;` 能编译能算，只是精度承诺只剩约 7 位十进制。
- **SDCC：连位级布局都不是 IEEE**。官方手册原话是"similar to IEEE, but it is not IEEE"：不支持 denormal（次正规数），指数/尾数的字节安排与 IEEE 不同。在 SDCC 下用 union/memcpy 按位拆浮点、把浮点字节原样发给 PC，得到的就是错的数。SDCC 本身是什么，详见《什么是SDCC》。

C 标准从不要求 IEEE 754，判断实现是否遵循的标准化方法是查 `__STDC_IEC_559__` 宏（C99/C11，定义为 1 才宣告遵循 IEC 60559 即 IEEE 754，8051 编译器都不定义）：

```c
#if defined(__STDC_IEC_559__) && __STDC_IEC_559__ == 1
// 本实现宣告遵循 IEEE 754
#endif
```

需要确认实际精度时用 `<float.h>` 里的 `FLT_MANT_DIG`、`DBL_MANT_DIG`（尾数位数）。再进一步说，"double=32 位"其实**低于 ISO C 对 double 的最低精度要求**（`DBL_DIG ≥ 10` 位十进制，32 位只有约 7 位）——这类 8051 编译器本来就在手册里公开声明了多处 ANSI C 偏差（如 C51 默认函数不可重入），属于 256 字节 RAM、无 FPU 平台上的公开取舍，而不是违规事故。顺带一提，"严格 IEEE"在桌面机上也不绝对：x87 的 80 位扩展精度、NEON 的 flush-to-zero 都是对 IEEE 默认行为的偏离。

### 6. 工程实践：怎么写跨平台代码

**用 `<stdint.h>` 的定宽类型代替裸 int/long**——定宽类型才是"严格规定"的：`int32_t` 一旦被提供就恰好 32 位、无填充位。

```c
#include <stdint.h>

uint8_t   reg_value;   // 明确 8 位
uint16_t  crc;         // 明确 16 位
int32_t   counter;     // 明确 32 位
```

**打印定宽类型用 `<inttypes.h>` 的格式宏**，避免平台间 `%ld`/`%lld` 不一致：

```c
#include <inttypes.h>
printf("counter = %" PRId32 ", crc = %" PRIX16 "\n", counter, crc);
```

**编译期断言兜底**，把对平台的前提变成显式检查：

```c
#include <limits.h>
#include <stdint.h>

#if CHAR_BIT != 8
#error "本平台字节不是 8 位，协议打包代码需要重新审查"
#endif

_Static_assert(sizeof(int) >= 4, "本代码假设 int 至少 32 位");
```

一份直接可跑的"体检"程序，在哪个平台都能立刻验证本文的结论：

```c
#include <stdio.h>
#include <limits.h>

int main(void)
{
    printf("char      = %zu 字节（%d 位）\n", sizeof(char), CHAR_BIT);
    printf("short     = %zu\n", sizeof(short));
    printf("int       = %zu\n", sizeof(int));
    printf("long      = %zu\n", sizeof(long));
    printf("long long = %zu\n", sizeof(long long));
    printf("float     = %zu\n", sizeof(float));
    printf("double    = %zu\n", sizeof(double));
    printf("指针      = %zu\n", sizeof(char *));
    return 0;
}
```

**其他守则**：

- 永远不要把指针塞进 `int`/`unsigned int`（64 位平台上会截断），用 `uintptr_t`
- 结构体布局、通信协议、flash 存储：一律定宽类型 + 显式字节序，别依赖平台默认
- 需要精确大小时用 `sizeof` 现算，不要硬编码 4
- 结构体成员顺序和内存对齐同样影响"实际占几个字节"，详见《结构体内存对齐与CAN报文解析》；sizeof 运算符本身的语义与数组退化陷阱，详见《sizeof运算符与数组大小计算》

### 7. 面试速记

- 标准对 int 的严格规定只有三条：**至少 16 位、不超过 long、取架构的自然字长**，从没规定过 4 字节
- STM32（ILP32）：int = long = 指针 = 4 字节；float 4、double 8
- 64 位分歧：Linux（LP64）long = 8；Windows（LLP64）long = 4，long long 都是 8
- 8 位 AVR、16 位 MSP430 的 int 都是 2 字节；TI C2000 连 char 都是 16 位
- float=4 / double=8 是 IEEE 754 的事实标准而非 C 标准强制；Keil C51/AVR/C2000 的 double 退化为 32 位单精度（格式仍是 IEEE），SDCC 连浮点位级布局都不是 IEEE；判据是 `__STDC_IEC_559__` 宏
- 跨平台代码：`stdint.h` 定宽类型 + `inttypes.h` 格式宏 + `_Static_assert` 前提检查
