# 什么是运行时

## 题目

什么是运行时（runtime）？runtime error 和运行时优化（runtime optimization）分别指什么？

## 考察点

"运行时"一词的三种用法（时间段/组件/环境）、C 运行时的构成与启动流程、原生与托管运行时、运行时错误的成因与各语言形态、JIT 优化与静态优化的边界。

## 回答要点

### 1. 一个词三用：时间段、软件组件、执行环境

| 用法 | 含义 | 例子 |
|------|------|------|
| 时间段 | 程序正在执行的那段时间，与编译期、链接期相对 | 运行时错误、运行时多态、RTTI |
| 组件（运行时系统） | 程序运行所需的整套支撑代码 | C 运行时（CRT）、JVM、CPython |
| 环境 | 让某类程序跑起来的整套环境（更松的用法） | 容器运行时（containerd/runc）、浏览器里的 JS 运行时 |

判断口诀：句子在对比编译期/链接期，是时间段用法；说"装了/带了/链了某个运行时"，是组件用法；说"某某的运行时"，是环境用法。多数困惑来自把三种用法搅在一起。

### 2. C 运行时拆开看：程序不是从 main 开始的

`gcc hello.c` 出来的可执行文件入口不是 `main`，而是链接器悄悄塞进来的启动代码：

```
_start（crt0）
  ├─ 设置栈、初始化 .data（Flash→RAM 拷贝）、清零 .bss
  ├─ 调用 C++ 全局构造函数
  ├─ main(argc, argv, envp)
  ├─ atexit 处理、全局析构
  └─ exit() 系统调用
```

这一套启动代码加上 `printf`/`malloc`/`memcpy` 背后的 libc，就是 C 运行时（CRT）；C++ 再加异常栈回退、RTTI、`new/delete` 的支持代码。

嵌入式工程师是把运行时看得最清楚的人群——MCU 的启动文件就是 crt0 的本尊，Reset_Handler 干的正是 `_start` 的活：

```c
extern uint32_t _sidata, _sdata, _edata, _sbss, _ebss;

void Reset_Handler(void)
{
    uint32_t *src = &_sidata;
    uint32_t *dst = &_sdata;

    while (dst < &_edata)
        *dst++ = *src++;

    for (dst = &_sbss; dst < &_ebss; dst++)
        *dst = 0;

    main();
    while (1)
        ;
}
```

重定向 `_write` 让 printf 有地方输出，则是 libc 部分的移植。裸机 `-nostdlib` 编译的本质是"只留运行时的启动部分，其余自己写"。

### 3. 原生与托管：运行时的两种重量级

```
原生（C/C++/Go）：    应用代码 → [轻量运行时：CRT/libc] → 系统调用 → 内核
托管（Java/C#/Python/JS）：应用代码（字节码） → [重量级运行时：JVM/CLR/CPython/V8] → 系统调用 → 内核
```

- C/C++ 编译成机器码直接跑在 CPU 上，运行时只是陪跑的服务库
- 托管语言的程序不直接跑在 CPU 上，跑在运行时上——解释/JIT、GC、类型检查都归它管，形同一个半虚拟机；装 JDK 时的 JRE 全称就是 Java Runtime Environment
- Go 是折中：编译成机器码，但调度器（goroutine）+ GC 整个运行时静态链进二进制，所以 Go 程序单文件就能跑、不用装运行时

Electron 说"每个渲染进程一套 V8"烧内存，指的就是组件用法：V8 是 JS 的托管运行时，每个进程各带一份。

### 4. runtime error：为什么编译器抓不住

运行时错误是**执行期间才暴露的错误**，与编译期错误（语法/类型）、链接期错误（undefined reference）相对。编译器抓不住它，因为它取决于运行时状态——输入数据、内存布局、时序、环境；而静态判定"所有输入下这个指针都不为空"本质上不可判定。编译器只保证语法和类型层面的正确，行为层面的错误只能留给运行时。各语言的形态差异由"谁在运行时盯着"决定：

| 世界 | 运行时错误的形态 | 谁发现的 |
|------|----------------|---------|
| C/C++（原生） | SIGSEGV、SIGFPE、SIGILL——直接撞硬件异常 | MMU/MPU 硬件，没人兜底 |
| 嵌入式（Cortex-M） | HardFault：野指针访问低位地址、栈溢出、函数指针飞了 | fault 检查逻辑 |
| C++ 异常 | `std::bad_alloc`、`std::out_of_range`——被驯化的运行时错误 | CRT/标准库主动抛 |
| Java/Python | `NullPointerException`、`ArrayIndexOutOfBoundsException` | 托管运行时兜底成异常 |

Java 里 `RuntimeException` 是字面上的类名——空指针、越界、类型转换失败全是这个家族的子类。托管语言"运行时错误体验好"，本质是运行时替你把崩溃翻译成了异常。C/C++ 这边是赤裸的：越界不报错（未定义行为），直到写坏别的变量才崩在无辜者家里。

检测手段因此分层：硬件兜底（MMU/MPU）→ 编译器插桩（ASan/UBSan）→ 托管运行时检查（数组边界）→ assert。

### 5. 运行时优化：编译器的天花板是 JIT 的起点

静态优化（`gcc -O2`）只看得见代码、看不见数据：哪个分支真的热、虚函数实际指向谁、对象逃不逃逸，都只能猜，于是只能保守。运行时优化（主力是托管运行时的 JIT）把这些信息全挣到了手：

| | 编译期优化（AOT） | 运行时优化（JIT） |
|---|---|---|
| 看得见什么 | 只有代码 | 代码 + 实测数据流 |
| 分支概率 | 猜 | profile 实测 |
| 优化范围 | 全程序一视同仁 | 只深度优化热点，冷代码先解释执行 |
| 推测错了怎么办 | 不敢推测 | 去优化（deopt）退回安全路径 |
| 代表 | gcc/clang -O2 | V8、HotSpot（C1→C2 分层编译） |

JIT 的两件招牌：**内联缓存**（V8 记住调用点见过的类型，直接生成直调）；**推测式优化 + deopt**（假设参数永远是某个类型，生成特化代码并带守卫，假设破了就地回退）。AOT 世界给不出这个能力——它编译时根本没有运行时可看。

原生世界也有"借运行时信息"的办法，思路是把信息喂回编译期而不是现场优化：PGO（先跑一遍带插桩的版本收集 profile，再带着 profile 重新编译）；更冷门的是 Linux 内核的 static key——运行时直接把指令补丁成 nop 或跳转。

口径澄清：口语里"运行时优化"有时指"给运行中的系统调优"（GC 参数、数据库调优），那是运维意义的调优；术语意义的"运行时优化"特指 JIT/动态优化这一族。

### 6. 一句话总结

运行时是"你的代码之外、你的程序之内"的那部分——时间段用法指它干活的时候，组件用法指它本体，环境用法指它打包后的样子。runtime error 是编译器管不了的行为错误在执行期爆雷；runtime optimization 是拿着执行期的真实数据做编译器不敢做的优化——同一个"运行时"，一面是风险，一面是红利。
