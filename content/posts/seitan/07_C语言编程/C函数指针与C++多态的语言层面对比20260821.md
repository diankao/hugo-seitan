# C函数指针与C++多态的语言层面对比

C 完全可以用函数指针 + struct 嵌套手写"继承 + 多态"，Linux 内核（VFS 的 `file_operations`）就是这么干的。那 C++ 的多态在语言层面到底是什么？一句话：**C 给的是机制（函数指针），C++ 给的是合同（由类型系统背书的分发规则）**。C++ 的多态不是"函数指针的语法糖"，而是把一种本来要手写的内存布局和调用约定，提升为类型系统认识的概念——由此获得语义保证、编译期检查和全自动维护。

## 手写对照：两边的代码

C 的手写版：

```c
struct animal_vt {
    void (*speak)(void *self);
    void (*destroy)(void *self);
};

struct animal {
    struct animal_vt const *vt;      /* 手写 vptr */
};

struct dog {
    struct animal base;              /* 手写"继承"：嵌基类 */
    int bark_count;
};

static void dog_speak(void *self)
{
    ((struct dog *)self)->bark_count++;
}

static void dog_destroy(void *self)
{
    free(self);
}

static struct animal_vt const DOG_VT = { dog_speak, dog_destroy };

struct animal *dog_create(void)
{
    struct dog *d = malloc(sizeof *d);
    d->bark_count = 0;
    d->base.vt = &DOG_VT;            /* 手动接线：忘了这行就是运行期炸弹 */
    return &d->base;                 /* 手动上转型：纯约定，编译器不管 */
}
```

C++ 版：

```cpp
struct Animal {
    virtual void speak() = 0;        // 纯虚：接口完整性由编译器强制
    virtual ~Animal() = default;
};

struct Dog : Animal {
    void speak() override { ++bark_count; }  // override：签名校验
    int bark_count = 0;
};
```

## 机器码层面是等价的

`a->speak()` 编译后就是"从对象头部取表指针、取槽位、间接跳转、把对象地址当第一个参数传"——`a->vt->speak(a)` 的翻版（Itanium/MSVC ABI 皆是如此）。**区别不在机器码，在于谁负责维护这套约定、错误在什么时候暴露。**

## 手写元素与语言特性的对照

| C 里手写的 | C++ 语言层对应的 | 多出来的保证 |
|------|------|------|
| struct 嵌套基类 | 继承声明 | 子类型关系进入类型系统 |
| 函数指针表 + 每个构造函数手动填 | 编译器生成的 vtable + 隐藏 vptr | 改基类接口，整棵继承树编译期报错 |
| 显式 `self` 参数 | 隐式 `this` | 调用约定统一 |
| `(struct animal *)&dog` 强转 | `Animal* a = new Dog;` 隐式上转型 | 编译器检查关系并做指针调整 |
| 接错指针没人管 | `override` / `final` | 签名不匹配、const 差异全在编译期暴露 |
| 接口靠自觉 | 纯虚函数 | 少实现一个函数，抽象类直接实例化不了 |
| 手写 destroy 指针 | 虚析构函数 | 经基类指针 delete 派生对象是良定义行为 |
| 手写 type tag | `dynamic_cast` / `typeid`（typeinfo 挂在 vtable 旁边） | 带检查的下转型 |
| 手动算地址偏移 | 多继承 this 指针调整 thunk | 语言保证转换正确 |

## 标准规定的是行为合同，不是 vtable

一个关键认知：**C++ 标准根本没有规定 vtable 和 vptr**。标准规定的是一份行为合同——什么调用派发到哪个函数、按什么规则检查。vtable 只是所有主流 ABI 不约而同选择的实现手法。这份合同里最有分量的几条：

- **构造期分发规则**：基类构造函数里调虚函数，派发到的是**基类自己的版本**（此时 vptr 还指着基类的表），这是良定义的；纯虚被调到则直接 `__cxa_pure_virtual` 崩溃。C 的手写版里"半初始化对象调到哪"没有任何规则，取决于指针填到哪一步
- **析构对称规则**：析构时 vptr 逆向回退，先派生后基类
- **协变返回类型**：子类重写可以返回更具体的类型，编译器生成 thunk 调整
- **名字查找规则**：派生类的一个 `f(double)` 会**隐藏**基类全部 `f` 重载（查找先于重载决议）——这条坑是语言规则，不是实现细节
- **`final` 存在的理由一半是优化**：编译器能证明静态类型时做去虚化（devirtualization），直接调用甚至内联

## 多态三件套：函数指针只能模拟其中一支

| 种类 | 机制 | 决议时机 | 成本 |
|------|------|------|------|
| 重载（ad-hoc） | 名字相同签名不同 | 编译期 | 零 |
| 模板（参数化） | 实例化时生成专用代码 | 编译期 | 零（还能内联） |
| 虚函数（子类型） | vptr → vtable | 运行期 | 一次间接寻址，不可内联 |

函数指针只能模拟**运行期**这一支。编译期这支是 C 模拟不了的：`std::sort` 之所以长期碾压 `qsort`，就是因为模板比较器**内联进排序循环**，而 `qsort` 的函数指针每次比较都是一次间接调用。这就是"零成本抽象"的另一半——**不用的东西不付钱，用的东西不比手写贵**。

## 真正的分水岭：错误暴露的时机

| 典型错误 | C 手写版 | C++ |
|------|------|------|
| 忘了初始化函数指针 | 运行期跳飞 | 不存在（vptr 自动设置） |
| 函数签名悄悄不匹配 | 运行期栈错乱 | 编译期（override） |
| 上转型转错偏移 | 运行期数据错乱 | 编译期（类型检查） |
| 派生类漏实现接口 | 运行期才发现 | 编译期（纯虚不可实例化） |

C 手写分发的所有错误都在运行期，C++ 的同类错误全部前移到编译期。当继承树有五层、三十个类、三个人维护时，这就是"能写 demo"和"能维护产品"的区别。

## 嵌入式成本账

| 项目 | 位置/开销 |
|------|------|
| vptr | 每个对象 +4/8 字节（RAM）——小对象别上虚函数，4 字节的结构会变 8 |
| vtable | 每个类一份，放 `.rodata`（Flash），通常还有 typeinfo、offset-to-top 两个隐藏槽 |
| 虚调用 | 两次 load + 间接跳转；单态调用点分支预测器能吃掉大部分开销 |
| 代价上限 | 无法内联（除非去虚化）——热路径上的小虚函数是性能杀手 |

顺带一句 Qt：信号槽**不是**虚函数分发——它是元对象系统里的回调注册表，解耦但多一层查表；Qt 里真正走虚函数的是 `event()`、`paintEvent()` 这条线。两套分发机制在同一个框架里并存，正好是"运行期多态的两种取舍"的活教材。

## 速记口诀

- C 给机制，C++ 给合同：函数指针表是手写实现技巧，virtual 是写进标准的分发规则
- 机器码等价（vptr + 表 + 间接跳转），差别在类型系统认不认识子类型关系
- 标准不规定 vtable，规定的是行为：构造期 vptr 渐进设置、析构逆向回退、纯虚崩溃
- override/final/纯虚 = 把运行期错误搬进编译期的三件工具
- 多态三件套：重载、模板（编译期零成本），虚函数（运行期一次间接）
- std::sort 赢 qsort 靠的是编译期多态 + 内联，函数指针给不了
- 嵌入式账本：vptr 占 RAM、vtable 占 Flash、热路径小虚函数不可内联
