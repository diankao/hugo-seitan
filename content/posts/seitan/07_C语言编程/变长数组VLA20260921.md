# 变长数组VLA

## 题目

什么是 VLA（变长数组）？为什么嵌入式编码规范一律禁用它？

## 考察点

C99 VLA 的语义与栈实现、静态栈分析为何失效、标准漂移史（C99/C11/C23/C++）、MISRA 与 Linux 内核的禁令、工程替代写法。

## 回答要点

### 1. 是什么

C99 引入的变长数组：长度是运行期表达式的局部数组。

```c
void process(int n)
{
    uint8_t buf[n];
    for (int i = 0; i < n; i++)
        buf[i] = 0;
}
```

`n` 不是常量，数组长度进函数那一刻才确定。配套的还有"变长类型"：`int arr[n][m]` 这样的二维形参、对 VLA 取 `sizeof` 会变成运行期求值。语法上很诱人——不用 malloc、不用拍脑袋定上限，长度刚刚好。

### 2. 关键属性：它在栈上分配

VLA 的实现就是运行时一条 `sub sp, r0`：长度多大栈指针就退多少，块结束再恢复，生命周期随作用域。它有个野生亲戚 `alloca()`——同样的运行时栈分配，连标准都没进。

致命后果：**编译期算不出这个函数的栈用量**。`-fstack-usage` 生成的 `.su` 文件里，含 VLA 的函数只会标一个 `dynamic`；"最深调用链求和"的静态估算法对它无解；水印实测的值换个输入就作废——栈大小三步法（估算、实测、余量）对 VLA 整体失效。

### 3. 危险链的经典形态

```c
void parse(const uint8_t *pkt, uint16_t len)
{
    uint8_t buf[len];
}
```

`len` 来自网络包——**攻击者可控**。20KB RAM 的 MCU 上来个 64KB 的 len，栈直接打穿；桌面端这是 2018 年 Stack Clash 漏洞家族的向量之一，GCC 为此专门加了 `-fstack-clash-protection`。RTOS 场景同样糟：VLA 吃的是所在任务的栈，任务栈配额从"设计值"变成"赌注"。

### 4. 标准的漂移史很能说明问题

| 时间 | 事件 |
|------|------|
| C99 | 引入 VLA |
| C11 | 降级为**可选**特性，实现可不支持（`__STDC_NO_VLA__` 标记） |
| C23 | 在类型层面改回强制 |
| C++ | 任何标准都**从未有过**，g++ 支持纯属性扩展 |

标准自己都犹豫过一轮。此外 VLA 与 `setjmp/longjmp` 的交互在历史上长期是未定义行为的重灾区。

### 5. 为什么嵌入式圈一律禁掉

- **MISRA C:2012 Rule 18.8 明令禁止**；AUTOSAR、Barr Group、JPL 等安全编码规范同样禁
- **Linux 内核 2018 年起全局 `-Werror=vla`**——几千万行 C 代码的工程表态：VLA 让最坏栈深不可证明
- 共同理由只有一条：**没有 MMU 兜底的系统里，栈深必须可静态证明**，VLA 破坏的正是这一条

### 6. 工程替代写法

| 需求 | 替代写法 |
|------|---------|
| 长度运行期才知道的缓冲 | 定长上限数组 + 实际长度参数（嵌入式标准姿势：`uint8_t buf[MAX_N]; int n;`） |
| 上限真不确定的大缓冲 | malloc / 内存池 |
| 结构体尾部变长数据 | C99 flexible array member（`struct { hdr_t hdr; uint8_t data[]; }` + 堆分配） |
| C++ | `std::vector`（堆）或固定容量容器 |

### 7. 一句话总结

**VLA 把"栈大小"从编译期可证明的问题变成运行期赌博**——所以从 MISRA 到 Linux 内核的选择高度一致：禁。想要"长度刚好"的优雅，用上限数组或堆去换，别在栈上赌。
