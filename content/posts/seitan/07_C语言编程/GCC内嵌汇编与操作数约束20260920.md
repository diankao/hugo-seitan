# GCC内嵌汇编与操作数约束

## 题目

在内嵌汇编中，可以将 C 语言表达式指定为汇编指令的操作数，不需要关心如何将 C 语言表达式的值读入哪个寄存器，以及如何将计算结果写回 C 变量。请给出示例并说明其机制。

## 考察点

GCC 扩展内嵌汇编（extended asm）的语法结构、操作数占位符与限定符、clobber 列表、volatile 的作用，以及嵌入式开发中真正需要内嵌汇编的场景。

## 回答要点

### 1. 基本内嵌汇编与扩展内嵌汇编

GCC 的 `asm` 有两种形态：

- 基本内嵌汇编：`asm("cpsid i")`，只有指令字符串，与外界 C 变量没有联系，寄存器要自己管
- 扩展内嵌汇编：带冒号分隔的操作数列表，C 表达式直接作为指令操作数，寄存器分配与数据搬运由编译器完成

题目描述的正是扩展内嵌汇编。写 `asm` 还是 `__asm__` 等价，后者在严格 ISO 模式（`-std=c99`）下也有效。

### 2. 最小示例

```c
int add(int a, int b)
{
    int result;
    __asm volatile (
        "add %0, %1, %2"
        : "=r"(result)
        : "r"(a), "r"(b)
    );
    return result;
}
```

逐段说明：

- `"add %0, %1, %2"` 是汇编模板，`%0`、`%1`、`%2` 是占位符，按顺序先对应输出操作数列表、再对应输入操作数列表里的 C 表达式：`%0` → result，`%1` → a，`%2` → b
- `"=r"(result)`：输出操作数，`=` 表示只写，`r` 表示任意通用寄存器
- `"r"(a)`、`"r"(b)`：输入操作数，寄存器由编译器自选
- ARM GCC 在 `-O2` 下可能只生成一条 `add r0, r0, r1`——a、b 本来就在 r0、r1，编译器让输出复用了 `%1` 的寄存器；若它选了别的寄存器，会在模板前后自动补 mov 把值搬进搬出。这些搬运代码一行都不用写，正是题干说的"不需要关心读写哪个寄存器"

### 3. 语法结构总览

```
asm [volatile] ( 汇编模板
                 : 输出操作数
                 : 输入操作数
                 : clobber 列表 );
```

常用约束字母：

| 约束 | 含义 |
|------|------|
| "r" | 任意通用寄存器（Thumb 下用 "l" 限定 r0~r7） |
| "m" | 内存操作数，直接用变量地址访问 |
| "i" | 编译期整数立即数 |
| "I" | ARM 数据处理指令合法立即数（8 位循环右移编码） |
| "0"、"1"… | 匹配约束，与指定编号的操作数共用寄存器 |

约束修饰符（加在输出操作数约束字母前面）：

| 修饰符 | 含义 |
|--------|------|
| = | 输出且只写 |
| + | 输出且可读可写（同一个操作数既当输入又当输出） |
| & | early clobber，该寄存器在指令用完全部输入之前就被改写，不能与输入复用 |

### 4. 嵌入式的真实需求：访问 C 表达不了的硬件

加法这种事编译器自己做得更好，内嵌汇编的刚需是 C 语言根本表达不了的动作——读写特殊寄存器、执行特权指令：

```c
static inline uint32_t enter_critical(void)
{
    uint32_t primask;
    __asm volatile ("mrs %0, primask" : "=r"(primask));
    __asm volatile ("cpsid i" ::: "memory");
    return primask;
}

static inline void exit_critical(uint32_t primask)
{
    __asm volatile ("msr primask, %0" :: "r"(primask) : "memory");
}
```

- `mrs`/`msr`/`cpsid` 在 C 里没有任何对应物，只能靠内嵌汇编
- 第二条 asm 没有输出操作数，输入段和 clobber 段之间两个冒号连写（`:::`）；clobber 列表写了 `"memory"`：告诉编译器这条指令影响内存可见性，防止优化器把前后的内存访问重排到临界区外
- CMSIS 里 `__disable_irq()` 的实现就是这一行 `cpsid`

### 5. volatile 与 "memory" clobber 的分工

一句话：`volatile` 保语句本身，`"memory"` 保语句两侧的内存访问，两者正交：

| | 管辖范围 | 具体承诺 |
|---|------|---------|
| `asm volatile` | 这**一条语句** | 有输出没人用也不许删、不许挪、不许合并 |
| `::: "memory"` | 语句**两侧的内存访问** | 缓存在寄存器里的内存值作废重读、排队的写先落盘、访问不得跨越重排 |
| C 的 volatile 变量 | **一个变量** | 对它的每次访问都是真访存、按序、不省略 |

后两行是一对偶：volatile 变量是"所有语句管一个变量"，memory clobber 是"一条语句管所有变量"。Linux 内核的 `barrier()` 宏一行讲清全部分工：

```c
#define barrier() __asm__ __volatile__("" ::: "memory")
```

模板是空的：`volatile` 让编译器别把这个空语句当无副作用的垃圾删掉，`:::"memory"` 让它前后的内存访问重新过内存。拆掉 `volatile`，空语句被优化消失；拆掉 `"memory"`，语句还站着但什么都没拦住。

只加 `volatile` 不加 `"memory"` 的经典漏洞（对照第 4 节的临界区）：

```c
__asm volatile ("cpsid i");
x = shared_buf[0];
__asm volatile ("cpsie i");
```

GCC 文档明说 volatile asm 的位置保证很弱，编译器可能把 `shared_buf[0]` 的加载提到 `cpsid` 之前——它不知道这条指令和内存有什么关系，临界区漏风。`"cpsid i" ::: "memory"` 才把门焊死。

还有一个必须澄清的边界：`"memory"` 只是**编译器屏障**，不管 CPU 乱序和缓存一致性。单核 MCU 上"关中断 + memory clobber"够用——关了中断就没人竞争；多核或 DMA 参与时需要真硬件屏障，CMSIS 的 `__DMB()` 因此写成 `dmb` 指令 + `"memory"` 的双层叠加：编译器屏障拦编译器，CPU 屏障拦 CPU。

口诀：volatile 保语句，"memory" 保内存访问，DMB 保 CPU。

### 6. 常见坑

- `volatile`：告诉编译器这条汇编有输出操作数之外的副作用，不许删除、不许挪动、不许多余执行。凡是访问硬件、含特权指令的 asm 都应加上
- 对优化器撒谎：指令实际改了某个寄存器却没进 clobber 列表，编译器可能把别的变量分配到这个寄存器上
- 占位符方向随架构走：ARM 汇编目的操作数在前（`add %0, %1, %2`），x86 AT&T 语法目的操作数在后，模板必须按目标架构写，同一份代码跨架构不能直接用

### 7. 命名操作数

占位符多了以后 `%0`、`%1` 的对应关系难读，可以给操作数命名：

```c
static inline uint32_t get_primask(void)
{
    uint32_t mask;
    __asm volatile ("mrs %[mask], primask" : [mask] "=r"(mask));
    return mask;
}
```

### 8. 为什么 CMSIS 之类的头文件喜欢 __ 开头

C/C++ 标准把一批命名空间划给"实现"（编译器及其标准库），用户代码禁止使用：`__` 开头和 `_`+大写字母开头处处保留，`_`+小写字母开头在文件作用域保留（C++ 里 `__` 出现在标识符中间也算）。

CMSIS 住进保留区有两个理由。其一，它的头文件被几乎所有用户代码 include，符号必须全球零冲突——叫 `disable_irq` 迟早撞上某人的宏，`__disable_irq` 永远安全。其二，`__disable_irq` 本来就是 ARM 编译器（armcc/armclang）的内置 intrinsic 名字，CMSIS 在 GCC 上只是用内嵌汇编模拟同名函数，IAR、armclang、GCC 三家最终指向同一个名字——`__` 是编译器 intrinsic 的家族姓氏。

同族惯例：`__builtin_*`（GCC/Clang 内建）、`__attribute__`、`__declspec`、glibc 的 `__libc_*`；Linux 内核还用 `__` 做安全分级——`readl()` 自带屏障，`__raw_readl()` 是无屏障的原始版；C 标准自己加的关键字也走保留区（`_Bool`、`_Static_assert`）。

反面警示：用户代码自己发明 `__my_var` 属于违章建筑，编译器升级后可能撞上新保留名；MISRA C（Rule 21.1/21.2）明令禁止用户定义 `_`/`__` 开头的标识符。`__` 不是装饰，是"此名 reserved for implementation"的契约。
