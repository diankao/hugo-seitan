# 智能指针线程安全分析

## 题目

智能指针是线程安全的吗？`shared_ptr` 在多线程下有哪些坑？

## 考察点

C++ 智能指针的引用计数机制、原子操作、`shared_ptr` 的线程安全边界。

## 回答要点

### 1. 先厘清"哪一层"的线程安全

讨论 `shared_ptr` 的线程安全，必须区分**两个层面**：

| 层面 | 是否线程安全 | 说明 |
|------|------------|------|
| 控制块（引用计数） | **是** | `shared_ptr` 的引用计数增减是原子操作，多线程拷贝/析构不同 `shared_ptr` 对象（指向同一控制块）是安全的 |
| 指向的对象本身 | **否** | 多线程通过不同的 `shared_ptr` 读写同一个对象，和裸指针一样有数据竞争，需自行加锁 |
| 同一个 `shared_ptr` 对象 | **否** | 多线程对**同一个** `shared_ptr` 变量做读写（赋值、reset）是数据竞争 |

```cpp
// 关键区分：是「同一个 shared_ptr 变量」还是「多个 shared_ptr 副本」
auto p = std::make_shared<int>(0);

// 场景 A：多个线程各自拷贝一份 p，操作各自的副本 → 安全（引用计数层面）
std::vector<std::thread> ts;
for (int i = 0; i < 4; ++i)
    ts.emplace_back([p]() {         // 拷贝 p，引用计数原子 +1/-1
        auto local = p;             // 安全
        (*local)++;                 // 不安全！操作的是同一份 int
    });

// 场景 B：多个线程直接对同一个变量 p 做 reset/赋值 → 不安全
std::thread t1([&p]() { p.reset(); });      // 数据竞争
std::thread t2([&p]() { p = nullptr; });    // 数据竞争
```

### 2. 引用计数为什么是线程安全的

`shared_ptr` 内部维护一个控制块，包含：

```cpp
// 控制块简化结构
struct control_block {
    std::atomic<long> strong_count;   // 强引用计数（原子）
    std::atomic<long> weak_count;     // 弱引用计数（原子）
    void (*deleter)(void*);
    void* managed_object;
};
```

`shared_ptr` 拷贝时执行 `strong_count.fetch_add(1, memory_order_relaxed)`，析构时 `strong_count.fetch_sub(1, memory_order_acq_rel)`。这两个原子操作保证：**任意时刻多个线程拷贝/析构不同的 `shared_ptr` 副本，计数一定准确，不会泄漏也不会双重释放。**

```cpp
// 模拟引用计数的原子操作
class shared_ptr_sim {
    control_block* cb;
public:
    shared_ptr_sim(const shared_ptr_sim& o) : cb(o.cb) {
        cb->strong_count.fetch_add(1, std::memory_order_relaxed);
    }
    ~shared_ptr_sim() {
        if (cb->strong_count.fetch_sub(1, std::memory_order_acq_rel) == 1) {
            delete cb->managed_object;
            delete cb;
        }
    }
};
```

### 3. 指向对象的访问不是线程安全的

这是最常见的陷阱：很多人误以为"用了 `shared_ptr` 就线程安全了"，实际上它只管指针本身的生命周期，不管对象内容。

```cpp
auto sp = std::make_shared<std::vector<int>>();

// 两个线程同时 push_back → 数据竞争，可能崩溃
std::thread t1([&sp]() { for(int i=0;i<1000;++i) sp->push_back(i); });
std::thread t2([&sp]() { for(int i=0;i<1000;++i) sp->push_back(i); });
// 必须加锁保护对 *sp 的访问
```

### 4. 同一个 `shared_ptr` 变量的并发读写

即使引用计数是原子的，**对一个 `shared_ptr` 变量本身**的赋值、reset、拷贝构造在 C++ 标准里仍不是线程安全的（标准规定 `shared_ptr` 的成员函数对同一实例的并发访问是未定义行为，但不同实例指向同一控制块是安全的）。

```cpp
// 需要并发改写同一个 shared_ptr 时，有三种正确做法：

// 方案 1：std::atomic<std::shared_ptr<T>>（C++20）
std::atomic<std::shared_ptr<Config>> cfg;
std::thread writer([&]() {
    cfg.store(std::make_shared<Config>(...));   // 原子替换
});
std::thread reader([&]() {
    auto p = cfg.load();                        // 原子读取
    p->use();
});

// 方案 2：用互斥锁包一层
std::mutex m;
std::shared_ptr<Config> cfg;
void update() {
    std::lock_guard<std::mutex> lk(m);
    cfg = std::make_shared<Config>(...);
}
std::shared_ptr<Config> get() {
    std::lock_guard<std::mutex> lk(m);
    return cfg;     // 在锁内拷贝出副本，之后使用副本无需持锁
}

// 方案 3：free 函数 std::atomic_load/std::atomic_store（C++11~17，C++20 已弃用）
auto p = std::atomic_load(&cfg);
std::atomic_store(&cfg, std::make_shared<Config>(...));
```

### 5. 各种智能指针的线程安全性对比

| 智能指针 | 引用计数原子？ | 同一实例并发读写安全？ | 适用多线程共享？ |
|---------|---------------|---------------------|----------------|
| `unique_ptr` | 无计数（独占） | 否 | 通常不共享，需外部同步 |
| `shared_ptr` | 是（控制块原子） | 否（不同实例共享同一控制块才安全） | 可，但访问对象需加锁 |
| `weak_ptr` | 依赖 `shared_ptr` 计数 | 同 `shared_ptr` | 用于观察，`lock()` 提升时仍需注意 |
| `auto_ptr`（已废弃） | 无 | 否 | 不推荐 |

### 6. `weak_ptr` 在多线程中的典型用法：解决悬空

`weak_ptr` 不增加强引用计数，常用于缓存、观察者模式。多线程下 `weak_ptr::lock()` 是安全的（原子地尝试提升为 `shared_ptr`）：

```cpp
class Cache {
    std::unordered_map<int, std::weak_ptr<Resource>> map;
    std::mutex m;
public:
    std::shared_ptr<Resource> get(int key) {
        std::lock_guard<std::mutex> lk(m);
        auto it = map.find(key);
        if (it != map.end()) {
            if (auto sp = it->second.lock()) {   // 原子提升，避免悬空
                return sp;
            }
        }
        auto sp = std::make_shared<Resource>(key);
        map[key] = sp;
        return sp;
    }
};
```

### 7. 线程安全的对象发布模式

推荐做法：**用不可变对象 + 原子替换 `shared_ptr`**，避免对对象本身加锁（Copy-On-Write 思想）。

```cpp
struct Config {           // 不可变对象
    int timeout;
    std::string host;
    // 所有字段 const 或不加修改
};

std::atomic<std::shared_ptr<const Config>> g_cfg;

void reload() {           // 后台线程：整体替换
    auto neo = std::make_shared<const Config>(...);
    g_cfg.store(neo);
}

void use() {              // 工作线程：快照后使用，无需加锁
    auto snap = g_cfg.load();
    do_work(snap->timeout, snap->host);
}
```

这种模式的好处：读取端无锁，对象不可变天然线程安全，更新端原子替换整体一致。

### 8. 平台 / 实现差异

- **GCC/libstdc++**：`shared_ptr` 引用计数使用 `__atomic_fetch_add`，是无锁原子。
- **MSVC**：同样使用原子操作，并优化了控制块布局。
- **C++20 之前**：标准库的 `shared_ptr` 本身不是"原子类型"，需要用 `std::atomic_load/store` 全局函数；C++20 新增 `std::atomic<std::shared_ptr<T>>` 才是真正的一等原子类型。

## 扩展问题

面试官可能会追问：
- `make_shared` 和 `new` + `shared_ptr` 构造的区别？（前者单次分配、控制块与对象同块，但内存延迟释放；后者两次分配）
- 为什么引用计数用原子操作而不是加锁？（性能、避免锁开销，且控制块可能被任意线程访问）
- `shared_ptr` 的循环引用如何解决？（用 `weak_ptr` 打破环）
- 控制块是什么时候创建的？（首次从 `make_shared` 或 `shared_ptr(new T)` 构造时；`make_shared` 合并分配）
