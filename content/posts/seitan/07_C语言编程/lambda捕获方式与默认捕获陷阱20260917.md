# lambda捕获方式与默认捕获陷阱

## 题目

lambda 的 `[=]` 和 `[&]` 是什么意思？`[=]` 明明是按值捕获，为什么还可能导致悬垂引用？实际项目中应该如何选择捕获方式？

## 考察点

捕获语法家族、按值/按引用捕获的底层差异（闭包成员的形态）、默认捕获 `[=]` 的隐式行为与 this 指针陷阱、异步场景下的生命周期问题、显式最小捕获原则。

## 回答要点

### 1. 捕获语法家族一览

| 写法 | 含义 |
|------|------|
| `[]` | 不捕获（可转换为普通函数指针） |
| `[x]` | 捕获 x，按值拷贝 |
| `[&x]` | 捕获 x，存引用 |
| `[=]` | **默认按值**：函数体里用到谁就拷谁 |
| `[&]` | **默认按引用**：用到谁就存谁的引用 |
| `[=, &y]` / `[&, x]` | 混合：默认按值但 y 例外 / 默认按引用但 x 例外 |
| `[this]` | 捕获 this 指针（拷贝的是指针本身） |
| `[*this]`（C++17） | 拷贝整个当前对象 |
| `[v = std::move(x)]`（C++14） | 初始化捕获：可 move、可改名、可存表达式结果 |

两条基本规则：

- **"用到才捕"**：默认捕获只拷贝/引用函数体里实际出现的外层变量，不是把整个作用域搬进闭包；
- **捕获发生在 lambda 定义那一刻**：按值拷的是当时的快照，按引用存的是当时变量的地址。

### 2. 按值与按引用的底层差异

lambda 是编译器生成的匿名闭包类，捕获变量就是它的成员（脱糖细节见《lambda表达式本质与实现机制》《闭包的C与C++实现》）：

```cpp
int x = 10;
auto f = [x](int a) { return a + x; };   // 成员 int x;  构造时拷贝 → 快照
auto g = [&x](int a) { return a + x; };  // 成员 int& x; 构造时存引用 → 跟随原变量
```

值捕获想修改闭包里的副本，需要 `mutable`（去掉 `operator()` 的 const），且改的是副本、原变量不受影响。

### 3. `[=]` 最大的坑：一半值语义、一半引用语义

在成员函数里写 `[=]`，看起来"全部按值拷贝"，实际语义是分裂的：

```cpp
class Widget {
    int value = 10;
    void test() {
        int local = 5;
        auto f = [=] { return value + local; };
        // 实际捕获：
        //   local → 按值拷贝，真快照，local 析构后闭包里还有副本
        //   value → 根本没被拷贝！拷的是 this 指针，经指针访问成员 → 引用语义
        auto g = [local, this] { return value + local; };   // f 的显式等价物
    }
};
```

**`[=]` 对局部变量是值语义，对成员变量是引用语义**（经 this 指针）。如果这个 lambda 被异步调用（定时器、线程、网络回调），而对象已经析构：`local` 还活着，`value` 已经悬垂——同一个闭包里两种生死。这是默认捕获最阴险的地方，也是 Effective Modern C++ 条款 31《避免使用默认捕获模式》的核心论据。

### 4. 隐式捕获的意外性

默认捕获的捕获集合由**函数体写了什么**决定，维护时容易悄悄变化：

```cpp
auto f = [=] { return a + b; };   // 捕获 a、b
// 后来维护者加了一行：
auto f = [=] { log(c); return a + b; };   // c 被默默捕获！
```

- `[=]` 的后果是多拷贝一个对象（性能损失，通常无害）；
- `[&]` 的后果严重得多：新引用的变量若是栈上对象，lambda 出域后调用即悬垂。

显式捕获（`[a, b]`、`[this]`）的捕获集合一眼可见，review 时新变量混进闭包立刻能发现。

### 5. 异步场景：悬垂的重灾区

```cpp
// 陷阱一：[&] 捕获局部变量 + 异步执行
void start() {
    int taskId = 42;
    std::thread([&]{ process(taskId); }).detach();   // taskId 出域后悬垂
}

// 陷阱二：[=] 捕获 this + 对象先死
class Worker {
    void start() {
        QTimer::singleShot(1000, [=]{ cleanup(); });  // [=] 实际只捕了 this
    }                                                  // 1 秒后对象可能已析构
};
```

修复手段按场景选：

```cpp
std::thread([taskId]{ process(taskId); }).detach();   // 需要的值单独按值捕获
QTimer::singleShot(1000, this, [this]{ cleanup(); }); // Qt：带 context 对象，析构自动断连
auto task = std::make_shared<Task>();
std::thread([task]{ task->run(); }).detach();          // shared_ptr 延长生命周期
[*this]{ ... };                                        // C++17：拷贝整个对象副本
```

### 6. C++20 的态度：弃用 `[=]` 隐式捕获 this

标准已经确认 `[=]` 里隐式捕获 this 是坏实践并予以弃用，想捕获必须显式：

```cpp
[=, this] { ... };    // 显式说明捕获 this 指针
[=, *this] { ... };   // 显式拷贝整个对象
```

方向很明确：**捕获应该写出来，而不是让编译器猜**。

### 7. 实践原则：显式最小捕获

| 场景 | 推荐写法 |
|------|---------|
| 只用到类成员 | `[this]` |
| 用到少量局部变量的值 | `[x, y]` 逐个列出 |
| 确需引用且同步执行（算法内） | `[&x]`，确认 lambda 生命周期短于变量 |
| 大对象想转移进闭包 | `[v = std::move(obj)]`（C++14 初始化捕获） |
| 异步 + 需要对象存活 | `[*this]` 或 `shared_ptr` 按值捕获 |
| Qt 信号槽 | `[this]` / `[this, i]` + context 对象（见《在Qt5的信号处理中如何使用lambda机制》） |

核心一句话：**用到什么捕获什么，值还是引用写明白，让捕获列表成为闭包的"资产负债表"**。

## 扩展问题

- 初始化捕获 `[v = std::move(p)]` 解决了 C++11 的什么缺陷？（无法 move 捕获，只能借助 bind 技巧）
- 闭包对象的大小怎么估？（值捕获各成员大小之和 + 对齐；引用捕获每项一个指针）
- `[&]` 在 STL 算法里（`std::sort` 的比较器）为什么通常安全？（算法同步执行完才返回，引用始终有效）
