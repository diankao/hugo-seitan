# 为什么嵌入式不用MSVC

## 题目

是不是没有用 MSVC 编译嵌入式程序的？嵌入式编译器的真实格局是怎样的？

## 考察点

MSVC 的目标边界（Windows ABI、PE/COFF、MSVCRT）、裸金属工具链的刚需（ELF/DWARF、可重定向 libc、链接脚本）、宿主机与目标机的角色区分、嵌入式编译器格局、与 MMU 分界线的重合。

## 回答要点

### 1. 基本正确：MSVC 出不了 Windows 生态圈

MSVC 的后端只支持**跑 Windows 的目标**：x86、x64、ARM/ARM64，产物是 PE/COFF + PDB，C 库是 MSVCRT。而裸金属编译要的是完全另一个世界的东西：

| 嵌入式工具链的刚需 | MSVC 的情况 |
|------|------|
| ELF + DWARF（bin/hex/elf 镜像） | 只出 PE/COFF + PDB |
| newlib/picolibc 这类可重定向 libc | MSVCRT 不可裁剪移植 |
| 链接脚本分内存区（FLASH/RAM/CCM） | 没有对应机制 |
| Cortex-M/RISC-V/AVR/Xtensa 后端 | 全部不存在 |
| JTAG/SWD + 厂商调试器工作流 | 不在其服务范围 |

商业逻辑更直接：微软的编译器为 Windows 应用生态服务，MCU 不跑 Windows，就没有生意可做。

### 2. 但"嵌入式开发"不等于"嵌入式编译"

宿主机这一侧反而是 Windows 的主场：Keil µVision、IAR EWARM 这些 IDE 跑在 Windows 上，闪录工具、调试前端、给硬件配套的上位机程序（Qt 在 Windows 上常配 MSVC）全在 Windows 里。准确的画面是：**嵌入式工程师坐在 Windows 里干活，但编译固件的编译器从来不是微软的**。这也是 `__attribute__`/`__declspec` 两家方言需要 CMSIS 裹宏的原因。

### 3. 嵌入式编译器的真实格局

- **GCC**（arm-none-eabi、riscv、ESP-IDF 的 xtensa）：开源事实标准
- **IAR**：汽车/功能安全认证之王（ISO 26262 认证编译器）
- **armclang**（Keil MDK v6）：IDE 王朝，编译器内核已换成 LLVM/Clang
- 细分市场：Green Hills（安全关键）、TASKING（英飞凌 TriCore）、SDCC（51/PIC）、Cosmic（STM8）——SDCC 这个 8 位机开源编译器的细节详见《什么是SDCC》
- 趋势是整体 LLVM 化——armclang、Zephyr 的 clang 支持、嵌入式 Rust 全在 LLVM 上；`clang-cl` 甚至会讲 MSVC 方言，是两边都会的双语者

### 4. 微软摸过嵌入式的几次，全在 MMU 另一侧

- **Windows CE + eMbedded Visual C++（eVC）**：史上最接近的一次，Pocket PC 时代的正统微软嵌入式工具链——CE 已退场，eVC 成文物
- **Windows 10 IoT Core**：树莓派上跑 UWP——但那是"带通用 OS 的单板机"那一侧，不是裸金属
- **x86 工控机/POS 机**：跑完整 Windows 的"嵌入式设备"，MSVC 编译毫无障碍——但本质是桌面 Windows 换了个铁壳，还是 A 核 + MMU + 通用 OS 那一侧

规律很干净：**微软只出现在有 MMU、跑通用操作系统的那一段**。MSVC 是"通用操作系统世界的编译器"，跨不过去的与其说是技术线，不如说是 Windows ABI 这条商业边界——而这条边界与单片机/单板机的分界线几乎重合。裸金属那一侧（Cortex-M、RISC-V、51），从没有过微软的编译器。

### 5. 一句话总结

MSVC 跨不过 Windows ABI 这条线，这条线又与 MMU 分界线重合：通用 OS 那侧是微软的地盘，裸金属这侧属于 GCC/IAR/armclang——所以嵌入式的世界里"Windows 只当工作台，不当工具链"。
