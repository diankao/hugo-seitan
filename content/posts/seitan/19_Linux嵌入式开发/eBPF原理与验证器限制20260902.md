# eBPF 原理与验证器限制

eBPF（extended Berkeley Packet Filter）让用户态程序把字节码安全地注入内核执行，是现代 Linux 可观测性与网络数据面的基础设施。本文整理它的执行链路、验证器约束、最小可运行示例、map 与挂载点清单，以及工具链选型。

## 执行链路

```
用户态编译 LLVM → bpf() syscall 加载
      ▼
验证器 verifier：静态检查（无越界、无死循环、合法指针）
      ▼
JIT 编译成本机指令（或解释执行）
      ▼
挂载点执行：kprobe/tracepoint/XDP/sockmap…
      ▼
结果经 map / perf buffer 回传用户态
```

## 验证器施加的约束

验证器（verifier）在加载时静态证明程序的安全性，由此带来几条硬性限制：

- **不能直接修改内核数据结构**：指针访问规则严格，任意内核写被禁止，写操作只能通过白名单 helper（如写 skb 字段的专用 helper）；
- **栈空间 512 字节**：每个函数帧的经典上限，大缓冲必须放 map（`BPF_MAP_TYPE_PERCPU_HASH` 等）或用 BPF to BPF 调用分层；
- **循环有界**：早期版本完全禁止循环，新内核允许可证明有界的循环；
- **无法调用任意内核函数**：只能调用 helper 白名单（`bpf_probe_read_kernel`、`bpf_ktime_get_ns`、`bpf_map_update_elem`…）。

读取内核内存的标准姿势是 helper `bpf_probe_read_kernel()`——它处理缺页与地址合法性，是 kprobe 里抓取内核数据的安全通道（用户态对应 `bpf_probe_read_user`）。

## 三层工具链：从一行命令到 C 程序

### bpftrace：一行式探针（排查首选）

```bash
# 统计哪个进程在频繁 open 文件
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'

# openat 的延迟分布（直方图）
bpftrace -e 'kprobe:__x64_sys_openat { @t[pid] = nsecs; }
             kretprobe:__x64_sys_openat /@t[pid]/ {
                 @us = hist((nsecs - @t[pid]) / 1000); delete(@t[pid]);
             }'
```

无需编译、即时生效，语法是 awk 风格的 `探针 /过滤/ { 动作 }`。生产排查 80% 的观测需求到这层就够了。

### BCC：Python 前端（复杂工具的开发框架）

```python
from bcc import BPF
b = BPF(text='''
#include <uapi/linux/ptrace.h>
int hello(struct pt_regs *ctx) {
    bpf_trace_printk("openat by pid %d\\n", bpf_get_current_pid_tgid());
    return 0;
}''')
b.attach_kprobe(event="__x64_sys_openat", fn_name="hello")
b.trace_print()
```

`biolatency`、`opensnoop`、`execsnoop` 等知名工具都是 BCC 写的，运行时编译（依赖目标机内核头文件）。

### libbpf + CO-RE：编译一次到处运行（现代标准）

```c
// minimal.bpf.c —— 编译为 minimal.bpf.o，skeleton 加载
#include "vmlinux.h"            // 内核类型定义（BTF 生成，CO-RE 核心）
#include <bpf/bpf_helpers.h>

SEC("tracepoint/syscalls/sys_enter_openat")
int handle_openat(void *ctx)
{
    char msg[] = "openat called";
    bpf_printk("%s", msg);      // 输出到 /sys/kernel/debug/tracing/trace_pipe
    return 0;
}
char LICENSE[] SEC("license") = "GPL";   // 内核要求显式声明
```

```bash
clang -target bpf -O2 -g -c minimal.bpf.c -o minimal.bpf.o   # 需内核 BTF（/sys/kernel/btf/vmlinux）
bpftool prog load minimal.bpf.o /sys/fs/bpf/minimal          # 挂载
cat /sys/kernel/debug/tracing/trace_pipe                       # 看输出
```

## map：内核态与用户态的数据通道

| 类型 | 用途 |
| --- | --- |
| `BPF_MAP_TYPE_HASH` | 通用键值（统计聚合） |
| `BPF_MAP_TYPE_ARRAY` | 定长数组（全局配置/计数） |
| `BPF_MAP_TYPE_PERCPU_HASH/ARRAY` | 每 CPU 一份，无锁，读取时汇总 |
| `BPF_MAP_TYPE_LRU_HASH` | 自动淘汰的哈希 |
| `BPF_MAP_TYPE_RINGBUF` | **事件流回传用户态**（新，替代 perf event array） |
| `BPF_MAP_TYPE_STACK_TRACE` | 抓调用栈 |

用户态用 `bpftool map dump` 或 libbpf API 读。典型观测程序 = eBPF 侧聚合进 map + 用户态轮询打印。

## 常见挂载点

| 挂载点 | 触发时机 | 典型用途 |
| --- | --- | --- |
| kprobe/kretprobe | 内核函数进出（不稳定接口） | 函数级 tracing、延迟测量 |
| tracepoint | 内核静态埋点（稳定） | syscall、调度事件 |
| perf_event | 周期采样 | CPU profile（通常配 perf） |
| **XDP** | 网卡收包最早点 | DDoS 过滤、负载均衡（性能最高） |
| tc | 流量控制点 | 包修改、限速 |
| socket filter / sockmap | socket 层 | 包过滤、socket 加速/splice |
| cgroup | cgroup 事件 | 设备/网络隔离策略 |

## eBPF vs 内核模块

| | eBPF | 内核模块 (LKM) |
| --- | --- | --- |
| 加载校验 | 验证器证明安全 | 无校验，一个野指针就 panic |
| 可做的事 | helper 白名单内的读/受限写 | 任意内核 API |
| 崩溃影响 | 验证器保证不崩内核 | 直接 oops/panic |
| 典型用途 | tracing、观测、XDP 转发 | 驱动、新子系统 |

一句话：**eBPF 用表达能力换安全**——观测与网络数据面首选；真正的设备驱动仍然要写内核模块（参见 [Linux内核模块常见崩溃场景](../19_Linux嵌入式开发/Linux内核模块常见崩溃场景20260902.md)）。

JIT：内核编译开启 `CONFIG_BPF_JIT` 后程序编译为本机指令（`/proc/sys/net/core/bpf_jit_enable` 控制），多数发行版默认开启；严格说 JIT 关闭时可用解释器兜底，但生产与主流口径都以"依赖 JIT"为准。
