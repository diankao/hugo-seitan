# Linux 内核模块常见崩溃场景

内核模块跑在最高特权级，没有内存保护兜底，几类典型错误会直接把系统带崩。本文整理最常见的崩溃场景：原子上下文睡眠、用户指针未校验、凭证对象乱改，解释 oops 与 panic 的分级，并给出防御性写法清单。

## 原子上下文睡眠：scheduling while atomic

**在中断、软中断或自旋锁持有的上下文中调用可能睡眠的函数**，是最经典的崩溃原因。典型如 `kmalloc(GFP_KERNEL)`：

- `GFP_KERNEL` 允许分配器在内存紧张时回收页、**睡眠等待**；
- 原子上下文里 schedule 会触发 `BUG: scheduling while atomic`，轻则 oops 重则 panic。

原子上下文应改用 `GFP_ATOMIC`（从预留池分配，可能失败，必须判空）。判断当前是否原子上下文：持有自旋锁、`in_interrupt()` 为真、中断已关闭，都算。

## 用户指针未校验

`__user` 标注的指针来自用户态，可能是非法/已换出/恶意的地址。内核直接解引用：

- 轻则 oops：`unable to handle kernel paging request`；
- 有 SMAP 的 CPU 上直接 fault；
- 更糟的是可能被利用为任意读/写漏洞。

正确做法：`access_ok()` 检查地址范围 + `copy_from_user/copy_to_user` 拷贝访问，绝不直接解引用。

## 凭证对象乱改

`current->cred` 有 cred guard 与 RCU 保护。直接改写字段会破坏引用计数与安全模型——轻则内存泄漏/panic，重则形成本地提权漏洞。合规路径是 `prepare_creds()` 复制 → 修改 → `commit_creds()` 提交，而且普通驱动模块根本不该碰。

## 崩溃分级：oops vs panic

| | oops | panic |
| --- | --- | --- |
| 含义 | 内核捕获的非法操作，打印现场后**当前进程**被杀 | 内核进入致命态，**整机停摆**（`panic=` 参数决定挂起或重启） |
| 典型原因 | 驱动解引用坏指针 | 原子上下文睡眠、临界资源破坏 |
| 现场 | dmesg 里的 call trace + 寄存器 | 最后一次打印 |

驱动里触发的 oops 通常表现为触发进程被杀、模块状态残废，之后往往连锁 panic——工程上都要按"崩溃"处理。

## 一个反例：不算崩溃的错误

未实现 `file_operations.release` 只是**资源泄漏**（引用计数、内存不释放），不会崩溃——它属于慢性问题，与上面几类"立刻崩"的错误要区分开。

## 读懂一份 oops 日志

模块崩了之后第一现场就是 dmesg 里这段日志，逐行拆一份典型样例：

```
BUG: unable to handle kernel NULL pointer dereference, 0000000000000008
PGD 0 P4D 0
Oops: 0000 [#1] SMP PTI
CPU: 3 PID: 1024 Comm: mytest Tainted: G           O 6.1.0      ← ① O=加载了外部模块
RIP: 0010:my_ioctl+0x1a/0x60 [mymod]                ← ② 出错指令：模块 mymod 的 my_ioctl+0x1a
Code: ...（出错指令机器码）
RSP: ... EFLAGS: ...
RAX: 0000000000000000 RBX: ... RCX: ...             ← ③ 现场寄存器
...
CR2: 0000000000000008                                ← ④ 触发缺页的地址（NULL+8，对上了！）
---[ end trace 0000000000000000 ]---
Call Trace:                                          ← ⑤ 调用链（自下而上是调用者）
 <TASK>
 my_ioctl+0x1a/0x60 [mymod]
 vfs_ioctl+0x14/0x30
 __x64_sys_ioctl+0x64/0xa0
 do_syscall_64+0x3d/0x90
 entry_SYSCALL_64_after_hwframe+0x6e/0xd6
 </TASK>
Modules linked in: mymod(O+) crc32 ...               ← ⑥ 崩溃时已加载模块（O=正在加载中）
```

定位到源码行的三步：

```bash
# 1. 从 RIP 的偏移反解源码行（模块要带 -g 编译）
addr2line -e mymod.ko -f -i $(printf %x $((0x1a)))
#    或直接反汇编看指令上下文
objdump -dS mymod.ko | less   # 找 <my_ioctl> 段，比对 +0x1a

# 2. 内核符号路径不同时，用 /proc/kallsyms 或 gdb
gdb mymod.ko
(gdb) list *(my_ioctl+0x1a)

# 3. 结合 CR2 与寄存器还原语义：RAX=0、CR2=0x8
#    → 大概率是 dev->private 之类字段没初始化就解引用（NULL+8 是结构体偏移）
```

阅读要点：**RIP 是"哪里崩"**（模块函数名+偏移，带 `[模块名]` 才是你的代码）、**CR2 是"访问了什么地址"**（NULL/野指针/越界的直接证据）、**Call Trace 是"怎么走到这的"**（从下往上读）、Modules linked in 里 **(O)** 表示加载中出错。`Tainted: G O` 的 O 就是外部模块标记——内核维护者看到 O 会先让你复现于无模块环境。

辅助开关：`/proc/sys/kernel/panic_on_oops`（oops 即 panic，高可用系统常用）、`kdump`+`crash` 抓完整转储、内核配置 `CONFIG_DEBUG_INFO` 让 addr2line 有行号可查。

## 防御性写法清单

- 分配：可睡眠上下文用 `GFP_KERNEL`，中断/锁内用 `GFP_ATOMIC`，DMA 用对应 `GFP_DMA*`；
- 用户指针：一律 `copy_from_user/copy_to_user`，长度先 `access_ok`；
- 全局变量并发：先想清楚上下文（进程/软中断/硬中断），再选锁（mutex/spinlock/spin_lock_irqsave）；
- 出口路径：probe 失败回滚、release 补齐资源释放。
