### Q2：为什么选 STM32H7 而不是 F4/F7？

> （考察：芯片选型能力、对硬件资源需求的理解）

**候选人回答：**

> 因为外设资源要求高，我需要 6 根 SPI 全部用满（4 路 SPI DMA 接收 + 1 路 SPI 发送命令 + 1 路 SPI 驱动 WiFi），还要 UART 收发指令、I2C 驱动屏幕。因为采样率高所以 FIFO 要求大，H743 的 AXI SRAM 足够放下 160KB 的 FIFO。480MHz 的算力具体怎么算还没完全想清楚。

**面试官点评：**

| 评价项      | 结果    | 说明                                                     |
| -------- | ----- | ------------------------------------------------------ |
| 外设需求     | ✅ 好   | 6 路 SPI + UART + I2C，说清了为什么 F4（最多 3 路 SPI）不行           |
| 存储需求     | ✅ 好   | 提到了 160KB FIFO 对 RAM 的要求，H743 有 1MB AXI SRAM           |
| 算力论证     | ⚠️ 不足 | "还没想好怎么算"是减分项，面试官会追问到底                                 |
| F4/F7 对比 | ⚠️ 缺失 | 没有明确说 F4/F7 具体差在哪里（F4 最高 84MHz/3SPI，F7 最高 216MHz/6SPI） |

**面试官补充——480MHz 算力怎么算：**

核心思路：算出单次采集周期内 CPU 必须完成的计算量，除以采样间隔，得到 CPU 占用率。

但注意！不能只算采集，还要算**数据传输**的开销喵\~

```
主循环一次迭代的全量工作（1kHz 采样率，采样间隔 = 1000μs）：

【采集阶段】~35μs
├── SPI6 轮询发送 35 个命令：35 × 0.8μs = 28μs（CPU 完全占用）
├── extract_ddr_words × 128 次：≈ 5.3μs
└── FIFO 写入 + 命令处理：≈ 2μs

【传输阶段】虽然是 DMA，但 CPU 仍有开销
├── WiFi 模式：DMA 发送 4096B，但 getReadPtr + readFinish + SPI5 驱动
│   └── CPU 开销：~5-10μs/次（DMA 配置 + 回调处理）
│   └── 注意：WiFi 每 ~1ms 发一次（512B/帧 → 8帧凑满 4096B）
├── SD 卡模式：SDMMC DMA 写 16KB，但 FatFs 文件系统层不是 DMA
│   └── CPU 开销：f_write 的 FatFs 层 ~20-50μs/次（簇分配、FAT 表更新）
│   └── SD 卡写入不是每个采样周期都触发，每 ~30ms 一次
├── USB 模式：USB CDC 发送，USB 中断处理
│   └── CPU 开销：~5-10μs/次
└── 共同开销：DMA 中断处理 + DCache 维护 ≈ 3-5μs/次

【其他开销】
├── CmdQueue 命令轮询 + 处理：~1-2μs
├── 喂狗 + 状态检测：~1μs
└── 中断嵌套开销（DMA 完成回调抢占主循环）：~2-5μs

在480MHz下（需求最高 5kHz）：
├── 1kHz：采集 35μs + 传输/命令 ~10μs = ~45μs / 1000μs = 4.5% ✅
├── 3kHz：采集 35μs × 3 + 传输/命令 ~30μs = ~135μs / 1000μs = 13.5% ✅
├── 5kHz：采集 35μs × 5 + 传输/命令 ~50μs = ~225μs / 1000μs = 22.5% ✅
└── 吞吐量：5kHz × 256ch × 2B = 2.56MB/s（WiFi 6Mbps 带宽足够）

F4 @ 84MHz 的对比：
└── 同样的工作量，CPU 慢 5.7 倍 → 5kHz 下占用率 22.5% × 5.7 ≈ 128% ❌ 不可行
```

**关键洞察：** DMA 不是零开销！DMA 减少的是 CPU 搬数据的部分，但 DMA 配置、中断回调、Cache 维护、FatFs 文件系统层都需要 CPU 参与。尤其是 SD 卡模式的 FatFs `f_write`，文件系统的元数据操作不是 DMA 能替代的。

**建议的回答话术：** "H743 的 480MHz 是从需求反推的。256 通道 10kHz 下采集 SPI 轮询 + 数据提取需要约 35μs，再加上 DMA 传输的中断回调、FatFs 文件系统层、Cache 维护这些 DMA 无法卸载的 CPU 开销，10kHz 下总占用约 40%。如果用 F4 @ 84MHz，光采集就占满 100% 了，根本没有余量跑传输和命令处理。"

### Q3：多模式切换架构的可扩展性？

> （考察：可扩展性设计、模块化思维）

**候选人回答：**

> 当前架构是 `SystemMode` 枚举 + switch-case 分发，加新模式只需要三步：① 加枚举值 ② 实现发送函数 ③ 在主循环 switch 里加 case。`data_process.c` 里确实有好几个 switch 散落在不同函数里（采集后的 LED 指示、模式切换的 LED、按键切换逻辑），如果模式多了会越来越臃肿。
>
> **更好的做法**是用函数指针表 / 策略模式：定义一个 `ModeHandler` 结构体，把每种模式的采集回调、发送回调、LED 指示都封装成函数指针，切换模式时只换一张函数表，所有 switch 都消掉。
>
> **但为什么没这么做？** 因为这个项目实际上只有 3 种模式，而且每种模式的生命周期是固定的——系统启动后用户选择一种模式，然后就一直跑这种模式直到关机。不存在运行时频繁切换、动态加载新模式的场景。用函数指针表反而增加了间接调用的开销和调试难度（函数指针断点不好打）。而且我们用的是裸机，没有 RTOS 的任务抽象，如果用策略模式，每种模式的"上下文"管理（SD 卡的 isRecording、WiFi 的连接状态）反而更复杂。
>
> **这其实也是为什么我选裸机而不是 RTOS的原因之一。** 这个系统的数据流是固定的三条管线：SPI 采集 → FIFO → 输出（WiFi/USB/SD），一旦模式选定就一直在跑，不存在大量任务的动态调度需求。用 RTOS 的话，每个模式一个任务，每个外设一个任务，看起来很"工程化"，但实际上引入了任务间通信（队列/信号量）、栈开销（每个任务至少 512 字节栈，6 个任务就 3KB）、调度延迟（上下文切换 ~1-2μs）这些额外复杂度。而裸机的 while(1) 主循环里按顺序处理采集、发送、命令，代码简单、时序确定、调试方便。后来发现有屏幕驱动的需求，如果屏幕刷新频率不高（比如 10Hz），在主循环里轮询处理也够用，不需要单独的任务。

**面试官点评：**

| 评价项   | 结果  | 说明                                  |
| ------ | --- | ----------------------------------- |
| 现状分析   | ✅ 好 | switch-case 的优缺点都说了                 |
| 改进方向   | ✅ 好 | 函数指针表 / 策略模式的思路正确                   |
| 工程判断   | ✅ 亮点 | "3 种模式不值得抽象"是有理由的工程决策，不是偷懒         |
| 裸机选型理由 | ✅ 好 | 结合数据流固定、无动态调度需求、栈开销、调度延迟解释了裸机的合理性   |

## 第二轮：并发与实时性（🔥重点）

### Q4：SPSC 无锁队列的内存顺序问题

> （考察：无锁编程、内存屏障、DCache 一致性）

**面试官拷打：**

你的 `CmdQueue_Enqueue` 先 `memcpy` 写数据，再更新 `gCmdQueue.head`。你说这保证了内存顺序。但是——Cortex-M7 有 7 级超标量流水线 + Store Buffer + DCache。仅靠 C 语言源码的语句顺序，编译器和硬件真的会按这个顺序执行吗？

**三个风险点：**

1. **编译器重排**：`-O2` 优化下，编译器可能把 `gCmdQueue.head = QUEUE_NEXT(idx)` 重排到 `memcpy` 前面（因为 `head` 和 `slot->data` 没有别名依赖）
2. **CPU 重排**：M7 的 Store Buffer 可能导致 head 的写入先于 data 到达 RAM（观察者重排序）
3. **DCache**：head 和 data 可能在不同 Cache Line，消费者 CPU 从 RAM 读到新 head 但 data 还是旧 Cache 值

**候选人回答：**

> 这个问题我分析过。当前 `CmdQueue_Enqueue` 里先 `memcpy` 写数据，再更新 `gCmdQueue.head`，代码层面没有显式加 `__DMB()` 内存屏障。但实际系统是安全的，原因如下：
>
> 1. **编译器重排**：`gCmdQueue.head` 是 `volatile uint8_t`，C 标准规定 volatile 写不能被编译器重排到其前面的 sequence point 之前。所以编译器不会把 `head` 的赋值重排到 `memcpy` 前面。
> 2. **CPU Store Buffer 重排**：M7 确实有写缓冲。但当前场景是 ISR（生产者）写 head、主循环（消费者）读 head。ARMv7-M 架构下，异常进入/退出有隐式的同步屏障（隐式 DSB），ISR 返回时 Store Buffer 已经 drain 完了，主循环一定能看到最新的 head 值。
> 3. **DCache**：这个风险点在我们系统里不存在——项目初始化时我选择关闭了 DCache。所有内存访问都是直通 RAM 的，不存在 Cache 一致性问题。之所以关掉 DCache，是因为 SPI DMA 接收缓冲区和 WiFi SPI 发送缓冲区的 Cache 一致性维护成本太高，不如直接关掉用确定性换性能。
>
> 综上，当前代码在"DCache 关闭 + ISR 模型"的条件下是安全的。但如果未来开 DCache 或迁移到 RTOS 多线程模型，就需要显式加 `__DMB()` 了，这个我清楚。

**面试官点评：**

| 评价项          | 结果   | 说明                                   |
| ------------ | ---- | ------------------------------------ |
| 问题认知         | ✅ 好  | 三个风险点都讲清楚了，并且逐个给出了当前系统的安全性论证         |
| volatile 局限性 | ✅ 好  | 明确说了 volatile 只管编译器重排                |
| ISR 隐式屏障     | ✅ 好  | ARMv7-M 异常进入/退出有隐式 DSB，这是架构文档可查的     |
| DCache 决策    | ✅ 亮点 | "关掉 DCache 用确定性换性能"是一个有理由的工程决策，不是偷懒  |
| 前瞻性          | ✅ 好  | 提到了开 DCache / 迁移 RTOS 时需要加 `__DMB()` |

**面试官追问防御：**

- "关 DCache 不浪费 M7 性能吗？" → DCache 对计算密集型代码（循环、查表）提速明显，但本项目是 I/O 密集型（SPI DMA 来回搬运），Cache 命中率本来就不高，关掉反而省去了每次 DMA 前后的 Cache 维护开销（`SCB_InvalidateDCache_by_Addr` / `SCB_CleanDCache_by_Addr`）。
- "如果以后要开 DCache 呢？" → 把 `gCmdQueue` 放到 DTCM（0x20000000，不经过 DCache），或者 Enqueue/Dequeue 里加 `__DMB()` + DCache 维护。推荐前者，DTCM 本来就是为这种低延迟数据结构设计的。
- "ICache 开了吗？" → 这个可以反问面试官，ICache 对代码执行提速很大（尤其是 SPI 轮询发送的 tight loop），而且 ICache 不涉及 DMA 一致性问题，开着没副作用。

**代码现状：** 已确认 [cmd\_queue.c](file:///d:/source/INTAN256_MAIN/INTAN256_MAIN_CHANGE_CMDBACK/CmdQueue/cmd_queue.c) 中无 `__DMB()` 调用，系统 DCache 已关闭，当前条件下安全。

### Q5：SPSC 在 USB + UART 双生产者场景下的安全性

> （考察：SPSC vs MPSC、中断优先级、竞态条件）

**面试官拷打：**

CmdQueue 是 SPSC（单生产者-单消费者），但 USB CDC 回调和 UART DMA IDLE 中断都可能入队。如果 USB 回调正在写 `head`，UART 中断抢占后也写 `head`，两个生产者同时推进 head，会怎样？

**候选人回答：**

> 这个问题确实存在。CmdQueue 设计为 SPSC（单生产者单消费者），但实际有两个生产者——UART DMA IDLE 中断和 USB CDC 回调都会调用 `CmdQueue_Enqueue`。如果两个生产者真的并发执行，就会出现这样的竞态：
>
> 1. USB 回调写入 slot[3] 的数据到一半
> 2. UART 中断抢占，也拿到 head=3，写入自己的数据
> 3. USB 回调恢复，推进 head=4
> 4. UART 中断也推进 head=4
> → 数据丢失 + 槽位被覆盖
>
> **但当前代码实际是安全的**，原因是 USB CDC 的 `CDC_Receive_FS` 回调并不在硬 ISR 中执行，而是在 USB 中断的底半部处理（HAL 库内部的状态机轮询），和 UART 的 DMA 中断不存在真正的抢占关系。UART 中断发生时 USB 回调不会被打断，反之亦然。
>
> **但这不是设计保证，而是实现巧合**——如果 HAL 库升级、USB 驱动改成中断直驱模式，这个安全假设就失效了。
>
> **如果要正式修复，两个方案：**
>
> 1. **入队时关中断**：在 `CmdQueue_Enqueue` 里用 `__disable_irq()` / `__set_PRIMASK()` 保护 head 的读取和更新。入队操作本身很短（一次 memcpy + 一次指针赋值），关中断时间不到 1μs，不会影响 SPI DMA 采集的时序。
> 2. **改成 MPSC 无锁队列**：用 CAS（Compare-And-Swap）原子操作更新 head，但 ARMv7-M 没有 hardware CAS 指令，需要用 `LDREX`/`STREX` 实现 exclusive access，代码复杂度显著增加。
>
> **我的选择是方案 1**——关中断最简单可靠，而且入队只在命令到来时触发（用户手动操作，频率极低），关中断的性能影响可以忽略不计。这和 Q6 里 main_fifo 的关中断策略是一致的：在不需要 ISR 互斥的场景下，关中断是最简单安全的方案。

**面试官参考答案：**

当前代码侥幸安全的原因：USB CDC 的 `CDC_Receive_FS` 回调实际不在 ISR 中，而是在 USB 中断底半部处理，和 UART ISR 不存在真正的并发。但这不是设计保证，而是实现巧合。

改进方案：

1. 改为 MPSC（多生产者单消费者），入队时关中断或用 CAS
2. 或保证 USB 回调也在 ISR 中，利用中断优先级天然互斥

### Q6：CmdQueue 无锁 vs main\_fifo 关中断，为什么不用同一种？

> （考察：理解不同并发策略的 tradeoff）

**候选人回答：**

> 两种方案看起来不一样，但其实是根据各自场景的约束条件选的。
>
> **CmdQueue 用无锁**是因为它运行在 ISR 上下文里。UART DMA IDLE 中断和 USB CDC 回调都会入队，ISR 里不能关中断（否则会阻塞更高优先级的中断，影响 SPI DMA 采集的时序）。而且 CmdQueue 的数据量很小——每条命令最多 64 字节，队列深度才 8 个槽位，用 SPSC 无锁模型（生产者只写 head、消费者只写 tail）天然就没有竞争，不需要临界区。
>
> **main\_fifo 用关中断**是因为它的约束完全不同。main\_fifo 是 160KB 的大缓冲区，维护三个共享变量（readPtr、writePtr、dataByteNum），这三个变量之间有一致性要求——比如写入时 writePtr 和 dataByteNum 必须同步更新，不能一个更新了另一个没更新。而且 main\_fifo 的生产者是主循环里的采集回调，消费者也是主循环，不存在"ISR 不能阻塞"的约束。关中断的临界区时间极短——只保护指针操作，`memcpy` 在临界区外面做，关中断的时间大概就几个时钟周期，对 5kHz 采样率的 SPI DMA 中断完全没有影响。
>
> 所以本质上是：**ISR 路径用无锁避免阻塞，主循环路径用关中断保证多变量一致性**。

**面试官点评：**

| 评价项     | 结果  | 说明                                       |
| ------- | --- | ---------------------------------------- |
| 场景区分    | ✅ 好 | ISR 路径 vs 主循环路径的约束分析清楚                   |
| 无锁选型理由  | ✅ 好 | "ISR 不能关中断" + "SPSC 天然无竞争" 两个理由都站得住      |
| 关中断选型理由 | ✅ 好 | "三变量一致性" + "memcpy 在临界区外" 解释了为什么关中断代价可接受 |
| 临界区时间   | ✅ 好 | 明确说了只保护指针操作，关中断时间极短                      |

**面试官追问防御：**

- "main\_fifo 的生产者不是 ISR，为什么还需要关中断？" → 因为 SPI DMA 接收完成回调（`HAL_SPI_RxCpltCallback`）是 ISR 上下文，它也可能触发相关操作。而且 main\_fifo 的 `checkDataByte()`、`getReadPtr()` 等接口可能在主循环和定时器回调里都被调用，关中断是最安全的通用方案。
- "CmdQueue 以后要支持多生产者怎么办？" → 当前 UART 和 USB 的入队实际不在同一优先级中断里，SPSC 够用。如果真要 MPSC，可以在入队时临时关中断（入队操作本身不到 1μs），或者改用 CAS + ring index 的 MPSC 方案。
- "关中断不会影响 SPI DMA 吗？" → 临界区只保护指针赋值（几个时钟周期），`memcpy` 在外面。SPI DMA 是硬件搬运，不受 CPU 关中断影响，DMA 完成中断最多延迟几个周期，不影响数据正确性。

### Q7：Cortex-M7 上关中断的代价是什么？

> （考察：M7 的流水线深度、中断延迟、Cache 影响）

**候选人回答：**

> 关中断的代价主要有三个方面：
>
> 1. **中断响应延迟**：关中断期间所有中断都被屏蔽，如果 SPI DMA 传输完成了，DMA 完成中断要等到开中断后才能处理。M7 的中断延迟本身很快（12 个时钟周期入栈 + tail-chain 6 个周期），但关中断的时间是叠加上去的。
> 2. **流水线冲刷**：M7 是 6 级超标量流水线（双发射），`__disable_irq()` 会触发 `CPSID I` 指令，这条指令需要等流水线里之前的指令全部完成（相当于一个流水线排空），大约 5-10 个时钟周期。
> 3. **丢失中断**：如果关中断时间超过了一个 SPI DMA 周期，就会丢一次 DMA 完成中断，导致采集数据丢失。
>
> 但在我们项目里这些代价都可以接受，因为 main\_fifo 的临界区极短——只保护 `readPtr`/`writePtr`/`dataByteNum` 三个变量的赋值操作，`memcpy` 在临界区外面。关中断时间大约 5-10 个时钟周期 @ 480MHz ≈ **10-20ns**，而 SPI DMA 在 1kHz 采样率下每 1ms 才触发一次，完全不会有问题。即使在 5kHz 下（200μs 一次），20ns 的关中断也只占 0.01%。

**面试官点评：**

| 评价项     | 结果  | 说明                           |
| ------- | --- | ---------------------------- |
| 三个代价讲清楚 | ✅ 好 | 中断延迟 + 流水线冲刷 + 丢失中断，覆盖全面     |
| 结合项目分析  | ✅ 好 | 算出了实际关中断时间（\~20ns），和采样周期对比   |
| 关键数据记住  | ✅ 好 | M7 中断入栈 12 周期、6 级流水线、CPSID I |

**速记版（面试时不用全背，记住关键词就行）：**

- 关中断代价 = **中断延迟叠加** + **流水线排空**（CPSID I ≈ 5-10 周期）+ **可能丢中断**
- 我们项目没事 = **临界区只保护指针赋值 ≈ 20ns**，远小于 SPI DMA 周期

### Q9：流水线延迟 2 的含义

> （考察：SPI 外设的流水线延迟处理）

**候选人回答：**

> 这是 SPI 通信中一个很常见的问题——**外设内部有流水线处理延迟**，发送命令后不能立即得到结果，需要等若干个 SPI 周期后才能读到有效数据。
>
> 在我们的 ADC 芯片上，延迟是 2 个 slot。意思是：
> - 第 N 个周期发送命令 C
> - 第 N+1 个周期收到的是之前某个旧命令的结果
> - 第 N+2 个周期才收到命令 C 的真正结果
>
> **代码里怎么处理的？** 命令序列是 32 个 CONVERT + 3 个 AUX = 35 个命令，但提取数据时从 `index = 2` 开始取 32 个，跳过前 2 个 slot。前 2 个 slot 实际上是上一轮 AUX 命令的残留结果，不是当前 CONVERT 命令的有效数据。
>
> **这个问题的本质**是 SPI 全双工通信的"时间错位"——MOSI 和 MISO 的数据不是严格对应的，发送和接收之间存在固定的相位差。这在很多 SPI 外设上都存在，比如有些 ADC 芯片延迟 1 个周期，有些 Flash 車存器读操作也有类似的 dummy cycle。处理方式都是一样的：知道延迟是多少，在软件里对齐就行了。
>
> **如果延迟不确定怎么办？** 那就需要在命令序列前后加足够多的 dummy 命令（NOP），确保有效数据落在确定的窗口内。我们这个芯片延迟是固定的 2，所以不需要额外处理。

**面试官参考答案：**

INTAN RHD2164 的 SPI 协议特性：

- 发送 `CONVERT(ch0)` 命令后，芯片内部需要 2 个 MISO 周期才能输出结果
- 即：发送 `CONVERT(ch0)` → 下一个周期收到的是上一轮 AUX3 的结果 → 再下一个周期才收到 `CONVERT(ch0)` 的真正结果
- 代码中 `bias = 2` 就是跳过前 2 个无效 slot
- 前 2 个 slot 实际上是上一轮 AUX2/AUX3 的残留结果

这就是为什么命令序列是 32 CONVERT + 3 AUX = 35 个命令，但只提取 `[bias : bias+32]` 的数据作为有效 CONVERT 结果。

### Q10：DMA + DCache 一致性

> （考察：嵌入式系统的经典坑——DMA 写 RAM 后 CPU 从 DCache 读到旧数据）

**候选人回答：**

> 这个问题在我们系统里不存在，因为我把 DCache 关掉了。
>
> `SPI_recv_1/2/3/4` 是 `static volatile uint32_t` 数组，DMA 写入后 CPU 在下一行就读来调 `extract_ddr_words()`。如果 DCache 开着，这确实是个经典坑：DMA 写的是物理 RAM，CPU 从 Cache 读，Cache 里是旧数据。而且 **volatile 解决不了这个问题**——volatile 只约束编译器不优化掉读写操作，不影响 CPU Cache 行为。
>
> **为什么关掉 DCache？** 这个项目的瓶颈是 I/O 而不是计算。SPI DMA 采集、WiFi SPI 发送、SDMMC DMA 写入，全都是 DMA 在搬运数据，CPU 的计算量主要是 `extract_ddr_words`（5μs 内的位操作）和 FIFO 的 `memcpy`。DCache 对 I/O 密集型代码的命中率本来就不高，开着反而要在每次 DMA 前后手动维护一致性（`SCB_InvalidateDCache_by_Addr` / `SCB_CleanDCache_by_Addr`），维护开销可能比 Cache 带来的加速还大。关掉 DCache 用"确定性换性能"是一个有理由的工程决策。
>
> **如果未来要开 DCache，三个解决方案：**
> - **方案 A**：把 `SPI_recv` 数组放到 DTCM（0x20000000），DTCM 不经过 DCache，从根本上避免问题
> - **方案 B**：在 DMA 完成回调里调 `SCB_InvalidateDCache_by_Addr(SPI_recv_1, sizeof(SPI_recv_1))` 使 Cache 无效化
> - **方案 C**：用 `__attribute__((section(".dma_buffer")))` 把 DMA 缓冲区放到 MPU 配置的非 Cache 区域
>
> 我推荐方案 A——DTCM 零等待访问，DMA 也可以访问 DTCM（通过总线矩阵），而且不占用 AXI SRAM 的 Cacheable 区域。

**面试官参考答案：**

关键点：**volatile 不能解决 DCache 一致性问题！** volatile 只保证编译器不优化掉读写操作，但不影响 Cache 行为。

解决方案有三种：

**方案 A（当前代码可能的处理方式）：**
将 `SPI_recv` 数组放在 DTCM（紧耦合内存），DTCM 不经过 DCache，DMA 写入后 CPU 直接读到新数据。需要检查链接脚本中这些数组的实际存放位置。

**方案 B（通用方案）：**
在 DMA 传输完成回调中调用：

```c
SCB_InvalidateDCache_by_Addr((uint32_t*)SPI_recv_1, sizeof(SPI_recv_1));
```

使 CPU 下次读取时从 RAM 重新加载。

**方案 C（最优）：**
使用 `__attribute__((section(".dma_buffer")))` 将 DMA 缓冲区放在 AXI SRAM 的非 Cache 区域，从根本上避免问题。

注意：代码中 `HAL_SPI_RxCpltCallback` 只置了 FLAG，没有看到 Cache invalidation。因为 DCache 已关闭。

### Q11：4 路 SPI 忙等的优化方案

> （考察：信号量/事件标志组、WFI 指令降低功耗）

**候选人回答：**

> 坦白说，我实际代码里用的就是忙等——`while (SPI1_RECV_FLAG == false || SPI2_RECV_FLAG == false || ...);` 没有用信号量或 WFI 优化。
>
> **为什么用忙等？** 原因有三层：
>
> 1. **等待时间极短**：SPI6 发送 35 个 16bit 命令只需要 28μs（@20MHz），这 28μs 里 4 路 SPI DMA 接收同步进行，DMA 完成中断会置位 `SPIx_RECV_FLAG`。28μs 的忙等 @480MHz 对应 13440 个时钟周期，CPU 空转一下而已，对功耗和性能影响都很小。
>
> 2. **裸机环境的权衡**：我们用裸机，没有 RTOS 的信号量、事件标志组这些同步原语。如果要自己实现一个简化版的信号量，需要维护计数器、等待队列，复杂度反而比忙等高。而且这个采集函数每 1ms（@1kHz）才调用一次，不是高频循环，忙等不会累积成问题。
>
> 3. **数据提取紧耦合**：SPI DMA 完成后的下一句就是 `extract_ddr_words()` 数据提取，这两个操作必须在同一个函数里串行执行。如果改成等 DMA 完成中断再回调做数据提取，会导致数据流被打断，代码结构变复杂。
>
> **如果真的要优化的话，我有几个思路：**
>
> - **方案 A：WFI 低功耗等待**——在忙等循环里加 `__WFI()`，让 CPU 进入低功耗模式，等 DMA 完成中断唤醒。但要注意 DMA 中断要足够高优先级，否则其他中断可能抢占导致 WFI 失效。
>
> - **方案 B：信号量同步**——如果用 RTOS，可以用 `osSignalWait()` 等待 4 路 SPI DMA 完成的信号组，RTOS 会自动调度其他任务。
>
> - **方案 C：双缓冲+异步处理**——用两套缓冲区轮换，A 缓冲区的 DMA 完成后，在中断里设置标志，主循环下次迭代时才提取数据。这样可以把等待和数据解耦，但代码复杂度显著增加。
>
> **我的选择是：** 在 28μs 的等待时间面前，这些优化的收益不明显，反而增加了代码复杂度和潜在 bug 的风险。而且坦白说，SPI6 改用 DMA 不一定能提升性能，甚至会引入新的问题。
>
> **为什么 SPI6 还没用 DMA？** 原因有四层：
>
> 1. **命令序列动态生成**：每次采集时命令序列 `txData` 是作为参数传入的，不是预先生成的静态 buffer。如果要改用 DMA，需要把命令序列先拷贝到 DMA buffer，这样反而多了一次内存拷贝（从 `txData` 到 DMA buffer）。
>
> 2. **时序同步要求严格**：INTAN 芯片要求 SPI6 发送命令的同时，4 路 SPI 必须同步接收数据。现在的轮询发送可以确保发送和接收完全同步——发一个命令，收 4 个数据。改用 DMA 后，SPI6 DMA 发送和 4 路 DMA 接收都是异步的，需要通过中断同步，增加了时序控制的复杂度。
>
> 3. **DMA 资源限制**：从硬件配置看，DMA1 和 DMA2 的 Stream 已经被 SPI1/2/3/4 的接收、SPI5（WiFi）、UART6、ADC1 占用了，需要检查是否还有空闲的 DMA 通道给 SPI6 TX。如果没有，可能需要用 BDMA 或者 MDMA，而 H743 上 SPI6 的 DMA 请求映射比较复杂。
>
> 4. **调试和维护成本**：轮询发送代码简单直观，出问题时很容易定位。改用 DMA 后，错误需要在中断回调里处理，调试难度显著增加。而且 28μs 的 CPU 占用在 1kHz 采样率下只占 2.8%，即使 5kHz 下也只有 14%，收益不明显。
>
> **如果真的要改成 DMA，需要解决这些问题：**
>
> - **命令序列管理**：预先生成命令序列到静态 DMA buffer，或者每次采集前拷贝到 buffer
> - **同步机制**：5 路 DMA（1 发送 + 4 接收）都完成后才能提取数据，需要用信号量或标志位同步
> - **错误处理**：任何一路 DMA 失败都需要整个采集流程回滚，错误处理复杂度增加
> - **优先级管理**：DMA 中断优先级要合理设置，避免高优先级中断抢占导致数据错位
>
> **我的判断是：** 在当前的约束条件下，轮询发送的简单方案已经足够了。如果未来采样率提高到 20kHz 以上，CPU 占用率超过 50%，再考虑改用 DMA 更合适。

## 第四轮：数据流与缓冲策略

### Q12：两级缓冲的设计决策

> （考察：生产者-消费者的速率不匹配问题）

**候选人回答：**

> 计算很简单：
>
> - 每帧数据量 = 524B（帧头 10B + 数据 512B + 2B margin）
> - 1kHz 采样率：524B × 1000 = **524KB/s**
> - 50ms 抖动积累：524B × 50 = **26.2KB** → 160KB FIFO 可以撑 ✅
> - 1 秒断连积累：524B × 1000 = **524KB** >> 160KB → **FIFO 溢出！** ❌
>
> **当前处理方式：** `checkAndAcq()` 里用 `checkDataByte() + length <= FIFO_SIZE` 判断，满了就丢弃当前帧。这是最简方案，没有丢帧统计、没有通知上位机、没有 frameCounter。
>
> **为什么这么简单？** 因为在实际使用场景里，WiFi 断连超过 1 秒意味着网络已经不可用，用户应该切换到 USB 或 SD 模式。这个项目的定位是实时传输，不是"先缓存再补发"的数据记录仪。160KB 的缓冲主要是为了应对 WiFi 的瞬时抖动（几十 ms），而不是长时间断连。
>
> **如果要做得更完善的话：**
> - 加丢帧计数器，上位机通过 DEBUG 命令查询
> - timestamp 从 16bit 扩展到 32bit，避免回绕歧义
> - FIFO 持续溢出时自动切换到 SD 模式保数据
>
> 但这些需要上位机配合改动，在当前项目阶段不是优先级最高的需求。

### Q13：零拷贝 getReadPtr 的跨边界问题

> （考察：环形缓冲区的经典问题——跨边界的数据不连续）


**面试官参考答案：**

环形缓冲区的经典问题：假设 `FIFO_SIZE = 160KB`，`readPtr = 159KB`，要读 16KB，后 15KB 在 buffer 开头 → 数据不连续。

当前代码 `getReadPtr()` 直接返回 `&fifoBuffer[readPtr]`，调用方（WiFi DMA / SD DMA）要求连续内存。

所以限制"读长度必须是 FIFO\_SIZE 的因子"：

- FIFO\_SIZE = 160KB = 163840B
- SD 写入：16KB = 16384B → 163840 / 16384 = 10 ✅ 整除
- WiFi 发送：4096B → 163840 / 4096 = 40 ✅ 整除
- USB 发送：4096B → 同上 ✅

这样保证 readPtr 对齐后，永远不会跨边界。但这个约束是隐式的，没有在代码中 assert 验证。如果有人改了发送大小但忘了改 FIFO\_SIZE，就会出 bug。

### Q14：零拷贝的时序问题

> （考察：DMA 发送完成回调中才能调用 readFinish）

**候选人回答：**

> 零拷贝的关键是：**DMA 发送完成之后才能移动读指针**，否则 DMA 还在读数据你就把指针挪了，新写入的数据会覆盖 DMA 正在发送的区域，数据就乱了。
>
> 在我们的代码里，`readFinish()` 是在 DMA 完成回调里调用的：
> - **WiFi 模式**：`HAL_SPI_TxCpltCallback(SPI5)` 里检查 `wifiSendFromFifo` 标志，如果是 FIFO 数据则调用 `readFinish(WIFI_SEND_SIZE)`。SPI5 是 WiFi 透传的 SPI，DMA 发完中断进来才移动指针。
> - **USB 模式**：`setUSBSendOverFlag(0x01)` 里检查 `usbSendFromFifo` 标志，确认是 FIFO 数据后才调 `readFinish(USB_SEND_SIZE)`。
> - **SD 卡模式**：`HAL_SD_TxCpltCallback(SDMMC1)` 里调 `readFinish(sdDmaTxCompletionSize)`。
>
> 另外还有一个细节：用 `wifiSendFromFifo` / `usbSendFromFifo` 标志区分了"FIFO 数据发送"和"命令响应发送"。因为同一个 SPI5/USB 通道既发 FIFO 采集数据，也发命令响应。如果是命令响应完成了，不应该调 `readFinish()` 移动 FIFO 的读指针。

**面试官点评：**

| 评价项 | 结果 | 说明 |
|--------|------|------|
| 核心原则 | ✅ 好 | "DMA 完成回调里才移动指针"说对了 |
| 三种模式都讲了 | ✅ 好 | WiFi（SPI5 回调）、USB（sendOverFlag）、SD（SDMMC 回调） |
| 标志位区分 | ✅ 亮点 | `wifiSendFromFifo` 区分 FIFO 数据和命令响应，说明理解了零拷贝的坑 |

## 第五轮：SD 卡与电源管理

### Q15：SD 卡批量写入

> （考察：SD 卡的写入性能与块大小密切相关）

**候选人回答：**

> 我们每次写 16 个 block = 8KB，用 `HAL_SD_WriteBlocks_DMA` 直接写裸扇区，没有用 FatFs 文件系统。
>
> **为什么不用 FatFs / exFAT？** 三个原因：
>
> 1. **确定性**：FatFs 的 `f_write` 内部有簇分配、FAT 表更新、目录项修改，这些操作的时间不可预测（几十 μs 到几 ms 都有可能）。我们是实时采集系统，SD 写入必须在 DMA 完成后的回调里快速推进，不能接受 FatFs 的不确定延迟。
> 2. **简化断电恢复**：不用文件系统意味着我们自己控制数据在 SD 卡上的物理布局。我在固定位置（`SD_INFO_BLOCK`）写了一个信息块，记录当前写入到了哪个扇区。断电重启后读这个信息块就能接着写，不需要文件系统的 journal 或 FAT 表恢复。
> 3. **PC 端解析**：上位机直接按扇区读取 SD 卡，按固定帧格式解析数据，不需要文件系统的挂载过程。
>
> **为什么一次写 8KB 而不是更大或更小？** SD 卡有最小写入开销——无论写多大，都有命令开销（CMD25 多块写入 + STOP\_TRANSMISSION）。一次写 1 个 block（512B）和写 16 个 block（8KB），命令开销是一样的。所以批量写能摊薄这个固定开销。但也不能写太大，因为 main\_fifo 的 `getReadPtr()` 零拷贝要求写入大小必须是 `FIFO_SIZE` 的因子（160KB / 8KB = 20，整除 ✅）。写太大会占用太多 FIFO 空间，影响 WiFi 预览通道的数据读取。

**面试官点评：**

| 评价项          | 结果   | 说明                                              |
| ------------ | ---- | ----------------------------------------------- |
| 不用 FatFs 的理由 | ✅ 亮点 | "确定性"是实时系统的硬需求，不是偷懒                             |
| 断电恢复方案       | ✅ 好  | 自定义 InfoBlock 比依赖文件系统 journal 更轻量               |
| 批量写入的理由      | ✅ 好  | 命令开销摊薄 + FIFO 整除约束，两个理由都站得住                     |

### Q16：SD 模式下的资源竞争

> （考察：总线竞争、CPU 时间、FIFO 读指针竞争）

**候选人回答：**

> SD 模式下我用了 `sdDmaBusy` 标志位来避免竞争，但坦白说，在这个项目的实际运行场景里，这个竞争问题本身并不存在。
>
> **为什么没有竞争？** 原因有三层：
>
> 1. **速度不匹配**：INTAN256 的 5kHz 采样率，每秒生成 5kHz × 256 通道 × 2 字节 = 2.56MB/s。而 SD 卡 4-bit 模式的写入速度能达到 10MB/s 以上，是数据生成速率的 4 倍。每次写 8KB，只需要不到 1ms，而 FIFO 积攒 8KB 数据需要 3ms，写入速度远快于生成速度。
>
> 2. **单路径设计**：SD 模式下只有一条数据流——从 SPI DMA 采集到 main_fifo，然后从 main_fifo 写到 SD 卡。没有 WiFi 或 USB 的并发争抢，FIFO 读指针只有一个消费者。
>
> 3. **主循环串行化**：`TryWriteBufferDataToSD()` 在主循环里调用，`HAL_SD_TxCpltCallback()` 在 SDMMC 中断里调用，这两个上下文通过 `sdDmaBusy` 标志位互斥。当 `sdDmaBusy = 1` 时，主循环跳过 SD 写入；当 DMA 完成后回调里清零 `sdDmaBusy`，主循环才会继续写下一块。
>
> **但我还是做了防御性设计**：
> - `sdDmaBusy` 标记为 `volatile`，确保 ISR 和主循环之间可见
> - `TryWriteBufferDataToSD()` 入口检查 `SD_Adapter_IsBusy()`，如果忙就返回 0，下次主循环再试
> - `HAL_SD_TxCpltCallback()` 完成 DMA 后根据 `sdCurrentWriteType` 区分是 FIFO 数据还是文件头尾，只有 FIFO 数据写入才调用 `readFinish()` 移动读指针
>
> **如果真的遇到竞争场景怎么办？** 比如采样率提高到 20kHz，或者换了个更慢的 SD 卡，FIFO 可能会满。那我会考虑：
> - 增加 FIFO 容量（现在 160KB 对应 62ms 缓冲）
> - 检查是否开启了 SD 卡的高速模式（HS-SDR25）
> - 如果竞争真的严重，考虑双缓冲或者把 `isRecording` 改为原子变量防止启动/停止竞态
>
> 但在这个项目的实际约束条件下，一个标志位就够了，过度设计反而增加复杂度。

## 第六轮：协议与通信

### Q18：帧头 0xAC 0x18 出现在数据中的误识别问题

> （考察：协议设计的鲁棒性）

**候选人回答：**

> 这个问题在理论上存在，但在我们的实际场景里风险极低。原因有两层保护：
>
> **第一层：协议层面的 dataLen 跳过机制。** `split_command` 的逻辑是：找到帧头 → 读 `dataLen` → 计算 `frameSize = sizeof(Msg) + dataLen` → 跳过整帧。即使数据负载里恰好出现 `0xAC 0x18`，只要前一帧的 `dataLen` 是正确的，解析器就会完整跳过数据区域，不会把数据里的 `0xAC 0x18` 误认为帧头。
>
> **第二层：DMA + IDLE 中断的接收模型。** 我们用的是 `HAL_UARTEx_ReceiveToIdle_DMA`，每次 IDLE 中断触发时，DMA 给出的 `Size` 就是一"包"完整数据。上位机是我们的可控软件，每次发完一帧后会有空闲间隔触发 IDLE，所以每次进 ISR 收到的就是一帧完整命令，不存在中间插了噪声字节的情况。再加上我们的命令频率很低（用户手动操作，不是高频自动发送），`UART_RX_BUFFER_SIZE = 64` 的缓冲区绰绰有余。
>
> 所以综合来看：协议层的 dataLen 跳过 + DMA IDLE 的包边界保证，误识别概率几乎为零。如果要更鲁棒，可以加 CRC，但对我们这个场景来说是过度设计——加 CRC 意味着每帧多 1-2 字节校验码，`split_command` 里每帧都要算一遍 CRC（命令最长 64B，CRC32 大约 20-30 个时钟周期），而且上位机也要同步改，收益不大。

**面试官点评：**

| 评价项 | 结果 | 说明 |
|--------|------|------|
| dataLen 跳过机制 | ✅ 好 | 代码层面确实有这层保护 |
| DMA IDLE 包边界 | ✅ 好 | 从接收模型角度解释了为什么不会误识别 |
| 风险评估 | ✅ 合理 | 命令频率低 + 上位机可控，实际风险确实极低 |

### Q19：UART DMA 跨帧拼接问题

> （考察：经典的串口协议问题——多帧粘连和帧截断）

**候选人回答：**

> **多帧粘连**的情况我们的代码能处理。`split_command` 本身就是 `while(index < size)` 循环解析的——如果 DMA 一次收了两帧，第一帧解析完后 index 移到第二帧位置，下一轮循环继续找帧头，能正确拆开两帧。
>
> **帧截断**的情况确实存在理论风险——如果 DMA 第一次只收到了半帧，第二次收到后半帧，`split_command` 会丢弃这两段数据，因为没有残包缓冲区。但实际上在我们的场景里这几乎不会发生：
> 1. 上位机每次发完一帧后有明确的空闲间隔，IDLE 中断会在帧尾触发
> 2. `UART_RX_BUFFER_SIZE = 64`，而我们的命令帧都很短（≤64B），不会被 DMA 缓冲区截断
> 3. 命令是用户手动触发的，不存在高频连续发送
>
> 如果以后要支持高频命令或者更大的帧，再加残包缓冲区就行——把上次未解析完的数据拷到临时缓冲区，下次 DMA 数据拼在后面继续解析。

**面试官点评：**

| 评价项 | 结果 | 说明 |
|--------|------|------|
| 多帧粘连处理 | ✅ 好 | `split_command` 循环解析，代码已验证 |
| 帧截断风险认知 | ✅ 好 | 承认了理论风险，但解释了为什么实际不会发生 |
| 改进方案 | ✅ 好 | 残包缓冲区的思路说对了 |

## 第七轮：性能与优化

### Q21：裸机架构 vs RTOS

> （考察：裸机轮询架构的局限性、RTOS 的栈开销、调度延迟）

**候选人回答：**

> 选裸机是因为我们系统的任务模型非常简单——只有三个主要的数据 stream（采集 + 传输 + 命令处理），启动后就是固定的 while(1) 循环轮询，不涉及大量任务的动态调度。每个"任务"本质上是：检查标志位 → 有事就做 → 没事跳过，逻辑非常清晰。
>
> 如果上 RTOS（FreeRTOS），要付出几个代价：
> 1. **栈开销**：每个任务要独立分配栈，256 通道数据量大，FIFO 相关的任务栈可能要 1-2KB，加上采集任务、命令任务、传输任务，光栈就要 4-6KB。H743 虽然内存够，但没有必要。
> 2. **调度延迟**：FreeRTOS 的 systick 调度（通常 1ms）引入不确定性。我们的采集是 5kHz（200μs 一次），如果 RTOS 调度粒度是 1ms，采集任务的响应延迟可能达到 1ms，不可接受。
> 3. **复杂度**：当前裸机架构下，主循环的执行顺序是确定的——采集 > 命令处理 > 数据发送，优先级天然由代码顺序保证。上了 RTOS 要考虑优先级反转、互斥锁、死锁这些问题。
>
> 不过后来发现有个问题——屏幕驱动（I2C OLED）。屏幕刷新是慢操作（I2C 100kHz，刷一帧要几十 ms），放在主循环里会阻塞采集。目前的处理方式是定时器中断里触发 SPI 采集，屏幕刷新放在主循环空闲时做，采集不会被阻塞。但如果以后屏幕 UI 越来越复杂（多级菜单、动画），可能就需要考虑把屏幕单独拆成一个低优先级任务，这时候上 RTOS 会更合理。

**面试官点评：**

| 评价项 | 结果 | 说明 |
|--------|------|------|
| 选裸机的理由 | ✅ 好 | "三 stream 固定轮询"的理由站得住，确实不需要 RTOS 的调度能力 |
| RTOS 代价分析 | ✅ 好 | 栈开销 + 调度延迟 + 复杂度，三个点都讲到了 |
| 诚实度 | ✅ 好 | 承认了屏幕驱动是裸机架构的痛点，没有硬撑 |
| 改进方向 | ✅ 好 | 提到了"以后 UI 复杂了可以考虑 RTOS" |

**面试官追问防御：**
- "定时器中断触发采集，和 while(1) 轮询采集有什么区别？" → 当前实际是 TIM 触发 SPI 采集开始，主循环里检查采集完成标志后处理数据。采集的时序由定时器保证（硬件级精确），数据处理由主循环完成（软件级轮询），两者解耦。
- "屏幕刷新影响采集怎么办？" → SPI 采集由定时器中断启动，不受主循环阻塞影响。屏幕刷新放在主循环的"无采集任务"间隙执行，不影响采集时序。
- "如果以后要加蓝牙、Web 配置页面呢？" → 那就得上 RTOS 了。蓝牙协议栈（BLE）本身就需要任务调度，Web 配置页需要 HTTP server，这些和实时采集争 CPU 时间，裸机的固定轮询搞不定。可以保留当前架构，用 FreeRTOS 的定时器任务替代 while(1)，采集任务设最高优先级。

### Q22：主循环执行时间估算

> （考察：1kHz 采样下，SPI DMA + 数据提取 + FIFO 写入 + 命令处理 + 发送的总耗时）

**候选人回答：**

> 主循环的结构很清晰：`checkAndAcq()` → `CmdHandler_ProcessLoop()` → 模式分发（发送）→ `updateBatteryInfo()` → 喂狗。按 1kHz 采样率估算：
>
> **1. 采集阶段（checkAndAcq）~35μs**
> - SPI6 轮询发送 35 个命令：35 × 0.8μs = 28μs（CPU 完全占用）
> - 4 路 SPI DMA 接收：与发送同步，0 额外 CPU 时间
> - `extract_ddr_words` × 128 次：≈ 5μs
> - 帧头打包 + FIFO 写入：≈ 2μs
>
> **2. 命令处理（CmdHandler_ProcessLoop）~1-5μs**
> - 无命令时：只检查队列是否为空，≈ 1μs
> - 有命令时：解析 + 执行（比如模式切换），≈ 5-50μs，但命令频率极低（用户手动操作）
>
> **3. 发送阶段（模式分发）**
> - WiFi 模式：`TrySendBufferDataToWifi()` 检查 FIFO 数据量是否够 4096B，不够就跳过 ≈ 1μs；够了就启动 SPI5 DMA 发送 + 等完成 ≈ 5-10μs。WiFi 发送不是每次循环都触发，大约每 8 次采集（8×524B ≈ 4KB）触发一次
> - USB 模式：类似，`TrySendBufferDataToUSB()` ≈ 5-10μs
> - SD 模式：`TryWriteBufferDataToSD()` 检查 SD 是否忙、FIFO 数据量是否够 8KB，不够就跳过 ≈ 1μs；够了就启动 SDMMC DMA 写 ≈ 5μs CPU 开销（DMA 配置）。每 ~16 次采集触发一次
>
> **4. 其他开销 ~2μs**
> - `updateBatteryInfo()`：I2C 读 BQ25895，约每 1000 帧才执行一次，均摊可忽略
> - 喂狗 `HAL_IWDG_Refresh`：≈ 1μs
> - DMA 中断回调抢占的开销：≈ 2-5μs
>
> **汇总（1kHz 采样率）：**
>
> | 阶段 | 耗时 | 说明 |
> |------|------|------|
> | 采集 | ~35μs | CPU 完全占用 |
> | 命令处理 | ~1-5μs | 大部分时候为空 |
> | 发送 | ~1-10μs | 不是每次都触发 |
> | 其他 | ~2μs | 喂狗+中断 |
> | **总计** | **~40-50μs** | **占 1000μs 的 4-5%** ✅ |
>
> **5kHz 采样率下：** 采集 35μs × 5 = 175μs（假设每轮都要采集），加上其他开销，总占用约 185-200μs / 200μs = **~90-100%** ⚠️ 已经接近极限。但这是理论估算，实际 5kHz 下每 200μs 触发一次采集，采集之间还有 165μs 做其他事情，应该勉强够用。
>
> **真正的瓶颈是 SPI6 轮询发送的 28μs**，占总采集时间的 80%。如果能改成 DMA 发送，采集阶段 CPU 占用可以降到 ~7μs（数据提取 + FIFO 写入），整体 CPU 占用率在 5kHz 下也能降到 ~35%。

### Q23：extract_ddr_words 的加速方案

> （考察：MDMA 内存到内存搬运、Cortex-M7 的 SIMD 向量指令）

**候选人回答：**

> `extract_ddr_words` 做的是把 SPI 接收到的 32bit 交织数据拆成两个 16bit 通道数据（INTAN DDR 模式下两个 stream 的 bit 是交替编码的）。当前用的是 5 步移位+掩码的解交织算法，每次调用约 10-15 个时钟周期，128 次总共约 5μs，已经很快了。
>
> 面试官提到的几个加速方向我都考虑过，但结论是都不太适用：
>
> 1. **MDMA**：只能做内存到内存的搬运，不支持位操作（移位、掩码）。`extract_ddr_words` 的核心是逐字做 bit 级解交织，MDMA 帮不上忙。
> 2. **Cortex-M7 向量指令**：这里有个常见误解——Cortex-M7 **没有** Helium（MVE）向量指令，那是 Cortex-M55/M85 才有的。M7 的 DSP/SIMD 指令只支持 8/16bit 的算术运算（加法、乘法、点积），不支持任意位操作，所以对解交织没用。
> 3. **查表法**：可以用 256 项查找表替代移位，但 DCache 关闭的情况下每次查表都是 RAM 访问，反而比 5 步纯寄存器运算慢。
> 4. **循环展开**：收益有限，4 路展开可能从 5μs 降到 4μs，不值得牺牲可读性。
>
> **结论：** 当前方案已经接近最优了。真正的瓶颈不在这里——5μs 的数据提取 vs 28μs 的 SPI6 轮询发送。如果要优化，应该优先把 SPI6 轮询改成 DMA 发送，而不是优化 extract。

**面试官点评：**

| 评价项 | 结果 | 说明 |
|--------|------|------|
| 加速方案分析 | ✅ 好 | 四个方案逐个分析"为什么不行"，不是泛泛而谈 |
| M7 能力边界 | ✅ 亮点 | "M7 没有 Helium，只有 DSP 算术指令"——纠正了面试官的隐含假设 |
| ROI 判断 | ✅ 好 | "瓶颈在 SPI 轮询不在 extract"——知道该优化什么 |

**面试官追问防御：**
- "那 SPI 轮询发送的 28μs 能优化吗？" → 可以改成 SPI6 DMA 发送 + 4 路 SPI DMA 接收并行，5 路 DMA 全并行，CPU 只负责启动和等完成标志。但需要把命令序列预先生成到 buffer 里，代码改动较大。
- "M7 的 DSP 指令具体能做什么？" → `__SMUAD`（双 16bit 乘加）、`__SMLAD`（双 16bit 乘累加）、`__SADD8`（4 路 8bit 饱和加法）等。适合 FIR 滤波、FFT 之类的信号处理，不适合位操作。
