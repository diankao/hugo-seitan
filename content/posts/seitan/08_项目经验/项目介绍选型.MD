# 项目技术选型

## INTAN256 项目：硬件选型分析

### 项目背景

**INTAN256_MAIN** 是一个基于 STM32H743 的 256 通道神经信号采集系统，用于科研和医疗领域的神经信号采集。

**核心需求：**
- 256 通道连续采集
- 采样率范围：1-10000 Hz
- 支持三种数据传输模式：WiFi、SD 卡、USB
- 实时数据处理和传输

**最终选择：STM32H743 + 裸机开发**

---

## 硬件选型：为什么选择 STM32H743？

### 1. 多 SPI 接口需求（核心原因）

INTAN256 芯片需要通过 SPI 接口进行数据采集，项目需要同时连接多个外设：

**SPI 接口需求：**
- **SPI1/2/3/4**：连接多片 INTAN 芯片（每片支持 32/64/128 通道，256 通道需要多片级联）
- **SPI5**：连接 WiFi 模块（ESP32/ESP8266），实现无线数据传输
- **可选 SPI6**：预留扩展接口或备用

**STM32H743 的 SPI 资源：**
- 6 个 SPI 接口（SPI1-SPI6），全部支持主/从模式
- 最高通信速率：50 MHz（APB2 总线）
- 支持 DMA 传输，减轻 CPU 负担
- 硬件 NSS、CRC 校验、TI 模式等高级功能

**对比其他 MCU 的 SPI 资源：**

| MCU 型号 | SPI 数量 | 最高速率 | 是否满足 |
|----------|----------|----------|----------|
| STM32H743 | 6 | 50 MHz | ✅ 完全满足 |
| STM32F407 | 3 | 42 MHz | ❌ 不够 |
| STM32F746 | 6 | 50 MHz | ✅ 满足但性能弱 |
| STM32L4 | 3 | 80 MHz | ❌ 数量不够 |
| ESP32 | 4 | 80 MHz | ❌ 不适合外设控制 |

### 2. 高性能 Cortex-M7 内核

**STM32H743 核心参数：**
- **主频**：480 MHz（Cortex-M7，双发射架构）
- **性能**：1027 DMIPS（每秒 10 亿条指令）
- **指令集**：ARMv7E-M，支持 DSP 指令集
- **FPU**：双精度浮点运算单元

**性能需求分析：**

256 通道 × 10000 Hz 采样率 = 2.56 MHz 数据流

数据处理需求：
```
每秒数据量：256 通道 × 10000 Hz × 2 字节/采样点 = 5.12 MB/s
每个采样点处理时间：< 1 μs（10000 Hz 采样率）

STM32H743 性能余量：
480 MHz / 2.56 MHz ≈ 187 倍余量
```

**对比其他 MCU 的性能：**

| MCU 型号 | 主频 | DMIPS | 性能余量 |
|----------|------|-------|----------|
| STM32H743 | 480 MHz | 1027 | 187× |
| STM32F407 | 168 MHz | 210 | 65× |
| STM32F746 | 216 MHz | 462 | 142× |
| STM32F103 | 72 MHz | 75 | 23× |

### 3. 大容量 SRAM 和高速存储

**STM32H743 存储资源：**
- **SRAM 总计**：1 MB
  - ITCM：64 KB（指令 TCM，存放中断向量表）
  - DTCM：128 KB（数据 TCM，零等待访问）
  - AXI SRAM：512 KB（高速 AXI 总线，存放缓冲区）
  - SRAM1/2/3/4：384 KB（通用 SRAM）
- **Flash**：2 MB

**环形缓冲区需求：**
- 设计：160 KB 环形缓冲区（10 块 × 32 扇区）
- 需要高速访问、低延迟的存储区域
- **AXI SRAM** 是最佳选择（512 KB，远超需求）

**对比其他 MCU 的 SRAM：**

| MCU 型号 | SRAM 总量 | AXI SRAM | 是否满足 |
|----------|-----------|----------|----------|
| STM32H743 | 1 MB | 512 KB | ✅ 完全满足 |
| STM32F407 | 192 KB | 无 | ❌ 不够 |
| STM32F746 | 320 KB | 256 KB | ⚠️ 勉强满足 |
| STM32L4 | 320 KB | 无 | ❌ 不够 |

### 4. 强大的 DMA/MDMA 能力

**STM32H743 DMA 资源：**
- **DMA1/2**：16 个流 × 2 = 32 个 DMA 通道
- **BDMA**：7 个通道（低功耗域）
- **MDMA**：主 DMA，支持内存到内存的高效传输

**DMA 应用场景：**
- **SPI DMA**：INTAN 数据采集，无需 CPU 干预
- **UART DMA**：命令接收，配合 IDLE 中断
- **SDMMC DMA**：SD 卡批量写入（32 blocks/次）
- **MDMA**：环形缓冲区的数据搬移和格式转换

**零拷贝优化：**
```
SPI DMA → AXI SRAM（环形缓冲区）→ SDMMC DMA → SD 卡
全程 DMA 传输，CPU 仅负责配置和错误处理
```

**对比其他 MCU 的 DMA 能力：**

| MCU 型号 | DMA 通道数 | MDMA | 是否满足 |
|----------|------------|------|----------|
| STM32H743 | 39 | ✅ | ✅ 完全满足 |
| STM32F407 | 16 | ❌ | ⚠️ 勉强满足 |
| STM32F746 | 16 | ❌ | ⚠️ 勉强满足 |

### 5. 丰富的外设接口

**项目需要的外设：**
- **SPI1-6**：INTAN 芯片、WiFi 模块
- **USART6**：命令接收（DMA + IDLE 中断）
- **USB OTG**：CDC 虚拟串口（预留）
- **SDMMC1**：SD 卡接口（支持 4-bit 模式）
- **TIM3**：定时器触发采样
- **GPIO**：WiFi 模块控制引脚（WIFI_DATA_EN 等）

**STM32H743 外设配置：**
- 6 个 SPI
- 4 个 USART + 4 个 UART
- 2 个 USB OTG
- 2 个 SDMMC
- 22 个定时器
- 140+ GPIO

### 6. DCache 和缓存管理

**STM32H743 的 DCache 特性：**
- **L1 Cache**：16 KB 指令 Cache + 16 KB 数据 Cache
- **AXI 总线**：支持突发传输，提高吞吐量
- **Cache 一致性管理**：SCB_CleanDCache、SCB_InvalidateDCache

**DMA 缓存一致性问题：**
```c
// 写入前清理 Cache
SCB_CleanDCache_by_Addr((uint32_t*)addr, size);

// 读取前失效 Cache
SCB_InvalidateDCache_by_Addr((uint32_t*)addr, size);
```

**为什么需要 DCache：**
- 高频 DMA 传输会绕过 CPU Cache
- 如果不管理一致性，DMA 传输的数据可能被 Cache 覆盖
- STM32H7 提供了完整的 Cache 管理机制
- STM32F7 也有 Cache，但性能较弱
- STM32F4 没有 DCache，需要手动管理内存属性

### 8. 为什么不选择其他 MCU？

#### STM32F407（不推荐）
❌ **SPI 数量不足**：只有 3 个，无法满足 INTAN + WiFi 需求
❌ **性能不足**：168 MHz 主频，处理 256 通道数据压力大
❌ **SRAM 太小**：192 KB，无法容纳 160 KB 环形缓冲区
❌ **无 DCache**：需要手动管理内存属性

#### STM32F746（勉强可用）
⚠️ **性能较弱**：216 MHz 主频，余量不足
⚠️ **SRAM 偏小**：320 KB，环形缓冲区占用一半以上
✅ **SPI 数量足够**：6 个 SPI 接口
✅ **有 DCache**：支持缓存管理

#### ESP32（不适合）
❌ **不适合外设控制**：主控 WiFi 功能，不适合做主控
❌ **开发模式不同**：基于 FreeRTOS，与裸机设计不符
❌ **稳定性**：实时性不如 STM32 系列

#### STM32L4（性能不足）
❌ **主频太低**：最高 120 MHz，无法满足高频采集
❌ **SPI 数量不足**：只有 3 个
❌ **SRAM 偏小**：320 KB，且无 AXI SRAM

### 9. 功耗设计考虑

**功耗需求分析：**

项目为科研和医疗设备，功耗是重要考量因素：

**STM32H743 功耗特性：**
- **运行功耗**：约 100-150 mA @ 480MHz（3.3V）
- **低功耗模式**：支持 Sleep、Stop、Standby 三种模式
- **动态功耗调节**：可根据负载调整时钟频率
- **外设功耗控制**：可独立关闭不使用的外设

**实际功耗估算：**
```
正常运行（全速采集 + WiFi 传输）：~500 mW
待机模式：~10 mW
SD 卡模式（WiFi 关闭）：~300 mW
```

**功耗优化策略：**
- 根据采样率动态调整主频（低采样率降低时钟）
- 不使用时关闭 WiFi 模块供电
- DMA 传输降低 CPU 占用率，间接降低功耗
- SD 卡写入完成后关闭 SDMMC 外设

**对比 FPGA 的功耗：**
FPGA 方案即使功能简单，功耗通常在 1-2W 以上，远高于 MCU 方案。

### 10. 为什么不选择 FPGA？

#### FPGA 的优势

❌ **不适用于本项目的原因：**

**1. 成本过高**
- FPGA 芯片成本：$20-50（同性能级别）
- STM32H743：$8-10
- FPGA 需要额外的配置 Flash、电源管理芯片
- 开发工具链成本高（Xilinx/Intel 工具 license 昂贵）

**2. 开发门槛高**
- 需要掌握 Verilog/VHDL 硬件描述语言
- 时序约束和时钟域设计复杂
- 调试难度远高于 MCU
- 团队成员不熟悉 FPGA 开发

**3. 开发周期长**
- FPGA 设计-仿真-综合-布局布线流程繁琐
- 时序收敛需要反复调试
- 硬件调试不如 MCU 灵活
- 迭代成本高（综合时间可能数小时）

**4. 过度设计**
- 项目逻辑相对简单（SPI 通信 + DMA + 缓冲区）
- 不需要 FPGA 的并行处理能力
- MCU 的性能已经完全满足需求
- FPGA 的优势（高速并行处理）无法发挥

**5. 功耗问题**
- FPGA 动态功耗远高于 MCU
- 即使空闲状态功耗也较高
- 不适合可能需要电池供电的场景

**6. 维护和扩展性**
- MCU 代码易于维护和扩展
- FPGA 代码修改需要重新综合
- 新人上手难度大
- 知识传承困难

**FPGA 适用的场景：**
✅ 超高速数据采集（GHz 级别）
✅ 复杂的并行算法处理（图像、视频）
✅ 需要自定义硬件加速器
✅ 超低延迟应用（< 100ns）
✅ 协议转换和接口桥接

**本项目特点：**
- 数据流相对简单（SPI 通信）
- 时序要求在 μs 级别（MCU 完全满足）
- 逻辑复杂度中等
- 成本敏感
- 开发周期要求短

**结论：FPGA 是过度设计，成本高、开发难，不适合本项目。**

## 软件架构选型：为什么选择裸机而不是 RTOS？

### 软件选型分析

### 1. 实时性要求极高

神经信号采集对时序要求非常严格：

```
定时器中断 → 采集数据 → DMA传输 → 环形缓冲区 → 写入SD卡
```

- **10000 Hz 采样率** 意味着每 100 μs 就要完成一次采集
- **256 通道** 数据量大，需要极高的吞吐量
- 裸机直接响应中断，无调度延迟，能保证 μs 级的精确时序控制

**RT OS 的问题：**
- 任务调度会引入不可预测的延迟（几十到几百 μs）
- 上下文切换开销会影响高频采集
- 抢占式调度可能打断关键数据流

### 2. 确定性和可预测性

在数据采集系统中，确定性比平均性能更重要：

| 场景 | 裸机 | RTOS |
|------|------|------|
| 定时器中断响应 | 固定延迟（几个时钟周期） | 变动延迟（取决于任务状态） |
| DMA 传输控制 | 完全可控 | 可能被任务调度打断 |
| 缓冲区管理 | 精确控制读写指针 | 依赖任务同步机制 |
| 临界区保护 | 简单关中断 | 需要互斥锁/信号量 |

**裸机的优势：**
- 可以精确计算每个环节的执行时间
- 不会出现意外的任务抢占
- 便于实现零拷贝的 DMA 传输

### 3. 资源利用率

STM32H7 虽然性能强大（480MHz），但资源仍需精打细算：

**裸机方案资源占用：**
- 代码空间：约 50-100 KB
- RAM：约 10-20 KB（环形缓冲区除外）
- 无额外开销

**RTOS 方案资源占用：**
- RTOS 内核：10-30 KB Flash
- 每个任务栈：1-4 KB RAM
- 系统对象（信号量、队列等）：额外 RAM
- 额外的调度开销：CPU 时间

对于 256 通道采集项目，160KB 的环形缓冲区已经是固定开销，再引入 RTOS 会增加不必要的资源消耗。

### 4. 功能相对单一

项目核心功能明确且集中：

```
主循环 + 中断驱动的模块化设计：
├── 定时器中断：触发数据采集
├── SPI DMA：WiFi 数据传输
├── SDMMC DMA：SD 卡写入
├── UART + IDLE：命令解析
└── 环形缓冲区：数据缓存
```

没有复杂的业务逻辑，无需多任务并发：
- 没有 UI 交互（UI 在上位机 Qt 应用）
- 没有复杂的协议栈（自定义协议）
- 没有文件系统（自定义文件格式）
- 没有网络协议栈（WiFi 模块自带）

### 5. 调试和可控性

裸机开发在调试上有明显优势：

**中断优先级配置：**
```
UART IDLE 中断（最高优先级）
    ↓ 接收命令
定时器中断
    ↓ 触发采集
DMA 传输完成中断
    ↓ 处理数据
```

- 优先级配置简单直观
- 不会出现优先级反转问题
- 便于追踪和定位问题

**DMA 缓存一致性问题：**
```c
// STM32H7 DCache 一致性管理
SCB_CleanDCache_by_Addr((uint32_t*)addr, size);   // 写前清理
SCB_InvalidateDCache_by_Addr((uint32_t*)addr, size); // 读前失效
```

- 裸机可以精确控制 DMA 缓存一致性
- 不会因为任务切换导致缓存状态不一致
- 便于实现零拷贝优化

### 6. 启动和响应速度

裸机方案的启动和响应更快：

| 指标 | 裸机 | RTOS |
|------|------|------|
| 启动时间 | < 10ms | 50-200ms（RTOS 初始化） |
| 首次中断响应 | < 1μs | 1-10μs（任务就绪检查） |
| 系统稳定时间 | 立即 | 需等待任务调度稳定 |

对于数据采集设备，快速启动意味着：
- 可以快速响应上位机命令
- 减少等待时间
- 提升用户体验

## 适用场景对比

### 裸机适用场景

✅ 高实时性要求（μs 级）
✅ 功能相对单一
✅ 数据流需要严格确定性
✅ 资源受限（Flash/RAM 紧张）
✅ 需要精细控制底层硬件
✅ 简单的命令-响应模式

### RTOS 适用场景

✅ 多任务并发（UI + 业务 + 通信）
✅ 复杂的状态机
✅ 需要文件系统、网络协议栈
✅ 多个独立的业务逻辑
✅ 需要模块化和团队协作
✅ 复杂的同步和通信需求

## 技术架构设计

### 裸机方案的模块化架构

虽然没有 RTOS，但依然采用了良好的模块化设计：

```
main()
├── 初始化阶段
│   ├── 硬件初始化（GPIO、定时器、DMA）
│   ├── 缓冲区初始化（环形缓冲区）
│   ├── 外设初始化（SPI、UART、SDMMC）
│   └── 中断优先级配置
│
├── 主循环（while(1)）
│   ├── 状态机处理
│   ├── 命令解析
│   └── 错误处理
│
└── 中断服务程序
    ├── TIM3 定时器中断：触发采集
    ├── UART6 IDLE 中断：接收命令
    ├── SPI5 DMA 完成中断：WiFi 传输
    └── SDMMC DMA 完成中断：SD 卡写入
```

这种设计既保持了裸机的确定性，又具备良好的代码组织结构。

## 总结

### 选择 STM32H743 的核心理由

**硬件选型：**
1. **多 SPI 接口**：6 个 SPI，满足 INTAN + WiFi 需求
2. **高性能内核**：480 MHz Cortex-M7，187 倍性能余量
3. **大容量 SRAM**：1 MB SRAM，512 KB AXI SRAM 存放缓冲区
4. **强大 DMA**：39 个 DMA 通道，支持零拷贝优化
5. **丰富外设**：SPI、UART、SDMMC、USB 等完整接口
6. **功耗优化**：动态功耗调节，待机功耗 ~10 mW

**为什么不选 FPGA：**
1. **成本过高**：芯片成本 2-5 倍，开发工具链昂贵
2. **开发门槛高**：需要 Verilog/VHDL，时序设计复杂
3. **开发周期长**：综合调试时间长，迭代成本高
4. **过度设计**：项目逻辑简单，MCU 性能完全满足
5. **功耗问题**：FPGA 动态功耗 1-2W，远高于 MCU
6. **维护困难**：新人上手难，知识传承困难

### 选择裸机的核心理由

1. **实时性**：256 通道、高采样率要求 μs 级响应
2. **确定性**：数据流需要严格的时序控制，不可接受调度延迟
3. **资源效率**：STM32H7 性能足够，无需 RTOS 开销
4. **功能单一**：核心功能明确，无需多任务并发
5. **可控性**：调试、优化、性能调优更直接
6. **快速响应**：启动快、中断响应快

### 团队合作优势

1. **技术栈统一**：团队熟悉 STM32 生态，降低学习成本
2. **开发效率高**：C 语言开发快，调试工具友好
3. **降低风险**：技术栈成熟，社区支持完善
4. **便于维护**：代码库统一，新人容易接手
5. **成本控制**：开发成本低，周期短，维护成本低

### 项目成果

通过 STM32H743 + 裸机方案成功实现：
- ✅ 稳定支持 1-10000 Hz 采样率
- ✅ 256 通道实时采集
- ✅ WiFi/SD 卡/USB 三种传输模式
- ✅ 零拷贝 DMA 传输
- ✅ 精确的缓冲区管理
- ✅ 端到端全栈开发（下位机 + 上位机）
- ✅ 功耗优化（运行 ~500mW，待机 ~10mW）

这是一个典型的**高性能数据采集场景**，STM32H743 + 裸机方案是**最优、最经济、最可靠**的技术选择。
