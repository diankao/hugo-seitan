# DMA数据传输中的cache问题与解决

## 题目

涉及DMA的数据传输中，如果没有正确处理cache，会导致什么现象？如何解决？
这道面试题本身就是一个 只在带 D$ 的平台上才有意义 的问题.
## 考察点

DMA原理、cache机制、软硬件协同

## 回答要点

### 1. DMA 与 CPU 的并行访问路径

```
┌──────────┐     ┌──────────────┐
│   CPU    │────▶│ L1/L2 Cache  │────┐
└──────────┘     └──────────────┘    │
                                       │
                                       ▼
                                 ┌──────────┐
                                 │  主存     │
                                 │  (DDR)   │
                                 └────┬─────┘
                                      ▲
┌──────────┐     ┌──────────────┐    │
│  外设    │────▶│  DMA 控制器  │────┘
└──────────┘     └──────────────┘
```

**关键矛盾**：

- CPU 通过 cache 访问内存，读到的是 cache 中的副本
- DMA 直接访问主存，绕过 cache
- 两者的数据视图可能不一致

### 2. 前提：哪些平台存在此问题

**DMA + cache 一致性问题只存在于带 D$ （Data Cache）的处理器上**：

| 处理器类型           | 有无 D$ | 是否需要处理 | 典型芯片            |
| --------------- | ----- | ------ | --------------- |
| Cortex-M0/M3/M4 | 无     | 不需要    | STM32F1/F4、GD32 |
| Cortex-M7       | 有     | 需要     | STM32H7、i.MX RT |
| Cortex-A 系列     | 有     | 需要     | i.MX6、RK3399    |
| 影像/医疗设备 SoC     | 有     | 需要     | 联影自研 SoC        |

**没有 D$ 的平台（如 Cortex-M4）**：CPU 和 DMA 直接操作同一物理内存，不存在一致性问题，CPU 写什么 DMA 就读到什么，不需要任何额外处理。

**有 D$ 的平台（如 Cortex-M7/A53）**：CPU 的 load/store 经过 cache，DMA 直接访问主存，两者看到的数据可能不同，下文所有场景均基于此类平台。

### 3. 未正确处理 cache 导致的现象

#### 场景一：CPU 发送数据，DMA 读取（TX 方向）

```
CPU 写入 buffer[] = {0xAA, 0xBB, 0xCC, 0xDD}
      │
      ▼
数据缓存在 L1 D$（Write-Back 模式）
主存中 buffer[] 仍然是旧值 {0x00, 0x00, 0x00, 0x00}
      │
      ▼
DMA 从主存读取 buffer[] ──▶ 发送出去的是 {0x00, 0x00, 0x00, 0x00}！
```

**现象**：

- 发送数据错误，对方收到旧数据或全零
- 偶发性出现（取决于 cache line 是否被 eviction）
- 数据量小时可能刚好 cache line 被替换，反而正常

#### 场景二：DMA 写入数据，CPU 读取（RX 方向）

```
DMA 接收数据写入 buffer[] = {0x11, 0x22, 0x33, 0x44}
      │
      ▼
主存中 buffer[] 已更新
但 CPU 的 L1 D$ 中仍有旧的 cache line {0x00, 0x00, 0x00, 0x00}
      │
      ▼
CPU 读取 buffer[] ──▶ 读到的是 cache 中的旧值 {0x00, 0x00, 0x00, 0x00}！
```

**现象**：

- 接收数据错误，CPU 读到旧数据
- 连续接收时可能"丢失"某些包的内容
- 前几次接收正常，后续出错（cache 被填满后）

#### 场景三：混合场景（双向通信）

- 发送和接收同时出现数据错误
- 错误模式不确定，与系统负载和 cache 替换策略有关
- 高负载时更容易出现（cache 压力大，eviction 频繁）

### 3. 解决方案

#### 方案一：手动 cache 维护（最常用）

```c
// TX 方向：CPU 写完后，flush cache 到主存
void dma_send(uint8_t *buf, uint32_t len) {
    // CPU 填充发送缓冲区
    prepare_tx_data(buf, len);

    // 将 cache 中的脏数据写回主存
    SCB_CleanDCache_by_Addr((uint32_t *)buf, len);
    // 或 Cortex-M7:
    // SCB_CleanDCache();

    // 启动 DMA 传输
    DMA_StartTransfer(DMA_CH_UART_TX, buf, len);
}

// RX 方向：DMA 完成后，invalidate cache
void dma_recv_complete(uint8_t *buf, uint32_t len) {
    // DMA 传输完成回调中
    // 使 cache line 失效，强制下次从主存读取
    SCB_InvalidateDCache_by_Addr((uint32_t *)buf, len);

    // CPU 读取接收到的数据
    process_rx_data(buf, len);
}
```

**注意事项**：

- `Clean` = 将脏 cache line 写回主存（写回，不失效）
- `Invalidate` = 将 cache line 标记为无效（丢弃，下次从主存读）
- `CleanAndInvalidate` = 先写回再失效（两者结合）
- 操作地址必须对齐到 cache line 大小（通常 32 字节）

#### 方案二：Non-Cacheable 内存区域

```c
// 通过 MPU 将 DMA buffer 区域配置为 Non-Cacheable
MPU_Region_InitTypeDef MPU_InitStruct = {
    .BaseAddress = 0x20000000,
    .Size = MPU_REGION_SIZE_16KB,
    .AccessPermission = MPU_REGION_FULL_ACCESS,
    .TypeExtField = MPU_TEX_LEVEL0,    // TEX = 000
    .IsCacheable = MPU_ACCESS_NOT_CACHEABLE,  // Non-Cacheable
    .IsBufferable = MPU_ACCESS_BUFFERABLE,
    .IsShareable = MPU_ACCESS_SHAREABLE,
};

// DMA buffer 放在此区域
__attribute__((section(".dma_buf"))) uint8_t dma_tx_buf[1024];
__attribute__((section(".dma_buf"))) uint8_t dma_rx_buf[1024];
```

**优缺点**：

| 方面  | 优点            | 缺点                  |
| --- | ------------- | ------------------- |
| 性能  | 无需手动 cache 维护 | CPU 访问该区域始终慢        |
| 复杂度 | 代码简单          | 需要 linker script 配合 |
| 实时性 | 数据一致性自动保证     | 每次 CPU 访问都访问主存      |

#### 方案三：紧耦合内存（TCM / SRAM）

```c
// Cortex-M7 的 DTCM 不经过 cache，适合 DMA buffer
__attribute__((section(".dtcm"))) uint8_t dma_buf[2048];

// 但注意：部分 SoC 的 DMA 无法访问 TCM！
// 需要查阅 Reference Manual 确认 DMA bus matrix
```

#### 方案四：cache line 对齐的 buffer 设计

```c
// 确保 DMA buffer 起始地址和长度都对齐到 cache line
#define CACHE_LINE_SIZE  32
#define ALIGNED_BUF(name, size) \
    __attribute__((aligned(CACHE_LINE_SIZE))) \
    uint8_t name[((size + CACHE_LINE_SIZE - 1) / CACHE_LINE_SIZE) * CACHE_LINE_SIZE]

ALIGNED_BUF(tx_buf, 256);
ALIGNED_BUF(rx_buf, 256);

// 这样 clean/invalidate 不会影响相邻数据
```

### 4. 不同 Cortex 系列的差异

| 特性           | Cortex-M4 | Cortex-M7             | Cortex-A     |
| ------------ | --------- | --------------------- | ------------ |
| D$           | 无         | 有（可选）                 | 有            |
| cache 维护     | 不需要       | SCB\_Clean/Invalidate | clrit/mcr 指令 |
| SCU          | 无         | 无                     | 有            |
| bus snooping | 无         | 部分支持                  | 有（仅核间）       |

**Cortex-M4**：没有 D$，DMA 与 CPU 直接操作同一主存，不存在一致性问题。

**Cortex-M7**：引入 D$，必须处理 cache 一致性。部分 STM32H7 的 DMA 支持通过 DTCM 或特定路径绕过 cache。

**Cortex-A**：有 SCU 维护核间一致性，但 DMA 仍需手动处理（DMA 不参与 SCU 协议）。

### 6. 常见陷阱

#### 陷阱一：cache line 边界污染

```c
// DMA buffer 未对齐到 cache line
uint8_t buf[100];    // 起始地址可能不对齐

// invalidate 时影响相邻变量
SCB_InvalidateDCache_by_Addr((uint32_t *)buf, 100);
// 如果 buf 起始地址不在 cache line 边界，
// 相邻变量的 cache 内容也会被 invalidate！
```

#### 陷阱二：部分 clean/invalidate 的原子性

```c
// DMA 正在写入时 invalidate
// 可能读到半新半旧的数据
// 必须在 DMA 完成中断后再 invalidate
```

#### 陷阱三：编译器优化导致地址不对齐

```c
// 编译器可能在 buffer 前插入其他变量
// 导致 buffer 起始地址不在 cache line 边界
// 解决：显式 aligned 属性或使用专用内存区域
```

### 6. 最佳实践总结

- **DMA buffer 必须对齐到 cache line**（32 字节或 64 字节，视平台）
- **TX 流程**：CPU 写入 → Clean cache → 启动 DMA
- **RX 流程**：DMA 完成中断 → Invalidate cache → CPU 读取
- **优先使用 Non-Cacheable 区域**放置 DMA buffer（如果带宽允许）
- **确认 DMA 可访问的地址空间**（TCM / SRAM / DDR）
- **在 DMA 传输期间禁止 CPU 访问同一 buffer**
