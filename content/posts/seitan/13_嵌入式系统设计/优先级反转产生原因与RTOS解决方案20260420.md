# 优先级反转产生原因与RTOS解决方案

## 题目

优先级反转是如何产生的？在RTOS中有哪些解决方案？如何评估这些方案的代价？

## 考察点

RTOS调度原理、优先级反转机制、实时性保障

## 回答要点

### 1. 优先级反转的产生过程

#### 经典三任务模型

```
优先级：H（高）> M（中）> L（低）

时间 ──────────────────────────────────────────────────▶

任务 L  ████████                          ████████
               │拿到 Mutex                    │释放 Mutex
               ▼                              ▼
任务 M               ████████████████████████
                      抢占了 L，L 无法释放 Mutex

任务 H                        │
                              ▼被 Mutex 阻塞
                              ▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄
                              ▲
                              │
                     H 等 M 运行完
                     M 等 L 释放 Mutex
                     但 L 被 M 抢占了！
                     → H 的实际延迟 = M 的执行时间
```

**关键步骤**：
1. L 获取 Mutex，进入临界区
2. H 就绪，抢占 L（H 优先级更高）
3. H 尝试获取同一个 Mutex，被阻塞
4. M 就绪，M 优先级高于 L 但低于 H
5. M 抢占 L 开始运行
6. L 无法运行 → 无法释放 Mutex → H 无法运行
7. **H 被 M 间接阻塞了**，虽然 H 的优先级远高于 M

#### 火星探路者号真实案例（1997）

- 火星探路者号上的 VxWorks RTOS 中发生了优先级反转
- 高优先级的总线管理任务被低优先级的气象任务阻塞
- 中优先级的通信任务持续运行，导致总线管理任务长时间得不到调度
- 触发了看门狗复位
- **解决方案**：地面团队远程开启了优先级继承，问题解决

### 2. 解决方案一：优先级继承（Priority Inheritance）

#### 原理

```
优先级：H（高）> M（中）> L（低）

时间 ──────────────────────────────────────────────────▶

任务 L  ████████                ████████
               │拿到 Mutex     │优先级恢复为 L
               │               │释放 Mutex（此时优先级已恢复）
               ▼               ▼
任务 M               │被 L（继承了 H 的优先级）阻止
                      无法抢占 L！

任务 H               │等待 Mutex
                      ▼
                      ▄▄▄▄▄▄▄▄▄▄
                                ▲
                          L 释放 Mutex
                          H 立即被唤醒
```

**当 H 等待 L 持有的 Mutex 时**：
- L 的优先级被临时提升到 H 的级别
- M 无法抢占 L
- L 尽快执行完临界区并释放 Mutex
- H 被唤醒，延迟 = L 临界区执行时间（而非 M 的执行时间）

#### FreeRTOS 实现

```c
// 使用 xSemaphoreCreateMutex（内置优先级继承）
SemaphoreHandle_t mutex = xSemaphoreCreateMutex();

// 优先级继承是自动的：
// 当高优先级任务尝试获取被低优先级任务持有的 Mutex 时
// FreeRTOS 自动将持有者的优先级提升到等待者的级别
// Mutex 释放后自动恢复原优先级
```

**注意事项**：
- `xSemaphoreCreateMutex()` 支持优先级继承
- `xSemaphoreCreateBinary()` **不支持**优先级继承
- `xSemaphoreCreateRecursiveMutex()` 也支持优先级继承

#### 代价

| 方面 | 影响 |
|------|------|
| 实现复杂度 | RTOS 内核支持，应用层无感 |
| 运行时开销 | 每次 Mutex 操作额外检查和修改优先级，开销很小 |
| 优先级变化 | 持锁任务的优先级被临时提升，可能影响其他同优先级任务的调度 |
| 连锁继承 | 如果多个任务形成等待链，需要逐级提升，复杂度增加 |
| 不防死锁 | 优先级继承只解决反转，不解决死锁 |

### 3. 解决方案二：优先级上限（Priority Ceiling）

#### 原理

```c
// 每个 Mutex 在创建时指定一个"天花板优先级"
// 天花板优先级 = 所有可能获取该 Mutex 的任务中最高优先级 + 1（或就等于最高）

// 当任务获取 Mutex 时，立即将自身优先级提升到天花板级别
// 不需要等到高优先级任务来请求才提升

#define CEILING_PRIO (configMAX_PRIORITIES - 2)  // 很高的优先级

// 获取 Mutex 的瞬间就提升
void ceiling_lock(SemaphoreHandle_t mutex) {
    vTaskPrioritySet(NULL, CEILING_PRIO);
    xSemaphoreTake(mutex, WAIT_FOREVER);
}

void ceiling_unlock(SemaphoreHandle_t mutex, UBaseType_t orig_prio) {
    xSemaphoreGive(mutex);
    vTaskPrioritySet(NULL, orig_prio);
}
```

#### 与优先级继承的区别

| 对比项 | 优先级继承 | 优先级上限 |
|--------|-----------|-----------|
| 提升时机 | 高优先级任务请求时 | 获取 Mutex 时立即提升 |
| 提升到什么级别 | 等待者的优先级 | 预设的天花板优先级 |
| 是否需要预知信息 | 不需要 | 需要预知哪些任务会用这把锁 |
| 防死锁 | 否 | 可以防（如果所有锁都有 ceiling） |

#### 代价

| 方面 | 影响 |
|------|------|
| 设计约束 | 需要预先分析所有使用该锁的任务优先级 |
| 优先级过度提升 | ceiling 可能设得过高，影响原本不该被影响的任务 |
| 不够灵活 | 任务优先级变化时需要同步更新 ceiling |

### 4. 解决方案三：禁止调度 / 关中断

#### 原理

```c
// 单核系统上，最简单粗暴的方式
// 临界区内不会被抢占 → 不可能发生优先级反转

// 方式1：关中断（最硬）
__disable_irq();
shared_var++;
__enable_irq();

// 方式2：锁调度器（稍软）
vTaskSuspendAll();
shared_var++;
xTaskResumeAll();

// 方式3：FreeRTOS 临界区
taskENTER_CRITICAL();
shared_var++;
taskEXIT_CRITICAL();
```

#### 代价

| 方面 | 影响 |
|------|------|
| 中断延迟 | 关中断期间所有中断被屏蔽，严重影响实时性 |
| 系统响应 | 其他高优先级任务也无法运行 |
| 只能用于极短操作 | 必须保证临界区在微秒级完成 |
| 仅限单核 | 多核系统关中断不能阻止其他核的并发访问 |

### 5. 三种方案对比

```
                    优先级继承        优先级上限        禁止调度
                    ──────────       ──────────       ──────────
实时性保障          良好              最优              取决于临界区长度
实现复杂度          低（内核支持）     中（需预设）       最低
运行时开销          小                小                无（但关中断代价大）
适用场景            通用              安全关键系统       极短临界区
多核支持            需要额外机制       需要额外机制       不支持
防死锁              否                可以              否
典型标准            POSIX             OSEK/VDX         简单单核系统
```

### 6. 实际工程中的选择建议

**通用嵌入式项目**：
- 使用 `xSemaphoreCreateMutex()`，开箱即用的优先级继承
- 大多数场景足够

**安全关键系统（医疗/汽车）**：
- 使用优先级上限协议（OSEK OS 的 Resource 机制就是 ceiling protocol）
- 符合 MISRA / ISO 26262 对实时性的严格要求

**极短临界区（读改写几行代码）**：
- `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`
- 简单直接，几条指令完成

**多核系统**：
- 单核的优先级继承和关中断都不够用
- 需要自旋锁（spinlock）+ 优先级继承的组合
- 或使用硬件原子操作实现无锁算法

### 7. 诊断优先级反转的方法

```c
// 监控 Mutex 持有时间
typedef struct {
    SemaphoreHandle_t handle;
    const char *name;
    TickType_t max_hold_time;
    TickType_t max_wait_time;
} monitored_mutex_t;

void monitored_take(monitored_mutex_t *m) {
    TickType_t t0 = xTaskGetTickCount();
    xSemaphoreTake(m->handle, WAIT_FOREVER);
    TickType_t wait = xTaskGetTickCount() - t0;
    if (wait > m->max_wait_time) {
        m->max_wait_time = wait;
        log_warning("mutex %s: new max wait %d ticks, by task %s",
                    m->name, wait, pcTaskGetName(NULL));
    }
}
```

**如果某个 Mutex 的等待时间远超预期**，且持锁任务优先级较低，很可能发生了优先级反转。
