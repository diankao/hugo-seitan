# ARM多核cache一致性保证与问题分析

## 题目

在ARM多核系统中，cache一致性是如何保证的？如果cache使用不当，可能会出现什么问题？

## 考察点

ARM体系结构、多核编程、缓存机制

## 回答要点

### 1. ARM 多核 cache 层次结构

```
┌────────────┐  ┌────────────┐
│  Core 0    │  │  Core 1    │
│ ┌────────┐ │  │ ┌────────┐ │
│ │ L1 I$  │ │  │ │ L1 I$  │ │
│ │ L1 D$  │ │  │ │ L1 D$  │ │
│ └───┬────┘ │  │ └───┬────┘ │
└─────┼──────┘  └─────┼──────┘
      │               │
      ▼               ▼
┌──────────────────────────┐
│     L2 Cache（共享）     │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│     主存（DDR）          │
└──────────────────────────┘
```

- **L1 Cache**：每个核心私有，分为指令缓存（I$）和数据缓存（D$）
- **L2 Cache**：多核共享，部分 SoC 也支持分区私有
- **SCU（Snoop Control Unit）**：Cortex-A 系列中负责维护 L1 间一致性

### 2. 硬件层面的 cache 一致性机制

#### MESI 协议（简化模型）

ARM 多核系统中广泛使用 MESI 及其变体来维护 cache line 状态：

| 状态 | 含义 | 说明 |
|------|------|------|
| **M**odified | 已修改 | 数据已被修改，仅存在于本核 cache，与主存不一致 |
| **E**xclusive | 独占 | 数据仅存在于本核 cache，与主存一致 |
| **S**hared | 共享 | 数据可能存在于多个核的 cache，与主存一致 |
| **I**nvalid | 无效 | cache line 无效，读取需从下级存储获取 |

#### SCU（Snoop Control Unit）工作原理

```
Core A 写入地址 X
       │
       ▼
  ┌─────────┐
  │   SCU   │─── 广播 invalidation ───▶ Core B 的 cache line X
  │         │                          状态置为 Invalid
  └─────────┘
```

- Core A 写入某 cache line 时，SCU 向其他核广播无效化请求
- 其他核中该 cache line 被标记为 Invalid
- 后续其他核读取时必须重新从 L2 或主存获取最新数据

#### 硬件自动保证的场景

- **核间普通变量访问**：SCU 自动维护 L1 D$ 一致性
- **DMA 与 cache**：部分 SoC 的 cache controller 支持总线监听（bus snooping），但不是所有平台都支持

### 3. 硬件无法自动保证的场景

#### Store Buffer 导致的重排

```
Core A                    Core B
────────                  ────────
STORE data = 42
  │（还在 store buffer）
  │                       LOAD flag → 看到 1
  │                       LOAD data → 可能还是旧值！
STORE flag = 1
  │（到达 cache）
```

**原因**：Core A 的 store 先进入 store buffer，尚未 commit 到 cache；Core B 通过 SCU 只能看到已 commit 的数据。

#### 解决方案：内存屏障

```c
// ARM 内存屏障指令
DMB  // Data Memory Barrier：确保之前的内存访问完成
DSB  // Data Synchronization Barrier：等待所有内存访问完成
ISB  // Instruction Synchronization Barrier：刷新流水线

// C 语言内建函数
__dmb(0xF);   // DMB ISH（Inner Shareable）
__dsb(0xF);   // DSB ISH
__isb(0xF);   // ISB
```

#### 正确的同步模式

```c
// 生产者（Core A）
data = 42;
__dmb(0xF);             // 确保 data 写入对其他核可见
flag = 1;

// 消费者（Core B）
while (flag != 1);
__dmb(0xF);             // 确保读到 flag 后刷新，读取最新 data
use(data);
```

### 4. cache 使用不当导致的典型问题

#### 问题一：DMA 与 cache 不一致

```
CPU 写入数据到 buffer ──▶ 数据缓存在 L1/L2
DMA 从同一 buffer 读取 ──▶ 直接访问主存，读到旧数据！
```

**解决方案**：
```c
// 方案1：cache flush（写场景）
// CPU 写完后，flush 到主存，DMA 再读取
SCB_CleanDCache_by_Addr((uint32_t *)buffer, size);

// 方案2：cache invalidate（读场景）
// DMA 写完后，invalidate cache，CPU 再读取
SCB_InvalidateDCache_by_Addr((uint32_t *)buffer, size);

// 方案3：将 DMA buffer 配置为 Non-Cacheable
// 通过 MPU 设置内存属性
```

#### 问题二：自修改代码

```c
// 修改代码段后直接执行
memcpy((void *)0x08001000, patch, sizeof(patch));
// I$ 中还是旧指令！
func();   // 执行旧代码

// 修复：
__dsb(0xF);
SCB_InvalidateICache();
__isb(0xF);
func();
```

#### 问题三：设备寄存器访问

```c
// 外设寄存器必须声明为 volatile
// 且访问地址区域应配置为 Device 类型（Non-Cacheable）
volatile uint32_t *reg = (volatile uint32_t *)0x40001000;
*reg = 0x01;          // 不能被缓存

// MPU 配置该区域为 Device nGnRnE
```

#### 问题四：多核无锁通信的可见性

```c
// 错误的无锁通信
struct ring_buf {
    volatile uint32_t head;
    volatile uint32_t tail;
    uint8_t data[256];
};

// 生产者更新 head 时，消费者可能看不到最新值
// 需要使用 acquire/release 语义或显式内存屏障
```

### 5. ARM 内存属性与 cache 策略

| 内存类型 | 属性 | 典型用途 |
|----------|------|----------|
| Normal Cacheable WB | 可缓存、写回 | 普通RAM |
| Normal Cacheable WT | 可缓存、写通 | 特殊RAM |
| Normal Non-Cacheable | 不可缓存 | 共享缓冲区 |
| Device nGnRnE | 设备、不可聚合 | 外设寄存器 |
| Device nGnRE | 设备、可聚合 | 较宽松的外设访问 |

**配置方式**：通过 MMU 页表属性位（MAIR + PTE）或 MPU 区域属性

### 6. 最佳实践总结

- **共享变量用原子操作或锁**：隐含正确的内存屏障
- **DMA buffer 做 cache 维护**：写前 clean，读前 invalidate
- **外设寄存器用 volatile + Device 属性**：禁止 cache 和重排
- **多核无锁结构要显式使用内存屏障**：`dmb` / `dsb` 或 C11 atomic
- **自修改代码要刷新 I$**：`InvalidateICache` + `ISB`
- **理解 ARM 内存模型**：Weakly Ordered，需要软件显式保证顺序
