# 系统性能下降瓶颈定位与判断

## 题目

如果系统运行一段时间后性能下降，但 CPU 利用率不高，从哪些角度去判断瓶颈是在 CPU、内存、IO 还是锁竞争？

## 考察点

性能分析方法论、系统调优经验

## 回答要点

### 1. 现象分析

**"CPU 利用率不高但性能下降"说明什么**：
- CPU 不是瓶颈，问题在其他子系统
- 可能是等待资源（IO、锁、内存）
- 可能是系统调用 / 上下文切换开销大
- 可能是 cache miss 率上升导致有效算力下降

### 2. 各维度排查方法

#### CPU 维度

**虽然利用率不高，仍需排查的子项**：
- **上下文切换频率**：用 `perf stat` 或 `/proc/stat` 监控自愿/非自愿切换次数
- **软中断开销**：`cat /proc/softirqs` 查看软中断分布，`net_rx` / `timer` 是否异常高
- **cache miss 率**：用 `perf stat -e cache-misses,cache-references` 检测，miss 率上升等于有效算力下降
- **频率降频**：检查是否因过热降频（thermal throttling），读取 CPU 频率信息

**典型特征**：
| 指标 | 正常 | 异常 |
|------|------|------|
| CPU 利用率 | 均匀分布 | 某核长时间低但响应慢 |
| 上下文切换 | < 1000/s | > 10000/s |
| cache miss 率 | < 5% | > 15% |

#### 内存维度

**内存导致性能下降的典型原因**：
- **内存泄漏**：可用内存持续下降，触发频繁 GC 或 OOM
- **内存碎片化**：`malloc` 耗时增长，分配失败率上升
- **swap 频繁**（Linux）：`vmstat` 查看 `si/so` 列，swap in/out 说明物理内存不足
- **TLB miss**：大内存随机访问场景下 TLB 压力大

**检测方法**：
```bash
# 监控内存使用趋势
cat /proc/meminfo | grep -E "MemFree|MemAvailable|Slab"

# 监控内存分配延迟
perf record -e kmem:kmalloc -ag

# 检查碎片化程度
cat /proc/buddyinfo
```

**嵌入式 RTOS 场景**：
- 监控 `xPortGetFreeHeapSize()` 趋势
- 检查任务栈高水位（`uxTaskGetStackHighWaterMark`）
- 统计 `malloc/free` 调用次数和耗时

#### IO 维度

**IO 瓶颈的表现**：
- 任务阻塞在读写操作上（`D` 状态，uninterruptible sleep）
- IO 等待时间占比高（`iowait`）
- 写入延迟增大（Flash 写入需要擦除，延迟不稳定）

**检测方法**：
```bash
# Linux 系统
iostat -x 1          # 查看 %util、await
vmstat 1             # 查看 wa（iowait）列
cat /proc/diskstats  # 原始 IO 统计
```

**嵌入式 Flash 场景**：
- Flash 写入前需要擦除整块，擦除耗时可能达数百 ms
- 垃圾回收（GC）触发时会阻塞读写
- 磨损均衡算法可能导致写放大

#### 锁竞争维度

**锁竞争导致性能下降的表现**：
- CPU 利用率不高，但任务响应变慢
- 某些任务长期处于 `pending` / `blocked` 状态
- 吞吐量下降但无明显计算瓶颈

**检测方法**：
```c
// RTOS 中记录锁等待时间
TickType_t t0 = xTaskGetTickCount();
if (xSemaphoreTake(mutex, MAX_WAIT) == pdTRUE) {
    TickType_t wait_time = xTaskGetTickCount() - t0;
    if (wait_time > THRESHOLD) {
        log_warning("mutex wait too long: %d ms", wait_time);
    }
}
```

**Linux 系统中**：
```bash
# perf 分析锁竞争
perf record -e lock:contention_begin -ag
perf record -e futex -ag

# 查看 futex 等待
perf top -e syscalls:sys_enter_futex
```

### 3. 系统化排查流程

```
性能下降（CPU 利用率不高）
         │
         ▼
   ┌─────────────┐
   │ 是否 iowait │──Yes──▶ IO 瓶颈
   │ 偏高？      │         │ Flash GC / 块设备慢
   └──────┬──────┘         │ 网络延迟
          │ No
          ▼
   ┌─────────────┐
   │ 内存是否    │──Yes──▶ 内存瓶颈
   │ 持续下降？  │         │ 泄漏 / 碎片化
   └──────┬──────┘         │ swap 频繁
          │ No
          ▼
   ┌─────────────┐
   │ 上下文切换  │──Yes──▶ 调度开销
   │ 是否频繁？  │         │ 锁竞争导致
   └──────┬──────┘         │ 中断风暴
          │ No
          ▼
   ┌─────────────┐
   │ cache miss  │──Yes──▶ 内存访问模式
   │ 率是否高？  │         │ 变差
   └──────┬──────┘
          │ No
          ▼
   进一步细分排查
```

### 4. 随时间退化的特殊原因

**"运行一段时间后"才下降的特殊性**：
- **内存泄漏**：逐渐耗尽可用内存
- **碎片化**：堆或 Flash 空间碎片化加剧
- **日志文件增长**：占用存储空间和 IO 带宽
- **资源泄漏**：文件描述符 / 信号量 / 任务句柄未释放
- **定时器累积**：软件定时器未删除，回调堆积
- **统计信息膨胀**：某些数据结构只增不减

### 5. 建立性能基线

**主动监控策略**：
- 在系统运行时持续记录关键指标（CPU、内存、IO、上下文切换）
- 设定阈值告警（如内存下降速率、IO 延迟、锁等待时间）
- 建立性能回归自动化检测
- 定期 dump 系统状态快照用于对比分析
