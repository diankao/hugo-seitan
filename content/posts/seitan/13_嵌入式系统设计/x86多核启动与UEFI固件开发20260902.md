# x86 多核启动与 UEFI 固件

x86 服务器的启动链路涉及多核唤醒、ACPI 电源管理接口与 UEFI 固件驱动模型。本文整理 BSP/AP 的启动分工、ACPI/CPPC/PCC 的关系、UEFI 阶段划分与 Protocol 驱动模型、UEFI 环境下 C++ 的使用边界，以及 VT-d 与 VT-x 的分工。

## 上电与 BSP/AP 分工

上电复位后 x86 全部核心都开始执行，但硬件只选一个核作为 **BSP（Boot Strap Processor）**，其余为 **AP（Application Processor）**：

```
上电
  │
  ▼
BSP 执行 BIOS/UEFI 固件 ←── 只有 BSP 跑固件，AP 停在等待 SIPI 状态
  │
  ├── 固件阶段：BSP 通过 INIT-SIPI-SIPI 序列唤醒需要的 AP
  ▼
OS 内核 SMP 初始化：BSP 再次向各 AP 发送 INIT-SIPI-SIPI
      │
      └── SIPI 携带启动向量（实模式 段:偏移）
            └── AP 从该向量处执行由 BSP 侧准备的初始化代码
```

- AP 的微码与执行状态由硬件初始化，但 **AP 执行的初始化代码与入口向量是 BSP 准备并分发的**；
- 这也决定了 AP 唤醒顺序、启动向量地址由固件/内核的 SMP bring-up 代码控制。

## ACPI、CPPC 与 PCC

三者的关系：

- **ACPI**：高级配置与电源接口规范，OS 通过 ACPI 表与固件协商电源管理；
- **CPPC**（Collaborative Processor Performance Control）：ACPI 定义的**连续调频调压**接口（替代传统 P-state），性能与能耗控制更精细；
- **PCC**（Platform Communication Channel）：CPPC 与平台通信用的**共享内存通道**（ACPI 6.x 定义）。

内核启动卡在 `ACPI: PCC probe failed` 意味着 PCC 通道探测失败、CPPC 调频建立不起来。排查方向是**在固件/内核启用 CPPC 电源管理**，让 CPPC 依赖的 PCC 正常建立——而不是去关 APEI（RAS 接口）、改 APIC 表或关 SMMU。

## UEFI 的阶段划分与内存初始化

```
SEC → PEI → DXE → BDS → (OS Loader)
       │      │
       │      └── 驱动/协议加载（Handle + Protocol 模型）
       └── 内存初始化在此阶段（MRC: Memory Reference Code）
```

内存初始化发生在 PEI 阶段（内存训练），失败时**首先检查内存硬件连接**：内存条是否插紧、金手指/插槽是否氧化、配置是否在兼容列表（QVL）内；其次才考虑 BIOS/MRC 版本、UEFI 驱动冲突、电源问题。

## UEFI Protocol 驱动模型

UEFI 驱动模型的核心是 **Protocol**：C 结构体 + GUID 标识的接口表。驱动安装 Protocol，消费者用 `LocateProtocol / HandleProtocol` 打开、用后 `CloseProtocol` 释放。

访问 NVMe SSD 走 **EFI_NVM_EXPRESS_PASS_THRU** 协议，它把 NVMe Admin 命令透传给控制器：

- Identify Controller / Identify Namespace：获取盘信息；
- **Format NVM（带 Secure Erase）或 Sanitize**：安全擦除用户数据。

对照：EFI_ATA_PASS_THRU 对应 SATA 盘，SCSI_IO 对应 SCSI 通路，USB_IO 对应 U 盘，都不适用于 NVMe。

## UEFI 下的 C++：RAII 与禁用特性

UEFI 环境没有完整 C 运行时，**异常处理与 RTTI 被禁用**（依赖运行时支持且体积大）：

- 不能用 `std::shared_ptr` 这类依赖堆与异常语义的机制管理资源；
- **RAII 的正确做法：构造时打开/安装 Protocol，析构函数中调用 `CloseProtocol / UninstallProtocolInterface`**，对象出作用域自动释放；
- 可以放心使用：模板类（零运行时开销）、不依赖异常的自实现智能指针。

## Secure Boot 与度量启动

平台安全启动由两条互补的链路构成，经常被混为一谈：

**Secure Boot（强制执行）**——UEFI 固件校验后续引导的签名，不合法就拒绝执行：

- 签名体系是四层密钥数据库（UEFI 变量区）：**PK**（平台密钥，最高层，接管即拥有平台）→ **KEK**（密钥交换密钥）→ **db**（允许的签名/证书）/ **dbx**（吊销黑名单）；
- 流程：固件验 bootloader（如 shim）→ shim 验 grub（shim 是发行版绕开微软 KEK 的中转方案）→ grub 验内核（kernel 的 EFI stub）；
- Setup Mode：清掉 PK 进入安装模式可导入自己的密钥，自己签自己的一切；
- 关闭 Secure Boot 的机器（很多工控/开发板）这条链路就不存在。

**TPM 度量启动（记录报告）**——TPM 是主板上的可信密码协处理器，只有度量没有强制：

- 代码执行前先把**哈希扩展进 TPM 的 PCR 寄存器**（Extend: `PCR_new = Hash(PCR_old || measurement)`，不可逆、不可抵赖）：

```
PCR[0-7]: 固件/BIOS 各阶段与配置
PCR[8-9]: shim/grub
PCR[10]:  grub 菜单与命令行
PCR[11-15]: 内核、initrd、IMA 文件度量
```

- 度量链：SRTM（固件 root）→ bootloader → kernel → IMA（运行期文件度量），**只记录不阻止**，启动后可以：
  - **Seal**：用 PCR 值封存密钥（磁盘加密密钥只有"启动链未被篡改"时 TPM 才解封）；
  - **远程证明**：Quote PCR 签名发给验证方，证明软件栈未被篡改；
- 与 VT-d 无关：度量启动是密码学记录，不涉及 DMA 重映射。

两条链的分工一句话：**Secure Boot 拦"不信任的代码"，TPM 记"到底跑过什么"**；服务器与安全敏感场景两者常同时启用。


## VT-d 与 VT-x 的分工

| 技术 | 作用 | 依赖 |
| --- | --- | --- |
| VT-x | CPU 硬件虚拟化（VMX root/non-root） | KVM 等 hypervisor 的基础 |
| **VT-d** | **DMA 重映射（IOMMU）**，隔离设备 DMA | 设备直通、SR-IOV 的前提 |
| TPM 2.0 | 可信度量启动 | 与 VT-d 无关 |

- **设备直通**（把物理设备 DMA 直接暴露给虚机）必须 VT-d 做 IOMMU 地址隔离，否则虚机可以 DMA 攻击宿主机内存；
- **SR-IOV** 生成的 VF 直通给虚机，VF 的 DMA 同样靠 VT-d 隔离；
- KVM 纯 CPU 虚拟化只需 VT-x。
