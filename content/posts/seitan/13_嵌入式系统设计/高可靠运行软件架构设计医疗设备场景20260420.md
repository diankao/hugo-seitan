# 高可靠运行软件架构设计（医疗设备场景）

## 题目

如果系统要求高可靠运行（比如医疗设备场景），从软件架构上做哪些设计？

## 考察点

系统架构设计、可靠性工程、安全标准意识

## 回答要点

### 1. 医疗设备的可靠性要求

**医疗设备与传统消费电子的本质区别**：
- 故障可能直接影响患者安全
- 监管要求（FDA、NMPA、CE）对软件有明确的开发流程和验证要求
- 需要符合 IEC 62304（医疗设备软件生命周期标准）
- 关键系统需要做到 "fail-safe"（故障安全）而非 "fail-proof"（免故障）

### 2. 架构设计原则

#### 2.1 分层隔离

```
┌──────────────────────────────────────┐
│           应用层（业务逻辑）           │  可修改，影响范围可控
├──────────────────────────────────────┤
│           中间件层（通信/存储/日志）    │  标准化接口
├──────────────────────────────────────┤
│           硬件抽象层（HAL）           │  隔离硬件差异
├──────────────────────────────────────┤
│           驱动层                      │  经过充分验证
├──────────────────────────────────────┤
│           硬件                        │
└──────────────────────────────────────┘

每层之间通过明确定义的接口通信
上层故障不扩散到下层
下层替换不影响上层
```

#### 2.2 模块解耦与通信

```c
// 模块间通过消息队列通信，不直接调用
// 好处：模块故障不会直接导致调用者崩溃

typedef struct {
    uint8_t  src_module;
    uint8_t  dst_module;
    uint8_t  msg_type;
    uint8_t  priority;
    uint16_t length;
    uint8_t  data[0];
} system_msg_t;

// 每个模块有独立的输入队列
// 调度器负责路由消息
// 模块崩溃后可被独立重启（watchdog 机制）
```

### 3. 容错设计

#### 3.1 看门狗层级

```
┌─────────────────────────────────────────┐
│ 硬件看门狗（独立芯片）                    │  最后防线
│ 超时 → 整板复位                          │
├─────────────────────────────────────────┤
│ 软件看门狗（RTOS 任务监控）               │  任务级监控
│ 超时 → 重启异常任务 / 记录日志            │
├─────────────────────────────────────────┤
│ 心跳监控（任务间互相检查）                │  模块级监控
│ 超时 → 降级运行 / 切换备份               │
└─────────────────────────────────────────┘
```

```c
// 任务注册机制：每个任务定期"喂狗"
typedef struct {
    TaskHandle_t handle;
    const char *name;
    uint32_t timeout_ms;
    uint32_t last_feed;
    uint32_t fail_count;
} watched_task_t;

// 独立监控任务检查所有注册任务
void watchdog_monitor_task(void *arg) {
    while (1) {
        uint32_t now = xTaskGetTickCount();
        for (int i = 0; i < watched_count; i++) {
            if (now - watched[i].last_feed > watched[i].timeout_ms) {
                log_critical("task %s watchdog timeout", watched[i].name);
                watched[i].fail_count++;
                if (watched[i].fail_count > MAX_FAIL) {
                    handle_task_failure(&watched[i]);
                }
            }
        }
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}
```

#### 3.2 数据完整性保护

```c
// 关键数据结构加 CRC / magic 校验
typedef struct {
    uint32_t magic;              // 0xCAFECAFE
    uint32_t calibration_a;
    uint32_t calibration_b;
    uint32_t patient_id;
    uint32_t crc32;
} critical_config_t;

// 每次读取前校验
bool config_load(critical_config_t *cfg) {
    flash_read(CONFIG_ADDR, cfg, sizeof(*cfg));
    if (cfg->magic != CONFIG_MAGIC) return false;
    if (crc32_calc(cfg, offsetof(critical_config_t, crc32)) != cfg->crc32) {
        return false;
    }
    return true;
}

// 读取失败时使用默认安全值
// 绝不使用校验失败的数据
```

#### 3.3 冗余与备份

```c
// 关键数据双备份存储
// 地址 A 和地址 B 各存一份，读取时选有效的

#define CONFIG_ADDR_A  0x08080000
#define CONFIG_ADDR_B  0x08081000

bool config_load_redundant(critical_config_t *cfg) {
    critical_config_t cfg_a, cfg_b;
    bool a_ok = false, b_ok = false;

    if (flash_read_and_verify(CONFIG_ADDR_A, &cfg_a)) a_ok = true;
    if (flash_read_and_verify(CONFIG_ADDR_B, &cfg_b)) b_ok = true;

    if (a_ok && b_ok) {
        // 两份都有效，选版本新的
        *cfg = (cfg_a.version >= cfg_b.version) ? cfg_a : cfg_b;
        return true;
    } else if (a_ok) {
        *cfg = cfg_a;
        // 修复 B
        flash_write_and_verify(CONFIG_ADDR_B, &cfg_a);
        return true;
    } else if (b_ok) {
        *cfg = cfg_b;
        flash_write_and_verify(CONFIG_ADDR_A, &cfg_b);
        return true;
    }
    return false;   // 两份都坏了，使用硬编码默认值
}
```

### 4. 安全状态设计（Fail-Safe）

```c
// 定义系统的安全状态
// 任何异常最终都应导向安全状态

typedef enum {
    SAFE_STATE_NORMAL,          // 正常运行
    SAFE_STATE_DEGRADED,        // 降级运行（部分功能不可用）
    SAFE_STATE_SAFE_SHUTDOWN,   // 安全停机（保存数据，关执行器）
    SAFE_STATE_EMERGENCY_STOP,  // 紧急停止（立即切断危险输出）
} safe_state_t;

// 异常处理统一入口
void handle_critical_fault(fault_id_t fault) {
    log_critical("fault %d detected", fault);

    // 立即执行安全动作
    switch (get_fault_level(fault)) {
    case FAULT_LEVEL_WARNING:
        // 记录日志，继续运行
        break;
    case FAULT_LEVEL_DEGRADED:
        // 降级运行
        enter_safe_state(SAFE_STATE_DEGRADED);
        break;
    case FAULT_LEVEL_CRITICAL:
        // 安全停机
        disable_actuators();
        save_critical_data();
        enter_safe_state(SAFE_STATE_SAFE_SHUTDOWN);
        break;
    case FAULT_LEVEL_EMERGENCY:
        // 紧急停止
        hardware_emergency_stop();
        enter_safe_state(SAFE_STATE_EMERGENCY_STOP);
        break;
    }
}
```

### 5. 输入验证与防御编程

```c
// 所有外部输入必须验证
// 包括：传感器数据、通信数据、配置数据、用户输入

bool validate_sensor_reading(sensor_data_t *data) {
    // 范围检查
    if (data->temperature < TEMP_MIN || data->temperature > TEMP_MAX)
        return false;

    // 变化率检查（防突变）
    if (abs(data->temperature - last_temperature) > MAX_RATE_OF_CHANGE)
        return false;

    // 一致性检查（多传感器交叉验证）
    if (abs(data->temperature - data->temperature_backup) > CONSISTENCY_THRESHOLD)
        return false;

    return true;
}

// 无效数据的处理策略
// 1. 使用上一次有效值（短时）
// 2. 使用安全默认值
// 3. 触发告警
// 4. 绝不忽略验证失败
```

### 7. 开发流程保障

| 要求 | 说明 |
|------|------|
| 编码规范 | MISRA C / MISRA C++，静态分析 |
| 代码审查 | 所有变更必须经过审查 |
| 单元测试 | 关键模块 100% 覆盖 |
| 集成测试 | 模块间接口测试 |
| 回归测试 | 每次变更后全量回归 |
| 追溯性 | 需求 → 设计 → 代码 → 测试用例，全程可追溯 |
