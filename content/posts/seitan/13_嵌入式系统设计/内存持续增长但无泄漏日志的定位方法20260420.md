# 内存持续增长但无泄漏日志的定位方法

## 题目

如果系统内存占用持续增长，但没有明显的内存泄漏日志，如何定位问题？

## 考察点

内存管理、调试方法论、问题定位能力

## 回答要点

### 1. "没有泄漏日志"意味着什么

- 系统没有集成泄漏检测工具（如 ASan、valgrind）
- 或者泄漏工具的粒度不够，没覆盖到实际的问题路径
- 或者根本不是传统意义上的"泄漏"，而是其他类型的内存增长

### 2. 可能的根因分类

| 类型 | 描述 | 泄漏工具能否检测 |
|------|------|----------------|
| 经典泄漏 | malloc 后忘记 free | 能 |
| 逻辑泄漏 | 数据结构只增不减（如链表/缓存无限增长） | 不能（每块都有引用） |
| 碎片化 | 大量小块分配释放导致空闲内存无法利用 | 不能（总量没变但可用减少） |
| 栈增长 | 任务栈实际使用量上升 | 不能 |
| 静态/全局变量 | 全局缓冲区持续追加数据 | 不能 |
| 内核/驱动 | 内核 slab 缓存增长 | 需要内核工具 |

### 3. 定位方法

#### 3.1 建立内存增长基线

```c
// RTOS 场景：定期采样空闲堆大小
void monitor_task(void *arg) {
    while (1) {
        size_t free_heap = xPortGetFreeHeapSize();
        size_t min_ever = xPortGetMinimumEverFreeHeapSize();
        log_info("heap: free=%u, min=%u, tasks=%u",
                 free_heap, min_ever, uxTaskGetNumberOfTasks());
        vTaskDelay(pdMS_TO_TICKS(5000));
    }
}

// 如果 free_heap 持续下降，但 min_ever 稳定
// → 说明有分配但最终释放了，可能是碎片化
// 如果 min_ever 也持续下降
// → 说明有内存真的被消耗掉了
```

#### 3.2 重写 malloc/free 添加追踪

```c
// 包装 malloc/free，记录调用者和大小
typedef struct {
    void *ptr;
    size_t size;
    uint32_t caller;
    uint32_t timestamp;
} alloc_record_t;

#define MAX_RECORDS 1024
static alloc_record_t alloc_table[MAX_RECORDS];
static uint32_t alloc_count = 0;

void *tracked_malloc(size_t size) {
    void *ptr = pvPortMalloc(size);
    if (ptr && alloc_count < MAX_RECORDS) {
        alloc_table[alloc_count].ptr = ptr;
        alloc_table[alloc_count].size = size;
        alloc_table[alloc_count].caller = (uint32_t)__builtin_return_address(0);
        alloc_table[alloc_count].timestamp = xTaskGetTickCount();
        alloc_count++;
    }
    return ptr;
}

void tracked_free(void *ptr) {
    for (uint32_t i = 0; i < alloc_count; i++) {
        if (alloc_table[i].ptr == ptr) {
            alloc_table[i] = alloc_table[alloc_count - 1];
            alloc_count--;
            break;
        }
    }
    vPortFree(ptr);
}
```

**分析 alloc_table**：
- 如果 alloc_count 持续增长 → 有分配没释放
- 按 size 分组统计，看哪类分配最多
- 按 caller 分组，定位是哪个函数在"泄漏"

// 定时 dump 所有分配记录，对比两次快照的差异
void dump_alloc_snapshot(void) {

    for (uint32_t i = 0; i < alloc_count; i++) {

#### 3.5 Linux 系统下的定位工具

```bash
# 1. 进程内存映射
cat /proc/<pid>/maps
cat /proc/<pid>/smaps    # 详细的内存区域信息

# 2. 堆使用统计
cat /proc/<pid>/status | grep VmRSS   # 实际物理内存
cat /proc/<pid>/status | grep VmSize  # 虚拟内存

# 3. valgrind 泄漏检测
valgrind --leak-check=full --show-leak-kinds=all ./app

# 4. AddressSanitizer
gcc -fsanitize=address -g app.c -o app
# 运行时会报告泄漏和越界

# 5. malloc 统计
LD_PRELOAD=libtcmalloc.so HEAPPROFILE=./heap.profile ./app
# 或使用 jemalloc 的 prof 功能

# 6. 实时监控
watch -n 1 'cat /proc/<pid>/status | grep Vm'
```

#### 3.6 内核内存增长排查

```bash
# slab 缓存统计
cat /proc/slabinfo
slabtop

# 内核内存分配统计
cat /proc/meminfo | grep -E "Slab|SReclaimable|SUnreclaim"

# 如果 Slab 持续增长：
# - 检查 dentry cache: cat /proc/sys/fs/dentry-state
# - 检查 inode cache: cat /proc/sys/fs/inode-state
# - 手动回收: echo 2 > /proc/sys/vm/drop_caches
```

### 4. 碎片化 vs 泄漏的区分

```
泄漏：
堆总量  ████████████████████████████████  持续增长
空闲量  ████                              持续下降
分配数  ████████████████                  持续增加

碎片化：
堆总量  ████████████████████              不变
空闲量  ██████████                        不变（总空闲够了）
最大连续  ██                                下降（但被切碎了）
malloc 失败率  ▄▄▄▄▄▄                    上升
```

**碎片化的解决方案**：
```c
// 方案1：内存池，固定大小的块
#define BLOCK_SIZE  64
#define BLOCK_COUNT 32
static uint8_t pool[BLOCK_SIZE * BLOCK_COUNT];
static uint8_t pool_used[BLOCK_COUNT];

void *pool_alloc(void) {
    for (int i = 0; i < BLOCK_COUNT; i++) {
        if (!pool_used[i]) {
            pool_used[i] = 1;
            return &pool[i * BLOCK_SIZE];
        }
    }
    return NULL;
}

// 方案2：TLSF 算法（Two-Level Segregated Fit）
// 外部库，替换标准 malloc，碎片率极低

// 方案3：避免混合大小分配
// 大块用独立区域，小块用内存池
```

### 6. 预防措施

- **关键路径使用内存池**，避免频繁 malloc/free
- **数据结构设上限**（缓存 LRU 淘汰、队列最大深度）
- **集成轻量级堆监控**，定期检查水位
- **开发阶段开启 ASan**，上线前关闭
- **malloc 包装器**记录分配来源，生产环境可按需开启
