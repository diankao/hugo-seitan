# 中断频率过高导致系统抖动的优化

## 题目

如果中断频率过高导致系统抖动，如何优化？

## 考察点

中断管理、实时性优化、系统调优

## 回答要点

### 1. 什么是"系统抖动"

```
理想的任务调度：
Task A  ██    ██    ██    ██    ██
         10ms  10ms  10ms  10ms  10ms

实际的抖动：
Task A  ██      ████  ██        ████
         10ms  14ms  8ms  16ms  12ms
                ▲             ▲
             被中断抢占     被中断抢占
```

**抖动的本质**：中断处理占用了不确定的时间，导致低优先级任务的执行时刻发生偏移。

**抖动的危害**：
- 控制环路周期不稳 → 控制精度下降
- UI 响应时间忽快忽慢 → 用户体验差
- 通信时序抖动 → 数据丢失或错误

### 2. 定位问题：确认抖动来源

#### 2.1 测量中断负载

```c
// 使用硬件定时器测量中断占用时间
// 在 ISR 入口和出口分别记录时间

static uint32_t isr_total_time = 0;
static uint32_t isr_count = 0;

void my_isr(void) {
    uint32_t t0 = DWT->CYCCNT;

    // ... ISR 处理 ...

    uint32_t elapsed = DWT->CYCCNT - t0;
    isr_total_time += elapsed;
    isr_count++;
}

// 计算 CPU 被中断占用比例
float isr_cpu_usage = (float)isr_total_time / (float)total_cycles;
```

#### 2.2 统计各中断源的频率和耗时

typedef struct {
    IRQn_Type irq;

} irq_stats_t;

### 3. 优化策略

#### 3.1 中断下半部（Top/Bottom Half）

```
优化前：
ISR: ████████████████████████████  （30μs，全部在 ISR 中处理）
     接收数据 + 解析协议 + 更新状态

优化后：
ISR: ████                          （5μs，只做最少工作）
     接收数据 + 设标志
                │
                ▼
Bottom Half:    ████████████████████ （25μs，在任务中处理）
                解析协议 + 更新状态
```

```c
// 方式1：使用 FreeRTOS 的 FromISR API 通知任务
void UART_IRQHandler(void) {
    uint8_t data = USART1->DR;
    BaseType_t woken = pdFALSE;

    // Top half：只存数据
    ring_buf_put(&rx_buf, data);

    // 满足条件时通知任务
    if (data == FRAME_END) {
        xTaskNotifyFromISR(parse_task_handle, 0, eNoAction, &woken);
    }

    portYIELD_FROM_ISR(woken);
    // Bottom half 在 parse_task 中执行
}

// 方式2：使用 deferred interrupt（Linux 的 softirq/tasklet 思路）
// 在 RTOS 中通常就是创建一个专门的处理任务
```

#### 3.2 中断合并（Interrupt Coalescing）

```c
// 优化前：每个数据包触发一次中断
// 1000 packets/s → 1000 次/s 中断

// 优化后：积累 N 个包或超时后才触发一次中断
#define COALESCE_COUNT  16
#define COALESCE_TIMEOUT_MS  2

static uint16_t coalesce_counter = 0;
static uint32_t coalesce_start = 0;

void packet_received_isr(void) {
    coalesce_counter++;

    if (coalesce_counter >= COALESCE_COUNT ||
        (get_tick() - coalesce_start) >= COALESCE_TIMEOUT_MS) {
        // 批量通知
        xTaskNotifyFromISR(process_task, coalesce_counter, eSetValueWithOverwrite, NULL);
        coalesce_counter = 0;
        coalesce_start = get_tick();
    }
}

// 中断频率从 1000/s 降到 ~62/s
// 代价：最大额外延迟 = COALESCE_TIMEOUT_MS
```

#### 3.3 使用 DMA 替代中断

```c
// 优化前：每接收 1 字节触发 1 次中断
// 115200 baud → ~11500 次/s 中断

void UART_IRQHandler(void) {
    rx_buf[rx_idx++] = USART1->DR;   // 每字节一次中断
}

// 优化后：DMA 接收 + 空闲中断
// 整帧接收完成后才触发 1 次中断

void UART_Init_DMA(void) {
    // 配置 DMA 循环接收
    HAL_UART_Receive_DMA(&huart1, rx_buf, BUF_SIZE);
}

// 空闲中断：检测到总线空闲时触发
void UART_IDLE_IRQHandler(void) {
    uint32_t received = BUF_SIZE - __HAL_DMA_GET_COUNTER(&hdma_usart1_rx);
    // 一次处理整帧数据
    process_frame(rx_buf, received);
}
// 中断频率从 11500/s 降到与帧率相同（可能只有几十次/s）
```

#### 3.4 中断频率限制（Rate Limiting）

```c
// 对高频中断做频率限制
// 适合：按键消抖、传感器采样等不需要每个事件都处理的场景

#define DEBOUNCE_INTERVAL_MS  10

void EXTI_IRQHandler(void) {
    static uint32_t last_time = 0;
    uint32_t now = xTaskGetTickCount();

    if (now - last_time < pdMS_TO_TICKS(DEBOUNCE_INTERVAL_MS)) {
        EXTI->PR = EXTI_LINE;   // 清标志但不处理
        return;
    }
    last_time = now;

    // 正常处理
    handle_exti_event();
}
```

#### 3.5 调整中断优先级

```c
// 原则：中断优先级不等于任务优先级
// 中断优先级决定的是"谁能打断谁"

// 错误：所有中断都是最高优先级
// → 任何中断都能打断其他所有中断和任务

// 正确：按实时性需求分级
NVIC_SetPriority(ADC_IRQn,        2);   // 电机控制 ADC：高优先级
NVIC_SetPriority(TIM1_UP_IRQn,    2);   // 控制环定时器：高优先级
NVIC_SetPriority(UART_IRQn,       4);   // 串口通信：中优先级
NVIC_SetPriority(ETH_IRQn,        6);   // 网络：低优先级
NVIC_SetPriority(SDIO_IRQn,       7);   // SD 卡：最低

// FreeRTOS 的 configMAX_SYSCALL_INTERRUPT_PRIORITY
// 高于此优先级的中断不受 FreeRTOS 管理，不能调用 FreeRTOS API
// 但也不会被 FreeRTOS 的临界区延迟

// configMAX_SYSCALL_INTERRUPT_PRIORITY = 5
// 优先级 0~4：自由中断，可抢占内核，不能调用 FreeRTOS API
// 优先级 5~7：受管中断，可调用 FromISR API
```

#### 3.6 轮询替代中断（特定场景）

```c
// 对于极高频率的事件，中断的开销反而比轮询更大
// 因为每次中断都要保存/恢复上下文（几十个寄存器）

// 判断标准：
// 如果中断间隔 < 上下文保存/恢复的时间（约 1~2μs）
// 则中断的开销占比过大，考虑用轮询或 DMA

// 典型场景：SPI 高速接收（20 MHz，每字节 0.4μs）
// 中断方式：每字节一次中断，ISR 开销可能 > 数据传输时间
// 更好的方式：DMA 接收整块数据
```

### 4. 优化效果对比

```
优化前：
中断频率：11500/s（UART 每字节中断）
ISR 平均耗时：3μs
CPU 占用率：3.45%
抖动：任务调度抖动 ±200μs

优化后（DMA + 空闲中断）：
中断频率：50/s（每帧一次）
ISR 平均耗时：5μs
CPU 占用率：0.025%
抖动：任务调度抖动 ±10μs
```

### 5. 优化选择流程

```
中断频率过高
      │
      ▼
┌──────────────┐
│ 能否用 DMA   │──Yes──▶ DMA 替代中断（效果最好）
│ 替代？       │
└──────┬───────┘
       │ No
       ▼
┌──────────────┐
│ ISR 是否做了 │──Yes──▶ Top/Bottom Half 分离
│ 太多工作？   │         （ISR 只设标志，任务中处理）
└──────┬───────┘
       │ No
       ▼
┌──────────────┐
│ 能否批量处理？│──Yes──▶ 中断合并 / Coalescing
│              │
└──────┬───────┘
       │ No
       ▼
┌──────────────┐
│ 调整中断优先 │         降低非关键中断优先级
│ 级？         │         或限制中断频率
└──────────────┘
```
