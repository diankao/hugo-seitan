# 自修改代码、JIT 与动态加载在嵌入式中的场景

## 三者是"打破代码编译完就固定"的三兄弟

层次从低到高:

```
自修改代码  ⊂  动态加载  ⊂  JIT
(改指令)    (装已编译模块) (现场编译生成)
```

| 概念 | 一句话 | 嵌入式代表 |
|------|--------|-----------|
| 自修改代码 | 运行时修改自己的指令 | Flash 擦写函数搬 RAM、断点、补丁 |
| 动态加载 | 运行时装入已编译模块 | .ko 驱动、.so 插件、模块化固件 |
| JIT | 运行时现场生成机器码 | MicroPython、PLC 梯形图 |

## 自修改代码的四个真实场景

### 场景 1:Flash 擦写函数搬运到 RAM 执行(最常遇)

很多 MCU 不支持在同一个 Flash bank 里"边执行边写"(没有 RWW,Read-While-Write 能力):

```
擦写 Flash 的代码本身也在 Flash 里
  → 执行它的时候 CPU 要取指
  → 但 Flash 正在被擦写,取指失败/总线死锁

解法:把擦写函数复制到 RAM,跳到 RAM 执行
```

```c
// STM32 HAL 里就有这个机制:RAMFUNC
__attribute__((section(".ramfunc")))
void flash_erase(void) { ... }
// 启动时由链接脚本/启动代码把这段从 Flash 拷到 RAM
```

只要做 OTA / 参数保存到 Flash / 板载烧录,就会碰到这个。

### 场景 2:调试断点的实现原理

JTAG/SWD 调试器设断点,实际是把断点地址的指令**替换成 BKPT**(软件断点),命中后再恢复原指令——标准自修改代码。硬件断点(FPB 单元)才不动指令。这解释了"为什么软件断点数量不限但烧 Flash 前要全清掉"。

### 场景 3:出货后打补丁

固件已发货,发现某个函数有 bug,不想全量 OTA:在 RAM 里放修正函数,通过函数指针/跳转表把调用引过去;或直接改 Flash 里几条指令为跳转。医疗器械、汽车 ECU 的"补丁段"机制就是这么做的。

### 场景 4:代码覆盖(Code Overlay)

Flash 只有 64KB,总代码 100KB:把不常用功能(自检、升级流程)放外置存储,用哪块搬哪块进 RAM。老 DSP 和超小 Flash 单片机项目会遇到。

## 为什么嵌入式比 PC 上更常见

四个刚性需求对比:

| 需求 | PC 上 | 嵌入式上 |
|------|-------|---------|
| 代码在 Flash 原地执行 | 代码早从磁盘加载进 RAM,想写就写 | XIP(就地执行),写 Flash 时总线停摆 → 擦写函数必须搬 RAM |
| 存储不够 | 几乎不可能 | Overlay、补丁段(改几条指令而不是重刷整个固件) |
| 出货后修复成本 | 发新版本就行 | OTA 风险大、医疗/车规认证贵 → 指令级小补丁反而最划算 |
| IP 保护 | 有但少 | 固件能被物理读出 → 加密存储、运行时解密到 RAM 执行是正经需求 |

核心一句话:**PC 上"改变程序行为"有更便宜的手段(发新版本、换库);嵌入式上重新烧固件太贵,直接对指令动手反而是工程最优解。**

## PC 上自修改代码去哪了

三个杀手:

1. **W^X 安全机制(DEP/NX)**:现代 OS 强制内存"要么可写、要么可执行,不能既写又执行",改代码段直接被杀。正规软件不走,走这条路的多是加壳病毒
2. **性能反噬**:现代 CPU 深流水线 + I-Cache + 分支预测,改一次代码 = 流水线冲刷 + 缓存全废。早期 CPU(8086/6502)没 cache,自修改还是优化技巧
3. **需求被接管**:.dll 动态链接、COM 组件、脚本引擎层层承包了"运行时改变行为"

反转:**JavaScript V8、Java JVM、.NET CLR 的 JIT,本质就是大规模工业化的自修改代码**——只是"受管"形态(mprotect 权限切换 + OS 监督 + 引擎保证缓存一致)。

> 嵌入式保留了自修改的"原始形态"(裸改指令),PC 把它升级成"受管形态"(JIT/动态链接),中间态基本灭绝。

随着 ARMv8-M TrustZone、MPU 强制化、MCU 也开始有 cache(M7/M55),嵌入式的自修改代码也会越来越受管,方向和 PC 历史演变一致,只是慢了二十年。

## 动态加载的三个场景

### 场景 1:嵌入式 Linux 内核模块 .ko(天天遇)

```bash
insmod my_driver.ko    # 热加载驱动,不用重启
rmmod my_driver.ko     # 卸载
```

内核的 module_init/module_exit、EXPORT_SYMBOL 全是围绕动态加载的机制。

### 场景 2:应用层插件架构 .so + dlopen

```c
void *handle = dlopen("libalgo.so", RTLD_NOW);
algo_fn fn = dlsym(handle, "run_algorithm");
fn(data);
```

算法迭代频繁的采集/处理设备,主程序(通信、采集、安全逻辑)固化,**算法层做成 .so 插件**——更新算法只换库文件,不动主程序。

### 场景 3:RTOS 模块化固件

VxWorks、QNX 支持 LOAD_MODULE 加载 ELF;自研固件框架把业务模块做成带头表的 bin,bootloader 选择性加载。OTA 差分升级(只升一个模块)也是这个思路。

裸机做动态加载的难点:

| 难点 | 说明 |
|------|------|
| 设备端链接器 | 要在 MCU 上做符号解析+重定位(简化版 ld.so) |
| 内存权限 | 需要 RWX 内存,MPU 要放开 |
| 依赖管理 | 模块间符号依赖、版本匹配 |
| 安全 | 必须验签,否则插件通道=后门 |

## JIT(解释执行)的场景

- **MicroPython / eLua**:ESP32、STM32H7 上跑 Python,REPL 交互调外设。开发调试阶段验证算法/时序,定型后 C 重写
- **PLC 梯形图(工业最大规模应用)**:梯形图/ST 语言下载到 PLC 后由运行时系统解释/编译执行,设备行为由现场下发的逻辑决定,不重新刷固件
- **JerryScript / Espruino**:智能手表、智能家居用 JS 做轻逻辑层
- **可配置表达式引擎**:上位机下发公式(如 `out = k1*ch1 + k2*ch2^2`),固件带小解析器

嵌入式上 JIT 的代价:

| 代价 | 说明 |
|------|------|
| 资源占用 | MicroPython 舒服跑要 512KB Flash + 128KB RAM |
| 实时性 | GC 停顿、解释开销 → 硬实时部分绝不能放脚本 |
| 混合架构是正解 | 实时层 C 固化 + 策略层脚本 |

## 三者的技术共同点

| 共同前提 | 说明 |
|---------|------|
| 可写可执行的内存 | RX 代码段要变 RWX,MPU/MMU 得配 |
| Cache 维护 | 改/加载完必须失效 I-Cache + ISB(见下一篇) |
| 重定位能力 | 模块不知道自己会被加载到哪 |
| 安全机制 | 验签、加密——动态通道都是攻击面 |

## 按开发角色对号入座

| 在做什么 | 会遇到 |
|--------|--------|
| OTA / Bootloader | 自修改:Flash 擦写函数搬 RAM;差分升级≈动态加载 |
| 参数/日志存 Flash | 同上,擦写搬 RAM 几乎必碰 |
| JTAG 调试 | 断点=自修改原理 |
| 嵌入式 Linux 驱动 | .ko 动态加载,日常 |
| 算法快速迭代的产品 | .so 插件化 |
| 原型验证 | MicroPython 系脚本 |
| 工业控制 | PLC 梯形图=动态逻辑 |
| 固件安全 | 对抗自修改(加壳、混淆)与动态加载(验签) |

## 速记口诀

- 自修改:改指令(Flash 擦写搬 RAM、断点、补丁)
- 动态加载:装模块(.ko、dlopen、模块化固件)
- JIT:现场造代码(MicroPython、PLC 梯形图)
- 改码必刷 I-Cache + ISB
- 动态通道 = 攻击面,必须验签
- 硬实时不放脚本,混合架构是正解
