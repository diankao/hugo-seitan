# BMC 与 IPMI 服务器远程管理

服务器主板上有一颗独立于主机 CPU 的管理控制器——BMC。主机死机、蓝屏甚至关机时，运维仍能通过网络远程管理整机，这就是"带外管理"。本文整理 BMC 的定位、IPMI 规范体系（SEL/SDR/FRU/RMCP+）、PECI 温度通路与读数为 0 的排查思路、IPMI 的能力边界以及常用软件访问方式。

## BMC 是什么

BMC（Baseboard Management Controller）是服务器主板上的独立管理控制器（常见如 ASPEED AST2500/2600），核心特征：

- **带外管理**：独立于主机 CPU 和操作系统运行，主机死机、关机、蓝屏时 BMC 依然可管理；
- **AC 上电即工作**：只要插上电源线，不按开机键 BMC 就已启动；
- 自带独立网口（或与主机共享 NIC 的 side-band 通道），通过网络提供远程管理控制台。

## IPMI 规范体系

IPMI（Intelligent Platform Management Interface）是 BMC 与外界交互的标准规范：

```
管理端（ipmitool / WebUI / Redfish客户端）
      │  带外: 网口 RMCP+ (IPMI v2.0, UDP 623, 认证加密)
      │  带内: KCS/BT 系统接口 (驱动访问 /dev/ipmi0)
      ▼
   BMC ── IPMB ── 机箱内其他管理控制器
      │
      ├── 传感器监控 (温度/电压/风扇，阈值告警)
      ├── SEL  (System Event Log，硬件事件日志)
      ├── SDR  (Sensor Data Record，传感器描述记录)
      ├── FRU  (Field Replaceable Unit，硬件信息)
      └── chassis 控制 (开关机/复位，SOL 串口重定向)
```

- IPMI v1.5 使用 RMCP（UDP 623，明文），v2.0 升级为 **RMCP+**（增加认证与加密协商），会话建立要经过 RAKP 认证与加密套件协商——协商失败会话就无法建立/维持；
- **SEL** 记录硬件事件：传感器越限、阈值告警、上下电事件等（不是用户登录、网络流量或固件更新记录），写满后可配置循环覆盖；
- 每个传感器的类型、量程、上下限阈值都由 **SDR（Sensor Data Record）** 描述，要实现"传感器阈值动态调整"，读取和修改的依据就是 SDR；
- **FRU** 存放设备厂商、序列号等更换件信息。

## PECI 温度通路与读数为 0 的排查

BMC 读 Intel 平台的 CPU 温度不走传统模拟热敏电阻，而是通过 **PECI（Platform Environment Control Interface）** 总线读取 CPU 内部数字温度（DTS）。

读数恒为 0 的常见原因按概率排序：

1. **PECI 接口未初始化**（最常见）：BMC 侧 PECI 驱动或主机侧未就绪，读回全 0；
2. 传感器地址冲突：多个客户端抢占总线上同一地址；
3. SEL 日志满只影响事件记录，不影响温度读取路径；
4. BIOS 禁用 ACPI 影响的是电源管理接口，与 PECI 温度通路无关。

## IPMI 能做什么、不能做什么

| 功能 | IPMI 标准是否支持 |
| --- | --- |
| 远程开关机/复位（chassis control） | ✅ 标准命令 |
| 监控 CPU/进风口温度等传感器 | ✅ 标准 |
| 读取/清空 SEL、调整传感器阈值 | ✅ 标准 |
| SOL（Serial Over LAN）串口重定向 | ✅ 标准 |
| BIOS/固件更新 | ✅ 通过厂商工具基于 IPMI 传输 |
| 配置 RAID 阵列 | ❌ 属于 RAID 卡自身固件工具的职责，IPMI 标准不含 |

## 会话中断的原因

- **RMCP+ 加密协商失败**：会话建立即失败；
- **Watchdog 超时**：BMC 看门狗按策略复位整机或 BMC 自身，会话随之中断；
- SEL 缓冲区溢出：只影响日志记录，不断会话；
- 用户权限不足：单次操作被拒绝（返回权限错误），会话仍然保持。

## 远程电源控制走什么协议

标准协议语境下，电源控制走 **IPMI**（新一代平台走 Redfish，REST over HTTPS）；HTTP、SNMP、MQTT 都不是 BMC 电源控制的标准协议——个别厂商有私有扩展，但不属规范。

## 软件访问方式

- 命令行 `ipmitool` 最常用：

```bash
ipmitool sensor list          # 传感器读数
ipmitool sel list             # 事件日志
ipmitool chassis power status # 电源状态
ipmitool chassis power cycle  # 电源重启
```

- Python 生态的 **pyipmi**（python-ipmi）直接实现 RMCP+ 协议栈，可脚本化监控与控制。

## Redfish：IPMI 的现代替代

IPMI 规范自 2015 年（v2.0 rev 1.1）后不再演进，且历史包袱重：RMCP+ 的 Cipher 0 漏洞、弱哈希（HMAC-MD5/SHA1）、明文兼容模式，使其长期位列"最不安全协议"清单。DMTF 推出的 **Redfish** 是替代标准：

- **传输**：HTTPS + REST API（TCP 443），复用 Web 基础设施与 TLS 生态；
- **数据模型**：JSON 文档 + OData 风格的资源树，而不是 IPMI 的二进制命令；
- **资源层级**：

```
/redfish/v1/
├── Systems/            ← 计算系统：开关机、BootOrder、处理器、内存、存储
│   └── 1/Actions/Reset （电源控制）
├── Managers/           ← BMC 自身：固件版本、网络配置、SerialConsole
├── Chassis/           ← 机箱：传感器、风扇、电源、物理拓扑
├── UpdateService/     ← 固件更新（推 OSDP/镜像、任务跟踪）
└── Tasks/             ← 长时任务（更新、复位）的异步跟踪
```

- 用 curl 就能操作：

```bash
# 查询系统状态
curl -k -u root:passwd https://<bmc>/redfish/v1/Systems/1 | jq '.PowerState'

# 远程开机（On/ForceOff/GracefulRestart/ForceRestart...）
curl -k -u root:passwd -X POST https://<bmc>/redfish/v1/Systems/1/Actions/Reset \
     -H 'Content-Type: application/json' -d '{"ResetType":"On"}'

# 传感器读数（IPMI sensor list 的等价物）
curl -k -u root:passwd https://<bmc>/redfish/v1/Chassis/1/Sensors | jq
```

- 与 IPMI 对照：

| | IPMI | Redfish |
| --- | --- | --- |
| 传输 | RMCP+（UDP 623） | HTTPS（TCP 443） |
| 接口风格 | 二进制命令 + 命令码 | REST 资源 + JSON |
| 安全 | 弱（Cipher 0、旧哈希） | TLS + 现代认证/审计 |
| 表达能力 | 固定命令集 | 可扩展 schema（OEM 扩展友好） |
| 工具 | ipmitool | curl/Redfish 客户端/DMTF 工具 |

现实是两者长期共存：新服务器 BMC 默认双栈（IPMI + Redfish + Web UI），存量自动化仍大量基于 ipmitool；新项目选 Redfish，图形化 BIOS 配置、虚拟媒体、固件编排这些 IPMI 表达不了的能力尤其如此。
