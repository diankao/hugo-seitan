# 远程升级失败兜底机制设计

## 题目

如果远程升级失败导致设备无法启动，如何设计系统的"兜底机制"？

## 考察点

固件升级设计、可靠性工程、故障恢复

## 回答要点

### 1. "无法启动"的几种情况

| 情况 | 原因 | 严重程度 |
|------|------|---------|
| Bootloader 正常但新固件 crash | 固件有 bug、外设初始化失败 | 中（可回退） |
| Bootloader 无法找到有效固件 | Flash 数据损坏、分区表被破坏 | 高（需恢复模式） |
| Bootloader 本身损坏 | 意外写入 Bootloader 区域 | 极高（硬件级恢复） |
| 硬件故障 | Flash 芯片损坏 | 无法软件恢复 |

### 2. 多层兜底架构

```
┌─────────────────────────────────────────┐
│ 第一层：AB 分区自动回退                    │  最常用
├─────────────────────────────────────────┤
│ 第二层：金固件（Golden Image）             │  AB 都坏时
├─────────────────────────────────────────┤
│ 第三层：Bootloader 恢复模式                │  需要人工介入
├─────────────────────────────────────────┤
│ 第四层：硬件级恢复（ROM Boot / JTAG）      │  最后手段
└─────────────────────────────────────────┘
```

### 3. 第一层：AB 分区自动回退

```c
// Bootloader 中的启动尝试计数器
// 存储在非易失性区域（RTC 备份寄存器或独立 Flash 扇区）

typedef struct {
    uint32_t boot_attempt_count;
    uint32_t last_boot_partition;
    uint32_t consecutive_fail_count;
} boot_stats_t;

static boot_stats_t boot_stats;

void bootloader_main(void) {
    load_boot_stats(&boot_stats);

    partition_meta_t meta_a, meta_b;
    read_meta(PART_A, &meta_a);
    read_meta(PART_B, &meta_b);

    // 选择启动分区
    int part = select_partition(&meta_a, &meta_b, &boot_stats);

    if (part < 0) {
        // 没有可启动的分区，进入下一层兜底
        enter_golden_recovery();
        return;
    }

    // 记录启动尝试
    boot_stats.boot_attempt_count++;
    boot_stats.last_boot_partition = part;
    boot_stats.consecutive_fail_count++;
    save_boot_stats(&boot_stats);

    boot_partition(part);
}
```

#### 应用层确认机制

```c
// 新固件启动后的自检流程
void app_init(void) {
    boot_stats_t stats;
    load_boot_stats(&stats);

    if (is_first_boot_after_upgrade()) {
        // 执行关键自检
        bool ok = true;
        ok &= test_memory();
        ok &= test_storage();
        ok &= test_network();
        ok &= test_peripherals();

        if (ok) {
            // 确认新固件正常
            stats.consecutive_fail_count = 0;
            mark_current_partition_active();
            save_boot_stats(&stats);
        } else {
            // 新固件有问题，标记无效并重启回退
            mark_current_partition_invalid();
            save_boot_stats(&stats);
            system_reboot();
        }
    }
}
```

#### 自动回退触发条件

```c
// Bootloader 中检查连续失败次数
#define MAX_BOOT_ATTEMPTS  3

int select_partition(partition_meta_t *a, partition_meta_t *b,
                     boot_stats_t *stats) {
    if (stats->consecutive_fail_count >= MAX_BOOT_ATTEMPTS) {
        // 当前分区连续失败太多，尝试另一个
        int other = (stats->last_boot_partition == PART_A) ? PART_B : PART_A;
        partition_meta_t *other_meta = (other == PART_A) ? a : b;

        if (other_meta->state == PART_STATE_ACTIVE ||
            other_meta->state == PART_STATE_VALID) {
            stats->consecutive_fail_count = 0;
            return other;
        }
        // 另一个也不可用，返回 -1 触发下一层兜底
        return -1;
    }

    // 正常选择逻辑：优先选 VALID/ACTIVE 的分区
    // ...
}
```

### 4. 第二层：金固件（Golden Image）

```
Flash 布局：
┌──────────────┐
│  Bootloader  │  永不更新
├──────────────┤
│  Golden Image│  出厂固件，只读保护
├──────────────┤
│  分区 A      │  可更新
├──────────────┤
│  分区 B      │  可更新
├──────────────┤
│  用户数据     │
└──────────────┘
```

```c
// Golden Image 特点：
// 1. 出厂时写入，设置 Flash 写保护
// 2. 功能最小化：只包含网络通信和 OTA 能力
// 3. 不依赖复杂外设，确保在各种硬件状态下都能启动

void enter_golden_recovery(void) {
    partition_meta_t golden;
    read_meta(PART_GOLDEN, &golden);

    if (golden.state == PART_STATE_VALID) {
        log_boot("no valid partition, booting golden image");
        boot_partition(PART_GOLDEN);
    } else {
        // Golden 也坏了，进入下一层
        enter_bootloader_recovery();
    }
}
```

### 5. 第三层：Bootloader 恢复模式

```c
// 当所有固件分区都无法启动时，Bootloader 进入恢复模式
// 提供最基础的通信能力，等待外部刷入新固件

void enter_bootloader_recovery(void) {
    // 初始化最小外设集
    uart_init(115200);
    led_blink(FAST);

    // 打印恢复信息
    uart_print("RECOVERY MODE\r\n");
    uart_print("Waiting for firmware via XMODEM...\r\n");

    // 支持多种恢复通道
    while (1) {
        // 通道1：串口 XMODEM 协议接收固件
        if (uart_has_data()) {
            int ret = xmodem_receive(firmware_buf, MAX_FIRMWARE_SIZE);
            if (ret > 0) {
                if (verify_firmware(firmware_buf, ret)) {
                    write_to_partition(PART_A, firmware_buf, ret);
                    mark_partition_valid(PART_A);
                    system_reboot();
                }
            }
        }

        // 通道2：USB DFU（Device Firmware Upgrade）
        // 通道3：SD 卡读取固件文件
        // 通道4：网络 TFTP 下载
    }
}
```

### 6. 第四层：硬件级恢复

| 方式 | 原理 | 适用场景 |
|------|------|---------|
| ROM Boot | 芯片内部 ROM 中的引导程序，支持从 USB/SD/UART 加载 | Bootloader 损坏 |
| JTAG/SWD | 通过调试接口直接烧写 Flash | 完全无法启动 |
| Boot 引脚 | 硬件引脚强制进入下载模式 | 批量生产/返修 |
| 双 Bank Flash | 两份 Bootloader，硬件级切换 | 极高可靠性要求 |

### 7. 兜底流程总结

```
设备上电
   │
   ▼
Bootloader 启动
   │
   ├─ 分区 A 有效？──Yes──▶ 尝试启动 A
   │                         │
   │                    A 正常启动？
   │                    ├─Yes──▶ 运行，确认后标记 ACTIVE
   │                    └─No──▶ 失败计数 +1
   │
   ├─ 分区 B 有效？──Yes──▶ 尝试启动 B
   │                         │
   │                    同上逻辑
   │
   ├─ 连续失败 < 3 次？──Yes──▶ 重试
   │
   ├─ Golden Image 有效？──Yes──▶ 启动 Golden
   │                              │
   │                         Golden 启动后可重新 OTA
   │
   └─ 进入 Recovery Mode
      │
      ├─ 串口/USB 接收固件
      ├─ SD 卡读取固件
      └─ 网络下载固件
```

### 8. 设计建议

- **Bootloader 永不 OTA 更新**，避免 Bootloader 本身损坏的风险
- **Golden Image 设 Flash 写保护**，确保总有一个可恢复的底线
- **启动计数器存在独立区域**，不受固件分区写入影响
- **恢复模式支持多种通道**，不依赖单一通信方式
- **远程监控升级结果**，设备长时间不上报则触发运维告警
- **灰度发布**，先小批量升级验证，确认稳定后再全量推送
