# 指令缓存一致性维护

自修改代码、JIT、DMA 搬运代码到 RAM 这类场景里,**最隐蔽的坑就是指令缓存(I-Cache)一致性**——改了代码但 CPU 执行的还是旧指令,而且不报任何错。

## 问题的本质:改代码和执行代码是两条路

现代 CPU 虽然统一编址(冯·诺依曼),但内部 cache 是哈佛式分离的:

```
           ┌── I-Cache ──→ 取指单元(执行)
           │
内存 ──────┤
           │
           └── D-Cache ──→ load/store(读写数据)
```

修改代码用的是 `STR`(store 指令)→ 走 **D-Cache**;
CPU 执行代码用的是取指 → 走 **I-Cache**。

两条断裂同时发生:

| 断裂 | 后果 |
|------|------|
| 新指令还在 D-Cache 里(没写回内存) | 内存里还是旧代码 |
| I-Cache 里缓存着旧指令 | 取指根本不去内存看 |

## 标准解决流程(三步,顺序不能错)

```
写完新代码后:
  ① Clean D-Cache      把新指令从 D-Cache 写回内存(是 clean 不是 invalidate!)
  ② Invalidate I-Cache 丢弃 I-Cache 里的旧指令
  ③ DSB + ISB          等待完成 + 冲刷流水线
  然后才能跳转执行
```

**Cortex-M7 实操代码(CMSIS)**:

```c
#include "cmsis_compiler.h"

void flush_code(void *code, uint32_t len)
{
    // 1. 新代码从 D-Cache 落到真实内存
    SCB_CleanDCache_by_Addr((uint32_t *)code, len);

    // 2. 丢弃 I-Cache 里缓存的旧指令(内部已含 DSB)
    SCB_InvalidateICache();

    // 3. 指令同步屏障:冲掉流水线里预取的旧指令
    __ISB();
}

// 之后才能安全跳转
typedef void (*entry_t)(void);
((entry_t)0x20001000)();
```

每一步省掉会怎样:

| 步骤 | 省掉会怎样 |
|------|-----------|
| Clean D-Cache | 内存里还是旧代码,失效 I-Cache 反而加载了旧指令 |
| Invalidate I-Cache | 取指命中旧缓存,白改 |
| `__ISB()` | 指令已在流水线里预取完,ISB 强制重新取指 |

**clean 和 invalidate 是两个方向**:clean 是"写回"(D-Cache→内存),invalidate 是"丢弃"(重新从内存读)。改代码要 clean D + invalidate I,**方向搞反是常见 bug**。

## 各架构差异

| 架构 | Cache | 要做维护吗 |
|------|-------|-----------|
| Cortex-M0/M3/M4 | 无 I/D-Cache | 不用(但 `__ISB()` 还是建议加) |
| **Cortex-M7** | 有 I+D-Cache | **必须完整三步**,最常见坑产地 |
| Cortex-M55/M85 | 有 | 同上 |
| Cortex-A(裸机/RTOS) | 有 | 必须,且还要考虑**多核**(其他核的 I-Cache 也要失效,广播 IPI) |
| Cortex-A(Linux 用户态) | 有 | 要,但**不能直接碰 cache**,见下 |
| x86 | 有 | **硬件自动维护**(一致性协议侦测到改代码自动失效),只需保证指令序列化 |

x86 vs ARM 是架构级差异:x86 硬件自动保证自修改代码的 I-Cache 一致性;ARM 出于功耗/面积考虑把一致性责任交给软件。所以 V8/JVM 在 x86 上不用刷 I-Cache,在 ARM 上必须做。

## Linux 用户态做法(JIT 场景)

用户态没有权限直接操作 cache,靠内核封装:

```c
// 方法1:GCC 内建,底层触发内核做 cache 维护
__builtin___clear_cache(start, end);

// 方法2:权限切换(配合 W^X)
void *page = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                  MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
write_jit_code(page);                          // 写入生成的机器码
mprotect(page, 4096, PROT_READ | PROT_EXEC);   // 内核切权限时顺带处理 cache
((void(*)(void))page)();
```

`mprotect` 从 RW 切到 RX 时,内核在 ARM 上会做 I-Cache 维护——规范 JIT 引擎都走"双权限切换",一步到位解决安全(W^X)和一致性。

## 关联场景:DMA 搬代码(Bootloader 必遇)

不只 CPU 自己改代码,DMA 往 RAM 搬代码(bootloader 加载固件、外部 Flash 搬程序)一样有坑,而且多一层:

```
DMA 写入新代码:不经过 CPU 的任何 cache
                ↓
问题1:CPU 的 D-Cache 若缓存了这块 RAM 的旧数据 → 读到旧的
问题2:CPU 的 I-Cache 同上
                ↓
搬运完成后:
  Invalidate D-Cache(丢旧数据,重新从内存读)
  Invalidate I-Cache
  __DSB(); __ISB();
  跳转
```

注意这里 D-Cache 是 **invalidate**(丢弃)而不是 clean——因为内存里的新内容是 DMA 写的,cache 里的旧副本要扔,而不是把旧副本写回去污染内存(写回会把 DMA 的新代码**覆盖回旧的**,灾难)。

## 速记口诀

- 改码走 D-Cache,执行走 I-Cache,两条路天然分裂
- 三步:Clean D → Invalidate I → DSB/ISB(CPU 改码)
- DMA 搬码:Invalidate D + Invalidate I(方向全是丢,不能 clean,否则旧数据写回毁掉 DMA 成果)
- M3/M4 幸免,M7 必做,x86 免单(硬件自动)
- Linux 用户态:`__builtin___clear_cache` / mprotect,别想手动碰 cache
- 多核还要广播失效其他核的 I-Cache
- clean = 写回,invalidate = 丢弃,方向搞反必出灵异 bug
