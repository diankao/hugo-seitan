# 硬实时系统能用MMU吗

## 题目

硬实时项目是不是不能选带 MMU 的芯片？带 MMU 还能保证确定性吗？

## 考察点

MMU 延迟的构成与有界性、静态映射与锁 TLB 技术、安全认证 RTOS 生态、实时性选型方法。

## 回答要点

### 1. 结论先行：不是 MMU 不能硬实时，是页表不能在运行期变

QNX、VxWorks、Integrity、LynxOS-178 这些通过 DO-178C DAL-A / ISO 26262 ASIL-D 最高等级认证的 RTOS，全都跑在带 MMU 的芯片上。Cortex-M/R 拒绝 MMU 是出于认证成本与简化确定性分析，不是技术上做不了。

### 2. 把 MMU 的延迟拆开看

| 情形 | 延迟 | 有界？ | 对硬实时 |
|------|------|--------|---------|
| TLB 命中 | 流水线内并行查找，≈0 额外周期 | 恒定 | 无害 |
| TLB miss → 硬件走表 | 几十~几百周期 | 有界 | 可分析 |
| 缺页异常（按需调页/swap/COW） | 微秒~毫秒级 | 无界 | 致命 |
| SMP 的 TLB shootdown | 微秒级起步，阻塞多核 | 无界 | 致命 |

致命项都不是"翻译"这个动作，而是**运行期修改页表**引发的动作。翻译本身在 TLB 命中时近乎免费，miss 时有确定上界，可以进 WCET（最坏执行时间）分析。

### 3. 带 MMU 做硬实时的正确姿势：把页表焊死

- 静态映射：启动阶段一次性建好所有映射，运行期绝不 remap/unmap → 永不缺页、永无 shootdown
- 钉死热表项：PowerPC e500 的 TLB1 bolted 条目是经典做法，VxWorks 启动时把关键映射写死，翻译延迟恒定
- 关掉动态机制：无 swap、无按需调页、无写时复制、无透明大页
- 单地址空间或精细 ASID 管理，避免地址空间切换冲刷 TLB

这样 MMU 的开销收敛为"每次访问多 0~几个周期 + 偶尔一次有界走表"，WCET 可分析、可认证。

### 4. 反面提醒：无 MMU ≠ 自动确定

Cortex-M7 开着 cache、再叠一路大流量 DMA 抢总线，抖动照样可观：

- 硬实时 MCU 的标配是 TCM（零等待 SRAM，绕开 cache 与总线仲裁）
- 需要时关 cache、MPU 设 no-cache 区、配置总线矩阵优先级
- 确定性是整个存储子系统的性质，MMU 只是其中一个变量

### 5. 选型矩阵

| 约束 | 主流方案 | MMU 状态 |
|------|---------|---------|
| 车规/飞控最高等级，微秒级 | Cortex-R（如 TI Hercules）或同类安全 MCU（英飞凌 AURIX/TriCore） | 无翻译，锁步核 |
| 安全认证 + 进程隔离/POSIX 生态 | QNX / VxWorks / Integrity / LynxOS-178 | 有 MMU，静态映射 |
| 工业硬实时 + Linux 生态 | PREEMPT_RT（6.12 起并入内核主线）或 Xenomai 双内核 | 有 MMU，预热页表 |
| 界面 + 网络 + 硬实时混合 | 异构芯片：STM32MP1 / i.MX8 / AM62x | A 核有，M 核无 |
| 成本敏感、逻辑简单 | Cortex-M + FreeRTOS | 无 MMU |

补充玩法：同一颗 A 核不上 Linux，用静态 1:1 映射直接跑 FreeRTOS（i.MX 等 AMP 方案），MMU 硬件在但只当透明层——这是"带 MMU 的硬实时"的朴素形态。

### 6. 抖动量级参考

| 方案 | 典型调度/中断延迟（数量级） |
|------|---------------------------|
| M 核裸跑 / FreeRTOS | 几十纳秒 |
| QNX / Xenomai | 微秒级 |
| 调好的 PREEMPT_RT | 几十微秒，尾部几百微秒 |
| 普通 Linux | 尾部毫秒级 |
