# Qt Creator运行、命令行编译与打包部署的三环境差异

## 问题背景

原生 C++ Qt 项目有一个经典陷阱：**同一个 exe，在 Qt Creator 里点绿三角运行一切正常，双击 exe 或发给别人就各种崩**。更隐蔽的是，让 AI 代理（agent）在命令行下控制编译时，构建行为和 Qt Creator 内部行为也有出入。

核心原因是：**Qt 应用的运行时行为依赖于"从哪里启动、工作目录是什么、exe 旁边放了什么"**。Qt Creator 的"运行"、命令行编译、打包部署，实际上是三种完全不同的环境。

## 一、Qt Creator 里的"运行"其实很娇贵

点绿色三角时，Qt Creator 做了几件容易忽略的事：

### 1. 工作目录默认是 build 目录

Qt Creator 默认把工作目录设为构建目录（`build-xxx-Desktop_Qt_.../`），而不是 exe 所在目录。代码里写相对路径 `"images/bird.png"`：

- 在 Creator 里能跑（相对 build 目录刚好找得到）
- 双击 exe 就找不到——因为 `QDir::currentPath()` 变了

### 2. 自动注入环境变量

Creator 会自动注入 `QT_PLUGIN_PATH`、`QML2_IMPORT_PATH` 指向本机 Qt 安装目录（如 `C:\Qt\6.x\mingw\plugins`、`\qml`）。后果是：

- **根本没部署任何插件**，程序在 Creator 里也能加载 jpeg 图片、能用 sqldrivers——它是从系统 Qt 安装里"白嫖"的
- 打包后没有这些环境变量，图加载不出来、数据库打不开，就是这里炸的

### 3. Qt 库查找靠 PATH

开发机上 Qt 的 DLL 在 PATH 里（或被 Creator 注入），所以 exe 旁边没有 Qt6Core.dll 也能跑。换一台干净机器立刻缺 DLL。

**正确做法**：资源定位永远用 `QCoreApplication::applicationDirPath()` 或编译期资源（`:/` qrc），不要依赖 `currentPath()`。用 `currentPath()` 的代码在 Creator 里"测试通过"是个假象。

## 二、命令行编译 vs Qt Creator 编译的出入

### 1. moc/uic/rcc 的自动触发

Creator 用它生成的构建树，`CMakeLists.txt` 里 `AUTOMOC ON`、`HEADERS` 列表齐全。命令行构建时，如果少列了一个含 `Q_OBJECT` 的头文件，增量编译不报错，**链接时才炸 `undefined reference to vtable`**——这个报错和"没跑 moc"的因果关系很不直观。

### 2. Kit 差异

Creator 里每个 Kit 是明确的（MSVC2019 64bit / MinGW）。同一台机器装了多套 Qt 时，命令行 `cmake` 找到的 Qt 可能和 Creator 用的不是同一套，编出来插件 ABI 不匹配，运行时插件静默加载失败——尤其是 platform 插件，典型报错：

```
could not find or load the Qt platform plugin "windows"
```

### 3. Shadow build（影子构建）

Creator 默认源码目录和 build 目录分离。如果代码或工程文件里硬编码了 `../generated/xxx.cpp` 这类相对源码目录的路径，Creator 能编，命令行 out-of-source build 可能找不到。

### 4. Debug/Release 混用

MSVC 下 Debug 和 Release 的 Qt DLL、插件、运行库不能混：

- Creator 按 Kit + 构建配置分得很清楚
- 命令行不指定 `--config` 时 CMake 默认可能是 Release，而链接的是 debug 的第三方库 → 链接错误或运行时崩

## 三、打包部署是第三个世界

### windeployqt 的能力边界

windeployqt 扫描 exe 的依赖并拷 DLL、插件、翻译文件到 exe 旁边，但它只拷"静态可分析到的"依赖。动态加载的东西靠默认规则猜：

- 运行时动态 load 的插件、`Q_IMPORT_PLUGIN` 的内容
- QML import：必须手动指定 `windeployqt --qmldir <qml源码目录>` 才能扫到 QML 模块依赖

### 插件目录结构必须保持

`plugins/platforms/qwindows.dll`、`plugins/imageformats/*.dll`、`plugins/sqldrivers/*.dll` 这些**子目录层级是 Qt 硬编码的搜索路径**，把 DLL 全部平铺到 exe 旁边是找不到的。

### qt.conf

exe 旁边放 qt.conf 可以改 Qt 找插件/翻译/库的根路径。默认布局（相对 exe）一般不需要，但一旦采用自定义目录布局就必须用它。

### qrc 资源为什么部署后最省心

`:/images/bird.png` 编译进二进制，任何环境下行为一致。打包方案和 Creator 运行行为差异最大的就是"文件系统资源"，最稳的策略是：**能用 qrc 就用 qrc**。

## 总结

| 环境 | 实际等式 |
|------|---------|
| Creator 运行 | 你的代码 + Creator 注入的环境变量和 PATH + 系统 Qt 安装 |
| 命令行运行 | 你的代码 + 当前 shell 的 PATH |
| 打包后运行 | 你的代码 + exe 旁边部署的那点东西 |

三者行为一致的前提：

1. 资源用 qrc 或 `applicationDirPath()`
2. 插件靠 windeployqt 部署且目录结构完整
3. 构建配置（Kit、Debug/Release、AUTOMOC 文件列表）在命令行下能完整复现

**"Creator 里好好的、打包就坏"的头号来源**：代码里的 `currentPath()` 相对路径，以及命令行构建时 Kit/配置和 Creator 不一致。
