# 信号槽的四种写法和五种连接方式

## 题目

connect 有哪几种写法？第五个参数的连接方式有哪几种，各自用在什么场景？

## 考察点

connect 中间参数的四种写法及其演进（宏 → 函数指针 → QOverload → lambda）、错误发现时机的差异（编译期 vs 运行期）、moc 元对象机制在其中的角色、五种 ConnectionType 的场景选择。

## 回答要点

### 1. connect 全貌

```cpp
connect(发送者, 信号, 接收者, 槽, 连接方式);
//        │       │      │     │      └─ 第五个参数：Qt::ConnectionType，默认 AutoConnection
//        │       │      │     └─ 中间三对参数有四种写法（见下）
```

### 2. 四种写法

**写法一：SIGNAL/SLOT 宏（Qt4 时代）**

```cpp
connect(this, SIGNAL(mySignal(int)), this, SLOT(onMySignal(int)));
```

**写法二：成员函数指针（Qt5 引入）**

```cpp
connect(this, &MainWindow::mySignal, this, &MainWindow::onMySignal);
```

**写法三：QOverload（Qt 5.7 引入，函数指针语法的补丁）**

成员函数指针语法有个先天短板：遇到**重载的信号**时，`&QSpinBox::valueChanged` 无法确定指向哪个重载，编译报"歧义"。`QOverload::of` 显式指定参数类型：

```cpp
// QSpinBox::valueChanged 有 valueChanged(int) 和 valueChanged(QString) 两个重载
connect(spinBox, QOverload<int>::of(&QSpinBox::valueChanged),
        this, &MainWindow::onValueChanged);

// C++17 起也可以直接 static_cast
connect(spinBox, static_cast<void (QSpinBox::*)(int)>(&QSpinBox::valueChanged),
        this, &MainWindow::onValueChanged);
```

（Qt 6 把大量重载信号拆成了不同名字，这个痛点在减弱。）

**写法四：lambda 表达式（Qt5 引入）**

```cpp
connect(this, &MainWindow::mySignal, this, [this](int v) {
    qDebug() << "收到" << v;
});
```

lambda 槽的捕获语义、context 对象、断连方式详见《在Qt5的信号处理中如何使用lambda机制》。

### 3. 深水区：四种写法的本质差异是"错误什么时候被发现"

| 写法 | 对接依据 | 签名错误何时暴露 | 失败形态 |
|------|---------|----------------|---------|
| SIGNAL/SLOT 宏 | **字符串**，运行期查表匹配 | 运行期 | 编译通过，运行时信号静默无反应，仅一条 warning |
| 函数指针 | 类型参与模板推导 | **编译期** | 直接编译错误 |
| QOverload | 同上，只是显式选定重载 | 编译期 | 编译错误 |
| lambda | 可调用对象重载 | 编译期 | 编译错误 |

宏写法运行期失败的原理链条：

1. `SIGNAL()`/`SLOT()` 宏的本质是**拼字符串**：`SLOT(a)` 展开为 `"1"#a`，`SIGNAL(a)` 展开为 `"2"#a`——就是带个标记前缀的字符串字面量；
2. moc（元对象编译器）扫描带 `Q_OBJECT` 的类，为每个类生成 `moc_xxx.cpp`，里面有信号、槽的**字符串表**和参数类型信息；
3. 宏写法的 connect 在**运行期**拿着 `"2mySignal(int)"` 去 sender 的字符串表里找、拿 `"1onMySignal(int)"` 去 receiver 的表里找，任一个找不到就返回 false 并输出 `QObject::connect: No such slot`；
4. 所以槽函数改了名、参数类型写错，编译器全程无感——字符串对不对，只有跑起来才知道。

函数指针写法把这件事搬进了类型系统：connect 是模板重载，成员函数指针的类型参与推导，信号与槽签名不匹配在**编译期**就报错。

这条演进线可以概括为：**运行期字符串查表（宏）→ 编译期类型检查（函数指针）→ 携带状态的可调用对象（lambda 闭包）**。理解了这条线，四种写法就不是并列的"茴字四种写法"，而是信号槽机制逐步向现代 C++ 靠拢的三个台阶。

### 4. 五种连接方式（第五个参数）

通过 `Qt::ConnectionType` 指定，决定信号触发时槽**在哪个线程、以什么方式**执行：

| 连接方式 | 行为 | 适用场景 |
|---------|------|---------|
| `AutoConnection`（默认） | 同线程直接调用，跨线程自动排队投递 | 绝大多数场景 |
| `DirectConnection` | 在**发送者**线程立即调用槽 | 单线程内同步处理 |
| `QueuedConnection` | 事件循环把调用投递到**接收者**线程队列，异步执行 | 跨线程通信的主力 |
| `BlockingQueuedConnection` | 排队投递并**阻塞等待**槽执行完才返回 | 跨线程取结果的同步语义；**收发同线程会死锁** |
| `UniqueConnection` | 已存在相同连接时不再重复连接（标志位，与上面四种按位或） | 防止重复连接导致槽被多次调用 |

各方式的代码示例与展开详见《QT信号槽的连接方式与应用场景》。

### 5. 与闭包的关联

函数指针与 lambda 两种写法的分野，正是"裸函数"与"闭包"的分野：前者只携带代码地址，后者携带捕获环境——这也是 lambda 槽能替代 QSignalMapper、能给信号补参数的根本原因。闭包原理详见《闭包的C与C++实现》。

## 扩展问题

- `SIGNAL()` 宏为什么要给字符串加 `"2"`、`SLOT()` 加 `"1"` 前缀？（运行期区分字符串指的是信号还是槽，省一次表查找）
- 为什么 `BlockingQueuedConnection` 在收发同线程时必然死锁？（等待的槽需要本线程事件循环调度，而本线程正阻塞在等待中）
- 宏写法把信号连接到信号，与连接到槽有何不同？（转发，参数原样传递）
